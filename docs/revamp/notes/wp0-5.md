### Compatibility goldens

`normalize(value, known)` turns a response into a golden: known volatile ids
become symbolic names (`<state:received>`, `<repo:source>`, `<installation:A>`…),
other UUIDs `<id>`, endpoints `<endpoint>`, absolute paths `<path>`, hashes
`<hash>`, `*_ms` values `<ms?>`, other numbers `<u64>` (except semantic keys such
as `lane`, `connections`, `reserved_connections`, `index`, `count`), `transport`
values `<transport>`, error strings `<error:CODE>`. Booleans, `null`, labels and
phases (`"launching worker"`, `"synchronizing remote metadata"`) stay literal.

`assert_same_shape(golden, actual)` is what later packages use: every golden key
must exist with the same JSON type (markers carry the type; `<ms?>` and
`<error:…>` are nullable; golden `null` accepts anything), extra keys are allowed
(the §7.3 `status` member), marker keys (`<repo:…>`) are templates for dynamic
keys, arrays compare element-wise.

### Qualification files

Every file starts with `mod support;`, names its owner in `#[ignore = "WPx.y"]`,
and reaches the product only through action JSON (`Node::raw_call`), worker JSON
ops (`rpc`, `WorkerProc::rpc`), CLI flags as strings and the public `tkfs::core`
store API, so it compiles before new `Action` variants, ops or flags exist.
Each scenario is a `Scenario`: it emits `QUAL` lines (`started`, metrics, notes,
`unsupported`, a final `status` of pass/fail/timeout/skipped with failures and
floor verdicts) and asserts its floors (`TKFS_QUAL_ENFORCE=0` reports only).
`TKFS_QUAL_BUDGET_S` bounds every measured phase so a slow build fails with
`timeout` instead of hanging; `TKFS_QUAL_SCALE` scales sizes for dry runs.

### Scripts

- `scripts/qualify.ps1 -Wave N | -All | -Baseline [-Files a,b] [-Filter name]
  [-BudgetS 120] [-FileTimeoutMin 90] [-Evidence path] [-NoBuild] [-Merge] [-Priority BelowNormal]`:
  builds the release test binaries, runs each selected qual file with
  `--ignored --test-threads=1 --nocapture` (below-normal priority so parallel
  worktrees keep their timing, per-file timeout with process-tree kill), reads
  the `QUAL` records from `TKFS_QUAL_OUT`, evaluates every floor of the selected
  files (`pass`, `fail`, `missing`, `incomplete` when the scenario timed out so
  its metric covers a partial run, `not_run`; enforced when `wave ≤ N`), and
  writes `test-evidence/qualification-<kind>.json` with git state, toolchain,
  hardware, settings, per-scenario status and metrics. `-Merge` replaces only the
  files run now inside an existing evidence file (floors and summary are
  recomputed; `merged_from` records the earlier run). Exit 1 on any enforced
  floor or scenario failure; `-Baseline` never fails. Every input is read as
  UTF-8 and the evidence is written as UTF-8 without BOM, LF line endings
  (strict JSON for `serde_json` and other tooling).
- `scripts/qualify.sh --wave N | --all | --baseline …`: the same contract on
  Linux (`timeout` + `nice`, Python 3 for the evidence), writing
  `qualification-<kind>-linux.json`. Line 2 re-executes the script with CRs
  stripped (`tr -d '\r'`), so a CRLF checkout works from WSL.
- `scripts/suite-lock.ps1 cargo test --all-targets`: takes `Local\tkfs-full-suite`
  (the name `C:/tkfs-build/suite-lock.ps1` uses, so both exclude each other) and
  then `Global\tkfs-full-suite` (machine-wide, across logon sessions); see
  deviation 13.

## Deviations (and why)

1. **Legacy worker fixture captured in-process.** The worker state was produced by
   the baseline library (`Store`, the exact code the baseline binary runs) in the
   ignored `capture_legacy_worker_fixture`, because conflicts, staged and
   quarantined rows and a partial spool need controlled delivery order. The
   orchestrator data dir *was* captured from two real baseline daemons.
2. **Pending save row.** `Engine::retain_pending` is private at 6298d0b and no
   public path makes a flush fail, so the capture writes the `staging/<uuid>.stage`
   file and the `pending_saves` row with `retain_pending`'s exact SQL and payload
   field order (`PendingSaveRecord`). Both the library and the real binary recover it.
3. **Fixture normalization.** WAL files were checkpointed into the databases;
   worker logs and `runtime.json` removed. `copy_legacy_datadir()` relocates the
   absolute `projects.directory`/`mount` paths from the capture root (recorded in
   the manifest) to the temp root; everything else is byte-for-byte baseline output.
4. **Compat goldens.** "Re-capture identically" is equality on the golden's key
   paths after normalization (additive members such as §7.3 `status` are ignored,
   `transport` is normalized because §7.3 changes it at WP3.1). The Stop golden is
   captured on the acceptor (no peers) because a dialer's lane status for a
   just-stopped folder is timing dependent. `inspect_mounted` needs WinFsp or
   `/dev/fuse`; the re-capture test skips it elsewhere.
5. **Large fixtures write rows directly.** At 6298d0b every local create costs
   O(history) (the startup snapshot is re-sealed every 128 events), so 150K
   creates would take ~40 min and a 2,000-file event is quadratic in
   `persist_projection`. Above 1,000 creates, `direct_creates` records exactly the
   rows of the incremental local-create path and the last create goes through
   `Store::create`, which seals a valid snapshot (150K events in ~75 s, 50K
   objects in ~27 s). `direct_rows_match_full_projection` proves equality with a
   full re-projection. Setup that would replay a large remote history uses
   `clone_replica`/`metadata_replica`/`synced_replicas` instead; a clone's
   startup snapshot is re-stamped with its new device id (`restamp_device`),
   otherwise every open of the clone fails `SNAPSHOT_VERSION_OR_IDENTITY` and
   rebuilds the whole history.
6. **Session scenarios on the legacy transport.** `session::Conn` does not exist
   at 6298d0b, so `qual_wp1_9_session` measures the same properties on `tkfs::ws`
   for the baseline record; WP1.9 swaps in `Conn`. `dead_peer_detection` reports
   `unsupported` (the legacy transport has no liveness).
7. **Feed scenarios.** The worker has no `feed-*` ops at 6298d0b; the scenarios
   report `unsupported` and, where §15 gives a baseline number (150K inventory,
   idle exchange), also measure the legacy `published-*` path.
8. **Extra scenarios for §15 floors that had no file in §14.6:** `subscribe_latency`
   (W2, in `qual_wp2_1_lifecycle`), `large_event_8mib` (W2, `qual_wp2_5_feed`),
   and the Wave 3 daemon-level `idle_exchange_daemons`, `feed_150k_daemons`,
   `large_event_8mib_daemons` (in `qual_wp3_int_e2e`). The "8 MiB" event is about
   1.9 MB: an event holds at most 10,000 changes, and names are bounded, so 8 MiB
   is not reachable with namespace changes; it is still far above the 349,525-byte
   legacy cliff.
9. **Fault point names.** Scenarios use the plan's names (`worker.accept_error`,
   `engine.poison`, `worker.watch_hang`, `worker.rpc.feed-exchange`,
   `core.commit.busy`) with `TKFS_FAULT_ACTION`/`TKFS_FAULT_COUNT`/`TKFS_FAULT_SCOPE`.
   The activator pause/slowdown point is not named in the plan; the scenarios use
   `worker.activator.slice` and the owners (WP2.3/WP2.5/WP3.INT) adjust it.
10. **Floors are asserted inside the scenarios** as well as by `qualify.ps1`, so a
    `cargo test --release -- --ignored` run fails visibly; `TKFS_QUAL_ENFORCE=0`
    turns that off.
11. **`raw_call`** uses `ws::connect` + `ws::call` as specified; when
    `data/orchestrator.token` exists (WP4.1) it sends the same JSON with an
    `X-Tkfs-Token` upgrade header, so the harness keeps working after WP4.1.
    Background threads (churners, the `subscribe` waiter) use the same path
    through `Node::control()` (`Control::call`); no qual file calls
    `ws::connect` on a control endpoint directly. Worker calls go through
    `runtime::rpc`, which WP4.1 extends with the token.
12. **`tests/support/mod.rs`** also allows `unused_imports` (the glob re-exports are
    unused in some test crates).
13. **Mutex scope.** §14 task 10 asks for a machine-wide mutex. `Local\` is per
    logon session, so a suite started from another session (SSH, a service)
    would not be excluded by it. `scripts/suite-lock.ps1` therefore takes two
    mutexes in a fixed order: `Local\tkfs-full-suite`, for name parity with
    `C:/tkfs-build/suite-lock.ps1` (outside the repository; it takes only that
    one), then `Global\tkfs-full-suite`. Creating a mutex in `Global\` needs no
    privilege (`SeCreateGlobalPrivilege` governs file-mapping and section
    objects only; the first-round rationale was wrong). The fixed order cannot
    deadlock with the Local-only script. If `Global\` cannot be opened (for
    example created by an elevated process whose DACL denies this one), the
    script warns and keeps the session lock. Moving
    `C:/tkfs-build/suite-lock.ps1` to `Global\` as well is for the integrator.
14. **`Node` drop sweeps leftover workers** of its root (only when a
    `runtime.json` remains), because a killed or adopting daemon leaves workers
    running and a slow baseline worker would otherwise keep burning CPU.

## CCRs filed

- **CCR-WP0.5-1 — root `.gitattributes`: `*.sh text eol=lf`.** This repository runs
  with `core.autocrlf=true`, so a Windows checkout gets `scripts/qualify.sh` with
  CRLF (observed in this worktree) and bash rejects it from WSL on `/mnt/c`.
  Adapter inside the owned file: line 2 is a comment-terminated prologue that
  re-executes the script with carriage returns stripped
  (`exec env TKFS_QUALIFY_LF=1 bash -c "$(tr -d '\r' < "$0")" "$0" "$@"`).
  The first-round commit had a literal LF between the `tr` quotes (deleting
  every newline, so the script was a silent exit-0 no-op); fix round 1 writes
  the CR as the `\r` escape, and `qualify_sh_runs_with_lf_and_crlf` (unix)
  checks LF and CRLF copies. The fixtures are protected by
  `tests/fixtures/legacy/.gitattributes`.
- **CCR-WP0.5-2 — `.gitignore` exceptions:** `!/tests/fixtures/**` (the `*.sqlite*`
  and `*.log` rules hide fixture databases) and `!/test-evidence/qualification-*.json`
  (§13 rule 8.5 says the integrators commit the evidence; `/test-evidence/` is
  ignored). Adapter: the fixtures and `test-evidence/qualification-baseline.json`
  were added with `git add -f`; once tracked, git follows them normally. Later
  evidence files need `git add -f` until the CCR lands.

- **CCR-WP0.5-3 — defect in `tests/orchestrator.rs` (owned later by WP2.1/WP3.1):**
  `real_partial_mount_fetches_on_read_without_blocking_unrelated_metadata` waits for
  `status.content.complete == true && has(...)`, but `content.complete` is vacuously
  true before any event is committed, so the wait can pass before the object is
  installed and the following `fs::remove_file(.../objects/<hash>)` panics with
  `NotFound`. It failed in 2 of 4 full-suite runs here (0 of 6 runs of the
  `orchestrator` binary alone) and, when it panics, its `Node` leaves a mounted
  worker running (the file's `Node::drop` never stops workers); one such orphan
  was still alive during the next failing run, and the run after killing it
  passed. Requested fix: also wait for
  `content.current_available >= 1` (or `cat-object`), and stop the folder's
  worker in `Node::drop`. Adapter: none needed by WP0.5 (the harness uses
  `support::content_complete`, which requires committed references, and its
  `Node::drop` sweeps leftover workers).

| 5 | `clone_replica`/`metadata_replica` kept author-only rows. | Partly accepted. Verified in `core.rs`: `published_objects` is written only for local authorship (`commit`, local && shared && unreviewed) and by the legacy migration, but the **outbox is not author-only**: `commit` inserts every committed shared event into `outbox` whether local or received (core.rs:1122-1124, not gated on `local`), and `remember_peer_inventory` acknowledges them. | 6 | The `concurrent_histories` determinism check compared only RNG-derived bookkeeping. | `ConcurrentSummary::history` is now read back from the stores (`canonical_history`: committed shared events with ids replaced by creation names and authors by replica index), checked equal on every replica of a run, equal across runs of a seed, different across seeds, and `history.len() + refused == ops`. | 8 | `idle_worker_cpu` dropped unreadable pids (`f64::max` ignores NaN). | Every pid must be read at both ends; otherwise `s.check` fails and the metric is NaN (fails the floor). With the `find_pids` fix the pid list holds only workers. |

- Activation: remote linear creates and two-way backlogs cost ~170 ms/event at
  the first ~350 events and ~510 ms/event by then (O(N²)); a local create after
  a resolved conflict takes 18 s at 2K events; one namespace op concurrent with a
  5K history takes 117 s.
- Objects: `content_status` 5.6 s at 50K objects; restart 3.2 s at 20K objects;
  12K tiny objects hit `INVENTORY_TOO_LARGE`; a corrupt mid-page part discards
  the completed objects; 256 MiB moves at 11.7 MiB/s between daemons (16.6 MiB/s
  worker to worker) and a 100 Mbit / 50 ms link reaches 0.39 of its rate; 10K ×
  4 KiB files move at ~1 file/s.
- Transport and lanes: a slow request blocks fast ones for 2.9 s; an idle peer
  socket is dropped before 60 s; a hung remote repository stalls the healthy one
  for the whole budget; `sync_interval_ms=20000` reconnects 9 times in 60 s; a
  crashing worker restarts 11 times in 20 s; `WORKER_BUSY` is counted as a
  failure; a v2 peer pairs (no fail-closed).
- Lifecycle: Shutdown aborts on a busy folder (`BUSY_VIEW`), a killed daemon's
  workers are replaced instead of adopted, a non-empty mount path kills the
  worker, startup with 5K staged events never reaches Ready in 60 s, a slow event
  at 2K blocks the engine for the full 15 s socket timeout, FS p99 is 663 ms
  during catch-up, idle workers burn 136 % CPU at 5K events / 10K objects (500 ms
  interval), and an idle exchange at 50K events costs ~8 s CPU per side and
  ~3.9 MB.
- Baseline passes that are expected: `foreign_mount_untouched`,
  `rotation_unauthorized_until_repaired`, `crash_resume` (spools resume),
  `relay_with_objects`, `legacy_fixture_upgrade_then_sync`, `duplex_32mib`
  (Windows loopback buffers absorb 16 MiB each way, so the legacy transport does
  not deadlock here), and the two vacuous fault scenarios
  (`accept_loop_survives_faults`, `transient_retry`: no fault hooks yet).

## Known limitations

- Fault-injection scenarios (`accept_loop_survives_faults`, `transient_retry`)
  pass vacuously on builds without the fault hooks; their notes say so.
- Scenarios for features that do not exist yet (watch, mount ops, Status,
  subscribe, feed ops, v3 handshake) are written from the plan's JSON shapes
  (§6.1, §6.3, §7.1–7.3); the owners will adjust field names to the final model.
- Daemon-level scenarios depend on machine load; `qualify.ps1` runs them at
  below-normal priority, one file at a time, and records the hardware.
- `qualify.sh` was exercised in WSL on one scenario; the Linux baseline evidence
  was not recorded (not required by WP0.5). In this worktree `git` cannot read
  the repository from WSL (the worktree's `.git` points at a Windows path), so
  the Linux evidence's `git` fields are empty there.
- `objects_before_activation` reads object presence from the CAS directory and
  `content.shared_available`; with objects v3 the owner may prefer the typed
  status counters.
