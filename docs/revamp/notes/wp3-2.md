## Summary

The worker half of §6.4: receiver-driven want lists, authorized range reads,
durable binary writes with whole-object verification and batched
registration, corruption reports, leases, and v3 loopback sessions on the
worker listener.

### Durability: `write_object_items` (invariants 1–3, literally)

* **Schema**: `spool_state(hash PK, durable, total, updated_ms)` in
  `objects::ensure_schema` (`schema:objects` 1 → 2; `CREATE TABLE IF NOT
  EXISTS`, own savepoint, §9).
* **Phase A, append and fsync**, per object under its `ObjectLocks` lock (all
  locks of a call taken in hash order and held to the end of the call, so two
  calls never wait in a cycle and no other writer sees a spool between its
  fsync and its commit). One query (`write_facts`) gives referenced /
  shareable / committed size / spool row. The spool is cut back to its
  committed durable offset; an append must start there
  (`RESUME_OFFSET_AHEAD` with the offset to resume from); bytes before it are
  compared byte for byte (`OBJECT_PART_CHANGED` resets the spool); a spool
  that changed is fsynced once. A spool without a row has no durable bytes
  and is (re)created by its first append (one create per new object). The
  appends and fsyncs of concurrent calls take turns: the **spool I/O gate**
  (`ObjectLocks::spool_io`, deviation 12), taken after the object locks and
  never held across the offset commit, the registration transaction or a
  whole-object hash.
* **Fault `object_spool_synced`** (`core::fault`, `TKFS_FAULT`, exit 86): after
  the fsyncs, before the commit.
* **Phase B, commit**: one `BEGIN IMMEDIATE` transaction records every new
  durable offset; only then is `Progressed{durable_offset}` answered
  (invariant 2).
* **Phase C, verify and install**: a full re-read SHA-256 of each complete
  spool (`CorruptAtSource` and the spool dropped on a mismatch: nothing is
  installed, invariant 1). The mtime stamp is set before the single fsync, so
  the installed object's availability marker is trusted at once. Install is
  "rename plus directory fsync" for the whole call (deviation 11): each
  verified spool is renamed into `objects/` (`rename_object`: `MoveFileExW`
  without WRITE_THROUGH, `rename(2)`), then **one** fsync of `objects/`
  (`sync_dir`: `FlushFileBuffers` on the directory opened with backup
  semantics on Windows, `fsync` elsewhere) makes every rename of the call
  durable before any of them is registered. If that directory fsync ever
  fails, the call's renamed objects are answered `OBJECT_IO_ERROR` (not
  registered, still wanted; the next transfer verifies the present copy and
  registers it) and the process falls back to one durable rename per object
  (`install_object`: `MoveFileExW` WRITE_THROUGH, or rename plus the
  directory's fsync). A verified copy already present (private bytes) is
  kept, covered by the same barrier, and registered: the transfer proved the
  source (I4).
* **Fault `object_installed`**: after the installs and their barrier, before
  registration.
* **Phase D, registration**: one `BEGIN IMMEDIATE` transaction for every
  object the call installed (sizes, `received_shared_objects`, requests and
  both error tables cleared, availability, spool rows dropped). If the batch
  fails, each object is registered alone, so one bad descriptor never undoes
  the others. An installed object whose registration failed is answered
  `Failed`: it is not shareable, so it is still wanted (invariant 3).
* **Startup** (`transfer::reconcile_spools`, end of phase 4 of `Store::open`):
  once per store (`spools_v1`), a legacy spool without a row adopts its file
  length (the legacy code fsynced each append); afterwards a spool without a
  row is removed (durable 0); a spool longer than its row is truncated to it;
  a row without a spool is dropped; the spool of an object already shareable
  and available is dropped. Best effort per spool (logged): a locked file
  never stops the store from opening, because phase A cuts every spool back
  under its lock anyway. Nothing is registered at startup (I4).
* **Legacy receive path** (`receive_part`, kept for `bulk_sync`,
  `published-*` and `paired_sync`): unchanged semantics, plus a best-effort
  `spool_state` row after each fsynced append **that leaves its object
  incomplete** (one autocommit per such part, next to its data fsync), and
  row removal on reset, corruption and completion only when the spool
  existed before the part or got a row. An object received in one part
  (every tiny one) costs no extra database write; a duplicate part deletes
  a row only when it removed an orphaned spool. One spool has one durable
  length whichever path wrote it (`legacy_receive_path_keeps_spool_state`).

### Worker ops (`runtime/objects_rpc.rs`)

`dispatch` serves `objects.want`, `objects.read`, `objects.write` and
`objects.report` on a pooled secondary store (never the engine lock), with the
route checked as the feed ops check it (`REPOSITORY_MISMATCH`,
`LOCAL_REPLICA_BINDING_MISMATCH`, `DUPLICATE_REPLICA_IDENTITY`), malformed
headers `INVALID_REQUEST`, an invalid lane `INVALID_BULK_LANE`, a body that
disagrees with its items `INVALID_OBJECT_PART`, unknown ops
`UNSUPPORTED_OPERATION` (pinned by `seam_stubs`).

* **Leases** (invariant 19, `ctx.inflight_objects`, `LEASE_TTL` 60 s
  "renewed on progress"): a want list never offers an object another live
  session holds and leases every free item it returns; a write for an object
  another session holds answers `InFlightElsewhere` and touches nothing; a
  write for a free or lapsed lease takes it (deviation 4). **Only progress
  renews a lease**: a `Progressed` write whose durable offset advanced. A
  want list that offers an item again to the session that holds it keeps the
  lease's expiry (and never moves its offset back: `max`), and a failed
  write renews nothing. Terminal outcomes release the lease.
* **Lapsed leases** (deviation 13): a lease that reaches its expiry was not
  released and saw no progress for a whole TTL. The next `objects.want` or
  `objects.write` sweeps it and backs its object off for the source that
  held it (the granting route's remote replica, kept in `LEASE_HOLDERS`
  because the frozen `ObjectLease` has no source) for `STALL_BACKOFF` (60 s,
  never shortening a longer backoff, no attempt counted), so the sessions of
  other sources are offered it. A source that cannot serve an object holds
  it for one TTL at a time.
* **Ordered parts**: a write whose first part for an object starts past this
  session's durable offset waits (at most `ORDER_WAIT`, 2 s, on a condvar
  woken by every write) for the session's earlier writes, so the ≤ 4 writes
  in flight of §6.4 can be served by a multi-threaded handler pool in any
  order (deviation 5).
* **Per-source backoff**: `CorruptAtSource`, `SizeMismatch` and an item the
  store refuses as malformed (`INVALID_OBJECT_PART`, `INVALID_OBJECT_ID`)
  back the object off for the route's remote replica (30 s → 1 h, one
  attempt per object per call however many of its items failed); want lists
  for that source skip it, except an object its own session holds a live
  lease on (a transfer in progress resumes); other sources still supply it
  (deviation 6).
* **Local failures**: any other failed item (`OBJECT_IO_ERROR`, a failed
  registration, ...) records the object backoff in `object_error_state`
  (`Store::record_object_failure`, 30 s → 1 h, which every want list honors)
  and releases the lease; contention and `SQLITE_BUSY` record nothing;
  `RESUME_OFFSET_AHEAD` and `OBJECT_PART_CHANGED` are resume points, not
  failures: the lease stays (not renewed).
* Completed registrations and quarantines mark the status cell's content
  wanted (`status_cell::want_content`).

### Loopback sessions (`runtime/server.rs`)

The worker listener peeks each new connection's upgrade request (nothing is
consumed): `X-Tkfs-Sync: 3-loopback` goes to `session::accept_loopback` (no
token until WP4.1) and `Conn::serve` with 8 handler threads and a queue of 64;
anything else is the JSON RPC, unchanged. On a session, `objects.*` carry
binary bodies; every other op is the JSON op over the session (header = the
payload, or the JSON body when the request has one; reply = the JSON as the
header, or `{"in_body": true}` with the JSON as the body above 60 KiB);
`stop` is refused there (it stays on the JSON RPC, whose reply flush the stop
ladder waits for). A JSON op over a session fires its `worker.rpc.<op>`
fault point once, as over the JSON RPC (in `route`); `objects.*` fire it in
the session handler, since they skip `route`. Over the JSON RPC,
`objects.want` and `objects.report` work; `objects.read` answers
`BINARY_OPS_REQUIRE_SESSION` (unchanged).

## Deviations from the spec, and why

1. **Current-object set.** §6.4 says "from the status cell's current-object
   set"; the cell has none (`worker/status_cell.rs`, WP2.3's file, not owned
   in Wave 3). `Store::current_objects` reads the stored projection with SQL
   and caches it per store root (≤ 5 s stale while commits continue).
   Priority is a hint; correctness never depends on it. CCR-WP3.2-2 asks for
   the cell to carry it.
2. **Order within classes.** Demand is newest first (a reader is waiting;
   §6.4 "newest first"); "smaller first" applies to current and history.
   *Fair interleaving* is realized as one fair slot: once a list is about to
   fill (its last item, or three quarters of its byte budget), its last slot
   goes to the class's **largest** pending item, never as the list's first
   item. A stream of small objects therefore never starves a large one (it
   takes the rest of every pull's budget), and a list of one item is still
   the smallest.
3. **A complete, unfinished spool** (a crash after its last fsync, before
   install) is offered one byte short (`offset = size − 1`): the sender's last
   byte, compared with the spool, finalizes it with any pipeline (no
   zero-length part needed).
4. **Lease acquisition on write.** A write whose object has no live lease
   takes it (a fresh lease, one TTL) instead of being refused, so a session
   whose lease lapsed during a slow transfer continues; a live lease of
   another session is still `InFlightElsewhere`. Safety is the same: the
   object is wanted (checked under its lock) and has one owner. A write
   never extends a live lease by itself; only its progress does.
5. **Ordered parts** (above) are an addition: without them, pipelined writes
   of one object fail with `RESUME_OFFSET_AHEAD` whenever two handler threads
   swap them.
6. **Per-source backoff in memory.** "The receiver backs off that object for
   that source": `object_error_state` has no source column (positional rules
   forbid nothing here, but it is WP1.8's table semantics), and `WorkerCtx`
   is frozen, so the backoff lives in a process-wide map keyed by store root,
   source replica and hash (CCR-WP3.2-3). A restart forgets it; the next
   corrupt copy re-arms it.
7. **Upgrade classification by `peek`.** §14 says `upgrade_kind == Loopback`;
   `session::upgrade_kind` needs a parsed request, which only the handshake
   that consumes it produces. The listener reads the header with the same
   rules (case-insensitive name, trimmed value) from peeked bytes, and
   `accept_loopback` re-checks with `upgrade_kind` (HTTP 400 otherwise).
8. **Write transactions are `BEGIN IMMEDIATE`** on a connection in autocommit:
   a deferred transaction that reads before it writes fails at once with
   `SQLITE_BUSY` when another connection committed meanwhile (the WAL
   snapshot-upgrade race), which concurrent `objects.write` calls hit in the
   first qualification run.
9. **Want backoff ignores local quarantine.** `want_objects` skips objects in
   `object_error_state` backoff except code `CORRUPT_OBJECT`: that backoff
   (written by `quarantine`) guards the legacy sender, never the download
   that repairs the local copy. This removes the reason CCR-WP1.8-3 was
   deferred (below).
10. **`CorruptAtSource` attribution.** A spool completed by an earlier
    source's bytes and finalized by another source's last part is blamed on
    the finalizing source. That source then re-verifies a good copy
    (`VerifiedOk`) and is backed off for that object only; the spool is
    dropped and re-fetched. Rare (a crash between the last fsync and the
    install) and harmless.
11. **One install barrier per call** (fix round 1). §6.4 allows "`MoveFileExW`
    WRITE_THROUGH, or rename plus directory fsync"; the worker uses the
    second form for a whole `objects.write` call: plain renames, then one
    fsync of `objects/`, then registration. Invariant 3's order (durable
    install, then registration) holds for every object. On Windows the
    directory fsync is `FlushFileBuffers` on the directory handle; NTFS
    journals renames, and flushing any handle flushes the journal up to
    then, which is also what `MoveFileExW` WRITE_THROUGH does (rename, then
    flush the renamed file's handle). A failing directory fsync degrades the
    process to one WRITE_THROUGH rename per object (and the objects of that
    call are not registered). Measured: the bare create/write/fsync/rename
    loop of 64-byte files did 194, 301, 243 objects/s with one WRITE_THROUGH
    rename per object against 291, 296, 317/s with plain renames and one
    directory flush per 64 (three interleaved rounds of 1,024 files).
12. **Spool I/O gate** (fix round 1). The appends, data fsyncs and installs
    of concurrent `objects.write` calls on one store take turns
    (`ObjectLocks::spool_io`; `ObjectLocks` is WP3.2's type, a private field
    added). Concurrent flushes of many small files thrash the NTFS journal:
    in process, 10K tiny objects written by 4 concurrent calls (the ≤ 4
    writes in flight of §6.4) went at 166–255 objects/s ungated against
    314–320/s gated (one call at a time: 286–359/s). The gate is never held
    across a database transaction or a whole-object hash, so those overlap.
    One large object's parts were already serialized by its object lock.
13. **Lapsed leases back the object off for their source** (fix round 1).
    §6.4 says leases are "renewed on progress" and want lists exclude
    objects "in backoff"; it does not say what ends a lease that never makes
    progress. Without a rule, a source that cannot serve an object (WP3.3:
    the orchestrator answers `NotAvailable` per object and keeps asking with
    a stable lease session) would hold it until it stopped asking. A lapse
    (expiry without release) now backs the object off for that source for
    `STALL_BACKOFF` = `LEASE_TTL` (60 s): this is the worker-side per-source
    `NotAvailable` backoff that CCR-WP3.3-4 offers as the alternative to an
    `exclude` list in the frozen `WantHeader`. A session that holds a live
    lease is still offered its object despite a backoff of its source (a
    transfer in progress resumes).
14. **Worker-side failure backoff** (fix round 1). `SizeMismatch` and
    malformed items back the object off for their source like
    `CorruptAtSource`; local failures record `object_error_state` (the
    legacy receivers' rule) and release the lease; resume points do neither.
    The orchestrator keeps its own per-object backoff (WP3.3).

## Known limitations

* The want scan is one statement over every referenced object (an anti-join
  over the indexes): about O(objects) per call, fine at 10K, worth an index of
  wanted objects at 100K+ (the orchestrator only calls it per pull).
* Per-source backoff, lease holders and leases are in memory (a restart
  forgets them).
* The tiny-object floor sits close to this disk's fsync rate: the worker
  runs at 86–100 % of the bare filesystem loop, and a run where that loop
  itself drops near 300/s misses (two of seven runs here, 289 and 297/s).
  `fs_objects_per_s` in the same record tells the two apart (CCR-WP3.2-6).
* An object that a source cannot serve is offered to that source's sessions
  until one TTL after its grant (60 s) before other sources get it
  (deviation 13); an `exclude` list in `WantHeader` (CCR-WP3.3-4) would
  shorten that.
* A failing directory fsync switches the whole process (all stores) to one
  durable rename per object until it restarts.
* `CorruptAtSource` may be attributed to the source that finalized a spool
  another source filled (deviation 10).
