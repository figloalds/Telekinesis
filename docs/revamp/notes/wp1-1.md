### `orchestrator::catalog`

| Item | What it is |
|---|---|
| `Catalog::open(&Config) -> anyhow::Result<Arc<Catalog>>` | Spawns `tkfs-catalog`, which takes `orchestrator.lock` (`orchestrator::lock`), opens `folders.sqlite` with the legacy pragmas (`journal_mode=WAL; synchronous=FULL`), runs the legacy `CREATE TABLE IF NOT EXISTS` statements and the legacy `INSERT OR IGNORE` of `settings.installation` (byte-identical SQL), then the migration and the legacy reconcile (below), and publishes generation 1. Returns once that is done, or the error (`ALREADY_RUNNING…` while another owner holds the lock, invariant 23). Like `Supervisor::open` it creates the data and default mount directories. |
| `impl CatalogApi for Catalog` | `snapshot()` is `Snapshot::load` (an `Arc` clone; never waits for a command). `apply(cmd)` sends the command to the actor and waits for its reply. `wait_newer(g, t)` is `Snapshot::wait_newer` then `load`. |
| `Catalog::{close, is_alive, data_directory}` | `close()` stops accepting commands (`CATALOG_UNAVAILABLE`), lets queued commands finish, and waits up to 5 s for the thread, which closes the database and then releases the lock; `Drop` calls it. `snapshot()` keeps working afterwards. |
| `validate_mount_path(snap, data_dir, state_dir, requested) -> Result<PathBuf, ErrorWire>` | The legacy `Supervisor::mount_path` rules as a function of a snapshot (see deviation 7). |
| constants | `THREAD_NAME`, `SCHEMA_VERSION = 1`, `BUSY_RETRIES = 3`, `BUSY_TIMEOUT = 1 s`, `BUSY_BACKOFF = 50 ms`, `CLOSE_WAIT = 5 s`, `MAX_LABEL_BYTES = 200`, `faults::{SLOW_WRITE = "catalog.slow_write", ACTOR = "catalog.actor"}` |

**Schema** (§9; only side tables and settings keys, nothing ALTERed). Guarded
by `settings('catalog_schema','1')`, in one `BEGIN IMMEDIATE` transaction:

- `folder_intents(state PK, sync_enabled, mount_enabled, updated_ms)`;
- `mount_gates(state PK, source_installation, source_endpoint, created_ms, override_ms, satisfied_ms)`;
- `peer_meta(installation PK, last_seen_ms, display_name, incompatible, revoked_ms)`;
- `settings('verifier_generation')`, starting at 0.

Then, on **every** open (same transaction), the legacy reconcile:

1. `mount_gates` rows for `initial_sync` rows that have none (`source_endpoint →
   installation` through `peers`, `created_ms` = now). On the first open this
   is the schema-1 backfill; later it picks up a gate a downgraded binary
   created (legacy Receive).
2. `mount_gates` rows whose `initial_sync` row is gone are deleted: a
   downgraded binary cleared the gate after its own gate rule held and
   mounted the folder.
3. Unknown `source_installation`s are resolved through `peers`.
4. If `settings.pairing` holds a verifier whose salt differs from
   `settings.verifier_salt`, `verifier_generation` is bumped and the salt
   recorded. A legacy data directory with a verifier therefore opens at
   generation 1, and a code rotated by a downgraded binary is a new
   generation on the next upgrade.

**Commands.** Each runs in one `BEGIN IMMEDIATE` transaction with
`prepare_cached` statements (cache capacity 64). The snapshot is rebuilt
inside the transaction (so it is exactly what is committed), the
`catalog.slow_write` fault point fires, the transaction commits, and the
snapshot is published and returned.

| Command | SQL and rules |
|---|---|
| `CreateFolder{record, gate}` | Legacy positional `INSERT INTO projects VALUES(?,?,?,?,?,?,1)` (identical text), then the legacy `UPDATE projects SET desired=0 …` when `!desired_running`; `folder_intents` row; when a gate is given **and** the record has a mount: legacy `INSERT INTO initial_sync VALUES(?,?)` plus the `mount_gates` row (installation resolved through `peers` if `None`; `created_ms` 0 → now). Rejects: empty state/repo/device or an existing state (`INVALID_REQUEST`), the legacy label rule (`INVALID_FOLDER_LABEL`), a managed repo (`REPOSITORY_ALREADY_MANAGED`), a mount overlapping another folder's (`MOUNT_OVERLAPS_FOLDER`). |
| `SetDesired` | Legacy `UPDATE projects SET desired=1/0 WHERE state=?`; no row → `FOLDER_NOT_FOUND`. |
| `SetMount` | Legacy `UPDATE projects SET mount=? WHERE state=?`; re-checks overlap with other folders' mounts. |
| `SetIntents` | Upserts `folder_intents`; `None` keeps the current value (a legacy folder with no row has both enabled). |
| `OverrideGate` | `override_ms = COALESCE(override_ms, now)` (the first override is kept); a folder without a gate is a no-op. |
| `ClearGate` | Legacy `DELETE FROM initial_sync WHERE state=?` and `DELETE FROM mount_gates WHERE state=?`. |
| `RetargetGate` | Updates `mount_gates` (installation resolved if `None`; `satisfied_ms` cleared) **and** `initial_sync.endpoint`, so a downgrade targets the same source. Both endpoint and installation empty → `INVALID_REQUEST`. |
| `UpsertPeer` | Legacy positional upsert (identical text); an empty `revision` gets a fresh id (the legacy upsert always generated one); then resolves unknown gate sources. Rejects an empty endpoint or installation (`INVALID_REQUEST`), our own installation (`CANNOT_PAIR_WITH_SELF`), connections outside 1..=16 (`INVALID_CONNECTION_COUNT`). |
| `RemovePeer` | Legacy `DELETE FROM peers WHERE endpoint=?`; a missing peer is a no-op (legacy Unpair). `peer_meta` is kept. |
| `SetVerifier` | Legacy `INSERT INTO settings VALUES('pairing',?) ON CONFLICT…` (identical text); `verifier_generation += 1`; records `verifier_salt`. |
| `RecordPeerSeen` | Upserts `peer_meta`: `last_seen_ms = max(old, at_ms)`, `display_name` kept when `None`, `incompatible` replaced (`None` clears it). |

Every per-folder command answers `FOLDER_NOT_FOUND` for an unknown state.

**Failure handling.** `catch_unwind` around every command; a panic rolls the
transaction back and answers `CATALOG_UNAVAILABLE` (`… panicked and was rolled
back: …`). `SQLITE_BUSY` (via `code_of`) is retried 3 times (50, 100, 150 ms
apart, each attempt with a 1 s busy handler), then returned. Opening uses the
same retry loop. If the actor thread dies (`catalog.actor` fault), an
`AliveGuard` marks it dead, every `apply` answers `CATALOG_UNAVAILABLE`, and
`snapshot()`/`wait_newer` keep serving the last good snapshot. Failed commands
are logged with `event!` (`info`, with their own code; a final `SQLITE_BUSY` at
`warn`; a panic at `error`, as `CATALOG_UNAVAILABLE`).

**Generations.** The first snapshot is generation 1. A successful command that
changes the visible catalog publishes exactly one new generation; a command
that changes nothing visible (setting a value to itself, overriding twice,
clearing a cleared gate, removing a missing peer) returns the current snapshot
and publishes nothing (deviation 1). Failed commands never publish.

### `orchestrator::published`

`PublishedCatalog` (implements `PublishedCatalogApi`): the entries in a
`util::lock::Tracked<BTreeMap<state, PublishedEntry>>` (the only critical
section, held for the map edit and the list rebuild), and the reply list in a
`util::Snapshot<Vec<PublishedEntry>>`, so `list()` is an `Arc` clone (O(1)),
returns the same `Arc` until something changes, and `wait_newer` is the
snapshot condvar.

- `update(state, Some(e))` with an identical entry, and `update(state, None)`
  for a missing state, change nothing and keep the generation.
- Every other update bumps the generation by exactly one; the list is in
  folder-state order.
- `PublishedCatalog::new()` starts the generation at the wall-clock
  milliseconds (deviation 6); `with_base(n)` for a deterministic start.
  Helpers: `generation()`, `entry(state)`.

## Deviations from the spec, and why

1. **No-op commands publish no generation.** "The generation increments
   exactly once per successful mutation" is read as: once per command that
   changed the visible catalog. Publishing for a no-op would wake every
   `wait_newer` caller (registry, peer manager, inbound policy) for nothing.
   `apply` still returns the snapshot that includes the command's effect.
2. **`CreateFolder` keeps the identical legacy INSERT**, whose `desired`
   column is the literal `1`; a record with `desired_running = false` is then
   written with the legacy `SetDesired` statement in the same transaction.
3. **A gate is only stored for a folder with a mount path**, as the legacy
   `create()` does (`initial_peer.filter(|_| mount.is_some())`): the gate holds
   the mount, and a headless folder would keep an unclearable marker. WP2.1's
   Receive can pass a gate unconditionally.
4. **Validation inside commands** (defence in depth; all codes are already in
   §8 or the Transient-default list): the legacy label rule, required ids,
   `REPOSITORY_ALREADY_MANAGED`, `CANNOT_PAIR_WITH_SELF`,
   `INVALID_CONNECTION_COUNT`, and a lexical re-check that a new mount does not
   overlap another folder's. The last one closes a race the legacy code
   avoided with the global `Supervisor` mutex: two Creates validated against
   the same snapshot can no longer both take overlapping mounts
   (`creates_validated_against_one_snapshot_cannot_both_take_a_mount`).
5. **Legacy reconcile on every open, and the settings key `verifier_salt`.**
   The spec guards the migration with `catalog_schema`; the reconcile
   (gate backfill/prune/resolve, verifier generation) also runs on later
   opens, so a downgrade → legacy changes → upgrade round trip keeps
   `mount_gates` equal to `initial_sync` and `verifier_generation` honest. It
   is idempotent and adds one settings row; nothing is altered.
6. **The published generation starts at wall-clock milliseconds**, not 0.
   `catalog.list{since}` answers `unchanged:true` when `since` equals the
   generation; a counter restarting at 0 could repeat a number a peer still
   holds from the previous daemon process and hide a changed list. Starting
   at the clock keeps generations increasing across restarts as long as a
   process makes fewer than one change per millisecond of its life (and stays
   below 2^53 for JSON clients). `with_base` exists for tests and callers that
   want another start.
7. **`validate_mount_path`.** Same steps, order, side effect (the parent is
   created, as today) and codes as the legacy `Supervisor::mount_path`; the
   folder's own current mount still counts as an overlap, as today. Two
   differences, neither reachable with the standard layout
   (`DATA/states/STATE`): the legacy raw `directory.starts_with(path)`
   comparison was dropped from `MOUNT_OVERLAPS_DATA` (it compared a raw path
   with a canonical one, so on Windows it never matched, and otherwise it only
   repeated the data-directory check), and a canonical state-directory check
   (`MOUNT_OVERLAPS_STATE`, through the nearest existing ancestor because
   Create validates before `Store::initialize`) was added for a state
   directory outside the data directory. I/O failures carry no code of their
   own, like the legacy `?` (`UNKNOWN_ERROR`). "Pure" is read as: a function
   of its arguments and the filesystem, with no catalog access.
8. **Busy budget.** `BUSY_TIMEOUT` is 1 s per attempt (rusqlite's default,
   which the legacy connection used, is 5 s), so "3 retries" bound a write to
   about 4.3 s before `SQLITE_BUSY`. Only the catalog writes the file.
9. **A panicked command answers `CATALOG_UNAVAILABLE`**: §8 has no dedicated
   code and `src/model/errors.rs` is frozen. The message says it panicked.
10. **`CatalogSnapshot` lookups** (`folder`, `folder_by_repo`,
    `peer_by_endpoint`, `peer_by_installation`) are the frozen linear scans;
    §3.2's "indexed by" would need hidden index fields in a frozen struct.
    At catalog sizes (tens to hundreds of rows) a scan costs microseconds, so
    no CCR is filed.
11. **Additive public API** beyond §14: `Catalog::{close, is_alive,
    data_directory}`, the constants and `faults` module above,
    `PublishedCatalog::{with_base, generation, entry}`. `Catalog::open` also
    creates the default mount directory (legacy `Supervisor::open` behaviour).

## Known limitations

- Not wired: WP2.1 replaces the legacy `Supervisor` catalog code with this
  actor. Until then the daemon never runs the migration.
- The downgrade test drives this build's legacy `Supervisor` (moved
  verbatim from 6298d0b by WP0.1), not the 6298d0b binary; WP1.INT's
  interoperability step (§13 rule 8.4) covers the old binary.
- A `RetargetGate` to an installation-only source (no endpoint) writes an
  empty `initial_sync.endpoint`; a downgraded binary cannot satisfy that gate
  (it has no override), so such a folder stays unmounted under a downgrade.
- `mount_gates.satisfied_ms` exists (§9) but nothing writes it: `GateRecord`
  has no such field and no command sets it; the satisfied state lives in the
  FolderController until `ClearGate`.
- Catalog generations are per process (restart at 1). Every visible change
  wakes every waiter, so consumers must diff the records they care about, and
  `RecordPeerSeen` should be recorded on session establishment, not per
  request.
- `apply` has no deadline: a SQLite call that never returns (wedged disk)
  blocks management writes, while reads keep working (§2.3 Catalog row). A
  `close()` that times out detaches the wedged thread, which keeps the lock
  until the process exits.
- Each command rebuilds the whole snapshot (O(catalog rows)); fine at
  catalog sizes.
