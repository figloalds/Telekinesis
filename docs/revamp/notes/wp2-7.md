# WP2.7 MetaScheduler, meta exchange, interim bulk lane: notes

Branch `revamp/wp2-7-meta-scheduler`, cut from `revamp/wave-2-base` (`ca7d8a9`).

Owned files, all that changed: `src/orchestrator/scheduler.rs`,
`src/orchestrator/meta_exchange.rs`, `src/orchestrator/objects.rs`,
`tests/meta_scheduler.rs` (new), and these notes. No frozen file, no other
package's file and no existing test was touched. The two frozen stub
signatures (`scheduler::run_control`, `objects::run_bulk_lane`) are
unchanged (`tests/seam_stubs.rs` pins them and passes).

Like the rest of the v3 peer stack in Wave 2, nothing here runs in the daemon
yet: WP2.6's PeerSupervisor spawns these lanes, and WP3.1 switches the
network to them. Everything below was built and tested standalone, against
real authenticated v3 sessions (`session::dial` ↔ `session::accept`) whose
server side is a scripted handler, and against a fake folder directory and
worker client.

## Summary

### `scheduler.rs`: the MetaScheduler and the shared scheduling engine

One engine (`drive`) serves both the control lane (`run_control`, op
`meta.exchange`) and the interim bulk lanes (`objects::run_bulk_lane`, op
`objects.exchange`). The op-specific half is a small internal `Job` trait.

- **Keys.** One key per repository that the peer's catalog
  (`PeerContext.catalog`) lists **and** a local folder holds
  (`FolderDirectory::by_repo`). A scheduler serves one peer and one op, so a
  key is one (peer, repo, op): the RC5 fix. A failure, a backoff or a hang
  belongs to its key only.
- **Slots.** At most `slots` exchanges at once (`limits::EXCHANGE_SLOTS` = 4
  on lane 0; `objects::REPOS_PER_LANE` = 2 on a bulk lane), at most one per
  key. Slot threads are a small pool per lane, started on demand. "One per
  key" also holds across scheduler instances in the process (a process-wide
  claim set keyed by local installation, peer, op scope and repo). So a lane
  respawned on a new session does not start a repository whose exchange on
  the old session is still ending (tested).
- **Deadlines.** Each exchange has its own deadlines: `feed-offer` 10 s, peer
  `meta.exchange` 30 s (`limits::EXCHANGE_DEADLINE`), `feed-apply` 10 s;
  bulk: worker offer and apply 30 s, peer `objects.exchange` 60 s.
- **Readiness** (never a failure): `Paused` (local `sync_enabled` false),
  `WaitingForWorker` (local folder not Running or without a worker
  endpoint), `WaitingForRemote` (remote entry not `running`). A key that is
  not ready is never dispatched and counts nothing; it is due at once when it
  becomes ready again.
- **When a key is due:**
  - *Reset* (due now, retry state cleared): the key became ready, the local
    worker instance changed, or the remote replica changed (the legacy "new
    worker address resets the repository's backoff" rule, generalized).
  - *Trigger* (due now, or right after the running exchange): the local feed
    tip (`WorkerHeartbeat.tip`) moved; the remote catalog tip moved; the local
    `generations.sync` moved, unless it is the echo of a local exchange (see
    *absorb* below). Bulk lanes use `generations.content` and the remote's
    published content counters instead of `generations.sync`.
  - *Anti-entropy:* `sync_interval_ms` after the last exchange ended.
  - *Continuation:* an exchange that moved data and has more (`page.more` on
    either side) runs again at once. An exchange that only recovered a cursor
    (`CursorMismatch`, or a reset page) runs again at once, at most
    `QUICK_LIMIT` (2) times in a row. A bulk exchange that moved object bytes
    runs again after 10 ms.
  - *Retry* after a failure, by class (below).
- **Absorbing the echo.** A worker bumps `generations.sync` after feed
  exchanges and activation slices, so each exchange would trigger the next
  one forever. The engine keeps a process-wide activity record per (local
  installation, class, repo). A generation bump seen while any local exchange
  of that repository runs, or within `ABSORB` (3 s, three heartbeat periods)
  after one ended, is that exchange's own echo and does not trigger. Tip
  changes always trigger, and they converge: they stop when nothing new is
  committed. The remote's `sync_generation` is deliberately not a trigger: it
  moves on every exchange we make with that peer.
- **Failures** (`failure_kind`, §8):

  | Kind | Codes | Retry | Counted |
  |---|---|---|---|
  | Contention | class Contention (`WORKER_BUSY`, `BUSY`, …) | `Backoff::contention()` 50 ms → 1 s | no |
  | Waiting | `WAITING_CODES`: `REMOTE_WORKER_STARTING`, `FOLDER_SYNC_PAUSED`, `LOCAL_WORKER_UNAVAILABLE`, `WORKER_NOT_RUNNING`, `WORKER_STOPPING`, `WORKER_EXITED` | recheck after `WAITING_RECHECK` (2 s, the catalog poll) | no |
  | Transient | class Transient (and unknown codes) | `Backoff::transient()` 1 s → 60 s ±20 % | yes |
  | NeedsUserAction | class NeedsUserAction | parked; recheck after 60 s, or at once on a reset | yes |
  | Incompatible, Fatal | those classes | parked; recheck after 10 min, or at once on a reset | yes |

  A remote `retry_after_ms` lengthens the delay. A Transient failure ends a
  Contention streak, so a Transient retry after Contention starts at attempt
  1 (tested). The delay chosen for a failure is reported as the
  `ExchangeFinished` error's `retry_after_ms`, which the hub shows as the
  pair's `backoff_until_ms`.
- **Uncertain requests** (invariant 16). A retry is always a fresh worker
  `feed-offer`, so it carries a new request id. As a guard, a process-wide
  set of the last 4,096 sent `meta.exchange` request ids refuses to send an
  id twice (`REQUEST_ID_REUSED`, counted), even if a faulty worker hands one
  out again (tested).
- **Lost session.** A peer call that fails with `ConnectionLost` (uncertain)
  or `Unavailable`, meaning the session is closed, closing or going away
  (GOAWAY), charges no key. The scheduler stops dispatching and returns, and
  the PeerSupervisor redials. Cancellation stops it too, as does `ctx.stopping`,
  which stops new dispatches.
- **Exit.** On stop the engine waits up to `EXIT_WAIT` (3 s) for exchanges in
  flight. A closed session fails them at once. Exchanges still in flight
  after that wait (a worker call cannot be interrupted) end on their own
  within their deadlines and release their claims themselves. The watcher
  thread exits within 250 ms.
- **Wake-ups.** Signal-based: one watcher thread per lane waits on
  `FolderDirectory::wait_newer` (250 ms slices), so a heartbeat change wakes
  the loop at once. Slot completions arrive on a channel, and cancellation
  arrives through a hook on a child token. The remote catalog generation and
  the session's `closed()` are sampled in the same 250 ms slice. The loop
  sleeps until the earliest due key (at most 1 s).
- **Session checks** (`check_session`, before anything runs). The session is
  authenticated as the peer (`PEER_INSTALLATION_CHANGED`, I12). It has the
  lane's role: a control lane on a bulk session is `METADATA_ON_BULK_LANE`,
  a bulk lane on a control or probe session is `BULK_ON_CONTROL_LANE`
  (invariant 18). A bulk lane's session must carry its own `LaneSpec`
  (`BULK_LANE_MISMATCH`), and the `LaneSpec` must be valid
  (`INVALID_BULK_LANE`). A lane that fails a check records
  `StatusEvent::Error{scope: Lane}` and holds until it is cancelled or the
  session closes. It does not return at once, so the supervisor does not
  respawn it in a tight loop.
- **Observability.** `DriveOptions::view: Option<Arc<Snapshot<SchedulerView>>>`
  publishes, per key: readiness, phase (`Due`, `Running`, `Idle`,
  `Contention`, `Backoff`, `Waiting`, `Parked`, `NotReady`), counted failures,
  Contention streak, exchanges, successes, time to due and last error. It also
  publishes `in_flight` and `peak_in_flight`. It is unset by default; the tests
  use it, and WP4.2 diagnostics can.

### `meta_exchange.rs`: one metadata exchange (§6.3.5)

`exchange(ctx, conn, peer, folder, remote) -> Result<ExchangeSummary, CallError>`
(the "Provides" signature) wraps `exchange_with(.., &ExchangeOptions, retry_after)`,
which returns an `ExchangeOutcome` (summary, gate view, page status, `more`,
`reset`, duration) or an `ExchangeError{step: Local|Peer, error}`.

1. Route `{peer: peer.installation, repo, local_replica: folder.record.device,
   remote_replica: remote.replica}`, from the local record and the
   authenticated peer's catalog entry (I12).
2. Worker `feed-offer{route}`. The request must be format 7 and for this
   route (`LOCAL_REPLICA_BINDING_MISMATCH`), with a uuid id
   (`INVALID_SYNC_REQUEST_ID`), never sent before (`REQUEST_ID_REUSED`).
3. Peer `meta.exchange`: header `{repo}`, body the JSON `MetaExchangeRequest`,
   priority `Response` (`catalog.list` and heartbeats stay ahead of large
   bodies). The reply is the JSON `MetaExchangeReply` in the body, or in the
   header if the body is empty. It must answer this request
   (`reply_to` ≠ request → `UNBOUND_PEER_RESPONSE`, invariant 10) and this
   repository (`REPOSITORY_MISMATCH`).
4. Worker `feed-apply{route, request_id, reply}` → `FeedApplyResult`.
5. The summary is the worker's, with `bytes_up`/`bytes_down` (request and
   reply body bytes) set by the orchestrator, and `sent_events` /
   `received_events` at least what the pages carried (payload entries;
   received also counts `need_served`).
6. `ExchangeStarted` (lane 0, op `meta.exchange`) at the start;
   `ExchangeFinished{direction: Outbound}` at the end with the **real**
   duration (monotonic clock), the summary, the body bytes, `objects_up/down = 0`
   and, on failure, the error with `retry_after_ms`. A panicking exchange is
   reported too (the engine records its `ExchangeFinished`), so the hub never
   keeps it in flight.
7. `GateEvidence` to the folder after a successful exchange while its gate is
   `Awaiting` or `Blocked` (the controller keeps only the gate source's
   evidence, and uses the rest for retargeting).

### `objects.rs`: the interim bulk lane (§6.5)

`run_bulk_lane(ctx, peer, lane, conn, cancel)` (frozen signature) and
`run_bulk_lane_with(.., BulkOptions)` run the same engine with 2 slots. One
exchange (`bulk_exchange`):

1. Worker `published-bulk-offer{route, lane: Lane{index, count}, inventory}`.
   `Lane` comes from the `LaneSpec` (the legacy `bulk_sync::Lane`, so
   `Lane::owns` sharding is unchanged, invariant 19). `inventory` is the
   peer's previous reply without parts, as the legacy lane cached it. It is
   dropped after any failure of that key, and on a key reset.
2. Peer `objects.exchange`: header `{repo, lane}`, body the JSON page,
   priority `Data`. The reply is the JSON page, as the body or as streamed
   body CHUNK frames (`hash: None`, in offset order, ≤ 64 MiB) before the
   RESPONSE. It must answer our request (`UNBOUND_PEER_RESPONSE`).
3. Worker `published-bulk-apply{route, lane, page, request}`.
4. `ExchangeFinished{op: objects.exchange, lane: index + 1}`:
   - `bytes_up` / `bytes_down` are the object bytes of the two pages;
   - `objects_down` counts objects that the reply's parts complete;
   - `objects_up` counts objects we sent in full that the peer's reply lists
     as available (`known_objects`).

   Only completed objects are counted (the WP1.INT re-review rule).

Bulk lanes carry no metadata: they never stage, activate or acknowledge
events (invariant 18).

## Deviations from the spec, and why

1. **Extra public API, frozen signatures unchanged.** Besides the "Provides"
   functions, the files export `run_control_with`, `run_bulk_lane_with`,
   `ControlOptions`, `BulkOptions`, `DriveOptions`, `ExchangeOptions`,
   `exchange_with`, `ExchangeOutcome`, `bulk_exchange`, `BulkOutcome`,
   `SchedulerView`/`KeyView`, `failure_kind`, `readiness`, `ExchangeError`.
   The tests need explicit deadlines: the RC5 scenario with the frozen 30 s
   deadline would take minutes. The view makes "not counted" observable
   without timing guesses. The `*_with` functions are additions, not
   changes (§13 rule 3).
2. **Triggers beyond `generations.sync`.** The spec lists heartbeat
   `generations.sync`, remote catalog tip changes, anti-entropy and backoff
   expiry. I added the local feed tip (a local commit is the clearest reason
   to send), and continuation for catch-up, which the spec's O(delta)
   catch-up needs: a 150K-event feed is about 37 pages. I also added the
   echo absorption. Without it, every exchange's own `generations.sync` bump
   triggers the next exchange forever. Under mutual pairing two daemons would
   do so for each other, through `feed-exchange` bumps on the acceptor. The
   cost: a generation-only change within 3 s of a local exchange of that
   repository waits for the anti-entropy interval. Tip changes are never
   absorbed.
3. **The bulk lane is scheduled, not a plain loop.** Task 4 says "loop …
   yield 10 ms after content moves, otherwise wait `sync_interval_ms`". The
   lane does exactly that per key, but runs up to `REPOS_PER_LANE` (2)
   repositories at once, with per-key backoff. With a sequential loop, one
   repository whose exchange hangs to its 60 s deadline would hold every
   other repository on that lane (RC5 again). It also reacts to the triggers
   above instead of waiting out the interval.
4. **Parked rather than never retried.** §8 says NeedsUserAction and Fatal do
   not retry in scope. A parked key is rechecked after 60 s (NeedsUserAction)
   or 10 min (Incompatible, Fatal), or at once on a reset (new worker, new
   remote replica, readiness regained). A rare automatic recheck is cheap; a
   key stuck until a daemon restart is not.
5. **Waiting answers.** Besides the remote's `REMOTE_WORKER_STARTING` /
   `FOLDER_SYNC_PAUSED`, a local worker that cannot be reached
   (`LOCAL_WORKER_UNAVAILABLE`, `WORKER_NOT_RUNNING`, `WORKER_STOPPING`,
   `WORKER_EXITED`) is treated as WaitingForWorker (not counted). The folder
   view said Running, but the FolderController owns that worker's liveness.
6. **A lost session ends the lane.** On `ConnectionLost` or a refused call
   (closed, closing, GOAWAY) the scheduler returns instead of waiting for
   cancellation: no request can be sent on that session again. WP2.6 should
   treat a lane thread's return as "session gone" (CCR-WP2.7-4).
7. **Status lane numbers.** Bulk lanes report status lane `index + 1` (lane 0
   is control). This matches the legacy pool numbering the hub's
   `legacy_lane_role` assumes.
8. **Bulk byte counts are object bytes**, not JSON or hex wire bytes. The
   hub uses these fields for object rates and the ETA. Hex would double them.

## CCRs filed

- **CCR-WP2.7-1: `model::protocol::max_body(ops::OBJECTS_EXCHANGE)` = 16 MiB
  (`frame::MAX_BODY_META`).**
  - *Requested change:* one arm in the frozen `max_body`.
  - *Reason:* the interim path carries legacy `bulk_sync::Page` JSON. A page
    holds up to `PAGE_BUDGET` 4 MiB of hex parts (2 MiB of objects) plus its
    inventories, so a typical page is over 1 MiB, the current `objects.*`
    limit. Today a request page over 1 MiB fails locally with
    `WS_MESSAGE_TOO_LARGE`, and a plain reply body over 1 MiB fails at the
    acceptor's `Responder::reply`. Any repository with about 512 KiB or more
    of pending objects therefore cannot move them on the interim path, and
    WP3.1's end-to-end tests may need that. 16 MiB fits every page that
    `bulk_sync`'s own limits allow in practice (`INVENTORY_TOO_LARGE` caps
    the inventories).
  - *Adapter:*
    - The client accepts the reply either as a body or as streamed body
      CHUNK frames, up to 64 MiB, the legacy message bound. So an acceptor
      that streams large replies with `Responder::chunk` works today (tested
      with a 1.5 MiB object).
    - An oversize request fails only its own key, with
      `WS_MESSAGE_TOO_LARGE` and backoff (tested).
    - The CCR removes the request-side limit. WP3.3 replaces the path in
      Wave 3.
- **CCR-WP2.7-2 (spec ratification; for WP2.8 and WP2.INT): wire shapes of
  the two ops.**
  - *Requested change:* §6.2's op table names payload types but not where
    they travel. This client sends `meta.exchange` as header `{repo}`
    (`MetaExchangeHeader`) and body = JSON `MetaExchangeRequest`, and reads
    the reply from the body (JSON `MetaExchangeReply`; the header is read if
    the body is empty). It sends `objects.exchange` as header `{repo, lane}`
    and body = JSON page, and reads the reply from the body or streamed body
    chunks.
  - *Reason:* bodies up to 16 MiB cannot travel in a 64 KiB header.
  - *Adapter:* none; the inbound side (WP2.8) must match.
- **CCR-WP2.7-3 (information; for WP2.3 and WP2.5): what drives the
  MetaScheduler.**
  - *Requested change:* `Generations.sync` should be bumped only when a feed
    exchange or an activation slice changed state (staged, acknowledged, a
    cursor moved, an inbox row changed state), not on every idle exchange.
    `WorkerHeartbeat.tip` should be filled: it is the scheduler's primary
    trigger.
  - *Reason:* a bump on every idle exchange makes exchanges trigger each
    other.
  - *Adapter:* the echo absorption above holds whatever the worker does.
- **CCR-WP2.7-4 (information; for WP2.6): the lane contract.**
  - `run_control` / `run_bulk_lane` return when cancelled (within `EXIT_WAIT`
    3 s + 0.5 s, sooner if the session is closed first) and when the session
    closes or refuses calls (GOAWAY).
  - They never close the session: the supervisor owns it, and closing it on
    cancel makes in-flight exchanges end at once.
  - A lane that refuses its session (role, lane, installation) holds until
    cancelled.
- **CCR-WP2.7-5 (spec ratification; for WP2.5): `GateView` semantics.**
  - *Requested change:* §6.3.6 should say that `GateView.caught_up` is the
    full gate claim and that `GateView.blocked` means blocked, quarantined or
    rejected rows from the source exist.
  - *Reason:* the FolderController reads `GateEvidence{caught_up && !blocked}`
    as satisfied and `caught_up && blocked` as the Blocked gate.
  - *Adapter:* `meta_exchange::gate_evidence` sends `caught_up =
    gate.caught_up || (gate.blocked && summary.caught_up)` (the metadata
    claim when the gate view is blocked), and `blocked = gate.blocked`. This
    yields the Blocked gate under either reading of `GateView.caught_up`.

## Known limitations

- **Interim bulk pages over 1 MiB.** See CCR-WP2.7-1. Until it is applied,
  or the acceptor streams large replies, bulk transfers of repositories with
  more than about 512 KiB of pending objects fail with
  `WS_MESSAGE_TOO_LARGE`. They fail per key, with backoff, and the session
  stays usable.
- **No real worker feed ops yet.** WP2.5 implements `feed-offer`,
  `feed-exchange` and `feed-apply` in parallel, and the base worker answers
  `UNSUPPORTED_OPERATION`. All metadata tests use a fake worker. Real
  end-to-end runs are WP2.INT's (daemon) and WP3.1's (cutover). The
  `ExchangeSummary` counters other than bytes and event counts are the
  worker's.
- **Echo absorption is coarse.** It is per (local installation, class, repo),
  shared by all peers. When several peers exchange the same repository every
  ≤ 3 s (the default 500 ms interval does), generation-only changes rarely
  trigger, and the anti-entropy interval (the same 500 ms) carries them. Tip
  changes still trigger immediately.
- **Detached exchanges.** On cancel, an exchange still blocked in a worker
  call after `EXIT_WAIT` finishes on its own, within its deadline (≤ 10 s
  for a worker call; the peer call fails as soon as the supervisor closes
  the session). It keeps its claim until then.
- **Sampling.** Remote catalog changes and session closure are sampled every
  250 ms by the lane's watcher. Folder changes wake it at once.
- **Threads.** Per lane: one watcher thread, plus slot threads started on
  demand (≤ 4 on lane 0, ≤ 2 per bulk lane).
- **A bug found and fixed during development**, recorded because it is easy
  to reintroduce: `Claim::take` first used `insert(..).then_some(Claim(key))`.
  `then_some` builds the `Claim` even when the key is taken. Its `Drop`
  locked the registry while the statement's guard was still held (a
  deadlock), and it would have released another exchange's claim.
  `a_cancelled_lane_…` caught it. The fix builds the claim lazily, after
  the lock is released.
