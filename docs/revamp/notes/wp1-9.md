# WP1.9 — Session core: frames, I/O thread, multiplexing

Branch `revamp/wp1-9-session-core` (cut from `revamp/wave-1-base`, commit `abc8234`).

## Summary

WP1.9 implements the v3 connection layer of REVAMP_PLAN §6.2, minus the
handshake (WP1.10). The WP0.4 public API is unchanged; every stub body in the
owned files is now real. Fix round 1 (see the section of that name) closed
three blockers, one major and five minors found by the independent review.
Fix round 2 closed the second review's major (a streamed request waiting for
a handler could hold the server's reads and starve the running streams) and
its minors; see *Fix round 2*.

### Behaviour

- **Requests.** Client-allocated u64 ids (from 1; id 0 is reserved, and a
  REQUEST, CANCEL or CHUNK with id 0 is a protocol violation); only the
  client side originates requests (`call` on a server-side `Conn` is
  `Unavailable` `UNSUPPORTED_OPERATION`; a REQUEST received by a client, or
  RESPONSE / PROGRESS / CANCEL in the wrong direction, is a protocol
  violation).
- **Deadlines.** `call` has an absolute deadline; `call_streaming` an optional
  absolute deadline plus an idle deadline that CHUNK and PROGRESS reset;
  `upload` an idle deadline (per `chunk()` space wait, which a PROGRESS also
  restarts, and for the reply). The waiting caller enforces its own deadlines
  exactly. An idle deadline restarts instead of expiring while this side
  holds its reads, or while part of the call's own request is still queued
  here (the peer cannot be judged on a request it has not received; a dead
  link is caught by `dead_after`). On expiry the caller removes its pending
  entry under the state lock (the arbiter against a racing reply), drops
  whatever of the request is still queued, and queues CANCEL. The same
  happens when `on_chunk` returns an error, when the caller unwinds
  (`PendingGuard`), and when an `Upload` is dropped unfinished. After a
  `chunk()` timeout, every later `chunk()` and `finish()` return that
  `Timeout` at once. On the server, the I/O thread's 250 ms scan cancels
  requests past their `deadline_ms`, expires stalled reassemblies and answers
  `REQUEST_TIMEOUT` to streamed requests idle past their `idle_ms` (a stream
  still waiting for a handler is not judged once its body has ended: it is a
  queued request).
- **Late replies.** Ids are never reused, so any frame for an allocated id that
  is no longer pending is discarded whatever its flags: a header-only RESPONSE,
  a RESPONSE with `MORE`, its CHUNK continuations (also when the call gave up
  in the middle of the reassembly, which is then freed at once), and stream
  chunks.
- **Outcomes.** RESPONSE `ok:false` → `CallError::Remote` and the connection
  stays usable (invariant 17). A connection failure fails every call in
  flight with `ConnectionLost` (uncertain); nothing is ever replayed
  (invariant 16). Refusals before anything is sent: `Unavailable` (closed,
  closing, or a GOAWAY in effect; its code is the reason's code), `Busy`
  (control queue full, or no room for a body or data before the deadline),
  `Remote(WS_MESSAGE_TOO_LARGE)` (body over the op's limit or header over
  64 KiB). When a call gets its outcome, whatever of its request is still
  queued is dropped (an early reply to an upload stops the rest of the body).
- **Queues, priority and bounds (invariant 22).** Control (header-only
  REQUEST/RESPONSE, PROGRESS, CANCEL, HEARTBEAT, GOAWAY; ≤
  `control_queue_bytes`, 16 MiB), response bodies (round-robin per id; ≤
  `control_queue_bytes`) and data CHUNKs (round-robin per id; ≤
  `data_queue_bytes`, 32 MiB). An empty queue admits one item of any size.
  Producers that find no room wait in FIFO order per queue (`wait_room`
  tickets; every batch uses one queue): later batches queue behind a waiting
  one, so a batch larger than the bound (a maximum `meta.exchange` body) is
  admitted once the queue drains instead of being starved by smaller ones.
  Producers block outside the I/O thread while their queue is full: data
  producers (`Upload::chunk`, `Responder::chunk`), request bodies, and handler
  replies (`Responder::reply`/`error`, which give up if the request is
  cancelled or expires, or the connection closes); a request header that finds
  the control queue full is refused `Busy`. At most one PROGRESS per request
  and one HEARTBEAT wait in the queue. Frames the I/O thread produces itself
  (`ping` replies, `BUSY`, refusals) cannot wait; instead a server holds its
  reads while its control queue is over the bound (see flow control). All
  frames of one id stay in order: a streamed reply's final RESPONSE follows
  its chunks through the data queue; CANCEL may overtake because the
  cancelled request's queued frames are purged first. While the socket is
  write-blocked, frames stay in the queues (purgeable, in priority order)
  instead of piling into tungstenite's buffer.
- **Bodies.** Above one chunk (1 MiB) the REQUEST/RESPONSE carries the first
  part with `MORE` and `total`; CHUNKs (`hash: None`, `MORE` until the last,
  which has `LAST`) carry the rest, reassembled up to
  `min(protocol::max_body(op), max_body)` (16 MiB `meta.exchange`, 1 MiB
  otherwise). Offsets, totals and flags are verified; a violation closes the
  connection. A server reassembles at most `4 × max_body` (64 MiB) of request
  bodies at once.
- **Streams.** A streamed reply is CHUNKs with `MORE` (each delivered to the
  `call_streaming` callback as a zero-copy slice of the received message) then
  the RESPONSE. *[Corrected by the WP1.INT post-integration re-review: a slice
  of the received message shares tungstenite's read buffer, so a chunk waiting
  for its callback pinned that whole allocation (+236 MiB of live heap for
  2.4 MiB charged with two interleaved streams). The I/O thread now copies
  each chunk body, as the server side always did; see `notes/wp1-int.md`.]* PROGRESS frames only count in the waiting call's slot (one
  `Event::Progress` however many arrived), so a peer sending them while
  nobody drains the slot (an `Upload` still sending parts) cannot grow it. A streamed request is a REQUEST with `MORE` and no `total`,
  CHUNKs with `MORE` (into `Incoming::chunks`, a bounded channel of 4 parts),
  and an empty CHUNK without `MORE` that ends the body and disconnects the
  channel. `Upload::chunk` fails once the request has ended (`Remote` for an
  early error reply, `Cancelled` for an early OK reply, which `finish` returns).
- **Flow control: reads are held** in two cases, and TCP then pushes back on
  the peer:
  - *receive side*: more than `data_queue_bytes` of received stream data
    waits for slow consumers (callback or handler); reading resumes once they
    are back under half of it. Every way out of a call (outcome, timeout,
    callback error or panic, `Upload` drop) returns its undelivered chunk
    bytes to this count. Only consumers that run can hold reads (fix round
    2): on a server, the parts of a streamed request still waiting in the
    handler queue (channel included) count against the same bound but never
    cause a hold. When the total is over the bound, waiting streams are
    refused `BUSY` (Contention, `retry_after_ms: 50`; newest first; nothing
    ran) and their parts dropped, until the total fits or only streams that
    idle handler threads are about to take are left; only then are reads
    held, so a hold always ends as running consumers catch up. Liveness is
    not judged while this hold lasts, and neither are the idle limits of
    streams that may be waiting behind it: a client's
    `call_streaming`/`Upload::finish` idle deadline restarts (the absolute
    deadline still applies); a server judges only streamed requests whose own
    running handler left parts untaken for their idle limit
    (`REQUEST_TIMEOUT`, which also ends the hold) and, every 250 ms scan,
    sends one PROGRESS to each other streamed request still receiving its
    body, so its client's idle windows restart too. Idle windows restart
    when reading resumes.
  - *receive-side bound* (exact): `data_queue_bytes` + the one part whose
    arrival crosses it (reads stop right after it) + the parts already in the
    channels of running handlers (`UPLOAD_CHANNEL` = 4 parts of ≤ 1 MiB per
    running streamed request, i.e. ≤ 4 MiB × `handlers` while handlers keep
    their `Incoming::chunks`: 16 MiB control, 8 MiB bulk). Channel bytes of a
    running handler are not counted because `Incoming::chunks` is a plain
    `Receiver` (frozen type): nothing tells the I/O thread when a part is
    taken. Request-body reassembly is bounded separately (4 × `max_body`).
  - *outgoing pressure (server)*: the control queue holds more than
    `control_queue_bytes`, i.e. the peer leaves our replies unread while it
    keeps sending requests. Reading resumes at half the bound. While this hold
    lasts the peer is judged by the write side: `TRANSPORT_DEAD` ("the peer
    read nothing for N ms") after `dead_after` without the socket taking any
    byte (a completed flush or writable readiness).
- **Handler pool.** `serve` starts `handlers` threads (`sess-<n>-h<i>`);
  requests wait in a queue of `handler_queue` beyond those idle handler
  threads are about to take (so `handler_queue: 0` serves while a handler is
  idle and refuses otherwise); a full queue answers `BUSY` (Contention,
  `retry_after_ms: 50`) from the I/O thread, as does a streamed request
  whose parts do not fit the receive bound while it waits (see flow
  control). A handler panic is
  caught; a `Responder` dropped unanswered replies `UNKNOWN_ERROR`. `ping` is
  answered by the I/O thread itself (`{alive:true}`), so liveness probes never
  wait behind busy handlers or `BUSY`. `Responder` is `Send + Sync` (its flags
  are atomics), so a handler may share `&Responder` with a progress thread.
- **Liveness.** HEARTBEAT `{seq, at_ms, echo}` after `heartbeat` (5 s) of send
  idleness; RTT from the echo (`now − echo.at_ms − echo.held_ms`). Dead
  (`TRANSPORT_DEAD`) after `dead_after` (20 s) without hearing from the peer:
  a received message, or readable readiness of the socket (bytes arrived, even
  when they only continue a large message on a slow link).
- **GOAWAY.** No new requests from either side once sent or received
  (requests already in transit are refused with `WS_CLOSED`); in-flight work
  completes; the connection closes when idle or after 5 s, and `closed()`
  reports the GOAWAY's code. *[Corrected by the WP1.INT post-integration
  re-review: the side that sent the GOAWAY closed as soon as it was idle and
  discarded the requests in transit, whose callers saw `ConnectionLost`. Only
  the side that received a GOAWAY now closes when idle; the sender keeps
  reading and refusing until the peer's Close or the 5 s grace.]*
- **Close reasons** (`closed()`): `WS_CLOSED` (local `close`, peer Close),
  `CONNECTION_LOST` (reset, EOF, I/O error), `TRANSPORT_DEAD`,
  `PROTOCOL_VIOLATION` (the peer also gets a best-effort GOAWAY with the
  detail and a Close with code 1002), or the GOAWAY's code.
- **Fairness.** A read turn yields after 1 MiB or 1,024 messages and a write
  turn after 1 MiB, so reading, writing and timers interleave while the socket
  never blocks (found necessary: an unbounded write turn delayed a control
  reply over WSS by the whole 30 MiB queue). Fix round 1 lowered the turns
  from 4 MiB to one 1 MiB frame: release loopback download went from about
  450–540 to 850–965 MiB/s, and the median control latency with 30 MiB queued
  from about 14 to 3 ms.
- **Metrics.** `ConnHealth`: `since_ms`, `rtt_ms`, `last_rx_ms`/`last_tx_ms`,
  `bytes_up`/`bytes_down` (frame bytes), `inflight` (pending calls + requests
  being served), `queued_bytes` (outgoing queues).

## Deviations from the spec and why

1. **`tests/contracts.rs` edited (one assertion; CCR-WP1.9-1).**
   `session_stubs_fail_closed_with_not_implemented` asserted
   `frame::encode(valid CANCEL frame).is_err()`. The plan makes WP1.9 provide
   the real codec, so that assertion cannot hold, and no adapter on WP1.9's side
   can keep it true without leaving a broken public `encode` for WP1.10's
   handshake. The full suite must pass, so the assertion was replaced by a
   stronger one: the frame encodes, decodes back equal, and `decode(&[])` still
   fails. Nothing else in the file changed. The review lists this under
   ownership (the file is WP0.4's); it stays applied here because VERIFY
   requires a green suite, and it is filed for the integrator to ratify (WP1.10
   did the same for the `accept`/`dial` lines of that test, in other hunks).
2. **`ping` never reaches the `Handler`.** The I/O thread answers it (§3.8 says
   "answered directly"). Liveness probes then cannot be refused with `BUSY` or
   wait behind long handlers.
3. **Wire conventions the plan leaves open** (both ends are this code):
   `MORE` means "more frames of this id follow" on REQUEST, RESPONSE and CHUNK;
   the streamed-request terminator is an empty CHUNK without `MORE`; the first
   body part rides in the REQUEST/RESPONSE frame; `Upload::chunk` and
   `Responder::chunk` overwrite `ChunkHeader.id` with the request id.
4. **Request deadlines are enforced by the waiting caller**, not by the
   250 ms scan: a call returns `Timeout` at its deadline (±scheduling), not up
   to 250 ms late. The 250 ms scan in the I/O thread covers the server side
   (deadlines of requests being served, stalled streamed bodies, expired
   reassemblies) and stale client reassemblies.
5. **Receive-side flow control** (above) is an addition: without it a slow
   consumer would make the receiver buffer without bound and "queue memory ≤
   cap with a slow receiver" could not hold end to end. Trade-off: a consumer
   that stops reading holds the connection's reads once `data_queue_bytes` are
   buffered (a per-stream credit scheme would need new frames). A server
   handler that does so is cancelled after its request's idle limit; a client
   callback that never returns holds them for good. *[Corrected by the WP1.INT
   post-integration re-review: that hold also suspended liveness and every
   other call's idle limit. A client hold in which no stream callback takes
   anything for `dead_after` now gives up the call with the most chunks
   queued (`Timeout`, CANCEL sent), so reading and liveness resume.]* Since fix round 2 only
   running consumers can cause a hold; a streamed request waiting for a
   handler is refused `BUSY` instead (deviation 12).
6. **Local refusals of oversized bodies/headers are `CallError::Remote`** with
   `WS_MESSAGE_TOO_LARGE` (connection usable, not uncertain), so the caller
   sees the exact code; an oversized *reply* becomes a `WS_MESSAGE_TOO_LARGE`
   error reply instead of a protocol violation. An error from the
   `call_streaming` callback is returned as `CallError::Remote` with the
   callback's own `ErrorWire` (after CANCEL).
7. **Additive API in owned files:** `ConnOptions::sanitized` (applied by
   `from_established`: timers ≥ 10 ms, `dead_after ≥ heartbeat`,
   `max_chunk ≤ 1 MiB`, `max_header ≤ 64 KiB`, ≥ 1 handler, queue bounds ≥ one
   frame), the `frame` helpers listed above. `FrameError::NotImplemented` is
   kept for API stability but never produced. Received bodies are always
   accepted up to the 1 MiB wire bound regardless of the local `max_chunk`.
8. **Debug-build thresholds in `tests/session_core.rs`.** Latency bounds are
   the §14 values in release builds and 5× in debug builds, where the test runs
   in parallel with the whole suite (REVAMP_PLAN §15.3: strict thresholds only
   in release qualification runs). Every sample is checked (no median); the
   release qual scenarios enforce the §14 values. The release qual metric
   for "a control call < 50 ms with 30 MiB queued" is the p99 of 200 calls
   (`control_queued_30mib_p99_ms`, as for `fast_p99_ms`), with the max
   recorded beside it, not the max: on Windows loopback, data already in the
   kernel crosses in steps of the 15.6 ms timer tick while the sender's socket
   is full (a trace showed both I/O threads idle 12–16 ms together: the client
   write-blocked, the server with nothing to read), so samples cluster at 1, 2
   or 3 ticks and the max landed at 32–49 ms in nine runs; a single 4-tick
   sample would fail a max check. On Linux (WSL) the same scenario gives a max
   of 1.9 ms.
9. **Outgoing bounds (fix round 1).** §6.2 bounds only the control (16 MiB)
   and data (32 MiB) queues. The response-body queue gets the control bound
   too (`ConnOptions` is frozen, so no new field); handler replies wait for
   room (`Responder::reply` may block while the peer is behind on reading).
   The server holds its reads while its control queue is over the bound,
   because the frames the I/O thread produces cannot wait; a client needs no
   such hold (reading produces nothing to send, and `submit` bounds its
   control queue).
10. **Liveness evidence (fix round 1).** "Dead after 20 s with no received
    frame" also counts readable readiness as hearing from the peer, so a large
    message arriving slowly does not read as silence; while a server holds its
    reads for outgoing pressure, the peer is judged by whether it takes our
    bytes (no write progress for `dead_after` → `TRANSPORT_DEAD`).
11. **"60 s idle stays up" is evidenced by the release qual scenario.**
    §14 lists it among the `session_core.rs` acceptance criteria;
    `session_core::idle_connection_stays_up` idles for 3 s with heartbeat
    200 ms / dead 1 s (15 heartbeat periods, 3 × `dead_after`) through a
    FaultProxy, plain and WSS, which exercises the same mechanism in a
    suite-friendly time. The literal 60 s idle with production timings
    (heartbeat 5 s, dead 20 s) is `qual_wp1_9_session::idle_60s` (ignored,
    release; one proxied connection, no reset, ping after the idle).
12. **`BUSY` for a streamed request waiting for a handler (fix round 2).**
    §6.2/§3.8 answer `BUSY` only for a full handler queue. A streamed
    request accepted into the queue may now also be answered `BUSY` later,
    while it still waits for a handler, when its parts do not fit the receive
    bound (newest waiting stream first; never one an idle handler thread is
    about to take). No handler ran it, so the refusal is certain and the
    client retries it like any `BUSY` (Contention, `retry_after_ms: 50`).
    The alternatives were worse: buffering without bound breaks invariant 22,
    and holding reads for it starves the running streams it waits for (the
    review's major finding). Refusing every streamed request that finds no
    idle handler (the review's option a) would also refuse a request that
    arrives while a handler is finishing its previous reply.
13. **`handler_queue` counts requests beyond idle handlers (fix round 2).**
    Requests reach handlers only through the queue, so `handler_queue: 0`
    used to refuse everything. The check is now `queued ≥ handler_queue +
    idle handler threads` (threads `serve` started that are not running a
    request, including ones still starting up), which keeps `0` meaningful
    ("never wait") instead of clamping it to 1 in `sanitized()`; with the
    default 16 a burst may now queue up to 16 + the idle threads before
    `BUSY`. A first version counted only threads blocked waiting for work;
    repeated runs caught a request that arrived right after `serve`, before
    the new threads reached their wait, being refused, so idle is now
    "started minus busy".

## CCRs filed

- **CCR-WP1.9-1 (applied in this worktree; for the integrator to ratify).**
  Requested change: `tests/contracts.rs`
  `session_stubs_fail_closed_with_not_implemented` — replace

- **CCR-WP1.9-3 (not applied; WP0.5's file).** Requested change: add a floor
  `{"id": "session_control_under_queued_data", "wave": 1, "scenario":

  "control_queued_30mib_p99_ms", "op": "<", "value": 50, "unit": "ms"}` to
  `tests/qualification-floors.json`. Reason: the §14 WP1.9 criterion "a control
  call answered < 50 ms while 30 MiB of data is queued" had no release floor.

while the socket was write-blocked, each loop turn still moved one more queued

purging/priority for those frames and looked like write progress. Frames now
stay queued until a flush gets through, and only a completed flush or writable
readiness counts as progress.

While measuring the control-latency metric, the read and write turns were
lowered from 4 MiB to one 1 MiB frame (see *Fairness*): it nearly doubled
release loopback download throughput and cut the median control latency
under 30 MiB of queued data from about 14 to 3 ms.

## Known limitations

- A client stream callback that never returns holds the connection's reads
  once `data_queue_bytes` are buffered (deviation 5); other streams then wait
  (their idle deadlines restart while reads are held; absolute deadlines still
  apply). Liveness is unaffected (heartbeats are still written, and silence
  while reads are held is not judged). A server handler that stops taking its
  parts is cancelled after its request's idle limit, which ends the hold.
- **Residual cross-side idle case.** While a server holds its reads, a
  client's idle limit still runs for a request the server has not read yet
  *and* whose frames have all left the client (they sit in the socket
  buffers behind the hold): the server cannot name it in a PROGRESS, and the
  client has nothing queued. The frozen frame set has no connection-level
  "holding reads" signal (HEARTBEAT is `{seq, at_ms, echo}`), and per-stream
  credits would need new frames. Exposure: the hold must outlast that
  request's idle limit (30 s for `objects.push`), i.e. the running consumer
  that causes it must drain `data_queue_bytes / 2` (16 MiB) slower than
  about 0.5 MiB/s, or be stuck (it is then cut at its own idle limit, which
  ends the hold). The outcome is a `Timeout` (Transient, retried), never a
  wrong result. The review probe `client_idle_runs_while_server_holds_reads`
  (1-frame receive buffer, 500 ms idle) shows it.
- Streamed requests beyond the free handlers are refused `BUSY` once their
  parts do not fit the receive bound while they wait (deviation 12): a client
  that pipelines more concurrent pushes per bulk lane than the server has
  handlers (2) retries them with Contention backoff, and the parts it sent
  before the refusal are sent again.
- `Responder::reply`/`error` block while the reply's queue is full (the peer
  is behind on reading); they return when there is room, the request is
  cancelled or expires, or the connection closes (a peer that takes nothing
  for `dead_after` is closed `TRANSPORT_DEAD`). Waiting producers are
  admitted in FIFO order per queue, so one waiting for a large batch also
  holds back later small ones on that queue until the queue has drained
  enough for it (at most until it is empty).
- The receive side may hold, beyond `data_queue_bytes` and one part, up to 4
  parts (≤ 4 MiB) in the channel of each running streamed request (see
  *Flow control*), because the frozen `Incoming::chunks` `Receiver` does not
  report when a handler takes a part.
- Write-side liveness while a server holds its reads counts a completed flush
  or writable readiness as progress. A peer reading very slowly but steadily
  stays connected (with bounded queues), as it should.
- Control latency is bounded by our queues, not by bytes already handed to the
  kernel: a control frame can wait behind the socket buffers' worth of data
  (no `SO_SNDBUF` tuning without a new dependency). With 30 MiB queued on
  Windows loopback the p50 is about 3 ms but the tail sits at 2–3 timer ticks
  (p99 about 39 ms, max up to 49 ms; deviation 8), so the every-sample
  release bound of `control_call_is_fast_while_data_is_queued` (10 samples)
  has a few milliseconds of margin there; debug runs use 250 ms. On a busy
  machine (fix round 2: p50 about 15 ms, p99 44–47 ms) that release check
  fails now and then with both the round-1 and the current tree; it is not
  part of VERIFY, and the release qual metric (p99 of 200 calls) passed. On
  Linux the max is about 2 ms. The WAN floors arrive in Wave 3.
- Dropping every `Conn` clone does not close the connection (frozen WP0.4
  semantics); the I/O thread runs until the peer closes, the link dies, or
  `close`/`goaway` is called.
- Only `MaybeTlsStream::{Plain, NativeTls}` are supported; any other variant
  makes `from_established` fail with `Unsupported`.
- The handshake (`dial`/`accept`/`dial_loopback`/`accept_loopback`) remains the
  WP1.10 stub in this worktree; the tests build sessions with
  `Conn::from_established` over in-process tungstenite pairs.
