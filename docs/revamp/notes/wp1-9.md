# WP1.9 — Session core: frames, I/O thread, multiplexing

Branch `revamp/wp1-9-session-core` (cut from `revamp/wave-1-base`, commit `abc8234`).

## Summary

WP1.9 implements the v3 connection layer of REVAMP_PLAN §6.2, minus the
handshake (WP1.10). The WP0.4 public API is unchanged; every stub body in the
owned files is now real.

| File | Content |
|---|---|
| `src/session/frame.rs` | Frame codec. `encode`/`decode` (the WP0.4 stubs) plus `encode_with` (typed header written straight into the output), `encode_parts`, `decode_ref` (zero-copy `FrameRef`), `allowed_flags`, `FrameLimits::max_message`. Every bound is checked on both encode and decode: truncated prefix or header, unknown kind, unknown flag bits or a flag the kind does not allow (`MORE` only on REQUEST/RESPONSE/CHUNK, `LAST` only on CHUNK), non-zero reserved field, header over the limit (16 KiB pre-auth, 64 KiB after), a header that is not exactly one JSON object, a body over 1 MiB, body bytes on a kind that carries none. 6 unit tests |
| `src/session/io.rs` | The per-connection I/O thread (`sess-<n>`). It owns the `WebSocket<MaybeTlsStream<TcpStream>>` (`Plain` and `NativeTls`) in non-blocking mode and a `polling::Poller` with oneshot interest re-armed after every delivered event. Each turn reads until `WouldBlock`, dispatches, runs the timers, writes from the priority queues while tungstenite holds < 256 KiB, flushes (`WouldBlock` arms writable interest), and waits for readiness, `notify()` or the next timer. Only this thread touches the socket, so tungstenite's automatic Pong/Close writes are safe |
| `src/session/conn.rs` | `Conn` (`from_established`, `call`, `call_streaming`, `upload`, `serve`, `goaway`, `close`, `health`, `closed`, `wait_closed`, `peer`), `Upload`, `Responder`, `Incoming`, the handler pool, the shared state (three outgoing queues, pending-call slots, served requests) and `ConnOptions::sanitized` |
| `src/session/mod.rs` | Module docs only (exports unchanged) |
| `tests/session_core.rs` | 36 acceptance tests, plain WS and WSS (`tests/fixtures/tls`) |
| `tests/qual_wp1_9_session.rs` | The five §14.6 scenarios rewritten on `session::Conn` |

### Behaviour

- **Requests.** Client-allocated u64 ids (from 1); only the client side
  originates requests (`call` on a server-side `Conn` is `Unavailable`
  `UNSUPPORTED_OPERATION`; a REQUEST received by a client, or RESPONSE /
  PROGRESS / CANCEL in the wrong direction, is a protocol violation).
- **Deadlines.** `call` has an absolute deadline; `call_streaming` an optional
  absolute deadline plus an idle deadline that CHUNK and PROGRESS reset;
  `upload` an idle deadline (per `chunk()` space wait and for the reply). The
  waiting caller enforces its own deadlines exactly. On expiry it removes its
  pending entry under the state lock (the arbiter against a racing reply),
  drops whatever of the request is still queued, and queues CANCEL; a late
  reply is discarded. The same happens when `on_chunk` returns an error, when
  the caller unwinds (`PendingGuard`), and when an `Upload` is dropped
  unfinished. On the server, the I/O thread's 250 ms scan cancels requests
  past their `deadline_ms`, expires stalled reassemblies and answers
  `REQUEST_TIMEOUT` to streamed requests idle past their `idle_ms`.
- **Outcomes.** RESPONSE `ok:false` → `CallError::Remote` and the connection
  stays usable (invariant 17). A connection failure fails every call in
  flight with `ConnectionLost` (uncertain); nothing is ever replayed
  (invariant 16). Refusals before anything is sent: `Unavailable` (closed,
  closing, or a GOAWAY in effect; its code is the reason's code), `Busy`
  (control queue full, or no data-queue space before the deadline),
  `Remote(WS_MESSAGE_TOO_LARGE)` (body over the op's limit or header over
  64 KiB).
- **Queues and priority.** Control (header-only REQUEST/RESPONSE, PROGRESS,
  CANCEL, HEARTBEAT, GOAWAY; ≤ 16 MiB), response bodies (round-robin per id)
  and data CHUNKs (round-robin per id; ≤ 32 MiB; producers block outside the
  I/O thread). All frames of one id stay in order: a streamed reply's final
  RESPONSE follows its chunks through the data queue; CANCEL may overtake
  because the cancelled request's queued frames are purged first.
- **Bodies.** Above one chunk (1 MiB) the REQUEST/RESPONSE carries the first
  part with `MORE` and `total`; CHUNKs (`hash: None`, `MORE` until the last,
  which has `LAST`) carry the rest, reassembled up to
  `min(protocol::max_body(op), max_body)` (16 MiB `meta.exchange`, 1 MiB
  otherwise). Offsets, totals and flags are verified; a violation closes the
  connection. A server reassembles at most `4 × max_body` (64 MiB) of request
  bodies at once.
- **Streams.** A streamed reply is CHUNKs with `MORE` (each delivered to the
  `call_streaming` callback as a zero-copy slice of the received message) then
  the RESPONSE. A streamed request is a REQUEST with `MORE` and no `total`,
  CHUNKs with `MORE` (into `Incoming::chunks`, a bounded channel of 4 parts),
  and an empty CHUNK without `MORE` that ends the body and disconnects the
  channel. `Upload::chunk` fails once the request has ended (`Remote` for an
  early error reply, `Cancelled` for an early OK reply, which `finish` returns).
- **Receive-side flow control.** When more than `data_queue_bytes` of received
  stream data waits for slow consumers (callback or handler), the I/O thread
  stops reading until they are back under half of it; TCP then holds the
  sender, whose producers block on their data queue. Liveness is not judged
  while reading is paused.
- **Handler pool.** `serve` starts `handlers` threads (`sess-<n>-h<i>`);
  requests wait in a queue of `handler_queue`; a full queue answers `BUSY`
  (Contention, `retry_after_ms: 50`) from the I/O thread. A handler panic is
  caught; a `Responder` dropped unanswered replies `UNKNOWN_ERROR`. `ping` is
  answered by the I/O thread itself (`{alive:true}`), so liveness probes never
  wait behind busy handlers or `BUSY`.
- **Liveness.** HEARTBEAT `{seq, at_ms, echo}` after `heartbeat` (5 s) of send
  idleness; RTT from the echo (`now − echo.at_ms − echo.held_ms`). Dead
  (`TRANSPORT_DEAD`) after `dead_after` (20 s) with no received message.
- **GOAWAY.** No new requests from either side once sent or received
  (requests already in transit are refused with `WS_CLOSED`); in-flight work
  completes; the connection closes when idle or after 5 s, and `closed()`
  reports the GOAWAY's code.
- **Close reasons** (`closed()`): `WS_CLOSED` (local `close`, peer Close),
  `CONNECTION_LOST` (reset, EOF, I/O error), `TRANSPORT_DEAD`,
  `PROTOCOL_VIOLATION` (the peer also gets a best-effort GOAWAY with the
  detail and a Close with code 1002), or the GOAWAY's code.
- **Fairness.** A read turn yields after 4 MiB or 1,024 messages and a write
  turn after 4 MiB, so reading, writing and timers interleave while the socket
  never blocks (found necessary: an unbounded write turn delayed a control
  reply over WSS by the whole 30 MiB queue).
- **Metrics.** `ConnHealth`: `since_ms`, `rtt_ms`, `last_rx_ms`/`last_tx_ms`,
  `bytes_up`/`bytes_down` (frame bytes), `inflight` (pending calls + requests
  being served), `queued_bytes` (outgoing queues).

## Deviations from the spec and why

1. **`tests/contracts.rs` edited (one assertion; CCR-WP1.9-1).**
   `session_stubs_fail_closed_with_not_implemented` asserted
   `frame::encode(valid CANCEL frame).is_err()`. The plan makes WP1.9 provide
   the real codec, so that assertion cannot hold, and no adapter on WP1.9's side
   can keep it true without leaving a broken public `encode` for WP1.10's
   handshake. The full suite must pass, so the assertion was replaced by a
   stronger one: the frame encodes, decodes back equal, and `decode(&[])` still
   fails. Nothing else in the file changed. WP1.10 will need the same treatment
   for the `accept`/`dial` lines of that test.
2. **`ping` never reaches the `Handler`.** The I/O thread answers it (§3.8 says
   "answered directly"). Liveness probes then cannot be refused with `BUSY` or
   wait behind long handlers.
3. **Wire conventions the plan leaves open** (both ends are this code):
   `MORE` means "more frames of this id follow" on REQUEST, RESPONSE and CHUNK;
   the streamed-request terminator is an empty CHUNK without `MORE`; the first
   body part rides in the REQUEST/RESPONSE frame; `Upload::chunk` and
   `Responder::chunk` overwrite `ChunkHeader.id` with the request id.
4. **Request deadlines are enforced by the waiting caller**, not by the
   250 ms scan: a call returns `Timeout` at its deadline (±scheduling), not up
   to 250 ms late. The 250 ms scan in the I/O thread covers the server side
   (deadlines of requests being served, stalled streamed bodies, expired
   reassemblies) and stale client reassemblies.
5. **Receive-side flow control** (above) is an addition: without it a slow
   consumer would make the receiver buffer without bound and "queue memory ≤
   cap with a slow receiver" could not hold end to end. Trade-off: a consumer
   that stops reading for good stalls the connection's reads once 32 MiB are
   buffered (a per-stream credit scheme would need new frames).
6. **Local refusals of oversized bodies/headers are `CallError::Remote`** with
   `WS_MESSAGE_TOO_LARGE` (connection usable, not uncertain), so the caller
   sees the exact code; an oversized *reply* becomes a `WS_MESSAGE_TOO_LARGE`
   error reply instead of a protocol violation. An error from the
   `call_streaming` callback is returned as `CallError::Remote` with the
   callback's own `ErrorWire` (after CANCEL).
7. **Additive API in owned files:** `ConnOptions::sanitized` (applied by
   `from_established`: timers ≥ 10 ms, `dead_after ≥ heartbeat`,
   `max_chunk ≤ 1 MiB`, `max_header ≤ 64 KiB`, ≥ 1 handler, queue bounds ≥ one
   frame), the `frame` helpers listed above. `FrameError::NotImplemented` is
   kept for API stability but never produced. Received bodies are always
   accepted up to the 1 MiB wire bound regardless of the local `max_chunk`.
8. **Debug-build thresholds in `tests/session_core.rs`.** Latency bounds are
   the §14 values in release builds and 5× in debug builds, where the test runs
   in parallel with the whole suite (REVAMP_PLAN §15.3: strict thresholds only
   in release qualification runs). The release qual scenarios enforce the
   floors.

## CCRs filed

- **CCR-WP1.9-1 (applied in this worktree; for the integrator to ratify).**
  Requested change: `tests/contracts.rs`
  `session_stubs_fail_closed_with_not_implemented` — replace
  `frame::encode(..).is_err() && frame::decode(&[], ..).is_err()` with an
  encode/decode round trip plus `decode(&[]).is_err()`. Reason: the assertion
  pins stub behaviour that WP1.9 is required to replace (§14 WP1.9 *Provides*);
  with it the full suite cannot pass. Adapter: none possible (see deviation 1).
- **CCR-WP1.9-2 (not applied; performance, for WP3.2/WP3.3).** Requested
  change: `session::Incoming::chunks` could carry `tungstenite::Bytes` instead
  of `Vec<u8>` (and `Reply::body` likewise), so streamed request parts reach
  the handler without a copy. Reason: on the client side the zero-copy
  delivery raised streamed-download throughput from about 340 to about
  550 MiB/s; uploads still pay one 1 MiB copy per part (about 270–430 MiB/s on
  loopback). Adapter: the I/O thread copies each part into a `Vec<u8>`.

## Test stability

Three test-only flakes were found by repeated runs under load and fixed
without weakening any assertion: a 200–300 ms call deadline could expire
before a starved I/O thread sent the request (the session then correctly
purges it, so the peer never sees it); a 100 ms sleep did not guarantee a
handler had picked up a request before its upload was dropped; and a 400 ms
idle bound was too close to 100 ms progress ticks. The tests now use 1 s
deadlines or wait for the observable state. One product defect was found the
same way and fixed: when this side's own GOAWAY grace expired first on the
peer, `closed()` reported `WS_CLOSED` instead of the GOAWAY code (a GOAWAY
sent by either side now explains the close).

## Known limitations

- A stream consumer that stops reading for good stalls the connection's reads
  after 32 MiB of buffered data (deviation 5); the peer's requests then wait.
  Liveness is unaffected (heartbeats are still written, and silence while
  paused is not judged).
- Control latency is bounded by our queues, not by bytes already handed to the
  kernel: a control frame can wait behind the socket buffers' worth of data
  (no `SO_SNDBUF` tuning without a new dependency). On loopback it stays well
  under 50 ms with 30 MiB queued; the WAN floors arrive in Wave 3.
- Dropping every `Conn` clone does not close the connection (frozen WP0.4
  semantics); the I/O thread runs until the peer closes, the link dies, or
  `close`/`goaway` is called.
- Only `MaybeTlsStream::{Plain, NativeTls}` are supported; any other variant
  makes `from_established` fail with `Unsupported`.
- The handshake (`dial`/`accept`/`dial_loopback`/`accept_loopback`) remains the
  WP1.10 stub in this worktree; the tests build sessions with
  `Conn::from_established` over in-process tungstenite pairs.
