### SQL-method extraction (`catalog_db.rs`, `impl Supervisor`)

Each method holds the **identical** SQL string that was inline before. Each call site now makes one
method call.

| Method | SQL text | Former call site |
|---|---|---|
| `set_desired(&self, state: &str, desired: bool)` | `UPDATE projects SET desired=1 WHERE state=?` / `UPDATE projects SET desired=0 WHERE state=?` | `manage` Start / Stop |
| `set_mount(&self, state: &str, mount: Option<PathBuf>)` | `UPDATE projects SET mount=? WHERE state=?` | `manage` ConfigureMount |
| `insert_project_tx(tx: &Transaction<'_>, state, label, repo, device, directory: &Path, mount: Option<&Path>)` | `INSERT INTO projects VALUES(?,?,?,?,?,?,1)` | `create` |
| `insert_initial_sync_tx(tx: &Transaction<'_>, state, endpoint)` | `INSERT INTO initial_sync VALUES(?,?)` | `create` |
| `upsert_peer(&self, endpoint, code, installation, connections: usize)` | `INSERT INTO peers VALUES(?,?,?,?,?) ON CONFLICT(endpoint) DO UPDATE SET ...` (unchanged) | `manage` Pair |
| `delete_peer(&self, endpoint)` | `DELETE FROM peers WHERE endpoint=?` | `manage` Unpair |
| `set_pairing_verifier(&self, verifier: &Verifier)` | `INSERT INTO settings VALUES('pairing',?) ON CONFLICT(key) DO UPDATE SET value=excluded.value` | `manage` ResetPairingCode |
| `delete_initial_sync(&self, state)` | `DELETE FROM initial_sync WHERE state=?` | `reconcile` |

All methods return `anyhow::Result<()>`. The old call sites used `?` and discarded the row count, so
the observable behaviour is the same. The bound values are the same too: `&str` replaces `&String`,
and `Option<&Path>` is lossily converted exactly as `Option<PathBuf>` was.

## Deviations from the spec, and why

1. **`set_desired` takes a bool and picks one of the two original literal strings.** Binding
   `desired=?` would have changed the SQL text, and the spec requires identical text.
2. **`insert_project_tx` and `insert_initial_sync_tx` are associated functions.** They take
   `&Transaction<'_>` and have no `self`, and are called as `Self::insert_project_tx(&tx, ...)`.
   The transaction is still opened (`self.db.unchecked_transaction()`) and committed in `create`.
   This keeps the transaction scope and the order of statements unchanged.
3. **`upsert_peer` generates the revision (`id()`) itself**, as the inline statement did. It is
   called at the same point, under the same lock.
4. **`Shared` lives in `supervisor.rs`.** The spec's table lists `Shared` only in `mod.rs`'s `pub use`.
   The alias stays next to the `Supervisor` struct (original line 306) and is re-exported from `mod.rs`.
5. **`mod.rs` imports `anyhow::ensure` under `#[cfg(unix)]`.** `lock()` uses `ensure!` only inside its
   `#[cfg(unix)]` block, so an unconditional import is unused on Windows and fails
   `clippy -D warnings`. The code of `lock()` itself is unchanged.
6. **Submodules are private `mod`s, and the public surface goes only through `pub use`.** The public API
   therefore stays exactly as before. Later packages that need `pub mod` can use the append-only
   mod-line exception in §13.
7. **`pub(crate)` is used throughout, never `pub(super)`.** `Supervisor` is `pub`, and its `pub(crate)`
   fields and methods expose `Worker`, `LinkStatus` and `Peer`. Declaring those types at least
   `pub(crate)` avoids `private_interfaces` warnings. In practice it reaches no further than
   `pub(super)` would, because the submodules are private to `orchestrator`.
8. **`git diff -M` shows no rename.** No single new file is more than 50% similar to the old file, so
   git reports a delete plus nine adds. Review the change with
   `git show --color-moved=dimmed-zebra --color-moved-ws=allow-indentation-change`.
   A line-multiset comparison against the deleted file (with `pub(crate) ` stripped) found only
   these differences:
   - the 9 removed inline SQL call sites;
   - the original `use` block;
   - on the added side: the 9 new call sites, the 8 new methods, the per-file `use` lists, the `mod` and
     `pub use` lines, and one extra `impl Supervisor {`/`}` pair because the impl is now split across
     two files.

## Known limitations

- This is a pure move. All the RC8 problems stay as they are: the global `Supervisor` mutex is held
  across I/O, `run()` uses a 10 ms polling loop, and the `peers()` error in the main loop is fatal.
  They are addressed by WP1.12 and WP2.1.
- `catalog_db.rs` and `supervisor.rs` are scheduled for deletion in WP2.INT. The new SQL methods exist
  only so that WP1.12 and WP2.1 can work on the legacy supervisor without editing SQL inline. They are
  not the WP1.1 catalog actor API.
