## Summary

### `worker_client.rs`: the v3 loopback session client

- **`SessionWorkerClient`** (`connect(ep) -> Result<Arc<Self>, CallError>`,
  implements `WorkerClient`): one multiplexed v3 loopback session
  (`session::dial_loopback`, `X-Tkfs-Sync: 3-loopback`, the endpoint's
  token when WP4.1 sets one) per worker instance. Methods: `want`, `read`,
  **`read_stream`** (ranges read with ≤ `INFLIGHT_READS` calls in flight and
  handed to the consumer **in range order**, at most that many results held;
  the consumer can skip an object or stop), **`write_batch`** (one
  `objects.write`: header `WriteHeader`, body the items' bytes), `report`,
  and the `WorkerClient` methods (`call` = header-only request whose reply is
  the JSON body or header; `call_bytes` = request with a body).
- A session that closed is redialed by the next call, **without the
  client's lock** (§2.2 rule 2; fix round 1): one caller dials, the others
  wait on a condvar for that dial and share its failure; `is_open` never
  waits for a dial (`the_session_client_dials_without_its_lock`). A call in
  flight on a closed session is uncertain and never replayed (invariant 16). A refusal that ran nothing
  (`BUSY`/`WORKER_BUSY`, a full local queue) is sent again (10 ms → 250 ms)
  within the call's deadline; nothing else is retried
  (`the_session_client_retries_refusals_and_never_replays_uncertain_calls`).
- Dial failures: a worker that does not echo the loopback header (a Wave 2
  worker) → `Unavailable(UNSUPPORTED_OPERATION: …)`; otherwise
  `LOCAL_WORKER_UNAVAILABLE` (or the refusal's code).
- **`session_for(ep)`**: the per-instance cache. A worker instance never
  changes its build, so "no loopback sessions" is remembered for the instance
  (no redial, `a_worker_without_loopback_sessions_is_remembered`); a failed
  dial for any other reason is not. Bounded at 256 instances (closed sessions
  first, then least recently used; whether a session is open is asked
  without the cache's lock). `drop_session(instance)` forgets one.
- `deadlines`: `WANT` 10 s, `READ`/`WRITE`/`REPORT` 60 s, plus
  `with_verify(base, size)` (64 MiB/s of whole-object hashing on top, at
  most `MAX_VERIFY` = 30 min, since sizes can come from a peer) for the
  calls that may verify a whole object: the write that completes one, the
  first read of one (verify-on-first-serve).
- `JsonWorkerClient::call_bytes` now goes through `session_for`; a worker
  without a session still answers `Unavailable(BINARY_OPS_REQUIRE_SESSION: …)`
  (with the reason), as WP1.3's test pins.

### `objects.rs`: the dialer's lane and the shared data plane

The module docs give the full design; in short:

- **Two schedulers per lane** (the WP2.7 engine, `scheduler::drive`):
  download (`objects.pull`, scope `objects.pull#<lane>`) and upload
  (`objects.push`, scope `objects.push#<lane>`), each with per-(peer, repo,
  op) keys, `REPOS_PER_LANE` slots, backoff by class and claims. A stalled
  push therefore never holds a pull of the same lane, and each direction
  backs off alone (§2.3 "Exchange (peer, repo, op)").
- **Lane gates** (all FIFO, so a releasing thread cannot jump the queue):
  - `RepoGate`: ≤ `REPOS_PER_LANE` (2) repositories with rounds on the lane
    at once, both directions of one counting once (task 3);
  - `Slots`: ≤ `PEER_CALLS` (2) peer `objects.*` calls at once, the
    acceptor's exchange slots per bulk session (CCR-WP3.3-1); a pipelined
    second pull only when a slot is free and nobody waits;
  - `Window`: the 16 MiB download window, shared by the lane's keys.
- **Download round:** what the lane continues or takes over from the
  handoff table (below), then worker `objects.want` (lease session
  alternating between two stable ids per lane **and repository**,
  `pull_lease`; fix round 1) → peer `objects.pull` with a
  budget reserved from the window (≤ 16 MiB; issued when half the window is
  free; ≤ 2 in flight) → CHUNKs into the **`Sink`** → per-object results.
  Credit comes back as bytes are written durably (or dropped) and, at a
  pull's end, whatever it did not deliver; so "in flight" (read at the
  source, not yet durable here) never exceeds 16 MiB.
- **`Sink`** (also the acceptor's push path): per object, contiguous data
  as received pieces (ranges ahead of a gap wait in `pending`, so two pulls
  of one large object may interleave on the wire); ≤ `INFLIGHT_WRITES` (4)
  `objects.write` calls in flight, one per object at a time, each at the
  object's durable offset, ≤ 1 MiB, tiny objects batched (≤ 256 per call,
  one lease per call). Every byte offered is released exactly once
  (`SinkEvent::Released`): this is what keeps the window and the per-pull
  accounting exact. A durable offset is only believed once a write returns
  it (invariant 2); a `Progressed` that disagrees with what was written
  resynchronizes the object (next want gives the worker's offset). A write
  call that is uncertain (`Timeout`/`ConnectionLost`) is never replayed: its
  objects resume from their durable offset in the next round. A worker that
  cannot be reached (`Unavailable`) stops the sink. A result says when a
  whole write call failed (`SinkResult::call`): a failure of the call, with
  the durable offset unknown, never of the object. When a round ends, what
  arrived is written also when the session ended (it is valid and
  contiguous); only a lane told to stop drops it (fix round 1).
- **Upload round:** peer `objects.wants` → our worker's reads
  (`read_stream`, ≤ 4 in flight) → peer `objects.push` (`Conn::upload`, ≤ 16
  MiB per push) → `ObjectsResult`. A `CorruptAtSource` result makes our
  worker re-verify its copy (worker `objects.report`).
- **Per-object results:** `CorruptAtSource` at our worker is reported to the
  peer (`objects.report{CORRUPT_AT_SOURCE}`) after the pulls; failed objects
  get an `ObjectError`, and a per-(peer, repo, direction, object) backoff
  (`Backoff::objects()`, 30 s → 1 h) keeps them out of the next wants (and
  parks them for another source); an object installed here resolves the
  errors of **every** source of it (`Resolved`), since another source may
  have delivered it.
- **Lease handoff (fix round 1, multi-source liveness).** Every worker want
  leases what it returns to its session, and that session's next want
  renews the lease, so a source that cannot serve an object kept it hidden
  from every other source of the daemon. All the sessions holding leases at
  a worker belong to its own orchestrator (our pull lanes, and the
  acceptor's push leases of the dialers it serves), so the daemon hands
  such objects on itself, within the frozen contract: a process-wide
  **handoff table** per worker instance (`handoff_*` in `objects.rs`)
  records an object its source cannot serve (*parked*: its lease, the
  worker's durable offset, no holder). Any other transfer of the daemon
  whose lane owns it and whose source is not backing it off **takes it
  over** and moves it **under the parked lease** (a lease is a session id;
  a write with it continues it); the source's own wants keep returning it
  but leave it to the holder; the holder continues it in later rounds,
  releases it once installed or another session's, and parks it again if
  it cannot serve it either. Entries lapse with the lease. Dialer: an
  object a want returns while in this source's backoff is parked; one the
  round failed for this source is parked when the round ends. Acceptor: see
  below. The worker stays the arbiter (`InFlightElsewhere`, appends at the
  durable offset).
- **Status:** `ExchangeStarted`/`ExchangeFinished{op: objects.pull |
  objects.push}` per pull or push on status lane `index + 1`, with the real
  duration (a pull's ends when the last of its bytes is written, so its
  rate is a write rate), the object bytes, and the objects **completed**
  (installed here for a pull; `Completed` in the peer's results for a push),
  per the WP1.INT re-review's rules for `ExchangeFinished` producers.
- **Triggers:** the local tip, the remote tip and content counters, and the
  local `generations.sync`, which moves when the metadata exchange **stages**
  events: their objects are pulled at once, before activation (the worker
  wants objects of validly staged events; the lane never waits for the
  activator) — `staging_alone_starts_a_download`.
- **Wire rules shared with the acceptor:** requests are the JSON header,
  replies the JSON body or header; `sender` is the requesting replica and
  `receiver` the acceptor's (as `meta.exchange`); the **allotment rule**
  (`allot`): items cover, in order, `[offset, offset + min(size − offset,
  budget left))`, an item's share fixed by the list whether or not it is
  served, a zero-size object being one empty chunk. Both sides therefore
  know exactly which bytes a pull or push covers.
- **Interim fallback** (deviation 1): a key whose local worker serves no
  objects v3, or whose peer answers `UNSUPPORTED_OPERATION`, runs the Wave 2
  `objects.exchange` on the download scheduler (both directions), retrying
  v3 when the key resets or after 10 min. `run_bulk_lane_with(…,
  BulkOptions)`, `bulk_exchange`, `fits`, `page_lane`, `status_lane` keep
  the interim lane exactly as Wave 2 had it.

### `inbound_objects.rs`: the acceptor

`objects.pull` (our worker's reads → CHUNK stream → `ObjectsResult`),
`objects.wants` (what the dialer's lane continues or takes over from the
handoff table, then our worker's want, leased to `push_lease(peer, lane)`;
objects in their backoff for that source are parked, not offered),
`objects.push` (the stream → the `Sink`, each object under the lease it was
offered under; read no faster than written: ≤ 8 MiB of contiguous bytes
wait), `objects.report` (our worker's report), and the interim
`objects.exchange` unchanged. Checks in order, none reaching a worker: bulk
session; the request parses; the request's lane is the session's
(`BULK_LANE_MISMATCH`); folder managed, not paused, Running; route from the
authenticated installation (invariant 15) and `receiver` is this folder
(`LOCAL_REPLICA_BINDING_MISMATCH`); items another lane owns →
`OBJECT_ON_WRONG_LANE` per item (invariant 19). A PROGRESS goes to the
dialer every 5 s while our worker reads, and after every write of a push;
the keepalive thread wakes at once when the exchange ends, so a reply never
waits for it. `ExchangeStarted`/`ExchangeFinished{direction: inbound}` per
pull and push (`objects_down`: objects a push completed here); a cancelled
pull is recorded `CANCELLED`.

Fix round 1:
- **Bounded push input (invariant 22).** Each object of a push has its share
  of the 16 MiB push budget (the allotment rule, as the dialer computes it).
  A chunk of an object without a share, outside its share, not contiguous
  with its last chunk, or of another size than the push declared ends the
  push `PROTOCOL_VIOLATION` before it is buffered (`admit`): at most the
  budget arrives, in order, so nothing waits ahead of a gap, and nothing is
  recorded for hashes the push did not list (`a_push_outside_its_shares_is_refused`).
- **A failed write call fails the push, not its objects (§2.3).** When a
  whole write call fails (our worker timed out, went away, refused, or
  erred for the call), the push answers that error: no per-object backoff
  or `ObjectError` here, and none at the dialer, whose upload key backs off
  by class instead (`a_failed_worker_call_fails_the_push_not_its_objects`).
- **Offers.** The acceptor remembers its last `objects.wants` reply per
  (worker instance, dialer lane): each object, its lease, and whether a push
  of the whole offer would give it a share. What the dialer then does on
  the same bulk session tells what it could not serve: an object with a
  share it sent nothing of in a push that ended normally, did not list in
  its push, or no push came before its next `objects.wants`. Such an object
  backs off for that dialer (silently: no `ObjectError`, not serving is no
  error here) and is parked under its lease; the next dialer of another
  source is offered it first and pushes it under that lease
  (`a_source_that_cannot_serve_hands_its_push_lease_on`).

Two defects found by measuring, and fixed before the numbers above:
- the acceptor's keepalive thread slept in 100 ms steps and the pull's reply
  waited for it: every pull's RESPONSE came up to 100 ms late, so the window
  sat full of delivered-but-unacknowledged pulls (`window=0 inflight=2` in
  a probe of the window over time): 1 GiB on loopback went from ~200 to
  250–300 MiB/s and 10K tiny files from ~4,900 to ~21,600 files/s (memory
  worker);
- the sink kept an object's data in one contiguous buffer and drained 1 MiB
  from its front per write, memmoving up to 15 MiB each time; it now keeps
  the received pieces and a write takes whole pieces.

## Deviations from the spec, and why

1. **The interim path stays as a fallback** (§14 WP3.3 and §6.5 say WP3.3
   *replaces* `objects.rs` and `inbound_objects.rs`). Existing tests owned
   by others exercise it and must not be weakened: `tests/meta_scheduler.rs`
   (WP2.7: interim lanes through `run_bulk_lane_with`, `bulk_exchange`,
   `fits`), `tests/inbound_v3.rs` (WP2.8: `objects.exchange` routing and
   trimming), and `tests/w2_integration.rs::the_v3_stack_syncs_two_daemons_end_to_end`
   (WP2.INT), which runs real workers through `PeerManager` →
   `run_bulk_lane`; in this worktree those workers serve no objects v3, so
   without the fallback that test fails. The fallback is per key and only
   on an explicit "not served" (`UNSUPPORTED_OPERATION` from the local
   worker's session or ops, or from the peer), so with WP3.2 merged every key
   runs v3. WP3.INT may delete it (CCR-WP3.3-2).
2. **Two schedulers per lane** (download, upload) rather than one exchange
   per key doing both directions: §6.4 and the acceptance "a stalled push
   does not block pulls on the same lane" call for independent directions,
   and §2.3 makes the failure domain (peer, repo, op). "≤ 2 repos per lane"
   is kept by the lane's `RepoGate`.
3. **At most 2 peer calls per lane** (`PEER_CALLS`), so "≤ 2 pulls in
   flight" holds only while no push waits: the acceptor runs at most
   `limits::BULK_HANDLERS` (2) exchanges per bulk session and answers a
   third `BUSY` (`inbound.rs`, WP2.8, not owned). CCR-WP3.3-1.
4. **A v3 objects request that does not parse is answered
   `UNSUPPORTED_OPERATION`**, not `INVALID_REQUEST`.
   `tests/inbound_v3.rs:1461-1464` (WP2.8) pins the Wave 2 stub's answer for
   `objects.pull` with header `{}`; both codes are Transient-default, and
   `UNSUPPORTED_OPERATION` is what an acceptor without objects v3 answers, so
   a dialer treats the two alike (falls back to the interim path). Requested
   to change in CCR-WP3.3-3.
5. **A pull's `ExchangeFinished` comes when its bytes are written**, not when
   its RESPONSE arrives: `objects_down` must count completed (installed)
   objects (WP1.INT re-review), which only the writes tell, and
   `duration_ms` then spans the whole transfer.
6. **Inbound pulls and pushes send `ExchangeStarted{direction: inbound}`**
   (§3.8 says the inbound server sends none; CCR-WP2.8-3 added the
   `direction` member so the hub books an inbound start on the inbound lane):
   the acceptor's lanes then show the transfer in flight (RC12).

## CCRs filed

- **CCR-WP3.3-1** (`src/orchestrator/inbound.rs`, WP2.8; performance).
  *Requested:* a bulk session's exchange slots (`SessionHandler.exchange_slots`,
  today the role's handler count, `limits::BULK_HANDLERS` = 2) become
  `INFLIGHT_PULLS + 2` = 4 for bulk sessions: two pipelined pulls, a push
  and a short `objects.wants`/`objects.report` at once. *Reason:* with 2, a
  lane whose push is in flight runs one pull at a time (no pipelining on a
  long fat link while uploading). *Adapter:* `objects::PEER_CALLS` = 2 FIFO
  peer-call slots per lane, the second pull only when free and nobody waits;
  a `BUSY` from the acceptor is Contention for the key. After the CCR,
  `LaneOptions::peer_calls` can be raised to 4.
- **CCR-WP3.3-2** (WP3.INT; cleanup). *Requested:* once WP3.2 is merged and
  every worker serves objects v3, decide whether to keep the interim
  fallback (deviation 1). Deleting it means: the "Interim path" sections of
  `objects.rs` and `inbound_objects.rs`, `LaneRun::interim_exchange` and the
  `on_interim` checks, and the interim tests of `tests/meta_scheduler.rs`
  and `tests/inbound_v3.rs` (to be rewritten against v3).
  `w2_integration::the_v3_stack_syncs_two_daemons_end_to_end` then runs on
  objects v3. *Adapter:* the per-key fallback.
- **CCR-WP3.3-3** (`tests/inbound_v3.rs`, WP2.8). *Requested:* line 1463
  expects `INVALID_REQUEST` for `objects.pull` with header `{}` (objects v3
  is served now), and `inbound_objects::request_of` answers
  `INVALID_REQUEST`. *Reason:* a malformed v3 request is an invalid request;
  answering `UNSUPPORTED_OPERATION` makes a buggy v3 dialer fall back to the
  interim path silently. *Adapter:* deviation 4.
- **CCR-WP3.3-4** (re-filed in fix round 1 as a **liveness** requirement;
  `model::protocol::objects::WantHeader`, frozen; WP3.2's worker, for
  WP3.INT). *Requested:* `#[serde(default)] exclude: Vec<String>` on
  `WantHeader` (≤ 256 hashes): the worker neither returns those hashes nor
  keeps this session's leases on them (it drops them), so a session never
  holds an object it will not move. Equivalent alternative: an explicit
  lease release (`objects.release{route, session, hashes}`). *Reason:* every
  want leases what it returns, and the same session's next want renews it:
  an object a source cannot serve (a relay with the metadata but not the
  bytes, a failed object) stays leased to that source's session for as long
  as its lane runs, and the worker hides it from every other session.
  Without this CCR **or** the adapter below, multi-source topologies stall
  (the reviewer's probe: a hub never received an object while another leaf
  renewed its lease; the two new handoff tests fail on the pre-fix code).
  *Adapter (WP3.3, in place):* the lease handoff (Summary): the daemon parks
  such objects under the holding lease and lets any other of its transfers
  continue them under that lease, so delivery does not wait for the lease to
  lapse; it is deterministic, needs no worker change, and WP3.INT may delete
  it once the worker excludes and releases. Residual without the CCR: a
  source holds (and renews) leases on objects it does not move; harmless
  while the handoff hands them on, but each want then costs a few table
  lookups.
- **CCR-WP3.3-5** (REVAMP_PLAN §6.4, spec ratification only). *Requested:*
  §6.4 states the objects v3 wire details this package fixed: requests are
  the JSON header and replies the JSON body or header; `sender` = requesting
  replica, `receiver` = acceptor's; the allotment rule; the per-item
  `ObjectsResult` of a pull at the sender (`Completed` sent through the end,
  `Progressed{durable_offset}` sent up to there, `Skipped` no bytes); lease
  session ids (`pull:<peer>:<i>/<n>:a|b` at the dialer, alternating per
  repository; `push:<peer>:<i>/<n>` at the acceptor); a zero-size object is
  one empty chunk. Added in fix round 1: a receiver refuses a pushed or
  pulled chunk outside its object's share or out of order
  (`PROTOCOL_VIOLATION`); an object with a share that got no bytes in a
  stream that ended normally (or that the dialer left out of its push, or
  did not push before its next `objects.wants` on the same session) is one
  its sender could not serve; a write under a lease taken over from another
  source is legitimate (the lease handoff).

## Fix round 1: review findings

| # | Severity | Finding | Resolution |
|---|---|---|---|
| 1 | blocker | A source that cannot serve an object keeps it leased forever (its wants renew the lease), so no other source delivers it | **Fixed** by the lease handoff (Summary): such objects are parked under their lease and continued by another source of the daemon under that lease, at once, without waiting for a lapse. Regression tests on both sides: `a_source_that_cannot_serve_hands_its_push_lease_on` (the reviewer's hub probe) and `a_source_that_cannot_serve_hands_its_pull_lease_on` (a dialer with two peers). Both fail on the pre-fix code and pass in under 1 s here, well inside the 60 s lease that the non-serving lane keeps renewing. CCR-WP3.3-4 re-filed as a liveness requirement. I did not take the suggested epoch rotation alone: a retired session's leases still hide the object for up to 60 s, after which the non-serving source races the others for it again at every lapse (about even odds), and an in-progress large object held by a retired session stalls for 60 s at every rotation. The handoff has neither cost, and it keeps the stable lease ids, so resume after a connection loss is unchanged |

## Known limitations

- Single-object throughput is bounded by sequential 1 MiB worker writes:
  appends must start at the durable offset, so one object has one write in
  flight, and `objects.write` bodies are ≤ 1 MiB (`protocol::max_body`). A
  larger write body would cut per-call costs (and fsyncs) proportionally;
  not requested, the floors are met.
- The lease handoff is in-process state (per worker instance, lapsing with
  the lease): after an orchestrator restart, an object a source cannot serve
  is parked again by that source's next want or push. A dialer that goes
  away right after being offered an object leaves it leased to its session
  until the lease lapses (≤ 60 s), as WP3.2's lease rules intend.
- An acceptor treats a dialer's `objects.wants` that follows an offer with
  no push on the same session as "served none of it". A lost wants reply
  (the dialer timed out and asked again on the same session) therefore backs
  the offered objects off for that dialer (30 s, no error) and parks them
  for other sources. This is rare, and bounded by the backoff.
- The release floors are asserted in `tests/objects_v3_lanes.rs`; wiring
  them into `scripts/qualify.ps1` or `tests/qualification-floors.json` is
  outside this package's files.
- A lane runs at most 2 peer calls at once (CCR-WP3.3-1).
- The interim fallback (deviation 1) is live code until WP3.INT decides.
- All measurements use the fake worker; WP3.INT's `qual_wp3_int_e2e` gives
  the daemon numbers with WP3.2's worker.
