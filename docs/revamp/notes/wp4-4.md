## Summary

### Startup snapshot format 2 (`src/core/snapshot.rs`)

A branch's snapshot is its **anchor**, the `startup_snapshots` row (the table,
its columns and its positional INSERT are unchanged, §9), plus sealed rows in
side tables for a large projection. Two layouts:

* **inline** while the anchor fits `inline_limit()` (1 MiB by default;
  `TKFS_SNAPSHOT_INLINE_LIMIT`, or `set_thread_inline_limit` in tests): the
  whole projection and every conflict row in the anchor, as in format 1. A
  seal rewrites at most the limit, and the CCR-WP2.4-3 interval
  (`seal_interval` of the anchor's size, unchanged) keeps it at about 4 KiB per
  event.
* **rows** beyond it: the anchor holds the projection's header (its current
  conflict and pending lists), the frontier, the journal binding and a digest
  of the rows; `snapshot_entries(branch, entity, entry, heads)` holds one row
  per entity exactly as `current_parts` does, `snapshot_conflicts(branch, id,
  payload, resolved_by)` one per conflict row. A seal rewrites the small
  anchor and **only the rows that changed since the previous seal**: O(change)
  whatever the projection's size. The anchor stays small, so a large
  projection seals every 128 events.

What changed is recorded durably by triggers in the writing transaction:
every `current_parts` insert/update and every `conflicts`
insert/update/delete marks its key in `snapshot_dirty(branch, kind, key)`.
Fast commits and the startup replay change exactly the entities they write as
parts; a slow commit passes the entities its stored-projection delta (or fold)
changed and the projection it holds; an unknown full rewrite seals in full. A
seal clears the branch's marks in its transaction. Fast commits never change
the header, so a seal without a projection keeps the previous anchor's.

The journal binding (`journal_hash`) is format 1's SHA-256 over the branch's
rows up to the cursor, unchanged in meaning, but the anchor also stores the
hash's **resumable state** (`journal_state`), so a seal hashes only its own
branch's rows since the previous seal instead of the whole history under the
lock (at 150K events format 1 re-hashed ~150 MB per seal). Those rows are
read through **`journal_branch(seq, branch)`**, a per-branch journal index
(fix round 1): one range scan of `(branch, seq)` and two key lookups per row,
whatever other branches added in between. It is built exactly as WP2.5's
`feed_journal` is: triggers on `journal_sequence` (insert, update, delete)
keep it for writes by any executable, and a new table is filled by a
chunked, resumable backfill (10,000 journal rows per transaction, a cursor
and a marker in `config`, startup progress) before the store is usable;
readers join it back to the journal and the event's branch, so a stale row is
never hashed. `sha2` keeps its state private (its `compress` feature is off
and `Cargo.toml` is frozen), so the FIPS 180-4 compression is in
`snapshot.rs`, checked against `sha2` for every length up to three blocks and
random splits and resumptions (`journal::tests`). Startup recomputes the hash
with `sha2` (O(history), as before) and checks that the stored state
finalizes to it; a rebuild's seal (`Changed::Rebuild`) recomputes it from the
journal and reuses nothing of the previous seal, so a snapshot a startup
refused is replaced, never continued.

Integrity: the anchor checksum as before; the rows by an order-independent
XOR of one SHA-256 per row (bound to branch and key), which a seal updates
from the rows it rewrites; counts and bytes too. Any mismatch, a damaged
anchor or row, a changed journal, an unknown or older format falls back to
reconstruction (invariant 5). **A seal never fails on what the snapshot
tables hold** (fix round 1): the previous anchor, the sealed rows a seal
reads back and the change marks are read without typed conversions; a value
that is not what a seal writes (not UTF-8 text, a BLOB, a cursor that is not
an integer) or does not check out makes the previous seal unusable, and the
seal is full, which deletes and rewrites the branch's rows and marks in the
same transaction (`previous`, `marks`, `sealed_entity`, `sealed_conflict`).
The cadence reads (`seal_due`, `seal_due_in`) treat an unreadable cursor as
"due now".

Every seal runs inside its caller's transaction (the commit's savepoint, the
startup replay's, a rebuild's): anchor, rows, marks and the commit are atomic
(invariant 4). Fault points (`core::fault`) after every step:
`seal_entries_written`, `seal_conflicts_written`, `seal_marks_cleared`,
`before_startup_snapshot`, `startup_snapshot_written`, and at startup
`startup_snapshot_restored`, `startup_suffix_applied`.

**Downgrade.** An older binary finds a format-2 anchor incompatible and
reconstructs every branch at its first open (rewriting `current_state`,
deleting `current_parts`), then seals format 1; it never reads the side tables.
Their stale rows are replaced at this binary's next full seal (the format-1
anchor makes the next open reconstruct too). Tested by
`seal_path::damaged_rows_and_older_snapshots_are_reconstructed`
(`format_1`, `format_1_stale_header`).

**Restore** (`try_resume_snapshot`): an inline anchor as before; a rows anchor
reads and checks every row, then stores a projection of at most
`FOLD_MAX_ENTRIES` entries as one `current_state` row (as an inline restore
does) and a larger one as the header plus one `current_parts` row per entity.
For the large one only what differs from the sealed rows is written (fix
round 1, `restore_parts`): one pass over the stored rows compares each one's
SHA-256 (`entity_digest`) with its sealed row's, computed anyway while the
rows are checked; a stored row that differs, is not UTF-8 text or has no
sealed row is deleted, and every sealed row without an equal stored one is
copied from `snapshot_entries`; `current_state` and the conflict rows are
rewritten only when they differ. An open at the tip writes no projection
row; after a tail, about the tail's entities. The sanity check that the
cursor lies within the branch's journal reads the branch's tip from
`journal_branch` (one index probe; the journal hash then checks every row up
to the cursor against the journal). The restored projection seeds the
connection's view only when a tail is replayed (the replay's successors read
it); the marks the restore wrote are cleared, the tail is replayed as before
and the end-of-replay seal is incremental. `Store::check_startup_snapshot`
checks a snapshot as a startup does and returns the sealed state (tests and
diagnostics).

### Seal path (`src/core/commit.rs`)

* `snapshot::seal` is the only writer of a payload; WP2.4's mirror
  (`seal_payload`, `seal_prepared`, `journal_row`, `SEAL_FORMAT`, the
  `seal_due` copy) and the event cache's journal hash are gone (CCR-WP2.4-2).
* A fast commit seals when `snapshot::seal_due` says so (the cadence query
  `SEALED_SQL` and `seal_interval`, unchanged), with the patched view as its
  projection when it is fresh (CCR-WP1.6-1 adapter, kept:
  `known_projection_seals`), else from the marked `current_parts` rows; the
  cursor is the commit's own event's sequence (format 1 read it with a join
  over every event of the branch).
* A slow commit's forced seal (P4, kept) passes its projection and changed
  entities; a prepared commit's inline seal uses the projection JSON
  serialized off-lock (`prepared_seals`), which is now computed only when the
  write (a full rewrite) or an inline seal needs it (`sealed_as_rows`).
* **CCR-WP2.INT-5**: `projection_delta` returns `Stored::{Delta, Fold,
  Rewrite}`. A change of the conflict or pending list no longer forces a
  rewrite of `current_state`: the lists go to the header row
  `current_meta(branch, payload)` (`snapshot::write_header`), which
  `load_projection` overlays, a full rewrite deletes, and the
  `projection_version` triggers cover (view freshness, I6). A fold (the full
  rewrite that moves the parts back into `current_state`) only happens for a
  projection of at most `FOLD_MAX_ENTRIES` (1,024) entries; a larger one keeps
  its parts (at most one row per entity), so no slow commit rewrites a large
  projection under the lock (at 150K entries a fold was 210 MB).
* Telemetry: `Store::seal_stats()` (`SealStats`: seals per layout, bytes,
  entity, conflict and journal rows, longest and total time, and the part
  of the time spent reading the previous seal and extending its journal
  binding, `journal_micros`), `Store::startup_resumes()`.
* A full seal's inline attempt is skipped when a lower bound of the inline
  anchor (entries times 100 bytes plus the branch's conflict rows'
  `octet_length`, read without serializing anything) is over the limit, so a
  large conflict history is not serialized only to be found too large (fix
  round 1).

### Cadence (`Store::seal_due_in`, `src/worker/activator.rs`)

`Store::seal_due_in(branch)` (CCR-WP2.3-5) is the commits until the branch's
next periodic seal, with the store's own rule; the activator's
`seal_forecast` uses it instead of its own copy of the query. The forecast,
the sealing commit's own slice and every other activator behaviour are
unchanged.

### The engine store's sub-journal (fix round 1, `src/core/inbox.rs`)

A commit runs in a savepoint nested in its slice's transaction, and SQLite
keeps the original image of every page that savepoint modifies in a
sub-journal, which it moves to a newly created temp file once it passes
64 KiB; creating that file on Windows stalled single statements for 30-60 ms
under the engine lock (no CPU, no page I/O: *Fix round 1*). On Windows the
worker's engine store, the one store opened with deferred activation, now
keeps sub-journals in memory: `startup_drain`, the last phase of its open,
sets **`temp_store=MEMORY`** first, after the open's rebuilds (which may
rewrite hundreds of MB in one statement and keep temp files) and before any
TEMP object exists (so the change resets no schema). In memory, a commit's
sub-journal is the pages it touches (a few MB: no slow commit rewrites a
projection above `FOLD_MAX_ENTRIES` entries). Other stores and other
platforms keep temp files: an in-memory journal grows in 1 KiB allocations,
which cost more than a temp file where creating one is cheap (Linux) or when
every connection of a process uses it (measured, *Fix round 1*).
`Store::set_temp_store_memory` (`commit.rs`) makes the change; changing
`temp_store` later drops the connection's TEMP objects, among them the
commit-epoch table of WP2.INT's rolled-back-commit detection, which the next
commit would take for a rolled-back commit and answer with an O(projection)
view reload, so the method carries the table's stored value over the change
(a commit rolled back before it is still detected) and re-keys a view that
was fresh. SQLite refuses the change inside a transaction (best effort).

### Staging cost (CCR-WP2.5-6, `src/core/inbox.rs`)

Every lookup was already indexed; the cost that grew with the inbox was
SQLite's page cache: six random-key index inserts per staged row
(`incoming_events` id, `incoming_sources`, `incoming_waits` twice,
`staged_objects` twice), whose pages stop fitting the default 2 MiB cache
past a few thousand staged rows. Changes:

* a staged row is classified first and inserted **once, in its state**
  (`insert_staged`): no second write of the row and its state index;
* every statement of the staging path is a cached prepared statement;
* a staging call of at least 64 events raises its connection's page cache to
  32 MiB for the call and restores it afterwards (`raise_cache`), also inside
  a caller's transaction (the feed stages inside `feed_write`).

Measured in release with a temporary A/B bench (a 1,000-event page staged
alternately into an empty inbox and into one of 40K staged rows, inside a
transaction, the commit excluded, so the machine's load hits both alike):
before, 52–75 us/event empty and 388–488 us/event at 40K; after, 42–45 and
109–121 us/event. `qual_wp4_4_seal::staging_cost_at_large_inboxes` keeps the
measurement (2.6x at 40K, 3.0x at 100K in its runs, *Qualification*). What
remains at an empty inbox is mostly the `staged_objects_insert` trigger
(CCR-WP4.4-1); what grows is the commit (*Known limitations*).

## Deviations from the spec, and why

1. **Two layouts, not rows always.** Small projections keep the inline
   anchor. Several existing tests of other packages read the anchor as a
   self-contained snapshot: `offlock_commit::assert_snapshot_valid` parses its
   `projection` and checks it against a replay, `harness_selftest` compares a
   restamped clone's payload byte for byte, `support::restamp_device` rewrites
   it, and `w3_integration::a_large_projection_seals_less_often` pins the
   CCR-WP2.4-3 cadence (`seal_interval` of the anchor's `octet_length`) and
   needs anchors above 512 KiB. The inline layout satisfies all of them and is
   bounded (at most `inline_limit()` per seal, about 4 KiB per event
   amortized); the rows layout takes over exactly where full seals stop being
   cheap. All those tests pass unchanged, and `the_inline_layout_switches_…`,
   `w3_integration` and the qualification exercise the switch.
2. **The seal stays in the committing transaction**, made O(change), rather
   than being moved to its own transaction off the lock. Keeping it atomic
   with the commit keeps the forced seal of P4 exact and the crash analysis
   simple (every crash point rolls the seal back with its commit). The
   measured seal itself is a few milliseconds (*Qualification*); the
   prepared slow path still serializes an inline seal's projection off-lock.
3. **`FOLD_MAX_ENTRIES`** (not in the spec): needed so that no slow commit
   rewrites a large projection under the lock; the fold tests of WP1.INT and
   WP2.4 (`slow_commits_store_their_projection_as_a_delta`,
   `prepared_slow_commits_store_their_projection_as_a_delta`) use small
   projections and are unchanged.
4. **The resumable SHA-256 is hand-written** (`Cargo.toml` is frozen, `sha2`'s
   `compress` feature is off), like `util::hmac` (§11 decision 3).
5. **The commit unit test `seal_payload_is_snapshot_persist_byte_for_byte`
   was replaced** by `a_seal_from_prepared_json_is_the_seal_of_the_projection`:
   it pinned the WP2.4 payload mirror that CCR-WP2.4-2 asked to remove; the
   new test pins the property that mattered (a seal from the off-lock JSON is
   byte for byte the seal of the projection, valid as a startup checks it),
   and `offlock_commit`'s differential fuzz still compares
   `startup_snapshots` between prepared and inline commits.
6. **Rows keyed by entity, not by acceptance cursor.** Task 1 offers "a
   delta chain or per-entry rows keyed by the acceptance cursor, compacted
   occasionally". The rows here are keyed by `(branch, entity)` and
   upserted, so a branch never has more than one row per entity and nothing
   needs compacting; the anchor's cursor (and its journal binding) says
   which journal prefix the whole set reflects, and the change marks say
   which rows a seal must rewrite.
7. **`tests/startup_snapshots.rs`** (owned): the only changed assertion is the
   format, 1 → 2 (task 5). Every scenario now runs in both layouts (the crash
   child gets `TKFS_SNAPSHOT_INLINE_LIMIT`), and the first one also asserts
   the open resumed and the layout under test.
8. **The 50 ms acceptance is applied to the seal's own time.** The spec asks
   for "the engine-lock hold for any seal < 50 ms". `qual_wp4_4_seal` floors
   `max_seal_ms`: the time the store measures inside the committing
   transaction from reading the previous seal to writing the anchor (rows,
   marks and journal binding included), i.e. what a seal adds to the commit
   that holds the engine lock. The sealing slice's whole hold also contains
   the commit's `COMMIT` (WAL append and fsync), which every committing slice
   pays whether it seals or not (non-sealing slices' p99 is higher than
   sealing slices' in the same runs), so it is reported
   (`sealing_hold_p99_ms`) without a floor. The module doc of the qual file
   said the floor applied to the sealing slice's hold; fix round 1 corrected
   it to what the check does.
9. **A new table, `journal_branch`** (fix round 1), in addition to the four of
   the first round: §9 allows new tables; it is listed in CCR-WP4.4-3 for the
   plan's table list. It is not a schema change of an existing table and
   older binaries keep it exact through its triggers.
10. **`temp_store=MEMORY` for the worker's engine store on Windows** (fix
    round 1, `src/core/inbox.rs`, owned): not a listed task, but the package
    goal ("never hold the engine/commit lock for long") and the 50 ms floor
    were missed because of it (*Fix round 1*). A connection setting of one
    store (opened with deferred activation) on one platform, chosen by
    measurement; no schema, protocol or other package's code changes.

## CCRs filed

* **CCR-WP4.4-1 (`src/core/objects.rs`, WP4.5's in Wave 4).** The
  `staged_objects_insert` trigger parses every staged payload in SQL twice
  (`json_valid`, `json_each`): measured in release, staging costs 17 us/event
  with the trigger dropped against 65 us/event with it at an empty inbox
  (before this package's other changes). Requested: write the
  `staged_objects` rows from Rust in `stage_incoming`, which holds the parsed
  event, and restrict the trigger to rows inserted without a state
  (`WHEN NEW.state IS NULL`: older binaries, startup evacuation), or an
  equivalent. Adapter: none possible from `inbox.rs`; the cost is measured
  and reported.
* **CCR-WP4.4-2 (`docs/ARCHITECTURE.md`, `docs/VALIDATION.md`, WP4.3).** The
  "Startup snapshots and cursor replay" section describes format 1 ("sealed in
  the same transaction as a full projection update", "at most 128 …
  advances"): describe format 2 (inline and rows layouts, marks, the
  resumable journal hash, `current_meta`, the downgrade path).
* **CCR-WP4.4-3 (`docs/revamp/REVAMP_PLAN.md`, WP4.INT).** Invariant 5's row
  ("Format unchanged; forced seal kept") and the scope cut "No snapshot
  FORMAT 2 (chain hash). The forced seal per slow commit stays O(N) bytes
  hashed" describe the superseded design: format 2 is the WP4.4 format (no
  chain hash; the journal hash is unchanged in meaning), and the forced seal

## Known limitations

* An inline seal still serializes the whole (at most 1 MiB) projection; a
  rows seal rewrites the whole header, so a projection with many unresolved
  conflicts pays O(open conflicts) per seal and per conflict change (the
  header row of CCR-WP2.INT-5 is written whole).
* Startup is unchanged in order: it re-hashes the branch's journal
  (O(history)) and reads and checks every sealed row (O(projection)), as
  WP3.INT parsed the whole payload; the restore itself now writes only the
  rows that differ. A full seal (a rebuild, the startup drain's
  `seal_branch`) still finds the branch's newest journal row with a join over
  the branch's journal (`cursor()`, O(history)): it is the snapshot's
  coverage claim, so it is read from the journal itself rather than from
  `journal_branch`; every commit passes its own event's sequence.
* An inactive branch's namespace tail is still reconstructed rather than
  replayed (unchanged; `branches_seal_from_their_own_marks` seals it first).
* Staging still costs about 2.4 times more per event at 40K staged rows and
  3.1 times at 100K than at an empty inbox (random-key index pages), and the
  page's commit grows with the inbox (150-209 ms against 8-9 ms): each staged
  row dirties a leaf of six random-key indexes, a write amplification no
  lookup change removes; bounding it would take sequential keys or fewer
  indexes (a schema change, partly in WP4.5's `staged_objects`). The trigger
  cost is CCR-WP4.4-1.
* The in-memory sub-journal is used by the worker's engine store on Windows
  only. Other stores (the CLI, tests, secondary connections such as the
  feed's staging connections) keep SQLite's temp files, and so the
  occasional 30-60 ms temp-file creation inside a large transaction on
  Windows; none of them holds the engine lock. A process-wide fix (raising
  SQLite's statement-journal spill threshold, `SQLITE_CONFIG_STMTJRNL_SPILL`,
  before the first connection opens, which keeps journals in memory in large
  chunks up to the threshold) would cover every connection without the
  1 KiB-chunk cost, but must run at process start, outside this package's
  files.
* Two timing tests of `worker_concurrency`
  (`revalidate_waits_for_a_pass_that_ran_while_the_writer_is_busy`,
  `a_slow_commit_never_waits_for_another_writer_under_the_engine_lock`) are
  flaky when their binary's tests run in parallel, with or without this
  package's changes (about 1 run in 12 on WSL and on Windows without the
  in-memory sub-journal): a 25 ms slice under CPU contention commits part of
  what the assertion expects.
* `derive_oracle::fuzz_stress_release` is not green: CCR-WP4.4-5, a
  pre-existing refusal-parity gap of the content successor (reproduced on
  `revamp/wave-4-base`), fails about 1 in 20 seed runs.
* The qualification's activator emulation tunes the engine connection and
  checkpoints the WAL off-lock as the activator does; it does not run the
  worker process (the seal's own time is what the store measures inside the
  commit).
