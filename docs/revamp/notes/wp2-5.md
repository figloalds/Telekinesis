## Fix round 1

The independent review of `968edf9` raised one major and four minor
findings. All five are fixed in `src/core/sharing.rs`, each with a test in
`tests/feed_v7.rs` that fails on `968edf9` and passes now. No finding was
rejected, and no new CCR was needed.

| Finding | Fix | Test |
|---|---|---|
| **major**: a listed need (`elided`/`large`) was never cleared when its source reset or regressed, and still counted after the source answered `unknown`. A source that lost a listed event (a restore, an evacuation) kept the peer's `metadata.caught_up` and `gate.caught_up` false and `to_receive ≥ 1` for good, which also stopped the stand-in activation | `forget_peer` (a reset page, or a detected regression) deletes the peer's `feed_needs`, and the re-read lists again what it still has. A listed need the peer reported `unknown` (`missing_at` set) is no longer outstanding in `PeerView::needs`, so `to_receive`, `metadata.caught_up` and the gate no longer count it (deviation 10) | `a_listed_need_the_source_lost_does_not_wedge_the_gate`, `a_listed_need_reported_unknown_is_not_outstanding` |
| minor: a probe page's `tip` was not checked, and `remaining()` subtracted unchecked (`i64::MIN` panicked in debug) | `check_page` requires `tip ≥ 0` for every page; `remaining()` uses `saturating_sub` | `peer_supplied_values_are_bounded_before_they_are_kept` |
| minor: the dialer's summary always reported `sent_events = 0` and `bytes_up = 0` | the offer's sent counts are recorded by request id and folded into the apply summary (deviation 12) | `the_dialer_summary_counts_what_its_request_sent` |
| minor: the sender digested the stored text but receivers digest the canonical re-serialization, so a non-canonical stored payload was refused everywhere | entries carry the digest and size of the canonical serialization (deviation 14) | `non_canonical_stored_payloads_travel_and_are_acked` |
| minor: unbounded peer-supplied epochs, cursor ids and `unknown` ids reached durable rows | 32-hex epochs, cursor shape checks (page cursors, `request.cursor`, `reply.cursor`, `expected`); `unknown` only marks needs we hold or parents an inbox row waits on; expired `parent` marks are deleted | `peer_supplied_values_are_bounded_before_they_are_kept` |

Also: a `feed_needs(event)` index, because an arriving event deletes every
peer's need of it, which was a full scan per received event while needs
existed.

## Summary

1. **Schema** (`sharing::ensure_schema`, `schema:sharing=1`, own savepoint,
   idempotent, new objects only, REVAMP_PLAN §9):
   - `config('journal_epoch')` (32 hex characters, set once), regenerated by
     `AFTER DELETE ON events` (spec) and `AFTER UPDATE ON events`
     (deviation 9) triggers. The evacuation at open deletes rows, so it starts
     a new feed.
   - `feed_in(peer PK, epoch, seq, id, tip, updated_ms, pending_active,
     blocked, quarantined)`: our cursor of the peer's feed plus the peer's
     last reported tip and `FeedState`.
   - `feed_out(peer, via, epoch, seq, id, reported_ms, PK(peer, via))`: the
     peer's reported cursor of our feed, per channel (`request` / `reply`,
     deviation 4).
   - `feed_needs(peer, event, reason, requested_ms, missing_at, seq, digest,
     PK)`: ids the peer's feed listed that we lack (`elided`, `large`, with
     the listed seq and digest) and missing parents we asked it for
     (`parent`).
   - `feed_rejected(peer, event, seq, code, message, payload, at_ms, PK)`:
     durable rejections.
   - Indexes on `incoming_sources(peer)` (per-peer inbox counts) and
     `feed_needs(event)` (an event that arrives clears every peer's need of
     it: a point lookup instead of a scan per received event), and the
     `feed_outbox_known` trigger (below).
2. **Store API** (`impl Store`, all `&self`, run on pooled secondary stores):
   `feed_epoch`, `feed_tip`, `journal_id_at`, `validate_cursor`,
   `feed_state`, `feed_page`, `build_exchange_request` (feed-offer),
   `handle_exchange_request` (feed-exchange), `apply_exchange_reply`
   (feed-apply), `peer_feed_counters`, `events_by_ids`, exactly the §14
   signatures; plus `feed_gate(peer)`, `feed_counters_after(peer, result)`,
   `feed_peers()`, `feed_rejections(peer)` and `feed_payload_reads()`.
   - **Feed** = committed events of shared branches in `journal_sequence`
     order. The tip, `journal_id_at` and cursor validation see shared events
     only: a private event never moves the tip, never appears at a seq and
     never makes a cursor valid (invariant 12). Queries pin
     `journal_sequence` as the outer loop (`CROSS JOIN`), so a page is a
     rowid range scan with point lookups, and the tip a reverse scan that
     stops at the first shared row.
   - **Sender** (§6.3.3): from the recorded `feed_out` (none: probe page;
     invalid: reset page from Start); ≤ 4,096 entries and ≤ 1 MiB of
     payload (a page always carries its first payload); entries the peer is
     known to hold are elided; events over 256 KiB are flagged `large` in
     reply pages (request pages: deviation 3); `through` is the last entry,
     `more = through.seq < tip`. Every entry's digest is of the event's
     canonical serialization (deviation 14).
   - **Receiver** (§6.3.4): structural checks first (bounded and ordered;
     `INVENTORY_TOO_LARGE`, `PROTOCOL_VIOLATION`, nothing kept on failure).
     Every peer-supplied value that is compared or stored is bounded first
     (invariant 22): page epochs are 32 lowercase hex characters, tips are
     not negative (probes included), and every cursor (page `after` and
     `through`, `request.cursor`, `reply.cursor`, `CursorMismatch.expected`)
     has an epoch or none, an id of at most 128 bytes and a seq ≥ 0.
     A probe stages nothing (and records the peer's tip; first contact
     records `Start(peer epoch)`); a page that does not continue from
     `feed_in` answers `CursorMismatch{expected}`; a reset page first forgets
     the peer (`DELETE peer_known`, outbox acks recomputed, the port of
     `remember_peer_inventory`'s re-queue). Each entry: a payload is checked
     (id, digest of its canonical serialization, repository,
     `PRIVATE_BRANCH_REJECTED`, `EVENT_METADATA_TOO_LARGE`, id/device/
     changes bounds, `FORGED_EVENT_ORIGIN`, `EVENT_ID_REUSED` against
     committed and staged payloads, `UNREFERENCED_OBJECT_SIZE`,
     `OBJECT_SIZE_CHANGED`, `BRANCH_DESCRIPTOR_CHANGED`) and staged through
     `stage_incoming` with source `(peer, seq)`; an elided or large entry is
     known (equal digest), `EVENT_ID_REUSED` (different digest) or a need.
     Refusals are durable `feed_rejected` rows and the cursor moves past
     them; `feed_in = through` in the same transaction as the staging.
   - **Acks** (invariant 10, I1): `peer_known(P, id)` only for an entry of
     P's committed feed (or an event P served from its committed journal
     through `need`, deviation 8) whose digest equals our committed or
     staged payload; `outbox.acknowledged = 1` only from `peer_known`, only
     for rows we committed. The cursor never acks; staged and rejected
     events never ack. A staged event that commits later gets its outbox row
     acked by the `feed_outbox_known` trigger (`AFTER INSERT ON outbox`,
     when a feed peer is already known to hold it), so receiving an event
     never leaves it queued forever.
   - **Need**: `need` = listed ids we lack, then missing parents of waiting
     rows (deviation 7), skipping ids the peer reported unknown in the last
     60 s; served from committed shared events only (a private id is
     `unknown`), ≤ `MAX_NEED_BYTES` = 12 MiB (CCR-WP0.INT-4 item 1, applied
     at WP1.INT; one 8 MiB event plus a 1 MiB page fit `MAX_BODY_META`).
     Served events are checked against the listed digest. `unknown` answers
     only touch what we could have asked for: a need of that peer we hold
     (its `missing_at` is set) or a missing parent of a waiting row (a
     `parent` mark, recorded only while some row waits on it); any other id
     is ignored, and expired `parent` marks (which suppress nothing) are
     deleted whenever a reply reports ids unknown.
   - **Regressions and resets** (§6.3.4, I2): a peer reporting a lower
     cursor of our feed than the valid one the same channel reported before
     regressed: we forget it (`peer_known`, outbox recomputed: withdrawn
     events are queued again and re-sent with payloads) and re-read its feed
     from the start (deviation 4). Forgetting a peer (a regression, or a
     reset page of its feed) also deletes its `feed_needs`: what its old
     feed listed may be gone (a restore, an evacuation), and the re-read
     lists again what it still has.
   - **Counters and gate** (§6.3.6): `metadata.caught_up` = our cursor at
     the peer's tip, no `ready|waiting|retry|unclassified` row sourced from
     it, no listed need outstanding (one the peer reported `unknown` is not
     outstanding: deviation 10); `gate.caught_up` adds no
     `blocked|quarantined` row from it, no `feed_rejected` row from it and
     its `pending_active == 0`; `gate.blocked` = something from it is
     blocked, quarantined or rejected; `waiting_on` gives the reasons
     ("12 events remaining at source", "3 events waiting for parents",
     "source has 1 unactivated event", "2 events quarantined",
     "1 event rejected", ...).
3. **Worker RPC** (`runtime::sync_rpc::dispatch`): `feed-offer`,
   `feed-exchange` (`{reply, local}`) and `feed-apply` check the route
   against the worker (`REPOSITORY_MISMATCH`,
   `LOCAL_REPLICA_BINDING_MISMATCH`, `DUPLICATE_REPLICA_IDENTITY`), run on a
   pooled `SyncStore` without the engine lock, then refresh
   `ctx.sync_obs[peer]` (from the exchange result, stamped now), bump
   `ctx.status_generation` and poke `ctx.activation`. Replies leave out null
   `event`/`large` entry members (CCR-WP2.5-3). Unknown ops answer
   `UNSUPPORTED_OPERATION: <op>`. Stand-in activation: deviation 5.

## Deviations from the spec, and why

1. **`to_send`** is the exact number of our feed entries after the peer's
   cursor (what it still has to read, elided or not), capped at
   `COUNT_CAP`. The first version subtracted entries the peer is known to
   hold: a joined, anti-joined scan of up to 100K rows cost 350–600 ms per
   call during a 150K catch-up (release, measured). Now it is a rowid range
   count when the replica has no private branch (every journal row is then
   a feed entry), else a count over shared rows. After a catch-up the
   (elided) echo shows as `to_send` until the peer has read it, which takes
   a few exchanges and is real work.
2. **`to_receive`** is an upper bound: `peer tip − our cursor` (seqs; the
   peer's private events and deleted rows hold seqs too) plus listed needs.
   No frozen message carries the peer's exact count (CCR-WP2.5-4).
3. **Large events in request pages travel inline**, as the page's last
   payload (a request page may then reach 1 MiB + 8 MiB; `MAX_BODY_META` is
   16 MiB). A reply has no `need` member, so an acceptor can never ask a
   dialer for anything: under one-way pairing a dialer's large event could
   never arrive (CCR-WP2.5-2). Reply pages flag large events as the spec
   says.
4. **Regression handling, made safe to act on.**
   - *Re-read after a regression.* Clearing `peer_known(P)` without
     re-reading P's feed would lose valid evidence for good: our cursor of
     P's feed is past the entries that produced it, so those acks would
     never come back (the outbox would show work forever). So a detected
     regression also deletes `feed_in(P)`, and P's feed is read again from
     the start (mostly elided entries). While re-reading we report *no
     cursor* (`None` in a request; an empty-epoch cursor in a reply), which
     the peer treats as invalid (it sends a reset or a page from the start)
     and never as a regression of ours, so there is no ping-pong.
   - *Per-channel reports.* `feed_out` keeps the last report of each
     channel: cursors carried by the peer's requests and by its replies to
     ours. A regression is a lower report than the same channel's previous
     valid one. Under mutual pairing a request can carry a cursor read
     before the peer applied our newer reply; compared across channels that
     stale cursor looks like a restore (and would trigger a full forget and
     re-read on every such race). The next page continues from the furthest
     valid report of either channel.
   - *Resets restart both channels*: answering with a reset page, or
     receiving `PageStatus::Reset` for ours, drops the recorded reports, so
     the low reports that follow by design are not regressions; a report
     recorded before our journal changed is invalid and never compared.
5. **Stand-in activation.** Staging never activates and WP2.3's activator
   does not exist in this tree. While `ctx.activator_running` is false (a
   Wave 1 worker, or the in-process `start_rpc` wrapper), a feed exchange
   that leaves nothing to receive from the peer and leaves activatable rows
   activates them in one bounded pass (`try_lock_engine` only, never a
   wait; slices of 64 through `Engine::receive_peer_budget`, which also
   refreshes clean sessions and queues namespace notifications; ≤ 100 ms),
   as the legacy lanes do. It is skipped while `worker.activator.slice` (the
   activator's pause point, which `qual_wp2_5_feed` arms) is armed. Without
   it, a worker in this wave would never activate what the feed staged.
   With WP2.3 merged the activator sets the flag and this path is inert.
6. **Malformed feed requests answer `UNSUPPORTED_OPERATION: <op>:
   malformed request: …`.** `tests/worker_lifecycle.rs` (WP1.4's, no Wave 2
   owner) still pins the Wave 0 stub's answer to a route-less
   `feed-offer`; the adapter keeps it green without editing it
   (CCR-WP2.5-1).
7. **Missing parents** are looked for only once our cursor is at the peer's
   tip, among the oldest 4,096 waits (a bounded query in `sharing.rs`),
   instead of calling `Store::missing_parents(256)` on every offer. That
   scan visits every wait: 0.8 s per offer at 34K staged rows during a
   catch-up (release, measured). While a feed streams, it brings parents
   before children (acceptance order); a wait on a missing parent never
   resolves, so it ages to the front of the window.
8. **Events served through `need` are evidence too** (`peer_known`): the
   peer serves only events committed in its own journal. Without this a
   large event (or a missing parent) received through `need` would never be
   acked, since the feed entry that listed it has already been passed.
9. **Extra schema objects**: `feed_epoch_update` (a rewritten journal row
   also starts a new feed: its digest changed), the `feed_outbox_known`
   trigger (summary 2), the `incoming_sources(peer)` index (per-peer counts
   are point-range lookups), the `feed_needs(event)` index (fix round 1: an
   arriving event clears every peer's need of it), extra columns in my own new tables (`feed_in`
   keeps the peer's `FeedState`; `feed_needs` keeps the listed seq and
   digest; `feed_rejected` keeps the message; `feed_out` is keyed by
   channel). Nothing is altered. Per-peer inbox counts use the global
   `inbox_counts()` (index-only) when every staged row came from that peer.
10. **`metadata.caught_up` also requires no listed need outstanding** (an
    elided or large entry we lack is metadata still to receive). A listed
    need stops being outstanding when the peer reports it `unknown` (it
    lost the event, or never had it to give; the id is still asked again
    every 60 s and counts again if the peer lists it again), and every
    listed need of a peer is dropped when the peer is forgotten (reset or
    regression). Without these two rules a source that lost a listed event
    kept `metadata.caught_up`/`gate.caught_up` false and `to_receive ≥ 1`
    for good, which also stopped the stand-in activation (fix round 1). The
    gate's "waiting" reason reads "waiting for parents": a `waiting` row
    may wait on a staged parent, not only a missing one.
11. **Codes.** A payload whose digest does not match its entry, or whose id
    differs, is `INVALID_EVENT`; malformed pages are `PROTOCOL_VIOLATION`
    (Transient default); oversized lists are `INVENTORY_TOO_LARGE`. Every
    code used is already registered in `model::errors`.
12. **`bytes_up`/`bytes_down`** are estimates (payload bytes plus 96 bytes
    per entry plus 512); the orchestrator knows the transport bytes. The
    dialer's `feed-apply` summary reports what its request sent
    (`sent_events`, `bytes_up`, and `metadata_advanced` when it sent
    payloads): `build_exchange_request` records it by request id in a
    bounded process-wide table (1,024 offers; the offer and the apply may
    run on different pooled stores) and `apply_exchange_reply` takes it. A
    reply to a request this process did not build (a worker restarted
    between the two) reports nothing sent.
13. **First contact is a probe round** (spec): the dialer's first page has
    no `after`; the acceptor records `Start(dialer epoch)` and pages its own
    feed from the start.
14. **Digests are of the canonical serialization.** §6.3.1 says "of the
    payload text". A payload-bearing entry reaches the receiver as an
    `Event` (the wire re-serializes it), so the receiver can only digest
    `serde_json::to_string(event)`; held-payload checks accept either form
    (`payload_matches`). The sender therefore digests (and sizes) the
    canonical serialization of every entry, elided and `large` ones
    included. For every payload `commit` and staging write this is the
    stored text itself; a payload stored otherwise (an older build without
    `dependencies`/`reviewed`, other key order, another tool) used to be
    refused by every receiver as `INVALID_EVENT` (or `EVENT_ID_REUSED` when
    elided) and now travels and is acked. Cost: one parse and one
    serialization per entry built (elided entries were only hashed before);
    an idle exchange builds none.

## CCRs filed

- **CCR-WP2.5-1** (`tests/worker_lifecycle.rs`,
  `ready_worker_record_and_hello_describe_the_same_process`, for WP2.INT):
  the test asserts that `{"op":"feed-offer","route":{}}` answers
  `UNSUPPORTED_OPERATION` (the Wave 0 stub). Requested: assert the code of a
  malformed request instead (`INVALID_REQUEST`), or drop that assertion now
  that the op exists. Adapter: deviation 6; afterwards `sync_rpc::request`
  can answer `INVALID_REQUEST`.
- **CCR-WP2.5-2** (`model::protocol::feed`, frozen): add
  `#[serde(default)] need: Vec<String>` (≤ `MAX_NEED`) to
  `MetaExchangeReply` and `#[serde(default)] need_served: Vec<Event>`
  (≤ `MAX_NEED_BYTES`) to `MetaExchangeRequest`, so the acceptor can ask the
  dialer for large events, elided entries it lacks and missing parents.
  Reason: one-way pairing. Adapter: deviation 3 (large events inline in
  request pages). Remaining gap until applied: an acceptor that lacks an
  elided entry or a missing parent waits for its own dial (mutual pairing)
  or a reset.
- **CCR-WP2.5-3** (`model::protocol::feed::FeedEntry`, frozen): make
  `event` and `large` `#[serde(default, skip_serializing_if =
  "Option::is_none")]`. An elided entry is then ~87 bytes on the peer wire
  instead of ~113 (the "echo < 100 B/event" target); WP2.7 re-serializes the
  typed messages, so the worker's stripping (`sync_rpc::wire`) does not reach
  the peer wire. Wire-compatible (both already default).
- **CCR-WP2.5-4** (`model::protocol::feed::FeedPage`, frozen): add
  `#[serde(default)] remaining: Option<u64>`: the sender's exact count of
  its entries after `through` for this receiver (capped at `COUNT_CAP`), for
  an exact `to_receive`. Adapter: deviation 2.
- **CCR-WP2.5-5** (WP2.3 / WP2.INT wiring, information):
  - `published-summary` (`server.rs`) reports `tip {epoch: "", seq:
    max(journal_sequence.seq)}`; it should be `{store.feed_epoch(),
    store.feed_tip()}`: the feed tip counts shared events only (the current
    max includes private events, and puts their existence in the remote
    catalog's tip).
  - The heartbeat's `JournalCounters.epoch` can come from
    `Store::feed_epoch()`; maintenance can refresh per-peer counters with
    `Store::feed_peers()` + `peer_feed_counters()` (keep the
    `last_exchange_ms` that `sync_rpc` stamps when it is newer).
  - The activator must set `ctx.activator_running` (the stand-in steps
    aside) and keep `worker.activator.slice` as its pause point (the WP2.5
    qualification uses it).
  - WP2.7: the dialer's `feed-apply` summary carries `sent_events` and
    `bytes_up` of the request built by the same worker process
    (deviation 12); for a request built before a worker restart they are 0,
    and the orchestrator, which holds the request it carried, can fill them.
- **CCR-WP2.5-6** (performance, `src/core/inbox.rs`, WP2.4 owns it in Wave
  2): `stage_incoming`'s cost per event grows with the staged backlog:
  65 µs per event with an empty inbox, 250 µs at 28K staged rows (release,
  in-process, 1,133-event pages). It is now the largest cost of a 150K
  catch-up and decides the `feed_150k_events` floor (Qualification).
  Requested: investigate (statements prepared per event with
  `Connection::execute`; per-event `apply_class` writes).

## Known limitations

- `feed_150k_events` passes with about 11% to spare on a quiet machine and
  misses while other packages' builds or suites run (by 1% in the first
  round, by up to about 35% in fix round 1, for `968edf9` as much as for this
  tree; Qualification; CCR-WP2.5-6).
- Building an entry now parses and re-serializes its payload (deviation 14):
  about +3–4 µs per entry in release; an idle exchange builds none.
- An acceptor cannot request anything from a dialer (CCR-WP2.5-2); large
  events travel inline in request pages instead.
- `to_receive` is an upper bound (CCR-WP2.5-4).
- `feed_rejected` rows are permanent: nothing clears them (the gate stays
  blocked on that source until an override), and `revalidate` only
  re-queues inbox rows. Unlike needs, a reset or regression of the source
  does not clear them either: §6.3.4 makes a refusal a durable record, even
  when the source's new journal no longer has the event.
- An expired `parent` mark of `feed_needs` is deleted the next time that
  peer reports ids unknown; until then it stays (it suppresses nothing).
  Marks are only recorded for ids some inbox row waits on.
- A listed need the source reported `unknown` is asked again every 60 s
  for as long as its row lives (until the event arrives, the source lists
  it again, or the source is forgotten).
- The dialer's sent counts are lost across a worker restart between
  `feed-offer` and `feed-apply` (deviation 12).
- The stand-in activation (deviation 5) holds the engine lock up to 100 ms
  per feed RPC in a worker without an activator.
- Bytes in summaries are estimates (deviation 12).
