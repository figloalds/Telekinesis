### Per-peer credentials (task 1)

- **Enrollment.** `pair` authenticates its probe with the code, then sends
  `peer.enroll` with a fresh 32-byte `S`; both sides store
  `K_peer = SHA-256("tkfs-peer-secret-v1" ‖ S)`: the acceptor as the
  dialer's `inbound` credential, the dialer as its `outbound` one, just
  before the peer record is stored (so a supervisor the record starts, also
  one the `peer-manager` thread starts before `pair` reconciles, presents it
  and never enrolls a second one; a failed record write forgets it again; a
  queued lane-0 enrollment is skipped once a credential exists). `S` is
  sealed (deviation 2): XOR with
  `HMAC(K, "tkfs-peer-enroll-v1" ‖ 0 ‖ "pad" ‖ 0 ‖ client ‖ 0 ‖ server ‖ 0 ‖ nonce)`
  plus a MAC over it, `K` being the pairing code's key (`Verifier::key` on the
  acceptor, `derive_key(salt, code)` on the dialer).
- **Later sessions** offer `peer-hmac-v1` in `ClientHello.features`; the
  acceptor echoes it and both proofs are `HMAC(K_peer, "client"/"server" ‖ T')`
  where `T'` is the §6.2 transcript under the context `tkfs-peer-hmac-v1`
  (domain-separated from the code's). The session still records the
  verifier generation, so a rotation sends it away like a code session.
- **Missing or revoked credential** → `GOAWAY{PEER_REVOKED}`. The dialer then
  drops that credential and re-dials with its code at once: a still valid
  code re-enrolls (a lost acceptor database heals itself), a rotated one
  blocks the peer `Unauthorized` (re-pair), as before WP4.1.
- **Older acceptors** (a WP3 v3 orchestrator) ignore the feature: the dialer
  authenticates with the code in the same handshake; `peer.enroll` answers
  `UNKNOWN_PEER_OPERATION` and the pairing stays code-only.
- **Upgrade path.** A data directory from before WP4.1 has no
  `peer_credentials` table: it is created on open. The dialer's lane 0
  authenticates with the code and enrolls on that session, with no user
  action (`code_paired_peers_enroll_on_their_next_connection`).

### Unpair and rotation (tasks 2 and 3)

- **Unpair** (dialer): when we hold an outbound credential for the peer,
  `peer.revoke` goes first (lane 0's session when Ready, else a probe
  session; `REVOKE_DEADLINE` 2 s, probe budget 3 s; failures are logged and
  the unpair goes on); then `RemovePeer`, which deletes the outbound
  credential in the same transaction. The acceptor revokes the dialer's
  inbound credential, answers, sends `GOAWAY{PEER_REVOKED}` to every session
  of that installation and closes the ones still open 500 ms later. Measured
  in `unpair_revokes_inbound_access_within_one_second`: revoked and every
  session gone well under 1 s from the start of the unpair.
- **ResetPairingCode** keeps its semantics (new verifier, generation bump:
  the inbound server's rotation watcher sends every older session
  `GOAWAY{PAIRING_CODE_CHANGED}`), and the same transaction revokes every
  inbound per-peer credential (invariant 21). Outbound credentials (granted
  by other peers' codes) are untouched.

### Local tokens (task 4)

- **`DATA/orchestrator.token`**: a fresh token at every daemon start
  (deviation 3), written owner-only before `orchestrator.json` names the
  control endpoint; required as `X-Tkfs-Token` on the control upgrade (HTTP
  403 otherwise, before any action is read). `client()`, `ControlClient`
  (CLI, GUI) and the harness (`tests/support` `Control`, which WP0.5 wrote
  for this) read it; a restarted daemon's new token is read on reconnect.
- **Worker token**: per instance, in `STATE/runtime.token` (owner-only),
  `worker.json` (`token`), the Ready line and so `WorkerEndpoint.token`
  (the controller already copied both, WP1.2/WP1.3). Required on the JSON RPC
  and on loopback session upgrades. `runtime.json` is unchanged and carries
  no token. `runtime::rpc`, `RpcLane`, `connect_worker` (and the CLI's
  worker commands) read the file, but only for the address the worker itself
  published next to it.
- **Owner-only**: Unix 0600 (token files from creation, `folders.sqlite` and
  its WAL files at every catalog open); Windows: the files inherit the
  ACL of the data and state directories, which live under the user's
  profile (the user, SYSTEM and Administrators).
- **Upgrade**: an existing data directory gets `orchestrator.token` at the
  daemon's next start and each worker its token at its next start; adopted
  workers keep theirs (`worker.json`); an adopted worker of an older build is
  restarted by the version check, and the clients' token header is ignored by
  it meanwhile.

## Deviations from the spec, and why

1. **`peer_credentials` is keyed by `(installation, side)`** (§9 says
   `installation PK`). With a mutual pairing, each daemon is both the dialer
   (its own `outbound` credential for the peer) and the acceptor (the peer's
   `inbound` credential); one row per installation cannot hold both, and
   sharing one secret for both directions would let the acceptor dial back
   without ever having been given the dialer's code. `side` is `inbound` or
   `outbound`.
2. **The secret travels sealed**, not as a bare `peer.enroll{secret}`: the
   session is plain `ws://` unless an operator TLS proxy is in front, and a
   bare `S` would hand any passive observer a permanent credential, while the
   code itself never crosses the wire (§6.2). The seal costs nothing extra
   and a stale verifier is detected (`INVALID_PAIRING_CODE`).
3. **The control token rotates at every daemon start** (the spec does not
   say). A leaked token dies with its daemon; every client re-reads the file
   on connect, so nothing else changes.
4. **Revocation does not ban the installation.** `peer.revoke` revokes the
   per-peer credential and closes the sessions; a later pairing with the
   (still valid) code works and re-enrolls, as pairing with a code always
   did. `peer_meta.revoked_ms` (which bans an installation outright and needs
   a frozen `CatalogCmd` to set) is left unused.
5. **`catalog_schema` stays 1.** `tests/catalog_actor.rs` (not owned) pins
   it at 1 after opening a legacy data directory; the new table is created
   with `CREATE TABLE IF NOT EXISTS` on every open instead (idempotent,
   additive, unknown to older binaries).
6. **`peer.revoke` is only sent when we hold an outbound credential**: without
   one there is nothing to revoke at the acceptor, and an unpair of a
   code-only (or fake-catalog) peer keeps its old timing
   (`peer_supervisor::a_lane_inside_a_dial_is_interrupted…` needs < 1.5 s).
7. **Adapters for files this package does not own** (CCRs below): the
   control endpoint is protected through `ws::tokens` (registry consulted by
   `ws::accept`) because `run.rs`/`ctx.rs` are frozen; `ws::connect` and
   `dial_loopback(addr, None)` present a token this process knows for the
   address (in-process daemons and workers of the test suites,
   `compat::worker_call`); `Discovery`'s `Deserialize` notes the token of a
   worker's own published record, so tests that read `runtime.json` and dial
   a worker process with no token (`tests/objects_v3_worker.rs`,
   `tests/qual_wp3_2_objects.rs`, WP4.5's) keep working. Every registry entry
   is a loopback address; a protected entry lives until its owner releases it
   (the control token: at the network shutdown, after `stopping` is set).
8. **`tests/worker_lifecycle.rs` (WP1.4's, not owned) changed in one test**
   (`ready_worker_record_and_hello_describe_the_same_process`):
   `assert!(ready.token.is_none())` and `keys(worker.json) == keys(golden)`
   pinned the W0 placeholder ("None until WP4.1", §6.1) that §14 WP4.1
   replaces. Now: Ready carries a 64-hex token equal to `runtime.token` and
   to `worker.json`'s, and the record's keys are the golden's plus `token`.
   Stricter than before; no other assertion changed. (CCR-WP4.1-7 asks the
   integrator to ratify it.)
9. **`PEER_REVOKED` in a handshake `GOAWAY` stays `DialError::Rejected`**
   (`tests/inbound_v3.rs` pins it); the lane classifies it by its code
   (NeedsUserAction → `Unauthorized`) and the credential fallback looks at
   the code.

## Known limitations

- **The worker token is in `worker.log`** in the Ready line the launcher
  copies there (CCR-WP4.1-4, `process.rs` is WP4.2's this wave). The file
  sits in the owner-only state directory next to `runtime.token`, but a
  diagnostics tail could carry it until the CCR is applied.
- **Windows ACLs are inherited, not set**: a data directory placed outside
  the user's profile with a permissive ACL exposes the token files and
  `folders.sqlite` accordingly (documented, §11.15).
- **The dialer keeps its plaintext code** in `peers.code` after enrolling
  (positional legacy table; downgrade safety; the code fallback for an
  acceptor without the scheme or one that lost its credential). The code is
  only ever a dial credential and never leaves the process (invariant 21).
- **During shutdown**, once the network has stopped (§3.6 step 2, after
  `stopping` is set), the control endpoint no longer checks the token; every
  action is refused `ORCHESTRATOR_STOPPING` by then. Until CCR-WP4.1-3 moves
  the check into `serve_control`.
- **A best-effort revoke can be lost** (the peer unreachable during the
  unpair): the acceptor keeps an inbound credential nobody holds any more
  (the dialer deleted its copy) until its code is rotated. It cannot be used
  without the key.
- A daemon built in-process and never shut down (a test that leaks it) keeps
  its control address protected in that process's registry; a later listener
  reusing the port in the same process would then demand the token from
  `ws::accept` clients.
