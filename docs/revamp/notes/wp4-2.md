Spec: REVAMP_PLAN §14 WP4.2 (tasks 1–4), §15.1 floors, §10 invariant 21;

## Summary

### 1. Logs (`src/util/log.rs`)

The frozen `event!` contract is unchanged (same API, same line shape
`{"at_ms","level","code",<fields>}`, same per-code rate limit of 20 events a
minute, fatal never suppressed, lines written after the logger's lock). Added:

- **Rotating files.** `RotatingFile` appends whole writes and rotates when the
  next write would take the file past `Rotation::max_bytes`
  (`log` → `log.1` → … → `log.<files-1>`, the oldest dropped). Defaults:
  10 MiB × 5 files (`ORCHESTRATOR_LOG_BYTES`, `ORCHESTRATOR_LOG_FILES`);
  `TKFS_LOG_ROTATE_BYTES` (≥ 256) and `TKFS_LOG_ROTATE_FILES` (1–100)
  override (`Rotation::from_env`). A failed rotation (another process holds
  the file without delete sharing) keeps appending, writes a note into the
  file, and is retried after another `max(max/8, 64 KiB)`; a failed write
  reopens the file at the next one. A file left without a final newline by
  another writer gets one before the first line.
  `rotate_files` moves the live file aside (`log.rotating`) **before** any
  older file moves, then frees `log.1` by shifting the history up to the
  first missing generation (the oldest is removed only when none is
  missing), then places the live file as `log.1`. A live file that cannot be
  renamed therefore changes nothing; a history file that cannot be renamed
  puts the live file back, and the retry fills the gap instead of removing
  another generation (fix round 1); a file left aside by an interrupted
  rotation is placed first by the next one.
- **Process log.** `install_file(path, rotation)` makes a rotating file the
  process sink (first install wins); `install_daemon_log(data)` installs
  `DATA/logs/orchestrator.log`; `file_log()` reports it (a `OnceLock`, read
  without a lock; installers are serialized by a mutex of their own that
  guards no data). The standard streams are classified first, against the
  file as it is **before** any rotation: the file is opened without
  rotating, the streams that are it are captured, and only then does a file
  already at or past the limit rotate (fix round 1: rotating first made an
  inherited oversized log look like another file, so nothing was captured
  and every event was teed into the renamed file):
  - a stream that *is* the log file (the desktop starts its daemon with
    stdout and stderr appended to `DATA/logs/orchestrator.log`), or that is
    missing or the null device, is **captured**: it is pointed at a pipe
    (never inherited by workers) and a `log-stdout`/`log-stderr` thread writes
    each line into the rotating file as an event with code `stdout` or
    `stderr` (a JSON object line kept whole under `json`, other text under
    `text`). On Windows each switch is settled 2 s later (fix round 2): the
    C runtime's descriptor 1 or 2 (which `printf` and every C write use, and
    which keeps the handle of startup: `SetStdHandle` does not reach it) is
    pointed at a non-inheritable duplicate of the pipe, under Rust's lock of
    that stream; then the handle that pointed at the old file is closed,
    unless the runtime closed it itself (it owned it) or a standard handle
    or a descriptor still refers to it, so the renamed file is not held open
    and no descriptor writes through a closed, reusable handle value. A
    panic hook writes
    panic messages (with a backtrace when `RUST_BACKTRACE` asks) straight to
    the file, so they survive a process that ends before the capture thread
    ran;
  - events are **teed** to stderr when it is a terminal, a pipe or another
    file (a console run; the test harness's `daemon.log`).
- **Desktop (GUI) mode.** `adopt_desktop_log()`: when the process's stderr is
  a file named `orchestrator.log` in a directory named `logs`, that file
  becomes the rotating log (both streams captured), also when it is already
  past the rotation size (the first start after an upgrade from unbounded
  raw output: the streams are captured, then the legacy file is rotated and
  never written again; fix round 1). `RealLauncher::new`
  (built once per daemon by `ctx::build_with`, after `orchestrator.lock` is
  held) calls it, so a daemon the desktop starts no longer appends unbounded
  raw output: its discovery line, events, stray output and panics all land in
  the rotating JSON-line log, which is the file the desktop's Log button
  opens (CCR-WP3.4-2's fallback path). This is the adapter of CCR-WP4.2-1.
- **Redaction (invariant 21).** Every line written by the logger: a field (at
  any depth) whose name contains `token`, `secret`, `password`,
  `passphrase`, `credential`, `verifier`, `pairing_code`, `authorization`,
  `cookie` or `private_key` is written as `<redacted>` unless its value is a
  number, boolean or null; a field named `code` whose string value is not
  shaped like an event code (`[A-Z0-9_]+`, `*`, `stdout`, `stderr`) is
  redacted (a pairing code is 64 hex digits); strings registered with
  `register_secret` are scrubbed wherever they appear. `redact_line` applies
  the same to foreign lines (worker stdout, captured streams, log tails).
- `tail_lines` (the end of a rotated log across its files, redacted line by
  line) for diagnostics.

### 2. `worker.log` (`src/orchestrator/process.rs`)

- At spawn, a `worker.log` larger than `LogPolicy::rotate_bytes` (10 MiB) is
  rotated (`worker.log.1` … at most `rotate_files` = 5 files); a failed
  rotation is logged (`PERMISSION_DENIED`/`UNKNOWN_ERROR`, detail "worker.log
  rotation failed") and the worker appends to the old file. Nothing writes
  the file during the rename: a worker is spawned only after the previous one
  released `owner.lock` (invariant 23).
- The stdout reader writes each line to `worker.log` through `redact_line`:
  the Ready line's worker token (WP4.1) reaches the controller (parsed from
  the raw line) but never the file.

### 3. Diagnostics (`src/orchestrator/diagnostics.rs`)

`diagnostics::collect(ctx)` (the `diagnostics` action, `tkfs manage
diagnostics`) writes `DATA/diagnostics/<YYYYMMDDTHHMMSS.mmmZ>/`:

| file | content |
|---|---|
| `status.json` | the hub's `StatusSnapshot` |
| `activity.json` | its activity log |
| `folders/<state>.heartbeat.json` | each controller's view: phase, gate, mount, worker endpoint without its token, last heartbeat, last errors, restarts, degraded |
| `catalog.redacted.json` | folders, peers (endpoint, installation, connections, revision, `has_code`), `pairing: {verifier_set, verifier_generation}`, gates, peer metadata |
| `logs/orchestrator.log.tail` | last 512 KiB of the daemon's installed log across its rotated files (only when a log is installed) |
| `logs/orchestrator.log.not-installed.tail` | with no installed log: the tail of a `DATA/logs/orchestrator.log` that exists, which is not this daemon's log (an earlier desktop-started daemon's, or raw output appended by whoever started this one) |
| `logs/<state>.worker.log.tail` | last 256 KiB of each folder's `worker.log` |
| `versions.json` | `tkfs` version, package, protocol, IPC, feed, status and bundle versions, OS/arch, pid, start time, the installed log, each worker's version |

and replies `{schema: 1, path, at_ms, files: [{path, bytes}], log_path,
secrets_redacted}`; `log_path` is the installed log's path, or `null` when
the daemon has none (fix round 1; before, it fell back to
`DATA/logs/orchestrator.log`, a file such a daemon does not write).
`versions.json`'s `log` is the installed log (`null` when none). Two
redaction passes run on every file: structured
redaction (`redact_value` on JSON, `redact_line` on every log line), then a
scrub of every secret the daemon can name (peer codes, the verifier hash,
`*.token` files in the data directory and in each state directory, sensitive
fields of each `worker.json`/`runtime.json`/`orchestrator.json`, worker
endpoint tokens, registered secrets). It reads only snapshots and files (no
worker RPC, no catalog command). The newest 10 bundles are kept.

### 4. Qualification

- `tests/qual_scale.rs` (the §14 WP4.2 list; stays `#[ignore]`, run by
  `qualify.ps1 -All`), deviation 2:
  - `feed_150k` reads B's progress from the worker's status cell and then
    reads the last entry from B's store, as WP3.INT did for
    `feed_150k_daemons`; A's event count also comes from the status cell

  WP4.INT).** Requested: every daemon installs its log, and reports it.
  In `run::run`, right after `ctx::build(config)?` returns (so

## Deviations from the spec, and why

1. **Every daemon logs to `DATA/logs/orchestrator.log` only once CCR-WP4.2-1
   is applied.** Installing the log at daemon start needs `run.rs`/`ctx.rs`,
   which no Wave 4 package owns. Here the desktop's daemon (the case the
   brief names: its output was appended, unbounded, to that file, and
   anything written after a rotation would have gone to a renamed, later
   deleted, file) is handled by the adapter in `RealLauncher::new`; a
   console daemon logs to stderr as before, and `DaemonStatus.log_path`
   stays `None` (the desktop's Log button falls back to the same file).
2. **`tests/qual_scale.rs` scenario changes** (WP0.5's file, owned by WP4.2
   in Wave 4): `feed_150k` reads progress from the status cell, then the
   last entry from the store (WP3.INT's deviation 6 for the same reason);
   the source count of the 150K feed comes from the status cell (the
   `events` op exceeds the message limit at 150K); four scenarios wait for
   the source's publication before the measured phase. Floors, budgets and
   metrics are unchanged; the checks are as strict (the last entry must be
   a live empty file; a publication that never comes fails the scenario).
3. **The Linux subset** (`qualify.sh`) runs every qualification file; the
   four per-object fsync throughput floors are tagged `platforms:
   ["windows"]` (measured reasons in Summary 4) and recorded, not enforced,
   on Linux; the script judges floors itself (`TKFS_QUAL_ENFORCE=0`) so a
   scenario failing only such a floor is not a failure there. The Linux run
   used a tmpfs for scenario data (deviation 4), so its disk-bound numbers
   are not durability-representative; the evidence says so (`disks`).
4. **Where the qualification data lived.** The first runs (Windows on C:,
   the Linux subset concurrently in WSL on its ext4 image, also on C:)
   filled C: (0.04 GB free): the WSL image (120.8 GB) could not grow, its
   filesystem returned I/O errors and the distribution then failed to start
   (`Wsl/Service/CreateInstance/E_FAIL`). This package stopped both of its
   runs (its own processes only), deleted its own build outputs
   (`C:/tkfs-target/wp4-2/{debug,release}`, rebuilt later) and, with every
   distribution stopped, ran `wsl --shutdown` once: the image's journal
   recovered and WSL started again. The Windows qualification was then run
   with `TMP`/`TEMP` on F: (SATA SSD, 130 GB free), and the Linux subset with
   `TMPDIR` on `/dev/shm` (a tmpfs, so the WSL image does not grow). The
   evidence records both disks. C: stayed at 3–13 GB free afterwards
   (other packages' builds); the coordinator should know that the WSL image
   is 120.8 GB and does not shrink by itself.
5. **Rotation count.** "10 MiB × 5" is read as five files in all
   (`orchestrator.log` and `.1` to `.4`, ≤ 50 MiB); `worker.log` keeps the
   same five.
6. **Captured stream lines carry the codes `stdout` and `stderr`.** They are
   not error codes (§8), so they are lower case (the contracts scanner reads
   only quoted SCREAMING_CASE literals as codes) and the redaction rule for
   `code` fields accepts them.
7. **Diagnostics reply extras**: `log_path` (the installed log, `null` when
   none) and `secrets_redacted` beside the bundle `path` and `files`; at most
   10 bundles are kept. Without an installed log the bundle has no
   `logs/orchestrator.log.tail`; a `DATA/logs/orchestrator.log` that exists
   is bundled as `logs/orchestrator.log.not-installed.tail` instead (fix
   round 1).
8. **The final VERIFY used `CARGO_TARGET_DIR=F:/tkfs-target/wp4-2`** (and
   `TMP`/`TEMP` on F: for the suite) instead of `C:/tkfs-target/wp4-2`: C:
   had 0–5 GB free and a debug build takes about 8 GB. The directory is this
   package's alone (isolation is kept); `CARGO_INCREMENTAL=0` throughout to
   save space. Earlier VERIFY steps (the first full suite, the WSL tests)
   used `C:/tkfs-target/wp4-2`. Fix round 1's VERIFY used
   `C:/tkfs-target/wp4-2` as specified (C: had 241 GB free by then), with
   incremental builds and the default `TMP`.
9. **The Windows evidence merges two runs** (`-Merge`, as WP3.INT did):
   `qual_wp3_2_objects`, `qual_wp3_int_e2e` and `qual_scale` come from the
   re-run on `f50b50f`, the other twelve files from the `-All` run on
   `c9578a0`; `merged_from` records the first.
10. **The install of the process log holds a lock across its I/O (fix round
    1).** §2.2 rule 2 ("no lock is held across I/O") is kept for shared
    state: the installed log is a `OnceLock<FileLog>` that `file_log()` and
    every other reader read without a lock (before fix round 1 they took the
    mutex the install held across its I/O). `install_file` itself is
    serialized by `INSTALLING: Mutex<()>`, which guards no data and is taken
    only by installers: the install redirects the process's standard streams
    and replaces the sink, side effects that cannot be undone, so two
    concurrent installers must not both run them. This is the
    `std::sync::Once` pattern (a `Once` blocks concurrent callers the same
    way), keeping a retry after a failed install (a `Once` would not retry).
    In practice it is taken once per process (`RealLauncher::new`, later
    CCR-WP4.2-1's call at daemon start).

## Known limitations

- `scale_idle_worker_cpu` fails (18.9 % against ≤ 1 %): CCR-WP4.2-5, in the
  objects v3 lanes (WP4.5's files). `qualify.ps1 -All` is therefore not
  green; every other floor of waves 1–4 passes.
- Until CCR-WP4.2-1, only a daemon whose stderr is `…/logs/orchestrator.log`
  (the desktop's) writes the rotating file; others log to stderr.
- Adoption needs the inherited file to allow write and delete sharing (the
  desktop opens it with Rust's defaults, which do). A daemon started with a
  `cmd` redirection (`>> orchestrator.log 2>&1`, opened without write
  sharing) cannot open its own log: the adapter does nothing and output is
  appended as before (checked by hand).
- Captured raw output (not events, not panics) goes through a pipe and a
  thread: a line written right before the process exits may be lost.
- If the capture of a stream that is the log file cannot start (the pipe or
  the capture thread cannot be created), that stream keeps writing raw
  output to the file it had open, which a rotation then renames; events
  still go to the rotating file (not teed). Pipe and thread creation do not
  fail in practice.
- Redaction is by field name, by the `code` shape and by known or
  registered secrets: a secret in free text that is none of these would
  pass; no such log line exists today (the grep tests), and CCR-WP4.2-3 asks
  WP4.1 to register its secrets.
- On Windows the C runtime's descriptors 1 and 2 follow a captured stream
  2 s after the capture starts (fix round 2). Until then C output still
  reaches the old file raw (not as events), and a child process spawned in
  that window with inherited standard streams inherits the old file; the
  daemon spawns none then (`RealLauncher::new` runs before any worker
  starts, and workers get their own streams). Should `_dup2` itself fail
  after closing the descriptor (its `DuplicateHandle` failing: only when the
  process is out of handles), the descriptor is left closed and a C write
  to it reaches the C runtime's invalid-parameter handler; the daemon runs
  no C code that writes to stdout or stderr (`native/*.c` does not).
- `worker.log` rotates only when a worker is spawned (as specified): a
  long-lived worker's file can grow past 10 MiB until its next start.
- The full suite's log of the first VERIFY run lost its first part to
  overlapping writes (PowerShell's and cargo's handles on one file without
  append mode); the final run appended.
- This package's build output is at `C:/tkfs-target/wp4-2` (debug, fix
  rounds 1 and 2), `C:/tkfs-target/wp4-2-mergecheck` (the WP4.1 trial merge
  of fix round 2), `F:/tkfs-target/wp4-2` (debug, the first VERIFY) and
  `$HOME/tkfs-target/wp4-2` in WSL.
