# WP4.2 — Operations: logs, diagnostics, qualification floors

Branch `revamp/wp4-2-operations`, cut from `revamp/wave-4-base` (`e8c2979`).
Spec: REVAMP_PLAN §14 WP4.2 (tasks 1–4), §15.1 floors, §10 invariant 21;
CCR-WP3.4-2 (logging information, `docs/revamp/notes/wp3-4.md`) and
CCR-WP2.3-3 (deferred to WP4.2 by WP3.INT).

## Summary

### 1. Logs (`src/util/log.rs`)

The frozen `event!` contract is unchanged (same API, same line shape
`{"at_ms","level","code",<fields>}`, same per-code rate limit of 20 events a
minute, fatal never suppressed, lines written after the logger's lock). Added:

- **Rotating files.** `RotatingFile` appends whole writes and rotates when the
  next write would take the file past `Rotation::max_bytes`
  (`log` → `log.1` → … → `log.<files-1>`, the oldest dropped). Defaults:
  10 MiB × 5 files (`ORCHESTRATOR_LOG_BYTES`, `ORCHESTRATOR_LOG_FILES`);
  `TKFS_LOG_ROTATE_BYTES` (≥ 256) and `TKFS_LOG_ROTATE_FILES` (1–100)
  override (`Rotation::from_env`). A failed rotation (another process holds
  the file without delete sharing) keeps appending, writes a note into the
  file, and is retried after another `max(max/8, 64 KiB)`; a failed write
  reopens the file at the next one. A file left without a final newline by
  another writer gets one before the first line.
- **Process log.** `install_file(path, rotation)` makes a rotating file the
  process sink (first install wins); `install_daemon_log(data)` installs
  `DATA/logs/orchestrator.log`; `file_log()` reports it. The standard
  streams are classified first:
  - a stream that *is* the log file (the desktop starts its daemon with
    stdout and stderr appended to `DATA/logs/orchestrator.log`), or that is
    missing or the null device, is **captured**: it is pointed at a pipe
    (never inherited by workers) and a `log-stdout`/`log-stderr` thread writes
    each line into the rotating file as an event with code `stdout` or
    `stderr` (a JSON object line kept whole under `json`, other text under
    `text`). The handle that pointed at the old file is closed 2 s later
    (Windows), so the renamed file is not held open. A panic hook writes
    panic messages (with a backtrace when `RUST_BACKTRACE` asks) straight to
    the file, so they survive a process that ends before the capture thread
    ran;
  - events are **teed** to stderr when it is a terminal, a pipe or another
    file (a console run; the test harness's `daemon.log`).
- **Desktop (GUI) mode.** `adopt_desktop_log()`: when the process's stderr is
  a file named `orchestrator.log` in a directory named `logs`, that file
  becomes the rotating log (both streams captured). `RealLauncher::new`
  (built once per daemon by `ctx::build_with`, after `orchestrator.lock` is
  held) calls it, so a daemon the desktop starts no longer appends unbounded
  raw output: its discovery line, events, stray output and panics all land in
  the rotating JSON-line log, which is the file the desktop's Log button
  opens (CCR-WP3.4-2's fallback path). This is the adapter of CCR-WP4.2-1.
- **Redaction (invariant 21).** Every line written by the logger: a field (at
  any depth) whose name contains `token`, `secret`, `password`,
  `passphrase`, `credential`, `verifier`, `pairing_code`, `authorization`,
  `cookie` or `private_key` is written as `<redacted>` unless its value is a
  number, boolean or null; a field named `code` whose string value is not
  shaped like an event code (`[A-Z0-9_]+`, `*`, `stdout`, `stderr`) is
  redacted (a pairing code is 64 hex digits); strings registered with
  `register_secret` are scrubbed wherever they appear. `redact_line` applies
  the same to foreign lines (worker stdout, captured streams, log tails).
- `tail_lines` (the end of a rotated log across its files, redacted line by
  line) for diagnostics.

### 2. `worker.log` (`src/orchestrator/process.rs`)

- At spawn, a `worker.log` larger than `LogPolicy::rotate_bytes` (10 MiB) is
  rotated (`worker.log.1` … at most `rotate_files` = 5 files); a failed
  rotation is logged (`PERMISSION_DENIED`/`UNKNOWN_ERROR`, detail "worker.log
  rotation failed") and the worker appends to the old file. Nothing writes
  the file during the rename: a worker is spawned only after the previous one
  released `owner.lock` (invariant 23).
- The stdout reader writes each line to `worker.log` through `redact_line`:
  the Ready line's worker token (WP4.1) reaches the controller (parsed from
  the raw line) but never the file.

### 3. Diagnostics (`src/orchestrator/diagnostics.rs`)

`diagnostics::collect(ctx)` (the `diagnostics` action, `tkfs manage
diagnostics`) writes `DATA/diagnostics/<YYYYMMDDTHHMMSS.mmmZ>/`:

| file | content |
|---|---|
| `status.json` | the hub's `StatusSnapshot` |
| `activity.json` | its activity log |
| `folders/<state>.heartbeat.json` | each controller's view: phase, gate, mount, worker endpoint without its token, last heartbeat, last errors, restarts, degraded |
| `catalog.redacted.json` | folders, peers (endpoint, installation, connections, revision, `has_code`), `pairing: {verifier_set, verifier_generation}`, gates, peer metadata |
| `logs/orchestrator.log.tail` | last 512 KiB of the daemon log across its rotated files |
| `logs/<state>.worker.log.tail` | last 256 KiB of each folder's `worker.log` |
| `versions.json` | `tkfs` version, package, protocol, IPC, feed, status and bundle versions, OS/arch, pid, start time, the installed log, each worker's version |

and replies `{schema: 1, path, at_ms, files: [{path, bytes}], log_path,
secrets_redacted}`. Two redaction passes run on every file: structured
redaction (`redact_value` on JSON, `redact_line` on every log line), then a
scrub of every secret the daemon can name (peer codes, the verifier hash,
`*.token` files in the data directory and in each state directory, sensitive
fields of each `worker.json`/`runtime.json`/`orchestrator.json`, worker
endpoint tokens, registered secrets). It reads only snapshots and files (no
worker RPC, no catalog command). The newest 10 bundles are kept.

### 4. Qualification

- `tests/qual_scale.rs` (the §14 WP4.2 list; stays `#[ignore]`, run by
  `qualify.ps1 -All`), deviation 2:
  - `feed_150k` reads B's progress from the worker's status cell and then
    reads the last entry from B's store, as WP3.INT did for
    `feed_150k_daemons`; A's event count also comes from the status cell
    (the `events` op returns every event: over the RPC's 64 MiB message
    limit at 150K, the connection is reset);
  - the scenarios that receive a folder right after writing it in-process
    (`remote_linear_*`, `feed_150k`, `tiny_files_10k`, `one_gib_object`)
    first wait, outside the measured phase, until the receiver sees the
    folder in the source's published catalog (`remote-list`): a large
    store's worker reports `running` before its published entry is
    `Running`, and `receive` answers `REMOTE_FOLDER_NOT_FOUND` meanwhile
    (seen at 150K events).
- `scripts/qualify.ps1`: `-All` defaults to `-BudgetS 2400 -FileTimeoutMin
  150` (the 150K and 1 GiB scenarios need them; explicit values win); floors
  may carry `platforms` (not enforced on a platform they do not name); the
  evidence records `platform`, the temporary and target disks (drive, free
  space, model, media, bus), the load when the run started (CPU load, build,
  tkfs and qual processes), the temp and target directories and
  `TKFS_BASELINE_BIN`.
- `scripts/qualify.sh` (the Linux subset): `--all` gets the same budgets;
  floors whose `platforms` do not name `linux` are recorded but not
  enforced (the scenarios run with `TKFS_QUAL_ENFORCE=0` and the script
  judges every floor; a scenario whose only failures are such floors counts
  as passed, with a note; any functional failure still fails it); `--merge`
  (as `qualify.ps1 -Merge`); the evidence records WSL, the disks and the
  load at start.
- `tests/qualification-floors.json`: an optional `platforms` field. The four
  per-object fsync throughput floors (`objects_worker_256mib`,
  `objects_worker_tiny_10k`, `e2e_tiny_files_10k`, `scale_tiny_files_10k`)
  are `["windows"]`: §15.1 sets them for the Windows dev box, and WSL's
  ext4 disk image cannot reach them whatever tkfs does (measured by this
  package on WSL ext4: the bare create/write/fsync/rename loop,
  `fs_objects_per_s`, 137.7/s against the 300/s floor; worker tiny objects
  118/s; 256 MiB worker to worker 68 MiB/s). They are still evaluated and
  recorded on Linux.

## CCRs filed

- **CCR-WP4.2-1 (`src/orchestrator/run.rs`, `src/orchestrator/ctx.rs`; for
  WP4.INT).** Requested: every daemon installs its log, and reports it.
  In `run::run`, right after `ctx::build(config)?` returns (so
  `orchestrator.lock` is held and a second daemon that fails to start never
  touches the running one's log), call
  `util::log::install_daemon_log(&daemon.ctx.config.data_directory)` (on an
  error, log it and keep logging to stderr), and publish the returned path as
  `DaemonEndpoints.log_path` and `DaemonStatus.log_path` (for example a
  `BuildOptions.log_path` read by `build_with`, or a setter on `Daemon` that
  stores the endpoints and re-sends `set_daemon`). Not in `build_with`
  itself: in-process test daemons call it, and the first install of a
  process wins. Reason: §14 WP4.2 task 1 (`data/logs/orchestrator.log` for
  every daemon) and CCR-WP3.4-2 (`DaemonStatus.log_path` is always `None`;
  the desktop's Log button falls back to `DATA/logs/orchestrator.log`).
  Neither file is owned in Wave 4. Adapter: `RealLauncher::new` (built once
  per daemon, after the lock) calls `util::log::adopt_desktop_log`, so the
  daemon the desktop starts (stdout and stderr appended to
  `DATA/logs/orchestrator.log`) already writes the rotating JSON-line log the
  Log button opens; a console daemon keeps logging to stderr until the CCR.
  With the CCR applied, a console daemon writes the file and tees its events
  to the terminal; the test harness's `daemon.log` keeps receiving every
  event (tee), so no test changes.
- **CCR-WP4.2-2 (`src/core/inbox.rs`, `src/worker/activator.rs`; WP4.4 owns
  both in Wave 4; or WP4.INT).** CCR-WP2.3-3, re-filed unchanged:
  `SliceOutcome` reports the rows a slice moved to `retry` (ids or a count)
  so `activation.retried` counts them. Deferred to WP4.2 by WP3.INT, but it
  lands in no file WP4.2 owns (§13 rule 1). Adapter: as before,
  `activation.retried` counts slow-path preparation and commit failures
  only (telemetry; no behaviour depends on it).
- **CCR-WP4.2-3 (information for WP4.1).** WP4.1's tokens and per-peer
  secrets stay out of logs by construction here: fields named `token`,
  `secret`, `credential`, … are redacted by `util::log`, the Ready line is
  redacted before `worker.log`, and the diagnostics bundle scrubs `*.token`
  files and the token fields of `worker.json`/`runtime.json`. WP4.1 may also
  call `util::log::register_secret` when it loads or creates a token or a
  per-peer secret, so a secret that reaches a log through free text (an
  error message) is scrubbed too. `tests/logging.rs::secrets_of` already
  greps for the values of any catalog table or setting named like a secret,
  token or credential, so WP4.1's `peer_credentials` is covered after the
  merge.
- **CCR-WP4.2-5 (`src/orchestrator/objects.rs`,
  `src/orchestrator/inbound_objects.rs`, `src/runtime/objects_rpc.rs`,
  `src/core/demand.rs`, `src/core/transfer.rs`; WP4.5 owns them in Wave 4,
  or WP4.INT).** Requested: an idle bulk lane does no O(objects) work per
  sync interval. Reason: the Wave 4 floor `scale_idle_worker_cpu` (idle
  worker CPU ≤ 1 % at 5K events / 10K objects, interval 500 ms) measures
  17.9 % (`qual_scale::idle_worker_cpu`). Isolated by this package (release,
  two daemons, `synced_replicas`, 10 s windows, the busier worker of A/B):
  | content | lanes | A | B |
  |---|---|---|---|
  | 5K events, 0 objects | 3 (2 bulk) | 0.6 % | 0.5 % |
  | 0 events, 10K objects | 3 (2 bulk) | 9.7 % | 17.0 % |
  | 5K events, 10K objects | 1 (1 bulk) | 5.6 % | 6.3 % |
  | 5K events, 10K objects | 3 (2 bulk) | 11.7 % | 17.7 % |
  | 5K events, 10K objects, peer daemon stopped | – | 0.0 % | – |

  Neither worker's database changes while idle (`PRAGMA data_version` and a
  hash of every table were constant over 6 s on both), so it is not the
  status cell's content scan (it is cached until the database changes) nor
  the metadata exchange (0.5 % with 5K events and no objects): the cost
  scales with objects × bulk lanes, i.e. the objects v3 rounds that each
  bulk lane runs every interval in both directions (`DriveOptions::new(
  REPOS_PER_LANE, interval)`: worker `objects.want` and the peer's
  `objects.wants`, each an O(objects) wanted-set computation on a worker,
  plus the acceptor side). A fix could skip a round whose triggers (local
  and remote feed tips, content counters, `generations.sync`, a lease or
  backoff expiring) did not move since a round that found nothing, or cache
  the worker's wanted set by its demand/availability generation. Adapter:
  none (the floor fails in the evidence).
- **CCR-WP4.2-4 (information for WP4.3).** New environment variables:
  `TKFS_LOG_ROTATE_BYTES`, `TKFS_LOG_ROTATE_FILES`; log locations
  (`DATA/logs/orchestrator.log` 10 MiB × 5, `STATE/worker.log` rotated at
  spawn past 10 MiB, 5 files); `tkfs manage diagnostics` and the bundle
  layout (this file, Summary 3); `qualify.ps1 -All` budgets.
