### The controller (§3.3)

- **One thread per folder** (`folder-<state>`). Its mailbox carries commands
  (with an optional reply for `request`), launcher `ProcessEvent`s,
  heartbeats and watch failures from the watch thread, worker RPC results
  (the mount attach result among them), `Shutdown{deadline}` and `Retire`. It
  loops `recv_timeout(next deadline)` (capped at 2 s) and publishes a
  `Snapshot<FolderView>` after every step.
- **The actor never blocks on a worker.** Every worker RPC (`hello`, `stop`,
  `mount-attach`/`detach`, `published-summary`, `revalidate`, the legacy
  `status`/`stop`) runs on a short-lived helper thread and comes back as
  `Msg::Rpc(ticket, kind, result)`; a result whose ticket is no longer
  current is ignored. The only blocking calls on the actor thread are
  in-memory sinks, `catalog.apply` (one SQLite transaction in the catalog
  actor), `launcher.launch/adopt/client`, `WorkerProcess::kill`, and reading
  `worker.json`/`runtime.json` and probing `owner.lock`.
- **Phases are derived, never stored.** The sub-states `failed`, `stop`
  (a `StopPlan`), `start` (`Adopt | Legacy | WaitLock | Spawned`),
  `backoff_state` and `running` map to `FolderPhase` in that precedence, so a
  phase cannot disagree with the plan driving it.
- **Start**: if `STATE/worker.json` names this repo/device, `launcher.adopt`;
  `Some` → `Starting{adopting}` and `hello` (2 s): identity (instance, repo,
  device) must match; same version and `ipc == 3` → `Running{adopted}`;
  another version → graceful stop, then spawn; silent → retried every 1 s
  until 30 s → `Failed{PREVIOUS_WORKER_UNRESPONSIVE}` (no kill). `None`
  (dead or foreign image) → never killed. Without `worker.json`, a matching
  `runtime.json` takes the legacy orphan path (`status`, then `stop`). Every
  spawn waits until `owner.lock` is free (invariant 23).
- **Spawn**: `LaunchSpec{supervised: true, log: STATE/worker.log}`;
  `startup::Watchdog` observes progress lines; Ready is validated
  (repo/device → `WORKER_STATE_MISMATCH`, `ipc != 3` →
  `WORKER_IPC_MISMATCH`; both kill the worker and end in `Failed`); the
  `token` is copied from Ready (and from `worker.json` on adoption) into
  `WorkerEndpoint`.
- **Failures**: exits are classified from the FatalLine (its class) or the
  exit code (75 → `ALREADY_RUNNING`, other → `WORKER_EXITED`; no code from an
  adopted worker → `WORKER_EXITED` "its exit code cannot be read"). Transient and
  Contention back off (`util::Backoff`, 1 s · 2^(n-1), cap 300 s, ±20 %,
  reset after 10 min Running); NeedsUserAction, Fatal and Incompatible go to
  `Failed`; 5 counted failures within 10 min → `Failed{CRASH_LOOP}`. Failed
  leaves only on Retry, Start, Restart or a catalog change for this folder,
  also when it still holds a live process (`PREVIOUS_WORKER_UNRESPONSIVE`,
  or a worker that survived its kills): the untrusted handle is dropped (never
  killed) and the start adopts the worker again (`hello`) or waits for
  `owner.lock` (fix round 2).
- **Stop ladder**: `Stop`/`ForceStop` persist `desired=0` first
  (`CatalogCmd::SetDesired`, skipped when the catalog already has it), then
  graceful `stop` (5 s). `BUSY_VIEW` → `StopBlocked` (reason = the worker's
  error, `last_error = STOP_BLOCKED_BY_OPEN_FILES`, open handles and unsaved
  files from the heartbeat), retried every 2 s; `Start` cancels it.
  `ForceStop` → `stop{force}` (15 s), wait 10 s for the exit, then a verified
  kill (`WorkerProcess::kill`); a second kill after 10 more seconds, then
  `Failed{WORKER_STOP_TIMEOUT}`. A worker that has not printed Ready is
  killed directly. Nothing is spawned before the exit event of the previous
  process. `Restart` is this ladder followed by a start, in every phase that
  has something to stop: Running, Stopping/StopBlocked, and Starting (a
  spawned worker is killed directly, an adopting one gets the graceful stop
  like `Stop`, a lock wait or the legacy path starts over; fix round 2).
- **Shutdown{deadline}** (real time): no `SetDesired` ever. Running and
  adopted workers get one graceful stop capped by the remaining budget:
  exit observed → `stopped`; `BUSY_VIEW`, any error or the deadline →
  `left_running`. A spawned worker still Starting is killed → `killed`
  (`shutdown_kill_starting`). No worker → `not_running`. An unresponsive
  adopted worker (`Failed`) → `left_running`. The controller thread then
  exits; liveness kills and restarts are suppressed while shutting down.
- **Liveness**: a dedicated client (a second `launcher.client(endpoint)`)
  loops `watch{after_seq, wait_ms: 2000}` with a 4 s deadline. No heartbeat for
  8 s, or 3 consecutive watch failures → `hello` (2 s); failure →
  `WORKER_UNRESPONSIVE`, verified kill, Backoff. A heartbeat from another
  instance counts as a failure. `engine.stalled` → `degraded` (no kill).
- **Gate and mount**: the worker's heartbeat is the mount state's source,
  except the first heartbeat after a `mount-attach`/`mount-detach` result,
  which may predate it and is not merged (fix round 2).
  `mount-attach{path}` (60 s) only while Running, not stopping, `mount_enabled`, a path set, the gate `None|Satisfied|Overridden`,
  and the worker's mount state known (Ready line or first heartbeat, so an
  adopted, already attached worker is not attached again). `Attached` →
  `CatalogCmd::ClearGate` (retried every 2 s if the catalog write fails);
  NeedsUserAction → held until `Attach`, `OverrideGate` or a mount change;
  Transient → 2 s → 120 s. `Detach{force}` → `mount-detach` and no automatic
  re-attach until `Attach`. Gate evidence from the source installation:
  caught up → `Satisfied`; caught up but blocked → `Blocked` (+ `GATE_BLOCKED`
  in `last_error`, resolved once the gate is `Satisfied`, `Overridden` or
  gone); otherwise `Awaiting{waiting_on}`. `Revalidate` reopens a Blocked gate.
  When the source peer is unpaired the gate is retargeted (below).
- **Published entry**: `published-summary` (3 s) on Running, when the
  heartbeat's `generations.branches` changes, and every 60 s while the
  entry is `unavailable`. A summary taken before the first heartbeat (the one
  on Ready, usually) has an unknown branches generation, so the first
  heartbeat after it requests one more (one extra call per start); tip, content and sync generation follow each
  heartbeat (an update only when they change). A failure marks only the
  entry `Unavailable{PUBLISHED_SUMMARY_FAILED: …}` and `published_error`.
  `SetSync{false}` → `Paused`. The entry is removed when the worker is gone.
- **Status**: `StatusEvent::FolderLifecycle(view)` whenever the view changes
  other than by its heartbeat; `StatusEvent::WorkerHeartbeat` per heartbeat;
  `FolderRemoved` on retire, and nothing for that folder after it (the retired
  controller still updates its own `Snapshot<FolderView>` while it stops the
  worker, but sends no more status events; fix round 2).

### The registry

- `Tracked<Inner>` (`folder-registry`, 50 ms debug hold check) maps
  `state → {tx, Arc<Snapshot<FolderView>>, client slot}` plus `repo → state`;
  held for map operations only.
- `start` spawns a controller per catalog folder, then a `folder-registry`
  thread that waits on `catalog.wait_newer` (500 ms slices): new folders get a
  controller, removed ones `Retire` (graceful stop, `FolderRemoved`), the rest
  `CatalogChanged` (each controller re-reads its own record, gate and the
  peers from the current snapshot). A retired controller ends once it owns no
  process; a busy worker (StopBlocked) and a `Failed` folder's live process
  (unresponsive, or survived its kills) are left running, and Retire
  overrides whatever a kill in progress would have done next (Backoff, Fail).
- `reconcile` holds a `reconciling` mutex for its whole run (channel sends and
  controller thread spawns; no catalog or worker call), and `shutdown` takes
  it once after setting `stopping`: every controller a reconcile spawns is in
  the map before shutdown collects the handles, or none is spawned.
- `generation`/`wait_newer`: a `Notify` poked by every published view.
- `maximum_running`: `Slots` shared by all controllers. A Start without a slot
  answers `WORKER_LIMIT` (`send`/`request` pre-check it; a controller that
  starts from a catalog change records it in `last_error`), and the folder is
  started when a slot frees (the legacy 2 s reconcile did the same).
- `shutdown(deadline)`: `Shutdown` to every controller in parallel, outcomes
  collected until the deadline (+250 ms); a controller that did not answer is
  `left_running` with `REQUEST_TIMEOUT`. Afterwards `send`/`request` answer
  `ORCHESTRATOR_STOPPING`; a second call returns the same outcomes.
- `request(state, cmd, wait)` returns the view once the command has settled
  (Stop, ForceStop, Restart: no longer Stopping, so `Stopped` or
  `StopBlocked`; Attach/Detach and Revalidate: their RPC answered; everything
  else: processed). When `wait` elapses it returns the latest view.

## Deviations from the spec, and why

1. **`LifecycleLimits` gained `worker_version: String`**, plus
   `LifecycleLimits::new(executable, maximum_running)` and `Default` (the
   `model::orchestrator::limits` values). Adoption must compare
   `hello.version` with the version this orchestrator would spawn, and no
   shared version string exists yet (CCR-WP1.2-2). The default is the package
   version; without `+build` metadata only the part of `hello.version`
   before `+` is compared, so `0.1.0` matches `0.1.0+6298d0b`; empty accepts
   any version. A literal built with `..LifecycleLimits::default()` keeps
   compiling.
2. **`ManualClock` is `util::time::ManualClock`** (frozen in Wave 0), not a
   copy in the test file; the fakes (`FakeLauncher`, `FakeWorkerClient`, …)
   are in the test file.
3. **`startup::Watchdog` has a fixed 30 s `LEEWAY`.** To honour
   `LifecycleLimits::startup_silence`, the controller passes
   `now + (LEEWAY - startup_silence)` to `Watchdog::expired` (exactly
   `now - last_progress >= startup_silence`). `startup.rs` belongs to WP1.4.
4. **`owner.lock` is probed before every spawn** (`orchestrator::lock_state`,
   released at once), including after a version-mismatch replacement and the
   legacy orphan stop. While it is held the folder shows
   `Starting{phase: "waiting for the previous worker to release owner.lock"}`
   for up to `limits::ADOPT_LOCK_WAIT` (10 s, polled every 250 ms), then fails
   Transient with `PREVIOUS_WORKER_STOP_TIMEOUT` (Backoff, then the breaker).
   The legacy code waited 5 s.
5. **Adoption is tried on every start**, not only when the controller starts:
   a `worker.json` of a dead worker is answered `None` by the launcher, so this
   is the same path as before, and a worker left running (for example by an
   earlier Shutdown) is never doubled. A record of an instance this
   controller replaced for a version mismatch is not adopted again. An adopted
   worker that dies during its `hello` probe is replaced at once (not counted
   as a failure).
6. **A graceful Stop of a `Failed` folder whose process is alive**
   (`PREVIOUS_WORKER_UNRESPONSIVE`, or a worker that survived its kills)
   persists `desired=0` and keeps it `Failed`; only ForceStop kills it (§3.3:
   "the user can ForceStop"). A `Retry` of such a folder while `desired=0`
   has nothing to start and also keeps it `Failed` (fix round 2): clearing
   it would show `Stopped` with a live worker behind it. `Start` (or a Retry
   once desired) adopts the worker again.
7. **A graceful stop RPC that fails uncertainly** (timeout, lost connection)
   triggers a `hello` probe: an answer retries the graceful stop after 2 s; no
   answer is the liveness rule (Unresponsive → verified kill). Remote errors
   other than `BUSY_VIEW` are treated like it (StopBlocked with that reason):
   a refusal is never escalated without ForceStop.
8. **`Stopping → Backoff (crashed while stopping)`** applies to stops that
   would restart (Restart, version replacement): a known non-zero exit code
   we did not cause (no kill of ours) is a counted failure. Without an exit
   code, a spawned worker (our child) was terminated by a signal: a crash.
   An adopted worker is not our child, so its code cannot be read (WP1.3's
   Unix pid probe reports `None`): its exit is the stop it was asked for
   (acknowledged, in flight, or lost with the connection), unless it had
   refused that stop (StopBlocked) and no retry was in flight. A stop that
   ends in Stopped ignores the exit code. Kills for Unresponsive and watchdog
   expiry also end in Backoff; Ready mismatches end in Failed.
9. **The controller persists intents itself** (Start/Restart `desired=1`,
   Stop/ForceStop `desired=0`, OverrideGate), skipping the write when the
   catalog already has the value. WP2.1/WP2.2 writing first (as §3.5 says)
   stays compatible. Catalog-driven changes (`CatalogChanged` with a new
   `desired_running`) never write.
10. **Gate retarget on unpair**: the controller has no remote catalogs, so a
    "peer sharing the repo" is a paired installation that has sent gate
    evidence for this folder. When the source is gone: retarget to such a
    peer (`CatalogCmd::RetargetGate`) at once, or else to the next paired
    peer whose evidence arrives. `Satisfied` stays in memory until the attach
    succeeds; after a daemon restart the gate is `Awaiting` again
    (conservative: invariant 26).
11. **`FolderCmd::Revalidate` runs the worker `revalidate` RPC itself** and
    reopens a Blocked gate. The `requeued` count is not part of `FolderView`;
    WP2.2 can call `FolderDirectory::client(state)` for it (and should then
    still send the command, or the gate stays Blocked).
12. **Mount state in the view**: the worker's heartbeat is the source, merged
    with the controller's own retry schedule (`next_retry_at_ms`, `None`
    while held for user action).
13. **`env!(stringify!(CARGO_PKG_VERSION))`** instead of the quoted name: the
    WP0.4 code-literal scan reads `"CARGO_PKG_VERSION"` as an unclassified
    error code (CCR-WP1.2-1).

## Fix round 1 (review of `c6ffb15`)

Every finding was accepted. The tests that cover findings 1-4 failed on
`c6ffb15` and pass now (list under VERIFY); finding 5 is a message fix.

1. **Major: an adopted worker's exit without an exit code was a crash.**
   `on_exit` counted `code != Some(0)` as "crashed while stopping", but WP1.3
   reports `code: None` for an adopted worker on Unix (its 1 Hz pid probe
   cannot read the code of a process that is not its child; checked in
   `revamp/wp1-3-process-launcher`, `process.rs` `probe_adopted` →
   `report_exit(events, None)`). Every Restart of an adopted worker and every
   version-mismatch replacement then ended in Backoff with `WORKER_EXITED`,
   counted toward `CRASH_LOOP`. Fix: `crashed_while_stopping` (deviation 8
   has the rule); it is evaluated before the worker's RPC tickets are
   dropped, because "a stop RPC in flight" is part of the rule (the exit can
   race the stop reply). `classify_exit` words an adopted worker's missing
   code as "its exit code cannot be read" instead of "terminated". The fake
   now reports `code: None` for an adopted worker's exit after `stop` (Unix
   semantics, the default) or `Some(0)` with `adopted_exit_known(true)`
   (Windows: WP1.3 reads the code through a process handle). Tests:
   `adoption_version_mismatch_stops_then_spawns` runs both variants,
   `restart_of_an_adopted_worker_spawns_at_once_whatever_its_exit_code`
   (both), `adopted_worker_that_refused_a_restart_and_died_counts_as_a_crash`
   (the "never acknowledged" side), and
   `restart_whose_spawned_worker_is_signalled_while_stopping_backs_off` (a
   spawned worker without a code is still a crash).
2. **Retire could leave the controller thread running.** (a) `on_retire` of
   a `Failed` folder with a live process now ends the controller and leaves
   the process running (as for a busy worker). (b) `stop_worker` lets Retire
   override any `after` (a kill bound for Backoff or Fail), and a new
   `end_if_retired` (after every loop step) ends a retired controller once it
   owns no process or has given up on it (`Failed`, for example
   `WORKER_STOP_TIMEOUT` after the kills). Tests:
   `retiring_a_failed_folder_leaves_its_unresponsive_worker_and_ends_the_controller`
   and `retiring_during_a_kill_ends_the_controller_even_if_the_worker_never_exits`
   (the ended controller is observed through its released
   `maximum_running` slot; before the fix the slot stayed held forever).
3. **Reconcile/shutdown race.** Serialized with the `reconciling` mutex (see
   "The registry"). Shutdown waits at most for one reconcile in progress,
   which only sends on channels and spawns controller threads. Test:
   `shutdown_racing_catalog_additions_reaches_every_controller` (a thread
   keeps adding folders while shutdown runs; every controller left in the map
   and every launched worker must have a shutdown outcome).
4. **Published entry could miss a branch change at startup.** The first
   heartbeat after a summary whose branches generation is unknown now
   requests one more summary instead of adopting the heartbeat's generation
   silently. `PublishedSummary` (frozen, `model::ipc`) has no generation
   field, so the reply cannot carry it; one extra call per start is the
   price. Test: `published_entry_taken_before_the_first_heartbeat_is_refreshed_once`
   (the watch is held until the branches change; the fake's summary label
   names the branches generation it saw; exactly 2 summaries afterwards).
5. **`WORKER_STOP_TIMEOUT` message** had about 30 spaces inside the literal;
   it now ends the line with `\`.

Test-file changes besides the new tests (no assertion was weakened or
removed):

- `adoption_version_mismatch_stops_then_spawns` loops over both exit-code
  variants and also asserts one launch and no `last_error`.
- `published_summary_failure_marks_the_entry_unavailable_and_branch_changes_refresh`
  waits for the first heartbeat before it lets the retried summary succeed.
  Without that wait the retry could be taken before any heartbeat, and the
  intended extra summary (item 4) would then land inside the "tip follows the
  heartbeat without an RPC" window, which counts summary calls. The
  assertions are unchanged; the failing call count now also prints the log.
- Fakes: `Mode::Hold` for `watch`, `FakeWorker::clean_exit`,
  `FakeLauncher::adopted_exit_known`, and a summary label `fake-b<branches>`
  (no test read the old constant label).

1. **Blocker: a `Failed` folder holding a live process could not be
   started again.** `cmd_start` cleared `failed` (`reset_failures`) before
   it tested `idle() || failed.is_some()`; with the worker handle still held
   neither was true, so nothing started and the view showed `Stopped` with
   `desired_running = true`, a held slot and a stale error. Fix: `cmd_start`
   remembers `was_failed` before the reset and calls `begin_start` when
   `idle() || was_failed`. `begin_start` already drops the untrusted handle
   (never kills it) and adopts the worker again from `worker.json` (`hello`,
   30 s patience), or waits for `owner.lock` before any spawn (invariant 23).
   `cmd_retry` with `desired=0` on such a folder now keeps it `Failed`
   (deviation 6) instead of clearing `failed` and keeping the handle, so a
   later Start takes the path above. The same root cause also blocked the
   third exit from Failed: `on_catalog_changed` started a Failed folder on a
   change to its record or gate only when it held no worker; that condition
   is gone (same `begin_start` path). Tests:
   `start_of_a_failed_folder_holding_a_live_worker_adopts_it_again` (Start →
   `Starting{adopting}`, `hello` again, then `Running{adopted}` with the old

   the old `on_catalog_changed` condition restored.
2. **Major: lifecycle events after `FolderRemoved`.** The WP1.11 StatusHub

   stores the local `Snapshot<FolderView>` and pokes the registry's change
   notify, but sends no `FolderLifecycle`; heartbeats of a retired folder are
   not sent either (the hub drops them already, so this is only hygiene). The
   other option (send `FolderRemoved` last, from `finish`) was not taken: the
   folder is already gone from `FolderDirectory::all()` when the catalog
   drops it, so status would disagree with List for the whole stop. Test:

   `FolderLifecycle`, `WorkerHeartbeat` or second `FolderRemoved` for the
   folder after its `FolderRemoved`, while lifecycle events did precede it;
   one graceful stop, no kill, no published entry).
3. **Minor: `GATE_BLOCKED` stayed active after the block ended.** After every
   step, a `GATE_BLOCKED` `last_error` is resolved when the gate is `None`,
   `Satisfied` or `Overridden` (`resolve_gate_blocked`, which shares a new
   `resolve_error_code` helper with `resolve_stop_blocked`). `Revalidate`
   alone (gate back to `Awaiting`) leaves it active: the block is over only
   when evidence, an override or the attach says so. Tests: the two gate
   tests named above.
4. **Minor: Restart while Starting answered OK and did nothing.** It now
   runs the stop ladder with `AfterStop::Start` there too (the reviewer's
   first option): a spawned worker before Ready is killed directly and
   spawned again; an adopting worker gets the graceful stop, exactly what
   `Stop` already did in that phase (a silent one goes through the probe and
   a verified kill, as the stop ladder does for any silent worker); a lock
   wait or the legacy path, which own no process, start over. Tests:
   `restart_while_starting_kills_the_spawned_worker_and_starts_again` and
   `restart_while_adopting_stops_the_adopted_worker_then_spawns`.
5. **Found during verification: a stale heartbeat could undo an attach
   result.** Stress runs (12 parallel copies of the test binary in WSL)
   failed `needs_user_action_attach_is_not_retried_until_attach` once with 3
   `mount-attach` calls instead of 2. A `watch` already in flight when the
   attach answered returned the earlier `AttachFailed` state; merged after
   the result, it re-armed the attach and sent a redundant `mount-attach`
   (against a real worker that is at best a wasted call, at worst an error
   on an attached mount and a flicker of `AttachFailed`). The watch loop is
   sequential and the mailbox FIFO, so only the first heartbeat handled after
   a `mount-attach`/`mount-detach` result can predate it: its mount state is
   now not merged (`MountCtl::stale_heartbeat`, set by `on_attach` and

## Known limitations

- Standalone: the real launcher, adoption FFI and JSON client are WP1.3, the
  worker ops (`hello`, `watch`, `stop{mode}`, `mount-*`) WP1.4/WP1.5; nothing
  calls `FolderRegistry::start` until WP2.1.
- Controller threads live until `shutdown` or retire: dropping the registry
  without `shutdown` leaves them running (the daemon always shuts down).
- One helper thread per worker RPC; superseded RPCs (for example a graceful
  stop overtaken by ForceStop) run until their own deadline.
- A panicking controller publishes `Failed{UNKNOWN_ERROR}` and its thread
  ends; `send` then answers `FOLDER_UNAVAILABLE` until the daemon restarts.
- `Satisfied` is not persisted (deviation 10), and evidence freshness is the
  sender's job (the Wave 2 bridge applies the 15 s legacy rule).
- `maximum_running` counts folders holding a worker, including adopted ones;
  an adoption beyond the limit (limit lowered between daemon runs) is refused
  with `WORKER_LIMIT` and the orphan keeps running unmanaged until a slot
  frees.
- A folder that leaves the catalog and comes back under the same state name
  while its retired controller is still stopping the worker gets a second
  controller at once. The two share that state's `maximum_running` slot key
  (the old controller's release frees it while the new one runs), and the new
  one may adopt the worker the old one is stopping. Retiring an idle or
  quickly stopping worker takes milliseconds, so this needs a remove and
  re-add within one stop; WP2.x can refuse the re-add until the old
  controller has ended (found while fixing round 2, not changed).
- Start, Retry and a catalog change of a `Failed` folder whose worker
  survived its kills (`WORKER_STOP_TIMEOUT`) adopt that worker again when its
  `worker.json` names it, or wait for `owner.lock` (10 s, then
  `PREVIOUS_WORKER_STOP_TIMEOUT` and Backoff) when it holds the lock without
  a record. A process that can be neither killed nor reached ends in
  `Failed` again (`PREVIOUS_WORKER_UNRESPONSIVE`, or `CRASH_LOOP` after
  repeated lock timeouts); a second worker is never spawned beside it.
