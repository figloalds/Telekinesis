# WP1.12 Interim stabilizers on the legacy lanes and supervisor: notes

Branch `revamp/wp1-12-legacy-stabilizers`, cut from `revamp/wave-1-base` (`abc8234`).

These changes ship in the wave 1 releasable point and are replaced by WP2.1 (supervisor, Shutdown)
and WP3.1 (legacy lanes). They are deliberately small. Nothing on the wire changed: every request,
reply and hello is the same JSON a 6298d0b peer sends and accepts. The legacy status JSON gains
additive members only (`busy_retries` per repository, `folders` in the Shutdown reply), which the
compat goldens allow (`assert_same_shape` ignores extra keys).

## Summary of changes

### `lanes.rs` (task 1)

| Task | Implementation |
|---|---|
| Charge `connection_failed` to the in-flight repository | The exchange result is always recorded on the repository (`RepositoryStatus::failed`) **before** a transport failure drops the lane (the old code returned first, `:1350-1352`). A drop caused this way is a *charged* drop: the lane reconnects after the base delay (1 s) **without** escalating the lane backoff, because the fault belongs to the repository, which now backs off on its own (1 s → 30 s). |
| Rotate the catalog start every pass | `rotate_catalog(&mut catalog, pass)`; `pass` lives for the lane's lifetime (across reconnects), so every repository leads a pass in turn. |
| Ping at least every 5 s while waiting | `lane_wait(.., Some(&mut socket), KEEPALIVE = 5 s)` sends the existing `ping` op during the between-pass wait. Any `sync_interval_ms` up to 60 s therefore stays under the acceptor's 15 s idle drop. A failed ping is a lane failure (reconnect). The reconnect wait passes no socket and does not ping. |
| Reset per-repository backoff when the local worker address changes | Each lane remembers the local worker address it last used per repository. Discovery now runs before the backoff check, and a changed address (restarted worker) calls `RepositoryStatus::reset_backoff()` (`consecutive_failures`, `busy_retries` and the retry time are cleared; the last error stays until the next success). |
| Clear the bulk inventory cache on any bulk error | On any failed parallel-bulk exchange the cached remote inventory **of that route** is removed (see deviations). A reconnect still clears the whole cache, as before. |
| Reset connection backoff only after 30 s of healthy passes | The lane uses `util::backoff::Backoff::lane()` (1 s → 60 s, ±20 %, reset after 30 s): every completed pass calls `success(now)`, every uncharged drop calls `failure(now)`. The old code reset the counter after every single pass. |
| `connected=true` only after the first successful request | `connected` is set after the pass's first request (`list` on lane 0, `ping` on bulk lanes) succeeds, not right after the dial. |

All `shared.lock().unwrap()` in `lanes.rs`, `peering.rs` and `run.rs` became `util::lock::lock`
(poison-tolerant).

### `status.rs` (task 2)

- `RepositoryStatus::failed(&error) -> bool` (returns `true` for Contention). An error is Contention
  when **any** code in its chain is classified Contention by `model::errors::classify`
  (`WORKER_BUSY`, `BUSY`, `BUSY_VIEW`, `IN_FLIGHT_ELSEWHERE`) or is `LOCAL_WORKER_UNAVAILABLE`.
  The whole chain is scanned with the frozen `code_in` token rule, because the lane wraps worker
  errors in its own context (`LOCAL_SYNC_OFFER_FAILED: WORKER_BUSY`), so `code_of` (first code)
  would return the wrapper.
- Contention: `busy_retries += 1`, retry eligible after 50, 100, then 200 ms; `error`,
  `consecutive_failures`, `caught_up` and `metadata_caught_up` are untouched.
- Every other error: as before (`consecutive_failures += 1`, `caught_up = false`, `error` set,
  1 s → 30 s), unchanged.
- `succeeded` also resets `busy_retries`. New `reset_backoff`.

### `run.rs` (task 3)

- A `peers()` error in the main loop is logged
  (`util::log::event!(warn, "CATALOG_UNAVAILABLE", {error, kept_peers})`, rate limited) and the last
  good list is kept. The daemon no longer exits on one SQLite error (`:1458`).
- Poison-tolerant locks.
- Supervision cadence: `reconcile` runs every 500 ms (was 2 s), and earlier when a backed-off
  restart falls due (`Supervisor::next_reconcile`). Without this a 1 s restart backoff could not be
  honoured, and exits were noticed up to 2 s late.

### `supervisor.rs`, `catalog_db.rs` (task 4)

- **Restart backoff.** `Supervisor.restarts: BTreeMap<state, Restart{backoff, not_before}>`.
  A worker failure in `reconcile` (exited, start timeout, state mismatch) or a failed launch calls
  `defer_restart`: `Backoff::new(1 s, 60 s, ±20 %, reset after 60 s)`. `reconcile` launches a
  desired folder only when `now >= not_before`. A Ready worker reports `success` every tick, so the
  attempt counter returns to zero after 60 s of running. An explicit `Start`/`Create`
  (`Supervisor::start`) forgets the backoff and launches at once; `reconcile` uses the private
  `launch`.
- **Orphan probe only when `owner.lock` is held.** `launch` first tries `owner.lock`: when it is
  free no worker can be running, so the `runtime.json` status/stop probe is skipped. Before, every
  restart of a crashed worker (whose stale `runtime.json` points at a closed port) paid a refused
  connect under the supervisor lock (1-2 s on Windows), which made `List` block during crash loops.
  When the lock is held the probe runs exactly as before (invariant 23 is unchanged: a second
  worker still cannot take `owner.lock`).
- **Ready with `mounted:false` + `mount_error`.** `ready_mount(line, project, requested)` checks the
  Ready line. A requested mount that the worker reports as failed (`mounted:false` with
  `mount_error`, an `ErrorWire` object per `model::ipc::ReadyLine`, or a string) is accepted: the
  worker is Ready, `Worker.mounted = false`, `Worker.mount_error` is kept and shown as the folder's
  `error` (it survives the per-poll failure clearing), and the worker is not restarted. `mounted:false`
  without `mount_error` when a mount was requested, `mounted:true` when none was, and repo/device
  mismatches are still `WORKER_STATE_MISMATCH`.
- **Shutdown.** `Supervisor::shutdown_folder(state) -> ShutdownOutcome` (`stopped`, `killed` for a
  worker that was still starting, `left_running` when stopping failed and the process is alive,
  `not_running`), built on `stop_outcome`; `stop()` is now a wrapper with the old signature.
  `reconcile` is a no-op once `stopping` is set, so a reconcile that was waiting for the lock cannot
  relaunch the folders Shutdown just stopped.
- `catalog_db.rs`: `Supervisor::open` initialises `restarts`.

### `api.rs` (the `Shutdown` arm only)

`stopping` is set first, then every folder is stopped with `shutdown_folder`, continuing past
failures. The reply is `{"stopped": true, "folders": [ShutdownOutcome…]}`; `stopped` keeps its
golden value. `desired_running` is never changed (invariant 26).

### `peering.rs` (task 5)

- `DeadlineLane`: a loopback worker connection for `published-summary` with a hard per-call
  deadline. It mirrors `runtime::RpcLane` (reuse, 10 s idle reconnect, reconnect on an address
  change, dropped after any transport error, never replayed) and sets the socket read/write timeout
  to what is left of the deadline after connecting. A socket timeout becomes
  `REQUEST_TIMEOUT: no reply within 3000 ms`.
- `published()` asks every running worker **concurrently** (scoped threads; inline for one worker),
  each under `model::ipc::deadlines::PUBLISHED_SUMMARY` (3 s). A failing or timed-out worker is left
  out and recorded as that folder's `publication_error`
  (`PUBLISHED_SUMMARY_FAILED: REQUEST_TIMEOUT: …`), exactly as other summary failures were.
  `serve_peer` keeps a separate `DeadlineLane` map for summaries; the exchange paths keep `RpcLane`.

## Deviations from the spec, and why

1. **Bulk inventory cache: the failing route's entry, not the whole map.** "Clear the bulk inventory
   cache on any bulk error" is implemented by removing the cached remote inventory of the repository
   whose exchange failed. The cache is keyed by repository, and the defect it fixes (RC13: a stale
   entry gives `BULK_ROUTE_MISMATCH` until reconnect) is per route. Clearing every entry would make
   every *other* repository's next upload page empty each time one repository fails (for example a
   persistent `CORRUPT_OBJECT`, as in `failed_repository_does_not_starve_healthy_folders_on_the_same_lane`).
   A reconnect still clears the whole cache.
2. **Contention retry delay without an early wake.** The 50-200 ms Contention delay makes the
   repository eligible again; it is retried on the lane's next pass, which still follows
   `sync_interval_ms`. I implemented and then removed an early wake: a woken pass re-runs the local
   `published-offer` (an O(repository) scan, RC2) and, on lane 0, a `list`, so a remote worker that
   stays busy for seconds would have multiplied that CPU and traffic by up to 10× per lane.
3. **Contention is hidden from `error`.** §8 says Contention is "hidden unless ≥ 30 s"; the legacy
   projection has no duration field, so Contention never writes `error`. It is visible as the new
   `busy_retries` counter. `qual_wp1_12_legacy::worker_busy_not_counted` was extended to observe
   `busy_retries` (and still fails any sample where a `WORKER_BUSY` error is counted).
4. **`LOCAL_WORKER_UNAVAILABLE` is Contention on the lanes only.** The package says so explicitly;
   §8 lists it as Transient. The rule is local to `status::is_contention`; `model::errors` is frozen
   and unchanged.
5. **Lane backoff cap 60 s (was 30 s) and jitter.** The lane uses `Backoff::lane()` (§8: lanes
   1 s → 60 s), which also provides the 30 s healthy reset the package asks for.
6. **Charged drops do not escalate the lane backoff** (see the `lanes.rs` table). Escalating them would
   push the healthy repositories on the same lane towards the 60 s cap whenever one repository's
   requests time out, which is the head-of-line stall this package removes.
7. **`published()` is concurrent**, not only bounded per worker: with several hung workers a
   sequential 3 s per worker could still exceed the dialer's 15 s `list` budget (5 × 3 s).
8. **Reconcile cadence 500 ms** (was 2 s) plus deadline scheduling, required to honour a 1 s restart
   backoff (see `run.rs`).
9. **The mount-failure acceptance test is `#[ignore]`d.** The worker in this wave's base still exits
   when its mount fails; WP1.4 (same wave) makes it print Ready with `mounted:false` and
   `mount_error`. The supervisor side is unit-tested here (`supervisor::tests::ready_line_*`), and
   `legacy_stabilizers::mount_failure_keeps_the_folder_syncing_headless` is written against the WP1.4
   Ready line, marked `#[ignore = "WP1.12: needs the WP1.4 Ready line …; WP1.INT un-ignores"]`.
   **WP1.INT: please un-ignore it after merging WP1.4.**

## CCRs filed

- **CCR-WP1.12-1** (`src/runtime/mod.rs`, owner WP1.4): add a deadline to `RpcLane`, for example
  `RpcLane::call_within(&mut self, info, request, payload, deadline: Duration)`, setting the socket
  read/write timeouts to the remaining deadline and dropping the connection after a timeout.
  *Reason:* the package text asks for "`RpcLane` with a short timeout" for `published()`, but
  `runtime/mod.rs` is not owned by WP1.12. *Adapter:* `orchestrator::peering::DeadlineLane`
  (same reuse/no-replay rules). The adapter can stay until WP2.1/WP3.1 delete this path; applying the
  CCR is optional.
- **CCR-WP1.12-2** (`src/orchestrator/api.rs`, outside the `Shutdown` arm): replace the remaining
  `shared.lock().unwrap()` in `manage` (the preamble, `Folder`, `Pair`, `Receive`) with
  `util::lock::lock`. *Reason:* the package makes the supervisor mutex poison-tolerant in every file
  it owns; after a panic under that lock, `manage` would still panic on every control request.
  *Adapter:* none possible from the owned files; the main loop, lanes and inbound paths are already
  tolerant.

## Known limitations

- **A hung remote worker drops out of the remote catalog.** With the 3 s summary deadline the
  acceptor leaves the hung folder out of `list`, so the dialer stops visiting it and prunes its
  repository status at the end of the next pass. The charge is visible on the lane that had an
  exchange in flight when the worker hung (until that prune), and on the acceptor as the folder's
  `publication_error`.
- **Unpatched (6298d0b) acceptors** still answer `list` serially with 15 s per hung worker; the
  dialer side then sees a lane-level failure (not charged, escalating backoff), as before.
- **The summary deadline does not bound the WebSocket upgrade.** `DeadlineLane` connects through
  `ws::connect` (3 s TCP connect timeout); the upgrade itself runs under `ws.rs`'s 15 s socket
  timeouts. A worker process frozen between `accept` and the upgrade response could still cost up to
  15 s once (the worker's accept and upgrade run on threads that never take the engine lock).
- **Contention never escalates.** `WORKER_BUSY` and `LOCAL_WORKER_UNAVAILABLE` are retried on every
  pass for as long as they last (no failure count, no `caught_up` reset), by design.
- **Shutdown is still sequential under the supervisor lock.** A folder whose stop RPC hangs costs
  that RPC's 15 s timeout; with such folders the control client's own 15 s read timeout can expire
  before the reply arrives, although the daemon finishes the shutdown and exits. Parallel stops under
  one deadline are WP2.1.
- **A failed mount is not retried.** The worker keeps syncing headless with the error reported until
  the folder is restarted (Stop/Start or ConfigureMount), as the package specifies.
