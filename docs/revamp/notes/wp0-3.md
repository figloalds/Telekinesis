### Verbatim check

ranges and asserts every original line is used exactly once (boundaries are
asserted by prefix). Afterwards a line-multiset comparison of the original
against all new files lists only these differences: the import list, the nine
`pub(super)` keywords listed below, module headers and hooks, the rewritten `open` (now phases), `view()` and
the `commit_ready` view patch (below), and `locks: Option<&crate::bulk_sync::ObjectLocks>`

### Open phases (`Store::open` → `open_with`)

Called in today's order, all on the opening thread:

1. `open_schema(root) -> Connection` (old `:338-361`)
2. `snapshot::initialize(&db)`
3. `open_identity(db, root, repo) -> Store` (old `:363-404`: legacy branches
   migration, identity, handle construction), then the empty hooks
   `objects::ensure_schema`, `inbox::ensure_schema`, `sharing::ensure_schema`
   (each `fn(&mut Store) -> Result<()>`)
4. `objects::startup_object_check(&mut store, options.verify)` (old `:405-455` verbatim)
5. `evacuate_unvalidated_journal` (with its progress line)
6. `rebuild_frontiers` (with its progress line)
7. `resume_or_rebuild` (old `:460-465`)
8. `inbox::startup_drain(&mut store, options.defer_activation)` (old `:466-467`; still drains)

New API: `pub struct OpenOptions { defer_activation: bool, verify: VerifyMode }`
(`Default` = `{false, Full}`), `pub enum VerifyMode { Full, Changed, Lazy }`,
`Store::open_existing_with(root, OpenOptions)` (`open_existing` delegates),
`Store::open_secondary(root, repo, device)` (alias of `open_transfer`). In
Wave 0 every mode behaves like `Full` and activation is never deferred.

### `StoreCaches`

`pub(crate) caches: StoreCaches { objects, inbox, commit, derive, sharing }`,
each an empty `#[derive(Default)] pub(crate) struct Cache {}` in its module.
`#[allow(dead_code)]` is set on the struct and the field because nothing reads
them yet (clippy `-D warnings`); owners remove it when they fill a cache.

### Oracle (`verify.rs`)

`Store::verify_derived_state(&mut self) -> Result<DerivedDiff>`:

1. `SAVEPOINT oracle`;
2. capture, per branch, the parsed `load_projection` (or "absent"), all
   conflict rows `(branch, id) -> (payload parsed with resolved_by cleared,
   resolved_by column)`, and all `event_frontier` rows;
3. `rebuild_frontiers()`, then `rebuild(branch)` for every branch;
4. capture again;
5. `ROLLBACK TO oracle; RELEASE oracle` (always, also on error);
6. clear the view cache;
7. compare parsed structs into `DerivedDiff { projection_mismatch,
   conflicts_missing, conflicts_extra, resolved_by_mismatch, frontier_mismatch }`
   (`is_empty()`; `Serialize`/`Deserialize` for evidence files).

A rebuild refusal (e.g. `NAMESPACE_HISTORY_LIMIT`, a corrupt payload) is
returned as the error after the rollback, so `Ok(empty)` also proves the
accepted history still rebuilds (WP1.7's refusal parity).

### View freshness (I6)

`view()`'s key is now `(branch, total_changes, PRAGMA data_version,
transactional)`. `data_version` is read with a cached prepared statement. In
`commit_ready`, the post-commit incremental patch of the cached view is applied
only if `data_version` still equals the value the view was loaded with;
otherwise the view is dropped. That read is infallible (`.ok()`) so a commit
can never report failure after it has committed. On a single connection the
behaviour is identical to before.

## Deviations from the spec

1. **`VerifyMode` lives in `core::objects`** (re-exported as
   `tkfs::core::VerifyMode`) rather than the root. `OpenOptions` (root) derives
   `Default` through `VerifyMode`'s `#[default]`. Reason: WP1.8 must make
   `open_existing` default to `Changed`, but WP1.8 does not own `core.rs`; it
   owns `objects.rs`, so it can move `#[default]` without a CCR. The W0 default
   is `{false, Full}` as specified.
2. **`open_identity` phase** is an extra named phase between
   `snapshot::initialize` and the hooks. The spec lists the phases but not where
   the legacy branch migration and identity read go; they stay in today's
   position. The schema hooks run after it so they receive `&mut Store`
   (database and root), which WP1.8's resumable backfills need.
3. **`ObjectLocks` is also re-exported from the core root** (in addition to
   `bulk_sync`). Harmless; it is the same type.

## Notes for WP0.INT and later owners

- **Glob imports:** `use crate::core::*` / `use tkfs::core::*` now also brings
  the module names `commit, demand, derive, inbox, objects, sharing, status,
  transfer, verify` and the types `OpenOptions`, `VerifyMode`, `ObjectLocks`,
  `DerivedDiff`. Explicit imports shadow them (e.g. `std::fs::OpenOptions` in
  `backend.rs`, `staging.rs`, `orchestrator.rs`, `tests/availability.rs`).
  A file that globs both `core::*` and another module exporting the same name
  (e.g. an orchestrator `status` module) gets an ambiguity error only if it
  uses that name unqualified. Nothing in the current tree does.
- **Engine reloads after foreign commits:** the data_version key also makes
  the *engine's* view reload after any commit by another connection, e.g.
  `bulk_sync::receive`'s `register_received` on a transfer view, which does not
  touch projection tables. A reload is O(projection) (`load_projection`).
  This is the behaviour the plan chose for I6. If it shows up in WP1.8/WP2.x
  qualification, a cheaper key is a projection generation counter bumped only
  by projection writes.
- WP1.6 owns `inbox.rs`/`commit.rs`: `startup_drain(store, defer)` and
  `inbox::ensure_schema(&mut Store)` are the frozen call sites in the root.
- WP1.8 owns `objects.rs`: `startup_object_check(store, verify)` and
  `objects::ensure_schema(&mut Store)` are the call sites; `VerifyMode`'s
  `#[default]` controls `OpenOptions::default()`.
- WP2.5 owns `sharing.rs`: `sharing::ensure_schema(&mut Store)`.

## Tests added (`tests/oracle_smoke.rs`)

- `oracle_empty_on_valid_histories`: sequential (creates, edits, rename,
  temp replacement, delete, directory move, basic metadata, a 140-save chain
  crossing a snapshot interval, then restart and snapshot resume); concurrent
  edits on two replicas before and after resolve; namespace collision before
  and after `recover` on both replicas; deleted parent with a concurrent child;
  concurrent directory cycle. The oracle is empty on every replica at every step.
- `oracle_detects_tampered_conflicts_and_frontier`: `UPDATE conflicts SET
  resolved_by=NULL` → `resolved_by_mismatch` only; `DELETE FROM event_frontier`
  → one `missing` frontier entry per deleted row; a deleted conflict row →
  `conflicts_missing`; a fabricated namespace row → `conflicts_extra`; a
  tampered stored projection → `projection_mismatch` names the entry.
- `oracle_has_no_side_effects`: every table's rows are identical before and
  after (on valid and on tampered state; differences are reported, never
  repaired); the savepoint is closed (`is_autocommit`); projection and
  conflicts unchanged; the store keeps committing afterwards; a rebuild error
  inside the oracle (corrupt event payload) is returned and fully rolled back.
- `secondary_handle_sees_engine_commits`: a warmed `open_secondary` handle sees
  the engine's creation, content and namespace fast-path commits and a
  full-replay commit (its projection equals the engine's); the engine sees
  creations and renames made through the other handle. Checked to fail
  without the `data_version` key (it fails at the first lookup after the
  engine's create).

No existing test or assertion was changed.

## Known limitations

- The oracle uses the same in-place repair as startup: `rebuild` never deletes
  register (non-namespace) conflict rows, so a stale register row that a fresh
  derivation would not produce is not reported as `conflicts_extra`. Stale
  namespace rows, missing rows, payload differences and `resolved_by`
  differences are reported.
- `VerifyMode::{Changed, Lazy}` and `defer_activation` are accepted but have
  no effect in Wave 0 (as specified).
- See "Engine reloads after foreign commits" above.
