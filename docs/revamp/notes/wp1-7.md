## Summary

A slow-path commit no longer re-derives the branch's whole conflict history.
`persist_projection(tx, branch, p, events, Some(E))` keeps its signature and
picks a mode from `TKFS_CONFLICT_MODE`:

| Mode | What a commit derives |
|---|---|
| `append` (default) | only what `E` can add, under an exactness precondition checked on every commit; otherwise full |
| `full` | the reference: every location pair, reviewed cut and namespace antichain, then the DELETE of namespace rows no longer derived |
| `verify` | both, each in its own savepoint; the full result is kept; any difference in conflict rows or `resolved_by` fails the commit with `CONFLICT_MODE_MISMATCH` |

A rebuild (`new_event == None`: startup repair, evacuation, the oracle, new
branches) always derives in full.

### `src/core/derive.rs`

- **API** (`tkfs::core::derive`): `ConflictMode { Append, Full, Verify }`
  (`parse`, `as_str`, serde lowercase); `conflict_mode()` (a thread override,
  else `TKFS_CONFLICT_MODE` read once per process through a `OnceLock`;
  unset or empty means `append`; an unrecognised value means `full`, with a
  stderr warning); `DeriveCounters` and `derive_counters()` (process-wide:
  rebuilds, full, append, fallbacks, verified, restricted, commit
  derivation time, checked commits). Test hooks, `#[doc(hidden)]`:
  `set_thread_conflict_mode`, `set_thread_commit_checks`,
  `thread_derive_counters`, `thread_last_fallback`,
  `thread_fallback_reasons`, and `Store::verify_derived_state_strict` (the
  CCR-WP1.7-1 adapter).
- **Append mode** (`derive_append`), in full mode's source order so that a
  refusal surfaces with the same error:
  1. structural guards (`append_guard`): no pending event; `E` is a sink (no
     committed event names it as a parent); the id-ambiguity guards below;
  2. `p.conflicts` and the stored rows `E` reviews (as in full mode);
  3. the location pairs that include `E`'s location change;
  4. `E`'s own reviewed cut, if `E` is a review;
  5. namespace history: `NsContext::append_plan` checks the cone
     precondition and lists the cones to derive; `derive_planned` derives
     them;
  6. register pairs (unchanged code: already new/old pairs only);
  7. the current-records check (`NsContext::current_records_survive`, new
     in fix round 1, see below);
  8. written without the namespace DELETE (`write_conflicts(.., false)`).
- **The cone precondition** (`append_plan`). For every cone of the new
  history that contains an entity whose kind, location or alive register
  `E` changes (the other cones are provably unchanged):
  - an old cone must keep every old relevant event
    (`relevant_O(C) ⊆ relevant_N(C)`); all its antichains are counted and
    the ones containing a newly relevant event (`E`, or a presence witness
    that `E`'s first tombstone brings in) are projected;
  - a new cone is derived in full;
  - an old cone that grew must be covered: `relevant_O(cone_O(x)) ⊆
    relevant_N(cone_N(x))` for a new cover, `relevant_O(cone_O(x)) ⊆
    relevant_O(cone_N(x)) ⊆ relevant_N(cone_N(x))` for an old one.
- **The current-records check** (`current_records_survive`). The stored
  rows also hold the old projection's namespace records (`p_O.conflicts` is
  a source of every rebuild), and these are not always records of a
  namespace-history cut (see "Fix round 1", finding 3). For the members of
  the cones that contain a touched entity, every record of the old
  projection that append mode does not derive (the new projection's records
  are part of what it derives) must be a record of its old cone's maximal
  antichain cut, which full mode re-derives; otherwise append falls back.
  Both projections are computed from the members' own registers
  (`namespace_records`), exact because the old history and its antichain
  cuts project (the rebuild succeeded). Outside those cones the records
  cannot change.

  A failed check of either kind derives in full (counted; reason recorded).
  The induction argument (append's result equals full mode's, its DELETE
  included, whenever the stored rows are what a rebuild from no rows
  derives) is written out in the module docs, component by component.
- **Id-ambiguity guards** (fall back to full): an entity id containing `,`;
  `E` relocating several entities; one event placing two entities in one
  slot; two events both relocating the same two entities. Outside these a
  conflict id determines its payload whichever source derives it, so full
  mode's "last record of an id wins" deduplication cannot differ between the
  modes. Honest histories never trip them (a fork or restore root is the only
  multi-location event of its branch).
- **Append-mode shortcuts** (exact; full mode, the oracle's reference, keeps
  the plain computation):
  - cones are computed only for the entities that reach a touched entity
    (`ConeGraph::reaching`), from one graph built once with per-edge
    "contributed only by `E`" counts, instead of two full cone analyses;
  - a cut is projected from the cone members' own kind, location and alive
    registers (`NsContext::namespace_records`) instead of the whole cut,
    when no cut of the branch can fail to project (`projection_cannot_fail`:
    every name valid, every kind a string and presence a boolean, every
    metadata value parses, every presence version placed in or before its
    own event). Exact because a cone is closed under slot competitors and
    every directory a member was ever placed in; a failure of `project` on
    another entity is the only other influence, and it is ruled out;
  - slot keys (`name_key`) are memoized process-wide (`slot_key`), bounded
    at 16 MiB of estimated bytes in two generations (`SlotKeys`).
- **Memoization, both modes** (`NsContext`, per derivation), all bounded:
  causal closures as bitsets computed once per event (64 MiB); each entity's
  alive-register analysis (reduced register graph, tombstone contexts,
  unbranched segments) once per entity on a compact graph of its versions;
  an entity index for relevance instead of a scan of every event per cone;
  each distinct antichain's cut projected once, up to 16 MiB of estimated
  retained records (`CUT_MEMO_BYTES`, `conflict_bytes`). Also
  behavior-neutral: `project` over borrowed events (`project_refs`); full
  mode's location-pair slot keys computed once per change instead of once
  per pair (evaluated in the same order, so a bad name fails at the same
  pair); register-pair history built only for the new event's registers on
  append. A verbatim copy of the Wave 0 code in the unit tests checks that
  the refactored full mode builds exactly the same source list, in order.
- **Commit checks** (`set_thread_commit_checks`, a thread-scoped test
  hook, off by default). Every slow-path commit of the thread, in any mode,
  runs in a savepoint and is then checked inside its own transaction (rolled
  back): the branch's conflict rows must equal a derivation from no rows
  (what the oracle's rebuild derives), and a refused commit must be refused
  by full mode with the same error text. A failure fails the commit with
  `CONFLICT_MODE_MISMATCH` (the §8 code; a new code would need a change to
  the frozen `src/model/errors.rs`).
- **Strict oracle adapter** (`Store::verify_derived_state_strict`): the
  plain oracle's findings plus a comparison of every stored conflict row
  with a rebuild that starts from an empty conflict table, in the same
  `DerivedDiff` text (a row both report is listed once). Outside a
  transaction it takes the write lock up front (`BEGIN IMMEDIATE`); inside a
  caller's it nests a savepoint; a rebuild error is returned before a
  rollback error. This is CCR-WP1.7-1's behaviour, on WP1.7's side until
  WP1.INT applies it to `verify_derived_state`.

## Deviations from the spec

1. **Touched-cone precondition generalized.** §5.2(c) asks for
   `relevant_after(C) \ {E} == relevant_before(C)`. The implementation
   requires `relevant_before(C) ⊆ relevant_after(C)` and projects the
   antichains containing any newly relevant event. Why: the first tombstone
   of an entity that has been saved turns on TRUE-presence compression and
   makes old presence witnesses relevant; with the spec's equality every
   such delete fell back to full mode (all fallbacks in the first fuzz runs
   were this case). Exactness: antichain-ness depends only on ancestry among
   the events, so the antichains of the larger set are the old ones (same
   cuts, stored records) plus those containing a new element (projected).
   The only remaining honest fallback is a witness displaced by `E`'s rank
   (pinned by `witness_displacement_falls_back` and
   `fallback_when_a_presence_witness_is_displaced`).
2. **`cones_before ⊆ cones_after` replaced by cover checks.** Moving a file
   into a directory adds the directory to the file's cone, so the old cone
   disappears as a set; the spec's precondition would send every move (the
   `concurrent_namespace_ops_5k` workload) to full mode. Cones only grow when
   events are added, so each old cone has a cover (the grown cone of the same
   entity); the checks make every old antichain an antichain of the cover
   with the same cut, and the cover's member filter is a superset.
3. **Extra preconditions** (id ambiguity, sink, pending) fall back to full
   mode. Not in the spec; needed for the "last record wins" deduplication to
   be mode-independent.
4. **The current-records check** (fix round 1) is a precondition the spec
   does not list. §5.2(d) states that under its precondition "No DELETE is
   needed: every old antichain still exists with an identical cut, so the
   old derived set is a subset of the new one". The old derived set also
   contains the old projection's records, which the history does not always
   re-derive (counterexample above), so the DELETE is a no-op only when this
   check holds.
5. **Append-mode shortcuts** (restricted cut projection, reverse-reachable
   cones, slot-key memo) go beyond "call `project(cut)` only for antichains
   containing E": without them a remote create still projected an O(N) cut
   and rebuilt every cone twice (about 37 ms of derivation per event near
   1.5K events of a two-way backlog; with them 2.84 ms per commit on average
   over the 2K backlog and 11.7 ms over 6.4K in the fix-round run). Full
   mode keeps the plain computation so that the oracle stays an independent
   reference.
6. **Verify mode compares rows semantically** (parsed payload with its
   `resolved_by` field cleared, plus the `resolved_by` column), as the
   oracle does. Every reader overrides the payload's own `resolved_by` field
   with the column, and after a startup-snapshot resume that field differs
   textually between rows full mode rewrites and rows append mode leaves.
7. **Unknown `TKFS_CONFLICT_MODE` means `full`** (the conservative
   reference) with a warning, rather than the default `append`.
8. **Thread-scoped test hooks** (`set_thread_conflict_mode`,
   `set_thread_commit_checks`, the thread counters) and the oracle adapter
   are public `#[doc(hidden)]` items: integration tests drive append, full
   and verify in one process (`std::env::set_var` is `unsafe` in edition 2024
   and the mode is read once per process), and the adapter must reach
   `Store`'s private rebuild from WP1.7's own file.
9. **The per-commit check covers conflict rows**, the state `derive.rs`
   derives; the projection and the frontier are checked by the store-level
   oracle after every local operation, delivery page and restart (task 4
   asks for the oracle after each commit; a delivery can commit several
   events and the store-level oracle needs `&mut Store`).
10. **No internal type named `NsMode`**: the plan's "internal `NsMode`" is
    the `Plan` and `AppendPlan` pair (internal either way).
11. **Qualification files keep `#[ignore = "WP1.7"]`**: they are long
    release scenarios run by `scripts/qualify.*` with `--ignored`, and
    `harness_selftest::qual_files_exist_and_ignores_name_their_owner`
    requires exactly that attribute.

## CCRs filed

**CCR-WP1.7-1** (for WP1.INT; file `src/core/verify.rs`, owned by WP0.3,
no later owner). Requested change to `Store::verify_derived_state`:

1. delete every conflict row inside the oracle's transaction before the
   rebuild, so every row and every `resolved_by` must be re-derived from the
   journal. Reason: the rebuild's upsert keeps stored rows it does not
   derive (it deletes only stale namespace rows) and its `resolved_by`
   maximum keeps an inflated stored value, so a fabricated register record,
   a stale row, or an inflated or invented `resolved_by` is not reported
   (the WP0.3 review note in `notes/wp0-int.md`);
2. return the rebuild's own error before the rollback's (today `rollback?`
   runs first and can hide it);
3. outside a transaction, `BEGIN IMMEDIATE` instead of a deferred
   `SAVEPOINT`: a deferred transaction that reads and then writes fails with
   `SQLITE_BUSY_SNAPSHOT` when another connection (a live worker's secondary
   handle) commits in between. Inside a caller's transaction keep the nested
   `SAVEPOINT oracle`.

Adapter: `Store::verify_derived_state_strict` in `src/core/derive.rs`
implements all three on top of the unchanged oracle (its findings plus the
from-empty comparison; same `DerivedDiff` text). The patch WP1.7 first
submitted is commit `69b8b3b`'s `src/core/verify.rs` (49 lines), with the
test that pins it now in `tests/derive_oracle.rs`
(`oracle_reports_excess_derived_state`, which runs against the adapter).
Once the CCR is applied, `verify_derived_state_strict` can delegate to
`verify_derived_state` or be removed, and the WP1.7 tests can call the
oracle directly. Note for the integrator: the stricter oracle also applies
to WP1.6's `activation_inbox` tests; it reports excess rows that the plain
oracle accepts.

## Known limitations

- The fuzzer drives the real `Store` API, which mints random UUIDs for events,
  entities and devices, so a seed does not replay byte for byte; a failure
  prints the seed, mode and the last 40 steps.
- Append mode is exact relative to full mode only when the stored rows are
  what a rebuild from no rows derives (the induction hypothesis). On a store
  that is already inconsistent (for example a history that full mode itself
  cannot rebuild), append mode keeps rows that a full-mode commit would
  delete. The strict oracle is the check for that state.
- A directory rename touches every cone that contains the directory (every
  entry ever placed under it); append mode then computes each such cone's
  relevant set (cheap), projects the shared new cut once per cone with
  restricted projections, and projects the members' old records once for
  the current-records check.
- Rebuilds (startup without a snapshot, the oracle) still run the full
  O(N²) derivation (2K events: ~12–20 s release). Their memos are bounded
  (64 MiB of closures, 16 MiB of cut records); a history with thousands of
  unresolved collisions re-projects cuts past the cut budget instead of
  holding them.
- Budget refusals are history-dependent in both modes: a receiver that holds
  more concurrent namespace chains than any author can refuse an event its
  author accepted, and replicas can then hold different journals. This is
  full mode's semantics (§5.2 keeps the refusal "before ACK"); append mode
  reproduces it exactly (checked by the fuzzer), it does not change it.
- Verify mode and the commit checks compare the whole conflict table of the
  branch on every commit (O(rows)), and the commit checks also derive the
  branch from no rows (O(N²)); both are diagnostic, for tests and
  qualification only.
- The memo budgets are estimates of heap bytes (they do not count allocator
  overhead); the probe measured about 35 MB of extra peak RSS for a full
  cut memo.
