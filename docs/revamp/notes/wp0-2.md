no logic changed.

Every path that was public before (`tkfs::runtime::{Engine, Handle, Session, Shared,
Discovery, RpcLane, rpc, start_rpc, prepare_content, namespace_notifications,
deliver_notifications, MAX_FRAME, PEER_FORMAT}`) still resolves. No caller outside
`src/runtime/` was edited apart from `main.rs` (below).

**Visibility changes (the only edits to moved code):**

- `Engine::retain_pending`: private → `pub(crate)`, as the spec requires.
- `published_rpc`, `fetch_verified`, `visible_paths`, `export_bucket`: private →
  `pub(super)`. Before the move these were private items of module `crate::runtime`,
  so they were visible in `crate::runtime` and its descendants. `pub(super)` from a
  child module gives exactly that scope again.
- Private fields (`Handle.directory`, `Engine.recovery_health`) and private helpers
  (`load_pending`, `flush_entity`, `dispatch_rpc`) are used only inside their new
  file, so they stay private.

**How the move was checked:** I took the original `runtime.rs` and the
concatenation of the new files, sorted the lines of each (with CR stripped) and
compared the two lists. The only lines missing from the new files are the 5
signatures whose visibility changed. The only added lines are the per-file `//!`
docs, the `use` lists, the `impl Engine {`/`}` wrapper in `control.rs`, the
`mod`/`pub use` lines, the 5 changed signatures and the two seams.

### 2. Worker entry: `main.rs::worker()` → `tkfs::worker::run`

- New `src/worker/mod.rs` with `pub fn run(state: &Path, mount: Option<&Path>) -> Result<()>`.
- It also takes the Linux `STOP` static and the `signal_stop` SIGINT/SIGTERM handler.
- The body is verbatim. A line diff against the old `main.rs` shows only these path
  edits:
  - `tkfs::startup` → `crate::startup`;
  - `tkfs::mount` → `crate::mount`;
  - `id()` → `crate::core::id()`, inside the Linux-only stop block, so Windows has
    no unused import.
- `main.rs`:
  - `Command::Daemon` now calls `tkfs::worker::run(state, mount.as_deref())`.
  - Imports the worker no longer needs were removed.
  - `Path::new` became `std::path::Path::new` in the Windows-only GUI branch.
    Otherwise `Path` would be an unused import on Linux.
- `src/lib.rs`: `pub mod worker;` appended (append-only registry line).

### 3. Seams (additive; no existing path changed)

- `pub fn runtime::lock_engine(e: &Shared) -> MutexGuard<'_, Engine>`. The body is
  `e.lock().unwrap()`. No existing call site was converted; WP1.4 does that
  together with the poison policy.
- `pub fn Engine::retain_all_dirty(&mut self) -> Result<usize>`:
  - It collects the dirty session ids, then calls `retain_pending` for each one with
    the reason `DIRTY_SESSION_RETAINED`.
  - It returns the number retained. With no failure, that equals the number of
    dirty sessions.
  - Every dirty session is attempted even after a failure. The first error is then
    returned with the context `PENDING_SAVE_PERSIST_FAILED: k of n dirty sessions not retained`.
  - Sessions stay in memory and stay dirty. A later `flush`, `close` or
    `retry_pending` commits them and deletes the row (existing `flush_entity`
    behaviour).
  - It is idempotent because the `pending_saves` upsert and `Staged::retain` are
    idempotent.

## Deviations from the spec

1. **Submodules are `pub mod`, not private `mod`.** The spec does not say which. I
   chose `pub mod` for two reasons:
   - WP1.4 names `runtime::server::start_rpc_ctx` as a public path, and WP0.INT
     adds further `runtime::*` modules (`ctx`, `sync_rpc`, `objects_rpc`) in the
     same style.
   - No item became more visible: the only new paths are module paths to items
     that were already public. Everything previously private is still private or
     `pub(super)`.
2. **Health side effect of `retain_all_dirty`.** This is inherited, not new.
   - `retain_pending` sets `health = "PENDING_SAVE: DIRTY_SESSION_RETAINED"` when
     health was `None`, or when it was already a recovery message.
   - So after a retain, `quiet()` returns `BUSY_VIEW` until the retained sessions
     commit. This is the existing pending-save degraded state, and it is the
     correct signal for a force detach or a poison exit.
   - The test asserts it.
3. **Error semantics of `retain_all_dirty`.** The spec does not cover what happens
   when one session fails. I chose to try every session, then report the first
   error (see above), because invariant 8 favours persisting as many dirty
   sessions as possible.
4. **Position of `pub mod worker;`.** It goes at the end of `src/lib.rs`, after
   `pub mod ws;`, because the spec says "append". The ordering is not alphabetical.

## Tests added

`tests/worker_seams.rs` (new file):

- **`retain_all_dirty_persists_every_dirty_session`** (the acceptance test named in
  the spec).
  - Setup: three dirty sessions with open handles:
    - in-memory staging;
    - a disk-spooled file over 256 KiB;
    - an edit of committed content, which carries a `content_base`.
  - Setup also includes two clean sessions with open handles: one flushed, one
    never written.
  - Asserts that the call returns 3, writes exactly 3 `pending_saves` rows, commits
    nothing and leaves the sessions dirty. Clean sessions are not retained.
  - Asserts the `PENDING_SAVE:` health and `quiet()` returning an error.
  - Asserts that a second call is idempotent.
  - Then simulates a crash (drop without flush) and reopens with
    `Store::open_existing` + `Engine::new`. Checks that `load_pending` recovers
    exactly the 3 sessions with their bytes and the original `content_base`.
  - Finally checks that `retry_pending` commits all three without conflicts, health
    clears, and no rows remain.
- **`retain_all_dirty_without_dirty_sessions_is_a_no_op`**: returns 0, health stays
  `None`, no rows are written.
- **`lock_engine_guards_the_shared_engine`**: the guard locks the shared engine
  (`try_lock` fails while it is held) and gives a working `Engine`.

No existing test or assertion was changed.

## Known limitations and notes for later packages

- **`lock_engine` is unused for now.** All engine locks still call
  `.lock().unwrap()` directly. WP1.4 converts them and adds `PoisonPolicy`.
- **Poison path and open savepoints (WP1.4).** `retain_all_dirty` writes through
  `store.db` in whatever transaction state the connection is in.
  - After a panic, the connection may still be inside an open savepoint, such as
    `control_request` or `staged_save`.
  - If so, the `pending_saves` upserts would be lost at `exit(70)`.
  - So WP1.4's poison handler should first roll back and release any open
    savepoint (`!db.is_autocommit()` → `ROLLBACK`), and only then call
    `retain_all_dirty`.
  - This does not apply to a force detach from a healthy engine, because the
    connection is in autocommit mode between engine calls.
- **Dropped sessions after a force detach (WP1.5).** If WP1.5 drops the dirty
  sessions after `retain_all_dirty`, only a restart reloads them (`load_pending`
  runs in `Engine::new`). To retry them in-process, WP1.5 must keep the sessions,
  or reload them from `pending_saves`.
- **Merge conflicts in `src/lib.rs`.** WP0.4 also appends lines there, so the
  integrator may see a trivial append/append conflict.
