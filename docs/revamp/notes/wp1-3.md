### `RealLauncher` (`process.rs`)

- `RealLauncher::new(policy: LogPolicy) -> Arc<Self>`. `LogPolicy` is this
  package's reading of the plan's `log_dir_policy`: the log path itself comes
  from the frozen `LaunchSpec.log`, so the policy holds how the log is used:
  `tail_bytes` (4096, the `stderr_tail` size), `drain_wait` (2 s, see below)
  and `max_line` (1 MiB). WP4.2 adds rotation here.
- `RealLauncher::command(spec) -> Command` builds
  `EXE daemon --state DIR [--supervised]` plus `spec.env`. `EXE` is
  `spec.executable`, or `current_exe()` when it is empty (the WP1.2 limits
  default it to `current_exe()`). `--supervised` follows `spec.supervised`, so
  a legacy-style launch is possible; there is no `--mount` (`LaunchSpec` has no
  mount, and supervised workers attach by RPC).
- `launch` = `launch_command(command(spec), &spec.log, &spec.state, sink)`.
  `launch_command` is public so tests can run scripted children through the
  exact same path:
  - stdin null, stdout piped, stderr = `worker.log` opened for append (the
    parent directory is created if needed);
  - Windows `CREATE_NO_WINDOW`; Unix `process_group(0)` (see deviation 3);
  - the **stdout reader** thread (`worker-out-<state>`) reads lines (bounded by
    `max_line`), copies every line to `worker.log` (parsed or not), parses it
    with `model::ipc::parse_line` and pushes `ProcessEvent::Line`;
  - the **exit waiter** thread (`worker-exit-<state>`) owns the `Child` and
    blocks in the OS wait. On exit it waits for the reader to reach EOF (at
    most `drain_wait`, so a final `FatalLine` is never lost and a grandchild
    holding the pipe cannot delay the event longer), reads the last 4 KiB of
    `worker.log`, and sends `Exited{code, fatal: last FatalLine, stderr_tail}`;
  - an `Emitter` serializes events: lines in stdout order, then exactly one
    `Exited`, then nothing (a grandchild's late lines are still logged but not
    emitted). Sink calls are wrapped in `catch_unwind`, so a panicking sink
    cannot stop the reader from draining the pipe or the waiter from reporting.
  - spawn failures are `WORKER_START` (Transient); nothing is emitted.
- `kill()` of a spawned child is race-free and idempotent:
  - Windows: `TerminateProcess` (exit code 1, as `Child::kill`) on a handle of
    our own, opened right after spawn; it pins the pid. Terminating an exited
    process is success.
  - Unix: the waiter `waitid(WEXITED|WNOWAIT)`s, marks the child exited under
    a mutex, then reaps. `kill` checks the mark under the same mutex before
    `SIGKILL`, so it never signals a recycled pid.
  - A spawned child's exit code is `Some(code)`; on Unix a signal death is
    `None`.
- Dropping a `WorkerProcess` never kills anything (workers outlive the daemon,
  §3.3; invariant 8).

### Identity, adoption, verified kill (`process.rs`)

- `process_identity(pid) -> Option<(u64, PathBuf)>`: `None` for no process, an
  exited one (Unix zombies included) or one that cannot be inspected.
  - Windows: `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION|SYNCHRONIZE)` (query
    only as a fallback), liveness by `WaitForSingleObject(h, 0)` (not
    `STILL_ACTIVE`, which an exit code 259 would fake), `GetProcessTimes`
    creation FILETIME as `high << 32 | low`, `QueryFullProcessImageNameW`.
  - Linux: `kill(pid, 0)`, `/proc/<pid>/stat` (state `Z`/`X` → gone; field 22
    starttime, parsed after the last `)`), `/proc/<pid>/exe` with a
    ` (deleted)` suffix removed (a binary replaced during an upgrade still
    matches its record; the `hello` version check then drives the restart).
  - These are exactly the values §6.1 says `worker.json` records. The test
    checks the Linux value against an independent parse of `/proc/self/stat`.
  - Other platforms: always `None` (nothing is adopted, nothing is killed by
    pid).
- Executable comparison: equal, or equal after Windows normalization (case,
  `\\?\`, separators), or equal after `canonicalize` (symlinks, 8.3 names).
- `adopt(record)` returns `Ok(None)` unless the pid is alive and both
  `process_start` and `executable` match (invariant 23). On Windows it then
  opens a watch handle and re-verifies the identity **on that handle** (the pid
  could be recycled between the first check and the open). `Err` only for
  `PERMISSION_DENIED` (the identity matches but the process cannot be watched)
  or a thread-spawn failure.
- The adopted process has a liveness probe thread (`worker-probe-<pid>`):
  Windows waits on the handle with a 1 s timeout (`limits::ADOPTED_PID_PROBE`),
  so the exit is immediate and carries the exit code; Unix re-checks the
  identity at 1 Hz, and every 25 ms for 2 s after a `kill()`. It emits
  `Exited{code, fatal: None, stderr_tail: ""}` and ends quietly when the
  `WorkerProcess` is dropped.
- `kill()` of an adopted process is `kill_verified(pid, process_start,
  executable)`:
  - `Ok(())`: killed now, or already gone;
  - `Err(WORKER_NOT_RUNNING)`: a live process has the pid but another identity
    (or cannot be inspected); nothing is killed;
  - `Err(PERMISSION_DENIED)`: the identity matches but the OS refused.
  - Windows verifies on the same handle it terminates (no race). Unix checks
    then signals; the residual window needs the recorded process to exit and
    its pid to be recycled within microseconds (documented on the function).

### `JsonWorkerClient` (`worker_client.rs`)

- `JsonWorkerClient::new(endpoint) -> Arc<Self>`; `with_options(endpoint,
  ClientOptions{max_idle, max_idle_age})`; `endpoint()`, `idle()`,
  `connects()` (for tests and diagnostics). `RealLauncher::client` returns one.
- Request: `{"request": <uuid>, "payload": {...payload, "op": op}}` as a JSON
  text frame; a `null` payload is `{}`; a non-object payload is refused before
  connecting (`Unavailable(INVALID_REQUEST)`). Reply: the `ws::call` envelope
  `{ok, result | error}`.
- Pool: up to `MAX_IDLE` (8) idle sockets, checked out per call and returned
  afterwards; the pool lock is held only to pop/push, never while a socket is
  used or closed. A socket idle longer than `MAX_IDLE_AGE` (10 s; the worker's
  per-connection read timeout is 15 s), or one the worker closed (a
  non-blocking `peek` sees EOF or unexpected data), is closed instead of
  reused, so a stale socket does not turn the next call uncertain.
- Deadline: the whole call (TCP connect, WebSocket upgrade, send, reply) is
  bounded by the call's deadline; each socket operation uses the time left as
  its timeout.
- Errors (`CallError`):
  - complete error reply → `Remote(ErrorWire{code: first code in the text or
    UNKNOWN_ERROR, class: classify(code), message: text})`; the socket goes
    back to the pool (invariant 17);
  - socket timeout after the request was written → `Timeout{after_ms}`; any
    other failure after that point (reset, close, malformed reply) →
    `ConnectionLost`. Both are uncertain, the socket is dropped, and the
    request is never replayed (invariant 16): the client has no retry path at
    all;
  - connect or upgrade failure (including an upgrade that times out) →
    `Unavailable(LOCAL_WORKER_UNAVAILABLE: …)`: nothing was sent;
  - deadline already spent when the socket is ready → `Unavailable
    (REQUEST_TIMEOUT: …)`, nothing sent, socket kept.
- `call_bytes` → `Unavailable("BINARY_OPS_REQUIRE_SESSION: …")` (WP3.3).

Every code literal used is already registered in `model::errors` (§8 table or
`TRANSIENT_DEFAULT_CODES`): `WORKER_START`, `WORKER_NOT_RUNNING`,
`PERMISSION_DENIED`, `LOCAL_WORKER_UNAVAILABLE`, `INVALID_REQUEST`,
`WS_MESSAGE_TOO_LARGE`, `REQUEST_TIMEOUT`, `WS_CLOSED`, `INVALID_WS_REPLY`,
`BINARY_OPS_REQUIRE_SESSION`, plus `UNKNOWN_ERROR` through `UNKNOWN_CODE`.
`contracts::classify_covers_every_code_literal_in_src` passes.

## Deviations from the spec, and why

1. **Kill requests do not travel through a channel to the exit waiter.** The
   plan says the waiter "serves `kill` requests through a channel". A thread
   cannot block in the OS wait and on a channel at once, and §2.2 rule 3
   ("signals instead of sampling") and §3.3 ("spawned children report exit
   immediately") rule out a polling waiter. The waiter blocks in the OS wait;
   `kill` uses a small shared control (Windows: its own process handle; Unix:
   an "exited" mark the waiter sets after `waitid(WNOWAIT)` and before
   reaping). It is as race-free as the channel design: a kill never reaches a
   recycled pid.
2. **The JSON client uses tungstenite directly, not `ws::Socket`.**
   `ws::connect` bounds the TCP connect by a fixed 3 s and the WebSocket
   upgrade by fixed 15 s socket timeouts, so a 2 s `hello` probe against a
   frozen worker (TCP accepted by the kernel backlog, upgrade never answered)
   would take 15 s, breaking the §3.3 liveness ladder. `ws::Socket` has no
   public constructor from a stream (and `ws.rs` is not this package's). The
   client therefore performs the same upgrade with tungstenite over a
   `TcpStream` it times out itself, with the same message limits
   (`ws::MAX_MESSAGE`) and the same `{request, payload}` / `{ok, result |
   error}` envelope. It does not send `X-Tkfs-Wire`, so the worker answers
   with JSON text frames (no gzip on loopback). The test
   `an_upgrade_that_never_completes_is_bounded_by_the_deadline` covers it.
3. **Unix workers get their own process group** (`process_group(0)`); this is
   not in the task list. Without it a terminal Ctrl-C aimed at the daemon also
   reaches every worker, which then stops on its own, racing the daemon's
   Shutdown sequence (§3.6), where busy workers must be left running for
   adoption. It follows "workers are not tied to daemon lifetime" (§3.3). On
   Windows `CREATE_NO_WINDOW` already gives the worker no console, so no
   console control events reach it.
4. **"Pool of ≤ 8" bounds idle sockets, not concurrent calls.** A ninth
   concurrent call opens an extra connection, which is closed afterwards.
   Blocking it would stall short calls (`hello`, `status`) behind long ones
   (`mount-attach` 60 s, `watch` 4 s), and refusing it (`Busy`) would turn
   ordinary parallelism into Contention errors. This is the same choice
   WP0.INT made for `SyncStorePool` (its deviation 2).
5. **`adopt` opens the watch handle without `PROCESS_TERMINATE`.** The plan
   lists `QUERY_LIMITED|SYNCHRONIZE|TERMINATE` for the adoption check.
   Identity checks only query, and `kill_verified` opens its own handle with
   `TERMINATE` when a kill is actually requested, so a process the daemon may
   watch but not terminate is still adoptable and a later kill reports
   `PERMISSION_DENIED` rather than failing the adoption.
6. **Adopted `Exited` events carry no `stderr_tail`.** `WorkerRecord` (frozen)
   does not name the log, and `adopt` receives only the record. The controller
   knows `STATE/worker.log`; `process::log_tail(path, max)` is public so it can
   fill `ExitRecord.stderr_tail` itself. The exit code is known on Windows
   (from the watch handle) and `None` on Unix (not our child).
7. **Kill-refusal code.** There is no dedicated "identity mismatch" code in
   the frozen §8 table, and new code literals need a CCR. `kill_verified`
   reports `WORKER_NOT_RUNNING` (Transient): the recorded worker is not
   running, because the pid now belongs to another process. See CCR-WP1.3-1.

## CCRs filed

- **CCR-WP1.3-1 (optional; no adapter needed).** Requested change: register a
  dedicated code such as `WORKER_IDENTITY_MISMATCH` (Transient) in
  `model::errors` for `kill_verified`'s refusal. Reason: today it reuses
  `WORKER_NOT_RUNNING`, which is accurate (the recorded worker is gone) but
  does not say why. Adapter: the message text says
  `pid N is not the recorded worker (its start time or image differs, …);
  nothing was killed`.
- **CCR-WP1.3-2 (for WP1.2/WP2.1; information, no contract change).** A
  controller should fill `ExitRecord.stderr_tail` for adopted workers with
  `process::log_tail(STATE/worker.log, 4096)` (deviation 6). Optionally, a
  later contract could add the log path to `WorkerLauncher::adopt`.

## Observations for other packages

- **Linux identity right after `spawn`.** `Command::spawn` can return before
  `/proc/<pid>/exe` switches to the new image: the vfork-style parent resumes
  when the child releases the old address space, just before the child's
  `mm` is replaced, and an identity read in that window shows the parent's
  image (this made the first WSL run of `kill_refuses_a_mismatched_identity`
  fail). The product is not affected: a worker records its own identity in
  `worker.json` after exec, and adoption reads that. Tests that read a fresh
  child's identity must wait for it to settle (`tests/worker_process.rs`
  `sleeper()` does).
- `WorkerRecord.executable` must be written with `std::env::current_exe()`
  (WP1.4). On Linux that equals `/proc/self/exe`; on Windows the comparison
  tolerates case, `\\?\` and 8.3 differences.

## Known limitations

- On Unix an adopted worker's exit code is unknown (`None`): it is not our
  child. The 1 Hz probe reports the exit within about 1 s (25 ms after a
  `kill()`).
- The Unix verified kill has a check-then-signal window (see above). `pidfd`
  would close it on Linux ≥ 5.3; it was left out for portability, as the
  start-time check already makes a wrong kill require a pid recycled within
  microseconds.
- The per-call deadline bounds each socket operation; a reply that arrives in
  many slow fragments could exceed it slightly (loopback replies are written
  in one go).
- The real `daemon --supervised` launch, Ready validation and adoption of a
  real worker are checked in WP1.INT (the flag lands in WP1.4), as the plan
  says.
