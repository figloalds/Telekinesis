# WP2.1 — Orchestrator wiring: actors, core management, legacy network bridge

Branch `revamp/wp2-1-orchestrator-wiring`, cut from `revamp/wave-2-base`
(`ca7d8a9`). Spec: REVAMP_PLAN §2.5, §3.1, §3.3, §3.5, §3.6, §7.3, §14 WP2.1.

## Summary

The daemon no longer has a global `Supervisor` mutex or a polling main loop
(RC8). `orchestrator::run` builds the Wave 1 actors and serves them:

| Thread | What it does |
|---|---|
| main | `ctx::build`, then waits on `ctx.shutdown`; runs or waits for the shutdown sequence; joins the control threads (2 s); removes `orchestrator.json` |
| `tkfs-catalog` | the catalog actor (WP1.1), the only `folders.sqlite` connection |
| `folder-registry`, `folder-<state>` | the FolderRegistry and one FolderController per folder (WP1.2), with the real launcher (WP1.3) |
| `hub-tick` | the StatusHub's 1 Hz tick (WP1.11) |
| `control-accept`, `control-conn-N` | blocking accept; one thread per control connection (≤ 64), a persistent `receive → manage → reply` loop |
| `net-accept`, `net-conn-N` | blocking accept on the peer listener; one thread per inbound legacy connection (≤ 128) |
| `legacy-lanes`, `legacy-lane-N` | the lane manager (follows the catalog generation) and one thread per `(peer, revision, lane)` |
| `folder-slots` | every 2 s, re-sends `Tick` to folders that wait for a `maximum_running` slot (safety net, see CCRs) |
| `shutdown-signal` (Unix) | turns SIGINT/SIGTERM (self-pipe) into `ctx.shutdown.cancel()` |

No orchestrator lock is held across I/O: shared state is the catalog
snapshot, the controllers' `Snapshot<FolderView>`, the hub, the published
cache, and the bridge's two maps (`Tracked`, map operations only). Every
worker or peer call happens on the thread that needs it, never under a lock.

### Files

- **`ctx.rs`** — `Daemon { ctx, control, network, bridge, hub, catalog,
  registry }`, `build(config)` and `build_with(config, BuildOptions)`: the
  §14 task 1 order (catalog → hub + ticker → published cache → listeners →
  registry → `Ctx` → bridge). `LifecycleLimits::worker_version` is
  `worker::version()` (CCR-WP1.2-2). `DaemonLauncher` wraps `RealLauncher`
  and fills an adopted worker's empty `stderr_tail` from `STATE/worker.log`
  (CCR-WP1.3-2). `extras(ctx)` is the side table for what `Ctx` (frozen) has
  no field for: the concrete hub (`set_stopping`) and the shutdown latch
  (CCR-WP2.1-1).
- **`run.rs`** — `run(config)` = (Windows) clear the inheritance of every
  inherited handle (CCR-WP1.INT-1, below) → `ctx::build` → `serve`.
  `serve`/`serve_with` write `orchestrator.json` (`{format:3, pid, version,
  installation, control, network, started_at_ms}`, temp + rename, removed by
  a drop guard), run the two accept loops, wait on `ctx.shutdown`, then stop
  accepting, let requests in flight finish, close the control connections
  and join them (2 s), remove `orchestrator.json` and only then close the
  catalog (which releases `orchestrator.lock`); the guard removes the file
  only if it still holds the bytes this daemon wrote. Stopping an accept
  loop sets its flag and wakes `accept` with a connection to the listener's
  port, on the loopback of its family when the listener is bound to
  `0.0.0.0` or `[::]`, then waits ≤ 2 s for the thread (a thread still
  blocked is logged and left to the process exit). An unparsable control
  request gets `INVALID_REQUEST: <serde error>` and the connection stays
  usable; a handler panic is answered `UNKNOWN_ERROR`. The `Shutdown` reply
  is written before `ctx.shutdown` is cancelled (§3.6 step 4 before 5–6);
  the connection cancels `ctx.shutdown` after any `Shutdown` request, also
  a refused or panicked one. The peer accept loop reserves the connection's
  slot (`LegacyBridge::reserve_inbound`, ≤ 128) before it starts the
  thread.
- **`shutdown.rs`** — `run(ctx, deadline)`: set `stopping` (and the hub's
  `daemon.stopping`), `network.shutdown(5 s)`, `folders.shutdown(deadline)`,
  reply `{stopped:true, folders:[{state, outcome, error}]}`. Idempotent per
  daemon (a latch: a later caller waits for the first result; a sequence
  that panics still finishes the latch, with an `UNKNOWN_ERROR` result, so
  nobody waits for it). Fault point `orchestrator.shutdown`
  (`shutdown::faults::SEQUENCE`) after step 1, for tests. `install(ctx)`
  registers `ctx.shutdown`: Windows `SetConsoleCtrlHandler` (Ctrl-C,
  Ctrl-Break, console close, logoff, system shutdown; for the last three the
  handler holds the process ≤ 4.5 s until the sequence completes), Unix
  SIGINT/SIGTERM through an async-signal-safe self-pipe (CLOEXEC) and a
  watcher thread. All triggers run the same sequence.
- **`manage.rs`** — `manage(ctx, action)`: every action first checks
  `stopping`; the legacy actions per §14 task 3; the v2 variants go to
  `manage_v2::handle` (WP2.2's stub until it merges). `project(record, view,
  gate_row)` is the §7.3 projection (public, table-tested); List/Inspect add
  the legacy `sync` member (`ctx.legacy()?.folder_sync`) and the typed
  `status` member (the hub's `FolderStatus`). Create/Receive validate the
  mount (`validate_mount_path`), run `Store::initialize` on the request
  thread, apply `CreateFolder` (with a `GateRecord` for a mounted Receive),
  wait for the new controller and send it `Start`. Start = `SetDesired(1)` +
  `FolderCmd::Start` (returns at once). Stop = `SetDesired(0)` first, then a
  graceful stop that waits ≤ 13 s (deviation 1) unless `wait:false`; a folder
  still stopping or StopBlocked adds `stopping:true, waiting_for`.
  ConfigureMount refuses (`STOP_FOLDER_BEFORE_CONFIGURING`) while the folder
  has a worker. Pair/Unpair/RemoteList go through `ctx.network()`, Peers
  through `ctx.legacy()`, ResetPairingCode is `SetVerifier`. A
  `CATALOG_UNAVAILABLE` answer also records a daemon-scoped status error.
- **`legacy_bridge.rs`** — `LegacyBridge::start(ctx)`: `NetworkApi` (v2
  `pair`, `remote_list`, `unpair`, `reconfigure`, `shutdown`) and
  `LegacyNetworkView` (`folder_sync`, `peers`: the exact legacy JSON, the
  code of `Supervisor::inspect` and `Action::Peers` moved). The lane manager
  spawns and cancels lanes per `(peer, revision, lane)` on catalog changes,
  respawns a lane whose thread ended without being retired (a panic; the
  legacy run loop did the same), and records `PeerConfigured`/`PeerRemoved`. `serve_inbound(stream)` serves
  one inbound connection on the caller's thread; its socket shutdown is a
  hook on a child of the bridge token.
- **`lanes.rs`** — the WP1.12 lane loop, moved: folders from the catalog
  snapshot (`desired && sync_enabled`), the worker from its controller's
  `FolderView` (never `runtime.json`), link status in the bridge's map,
  retirement by `Cancel`. Status events: `LaneState`, `ExchangeFinished`
  (ops `exchange`, `objects`, `bulk.exchange`; the v6 `metadata_progress` as
  an `ExchangeSummary`, completed objects counted per page), `PeerCatalog`
  (on change) and the `LegacyLink` passthrough. The legacy gate rule: a
  control-lane exchange that leaves the folder `metadata_caught_up` with no
  error sends `FolderCmd::GateEvidence{caught_up:true}` to a folder that has
  a gate row; the controller attaches the mount in place and clears the
  marker after `Attached`.
- **`peering.rs`** — `dial`/`dial_role` unchanged; `remote_catalog` shared
  by the bridge and the legacy `remote_list(&Shared)` wrapper; `DeadlineLane`
  gains `call_as` (caller's request id); `serve_inbound` (the old
  `serve_peer`) checks the verifier from the snapshot on every request
  (`PAIRING_CODE_CHANGED`), answers `list` from the published cache (Running
  entries, catalog labels), answers `FOLDER_SYNC_PAUSED` for a paused
  folder and `LOCAL_WORKER_UNAVAILABLE` for one without a running worker,
  bounds each worker call to 15 s, and records `InboundSession` and inbound
  `ExchangeFinished`. The old `published()` fan-out is gone (§3.5: `list` is
  O(1)).
- **`mod.rs`** — `#[allow(dead_code)]` on `mod catalog_db;` and
  `mod supervisor;` (task 6: they stay compiled, reachable only through the
  legacy `api::manage`, until WP2.INT deletes them); exports `serve`,
  `serve_with`. `status.rs` is unchanged.

## Deviations from the spec, and why

1. **Stop waits 13 s, not 15 s** (`manage::STOP_REPLY_WAIT`). The legacy
   client (`api::client`, `ws::connect`) has a 15 s socket read timeout, so
   a reply that comes after a full 15 s wait races it (measured: the first
   version timed out in `a_slow_stopping_folder…`). 13 s is within "≤ 15 s"
   (§3.5). CCR-WP2.1-5 asks WP2.2's client for a longer read timeout.
2. **Listeners are bound before `FolderRegistry::start`** (task 1 lists the
   registry first). A busy port then fails the start before any worker is
   started or adopted, as the legacy daemon did.
3. **The `Folder` passthrough** uses the controller's endpoint
   (`FolderView.worker`) through `DeadlineLane::call_as` with the caller's
   request id and the 30 s deadline, not `FolderDirectory::client`:
   `JsonWorkerClient` assigns its own request ids, and the worker's receipts
   make a retried mutation with the *same* id idempotent.
4. **The `status` member of List/Inspect carries open errors only.** The
   hub's `FolderStatus.errors` also holds resolved history (50 entries); a
   List row describes the folder now, and the history stays in `Status`
   (WP2.2). Without this, `harness_selftest::compat_goldens_recapture_identically`
   (any key `error` with a value counts as an error) never settles.
   Command replies (Create, Start, Stop) rebuild the hub snapshot
   (`snapshot_now`) so their `status` shows the command's effect; List and
   Inspect use the throttled snapshot. CCR-WP2.1-4.
5. **Inbound worker calls are bounded by 15 s per call** (`DeadlineLane`)
   instead of `RpcLane`'s 15 s per socket read: the same bound for a
   one-message reply, with a `REQUEST_TIMEOUT` code.
6. **`list` waits ≤ 1 s for a Running folder's first `published-summary`**
   (`peering::FIRST_SUMMARY_WAIT`). The cache is filled asynchronously right
   after Ready; without the wait a `Receive` issued right after the source's
   Create could miss the folder (the legacy `list` asked the workers
   synchronously). Once a summary answered or failed, `list` never waits.
7. **Additive interfaces** beyond "Provides": `Daemon` has `bridge`, `hub`,
   `catalog`, `registry`; `ctx::build_with(config, BuildOptions)`;
   `run::serve`/`serve_with(daemon, signals)` (in-process tests must not
   install process-wide signal handlers); `manage::project`;
   `LegacyBridge::{inbound_sessions, lanes, reserve_inbound,
   serve_inbound_reserved}` and `legacy_bridge::InboundSlot` (the
   provided `serve_inbound(stream)` is unchanged; it takes its own slot);
   `shutdown::faults::SEQUENCE`.
8. **All inherited handles, not only the standard handles, are made
   non-inheritable** at daemon start (CCR-WP1.INT-1 asked for the standard
   handles). A daemon also inherits, by value, every inheritable handle of
   its parent; a test proved a worker inherited one of them (it held a pipe
   the test lent the daemon). `run` clears the inheritance flag of every
   handle in its table (`NtQueryInformationProcess(ProcessHandleInformation)`)
   before it starts any process; Rust creates its own handles
   non-inheritable, so nothing the daemon owns is affected. Linux is
   unaffected (`O_CLOEXEC`).
9. **`qual_wp2_1_lifecycle` (owned) changes to the WP0.5 drafts**:
   - the crasher is `TKFS_FAULT_POINT=worker.startup` (exit) scoped to the
     folder, as the acceptance says; deleting the store (the draft) is a
     Fatal `STATE_NOT_INITIALIZED` now, `Failed` at once, never a loop;
   - `hung_worker_restarted` freezes the worker process (SIGSTOP /
     `NtSuspendProcess`). With `worker.watch_hang` alone the worker still
     answers `hello`, and §3.3 (WP1.2's controller) treats a worker that
     answers `hello` as alive: it is never killed (a responsive worker may
     hold dirty sessions, invariant 8). The new
     `watch_hang_alone_is_not_unresponsive` pins that. CCR-WP2.1-6;
   - `api_latency_under_churn` also checks the crasher really loops and
     scans the daemon log for lock holds; `sigterm_matches_shutdown` stops
     two folders and compares with the Shutdown action;
   - the scenarios stay `#[ignore = "WP2.1"]` (the qualify convention, as
     WP1.4 did): `qualify.ps1` runs them in release.
10. **Create's `WORKER_LIMIT` pre-check** counts the folders whose view is
    not Stopped or Failed (the registry enforces the limit on every Start;
    the pre-check keeps a refused Create from creating anything, like the
    legacy `create`).
11. **Shutdown budgets** are the spec's: network 5 s, then folders 30 s
    (`limits::SHUTDOWN_*`); only if both run to their limits does the whole
    sequence exceed 30 s.
12. **Requests during shutdown** are all refused (`ORCHESTRATOR_STOPPING`,
    §3.6 step 1); the legacy daemon still served `Folder`, `Pair`,
    `RemoteList` and `Receive` while stopping.
13. **The legacy gate rule** sends only positive evidence, and only to
    folders with a gate row (the legacy reconcile acted only on a positive
    observation). `blocked` is always `false` (the v6 result cannot
    attribute quarantined rows to the source; the source-based rule arrives
    with the feed in Wave 3).
14. **Legacy `ExchangeFinished` events** have no feed tips or cursors (0) and
    count completed objects as the parts of a page that end their object.

## Known limitations

- **Windows: socket shutdown does not wake a blocked receive.** A cancelled
  lane (unpair, re-pair, shutdown) that is waiting between passes wakes at
  once; one parked in a request to a silent peer ends at the legacy 15 s
  socket timeout (on Linux at once). `network.shutdown` waits 5 s and then
  continues; the process exit ends the rest. Idle persistent control
  connections at shutdown get a FIN (a client that reads closes); the join
  waits 2 s. The v3 sessions (Wave 3) use non-blocking I/O and are not
  affected.
- The four `legacy_stabilizers` tests of CCR-WP2.1-2 fail on this branch
  until the plan owner or integrator applies the CCR.
- An accept loop whose wake-up connection fails (for example an interface
  address that disappeared after the bind) is logged and left blocked in
  `accept` until the process exits; shutdown does not wait for it beyond
  2 s. In an in-process daemon (tests), its listener then stays bound.
- A dead catalog thread is not restarted: management writes answer
  `CATALOG_UNAVAILABLE` (also a daemon status error) and everything else
  keeps the last snapshot. Restarting needs a new `Catalog` behind the
  `Arc<dyn CatalogApi>` that the registry and every controller hold, with
  generation continuity across the swap.
- The `folder-slots` safety net is a 2 s timer (a lost slot wake-up heals in
  ≤ 2 s), not a fix in `registry.rs`.
- `manage_v2` is WP2.2's stub here: `status`, `subscribe` and the other v2
  actions answer `NOT_IMPLEMENTED` until WP2.2 merges, so
  `qual…::subscribe_latency` reports `UNSUPPORTED` on this branch.
- The `status` member and the hub see the legacy lanes through the events
  the bridge records (no feed tips; cursors 0); the legacy `sync` member is
  the authoritative per-lane view until WP3.1.
- Peer catalogs, link status and lane state are in memory: after a daemon
  restart they are rebuilt by the lanes (as before).
