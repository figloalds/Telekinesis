## Measured first

On the reference machine (AMD Ryzen 9 7950X3D, 32 threads; `C:` a Samsung
9100 PRO NVMe; Windows 11 with Defender real-time protection on; WinFsp 2.x),
shared with other agents' builds and test suites: the same binary varied by
up to 2x between runs, so every comparison below is interleaved, best of 3.
Dataset: 2,000 files of 1–64 KiB in 100 directories (66.5 MB), copied into a
fresh standalone worker's WinFsp mount (`tkfs init --state S`, then `tkfs
daemon --state S --mount M`, which both builds accept), then a graceful stop
retried until accepted (a stop is accepted once every file is committed).
Binaries: the 6298d0b baseline (`C:/tkfs-build/lab/target-baseline/release/tkfs.exe`,
SHA-256 `69c6e8f8414f…`, read only), the wave-5 base (`c6948c9`, release,
built here, SHA-256 `89cd85f658bf…`) and this package (release).

### Where the time went in the wave-5 base

A per-operation profile (temporary spans, not committed) of the copy with
the lab's PowerShell script: per file, 28 filesystem callbacks (1 create,
5 opens, 6 cleanups, 6 closes, 5 file-information queries, 2 name lookups,
1 write, 1 read: Defender reads every closed file back through the mount).
The save in the cleanup took **27.1 ms** of the file's ~37 ms, under the
engine lock:

| Part of a 32 KiB file's save (wave-5 base) | ms |
|---|---|
| `put_object`: hash, write, `fsync` (1.3), write-through rename (0.8), availability row (1.1, a commit of its own) | ~4 |
| the content commit (its `check_commit` re-hash 0.4, the SQLite commit 1.5) | ~2 |
| **a full reload of the engine's projection view** (measured: 2,066 reloads, 20.6 ms each, for 1,995 saves) | **20.6** |

The reload: `put_object` records the object's availability on the engine's
own connection outside the commit (`note_available`), which moves that
connection's `total_changes`, the view's freshness key, so the commit that
follows reloaded the whole projection (~2K entries). 6298d0b has no
availability index; that is why the wave-5 base copied slower than the
baseline (the lab: 163.6 s against 102.6 s). The create callback took 2 ms
(its commit), and every callback spent 21 µs in `publish_observation` (a SQL
query of every branch and a JSON rebuild of a value nothing reads).

Measured after the save left the lock: the commit's re-hash of an object just
installed waited ~3 ms for Defender's scan of that new file, under the lock;
the creates (~3 ms, their commit) and the background commits (~2.5 ms) are
what holds the engine; and Defender scans each written file through the mount
synchronously when the application closes it: 5–7 ms per written file even
with the engine idle (a probe: an empty file closes in 0.05 ms, a 32 KiB one
in 5–7 ms; on plain NTFS 0.06 ms), plus ~3.5 ms per open of an existing file.
Those are fixed costs of WinFsp plus Defender, which the baseline pays too:
per file the copy now spends ~3 ms in our create and ~5 ms in Defender's
close, the baseline ~3 ms and ~13 ms (its save is in the close).

## Summary of the changes

### 1. CCR-WP4.INT-5: saves off the engine lock (`engine.rs`, `staging.rs`)

A save has three phases (`engine.rs` module docs, *Saves off the engine
lock*):

1. `Engine::begin_save`, under the lock: snapshots the session's bytes
   (`Staged::snapshot`: a copy of in-memory bytes, at most 256 KiB, or a second
   handle to its staging file) and marks the session `saving`;
2. `store_snapshot`, **without** the lock: hashes the bytes, writes them to
   `objects/<id>.part`, `fsync`s it and installs it under its hash with a
   write-through rename (invariant 1), or verifies the copy already there;
3. `Engine::finish_save`, under the lock: commits the object as the
   session's content with the snapshot's bases (the base check: the branch,
   the generation and the session's bases must be the snapshot's; saves of
   one entity never overlap), together with the removal of the session's
   `pending_saves` record when the session was not edited since the snapshot
   (its bytes are the ones committed), or its rebase onto the new revision
   when it was (the record then holds later bytes).

While a save reads a staging file nothing writes it: writers wait for the
save without the lock (`lock_for_write`, `Engine::write_blocked`), and an
unsynchronized `Engine::write`/`truncate` is refused `BUSY_VIEW` rather than
tearing the snapshot. In-memory bytes may change during the save; the session
then stays dirty (`Session::edits`) and saves again. Every failure of any
phase (a panic in phase 2 too) retains the session in `pending_saves`, as a
failed save always did. The in-lock `Engine::flush`/`close`/`cleanup` (tests,
in-process callers) run the three phases back to back.

The availability rows of saved objects are no longer written on the engine's
connection (the reload above) but on a connection of their own, in batches
once a second (`AvailabilityNotes`). Until its row lands an object counts as
present by the listing of `objects/` (never as corrupt), and one whose row a
crash lost is verified again at the next startup.

**The first write to a large file** (a reference above 256 KiB) no longer
copies it under the lock: `content::prepare_writable` copies and verifies it
into a staging file without the lock (`staging::writable_copy`, one read of
the object) and installs the copy only if the session still references that
object (`Staged::install_writable`); a resize to zero, or an allocation that
does not shrink, copies nothing. An empty reference (every new file's session)
needs no verification any more.

**Durability.** Dirty sessions keep surviving detach, stop and restart
(invariant 8): a save in progress is a dirty session until its commit, so a
graceful stop, detach or checkout waits for it (`quiet()` refuses it), a force
detach or a poison exit retains it (its commit later removes the record), and
a restart restores it. A crash at any step leaves the last committed bytes; an
orphaned `.part` is removed at the next startup (`remove_orphaned_spools`).

### 2. The WinFsp write path (`mount.rs`, `native/mount.c`, `engine.rs`)

- **Every callback** does the work that needs no engine lock first and takes
  the engine only for its own short phases.
- **Write-behind during a burst of closes.** A lone close (cleanup) is saved
  before it returns, off the lock, as before in effect: a stop, a fork or a
  delete that follows it never waits for it. During a burst (background saves
  run or wait, or a save ended less than 100 ms ago, `write_behind`) the
  cleanup marks the handle cleaned and queues the save for a bounded pool of
  saver threads (at most 8 threads, 64 queued; `save_handle_in_background`),
  so the application goes on with its next file. A saver commits a file 10 ms
  after it stored its bytes (`SETTLE`: the commit's re-hash of the new object
  waited for Defender's scan of it under the lock, ~3 ms of a 32 KiB file's
  commit; 0.33 ms after the settle) and, before each phase that takes the
  engine, lets the application's callbacks go first (`foreground`, at most
  20 ms). After a job it sweeps the closed files of that engine left unsaved
  (`orphan_dirty`, honouring the pending-save backoff). A flush
  (`FlushFileBuffers`), a rename and a delete-on-close wait for the save; a
  delete or a rename over a closed file settles it first (`settle_entity`), so
  a background save never commits after a delete. The close never saves. The
  pending-save retry (maintenance) hands its saves to the savers when the
  mount adapter bound the shared engine (`Engine::adopt_shared`), and never
  saves a backlog under the lock (an experiment that slowed the savers saw
  closes of up to 1.5 s while it did).
- A file being saved in the background is an unsaved file for `quiet()`; a
  graceful detach waits for such saves (the fence, up to 8 s) and a checkout
  refuses them.
- **Per-callback costs.** `publish_observation` rebuilds the observation only
  when what it shows changed and reads the branch descriptor only after a
  checkout (21 µs → 2 µs per callback). Notifications: none on this path.
  fsyncs: the availability commit per file is batched; the object's `fsync`
  and write-through rename stay (invariant 1), and so do the two journal
  commits per new file (create, content; invariant 4).
- **Dispatcher threads and request timeout** are explicit: the processor
  count clamped to 8–64, and `IrpTimeout` 300 s (the WinFsp default).

### 3. CCR-WP4.INT-2: reads of content still downloading (`content.rs`, adapters)

A read of a file whose object is not here registers demand (`request_object`,
renewed every 10 s while it waits) and waits while the download progresses:
progress is the length of the object's spool (`incoming-objects/<hash>`), read
without any lock. The wait ends with the verified object (only verified bytes
are served), or fails `CONTENT_UNAVAILABLE` when no byte arrived for 60 s, when
the wait reached 240 s (a minute below the WinFsp request timeout), or at once
when a detach or checkout fences the mount (`adapter::fenced`), so a drain is
never held up by a download. At most half the dispatcher threads (WinFsp) or
32 requests (FUSE) wait at once; past that a read fails at once instead of
occupying a thread, so stats, lookups and other reads never run out of
threads (the Visual Studio case). The failure is one programs report
meaningfully: WinFsp `STATUS_DEVICE_NOT_READY` ("The device is not ready.";
`EACCES` in the C runtime) instead of `STATUS_FILE_IS_OFFLINE` (`EINVAL`,
"invalid argument"), FUSE `EIO` instead of `EAGAIN`. `TKFS_CONTENT_STALL_MS` /
`TKFS_CONTENT_BOUND_MS` shorten the bounds (tests; never longer than the
defaults).

### 4. FUSE (`fuse_linux.rs`)

The same pre-lock work: reads, writes, fsyncs and size changes run on threads
of their own (up to 64) and wait, copy and save without the engine lock; a
flush saves the closed file (during a burst, queues its save); a release
closes through `close_handle`; an unlink, an rmdir and a rename settle the
entry they remove or replace first. The pre-lock work honours the fence as
`dispatch` does (found by
`mount_lifecycle::force_detach_persists_dirty_sessions_and_reattach_shows_them`
in WSL: an unmount makes the kernel send fsyncs, and the pre-lock save ran
them past the fence and committed what the force detach was retaining).

## Deviations from the spec, and why

1. **Write-behind during bursts.** Before, every close through the mount
   returned only after its save committed. Now a close inside a burst of
   closes returns before (deviation from the old behaviour, not from the
   spec's words): the save commits within tens of milliseconds;
   `FlushFileBuffers`/`fsync`, a graceful stop or detach, a checkout and the
   control requests that need a quiet engine wait for it (refused `BUSY_VIEW`
   and retried while it runs), and a force stop or a poison exit retains it,
   as any dirty session (invariant 8). What a hard crash (power loss, a killed
   process) can lose is bounded: the closed files whose saves were queued or
   running (at most 72), never a torn or half-committed file, the way a local
   filesystem loses what was not `fsync`ed. Why: the save is most of a small
   file's cost; synchronous off-lock saves measured 41 s with the lab's script
   against the baseline's 43–60 s, far from 2x.
2. **Right after a burst**, a stop, a checkout or a control request finds the
   last files still being saved for a few milliseconds and is refused
   `BUSY_VIEW` (the folder controller retries a stop every 2 s; a command can
   be repeated). A first version did not count those files in `quiet()`,
   which let a fork run ahead of a save; refusing is the safe choice.
   CCR-WP5.2-4 asks for the stop and control paths to wait instead.
3. **`SETTLE` (10 ms) before a background commit** is a measured adaptation to
   on-access scanners, not a correctness rule; it goes with CCR-WP5.2-1.
4. **The read waits for the whole object** (the CCR's second option), not for
   the durable prefix of its spool: a prefix is not verified (the hash covers
   the whole object), and §14.5b says "serves verified bytes". A file that
   cannot download within 240 s (several GiB on a slow link) still fails, now
   with a meaningful status.
5. **Two harnesses.** The qualification scenario copies with a native copier
   (the lab script's steps, without PowerShell's per-file buffer); both are
   reported. The lab's script gives 1.66x.
6. **`fs_writes_during_catch_up` has no floor.** With the application writing
   during the catch-up, each local commit makes the next remote event
   concurrent with it and the activator takes its slow path, whose commits
   hold the engine up to ~1 s: filesystem p99 81–99 ms. That cost is WP5.1's
   (CCR-WP4.INT-3); the scenario checks that nothing fails and everything is
   committed. The reads-only scenario (`fs_p99_during_catch_up`, the floor's
   rule) is the acceptance one.
7. **FUSE thread caps.** Content requests were capped at 16 threads; now 64
   threaded requests of any kind, 32 of them waiting for content.

## CCRs filed

- **CCR-WP5.2-1** (`src/core/commit.rs`, WP5.1): `check_commit` re-hashes a
  local event's new object under the engine lock (and SQLite's writer). WP5.1
  is adding a process-wide verified set (`core::commit::verified::note(root,
  hash, len, mtime_ns)`, in its worktree). Requested: at merge,
  `runtime::engine::store_snapshot` calls it for every object it installs or
  verifies (`install_new`, `store_file`, `verified_existing` have the hash,
  the size and the mtime), and `SETTLE` goes. Adapter: `SETTLE`; a large
  object's re-hash stays under the lock (~1 s per GiB) until then.
- **CCR-WP5.2-2** (`src/core/objects.rs`, WP5.3): `Store::put_object` /
  `put_stream` (and their dedupe, `verify_existing`) write the availability
  row on the caller's connection outside any commit; on the engine's
  connection that makes the projection view stale and the next commit reloads
  it whole (measured: 20.6 ms of a 32 KiB file's 27.1 ms save at 2K files in
  the wave-5 base). Requested: an install that hands the row to the caller
  (to batch, or to write elsewhere), or that leaves the view's key alone.
  Adapter: the engine stores saves itself and batches the rows on its own
  connection. Other callers of `put_object` on the engine connection (control
  `import`) still reload.
- **CCR-WP5.2-3** (`src/core/commit.rs`, WP5.1): a commit that overlaps
  another connection's commit drops the view (`write_commit_inner`: when
  `data_version` moved, `*cache = None`) even when that commit changed no
  projection table; it could re-key it as `adopt_foreign_commits` does when
  `projection_version` is unchanged. Observed: 54–83 full reloads (~25 ms
  each) per 2K-file copy when the availability rows were batched every
  200 ms; hence once a second now.
- **CCR-WP5.2-4** (`src/runtime/server.rs`, `src/runtime/control.rs`; the
  integrator): a graceful stop and the control requests that need a quiet
  engine should wait, bounded, for background saves
  (`engine::background_saves()`, `Engine::settling()`) before `quiet()`, so a
  command right after a burst is never refused. Adapter: deviation 2.
- **CCR-WP5.2-5** (docs, WP5.INT): REVAMP_PLAN §12 still lists "No off-lock
  save of a file's bytes in this release" (done here), ARCHITECTURE's lock
  table states the old save cost, and README *Known limitations* should state
  deviations 1, 2 and 4 (and the content-wait bounds and statuses).
- **CCR-WP5.2-6** (`tests/harness_selftest.rs`, `tests/qualification-floors.json`,
  WP5.INT): list `qual_wp5_2_local` (owner WP5.2) in `QUAL_FILES`, and add the
  floors: `copy_2000_small_files_into_a_mount` `speedup_vs_baseline >= 2` (with

## Known limitations

- **A close inside a burst is not a durability point** (deviation 1): a hard
  crash can lose the files closed in the last tens of milliseconds (at most
  72), never tear one.
- **Right after a burst** a stop or a control request may be refused
  `BUSY_VIEW` for a few milliseconds (deviation 2, CCR-WP5.2-4).
- **A large object is still re-hashed under the lock at its commit**
  (`check_commit`) until CCR-WP5.2-1: about 1 s per GiB. Its hashing and copy
  in the save are off the lock.
- **Two journal commits per new file** (the create, then the content) stay,
  each `fsync`ing the WAL under the engine lock (`synchronous=FULL`,
  invariant 4); merging them would need deferred creates, a namespace change
  of its own. With Defender's synchronous scan of every closed file, they set
  the floor of a small-file copy on this machine (~8.5 ms per file against
  the baseline's ~16.5 ms).
- **A read of content that cannot download within 240 s fails**
  (`STATUS_DEVICE_NOT_READY` / `EIO`); at most half the dispatcher threads wait
  for downloads, and reads beyond that fail at once.
- **Writes during a catch-up** meet the activator's slow path (deviation 6).
- **The 2x of the acceptance** is met with a native copier within this
  machine's noise (1.95–2.24x), not with the lab's PowerShell script (1.66x).
