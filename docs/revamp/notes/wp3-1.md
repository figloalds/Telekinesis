### The cutover (tasks 1 and 2)

- **`ctx.network` = `DaemonNetwork`.** It wraps the `PeerManager`
  (`NetworkApi::pair`, `remote_list`, `unpair`, `reconfigure` delegate) and
  holds the inbound server once `run::serve` started it. `shutdown(deadline)`
  stops both at once (the inbound side on a thread of its own), each within
  the deadline, then lets go of both: they hold the `Ctx`, and the `Ctx` holds
  this, so the cycle ends with the daemon. Idempotent.
- **Dialer-side visibility of a refused pairing.** `Pair` with a 6298d0b
  acceptor fails with `PEER_NEEDS_UPGRADE` before anything is sent (no
  `X-Tkfs-Sync` echo, §6.2), and no catalog peer (so no lane) exists to show
  it. `DaemonNetwork` records the refusal (any Incompatible-class pair error)
  as an error scoped to the endpoint, `Scope::Peer{installation:
  "<endpoint>"}` (a peer we never authenticated has no other identity), so
  Status shows it (`daemon.errors`) until that endpoint pairs, or a later
  pairing with it fails otherwise, or it is unpaired; at most 16 endpoints
  (the oldest is resolved). A peer paired before the upgrade (a 6298d0b
  data directory) that still runs 6298d0b shows on its lanes:
  `incompatible`, `PEER_NEEDS_UPGRADE`, rechecked every 10 min (WP2.6).
- **Acceptor-side visibility**: WP2.8's legacy refusal (the legacy-format
  `PEER_NEEDS_UPGRADE` reply, `InboundIncompatible`, a daemon notice in
  Status). A 6298d0b dialer shows the same code in its own Peers reply
  (`upgrade_against_a_6298d0b_peer_fails_closed_on_both_sides`, run against
  a real 6298d0b binary).
- **`ctx.legacy` = `HubLegacyView`.** List/Inspect `sync` and Peers come from
  the hub's projection for the catalog's peers (the outbound ones; an
  acceptor lists `[]`, as before). `transport` is `tkfs-peer/3`.
- **The gate.** The legacy rule (v6 `metadata_caught_up` within 15 s, in the
  bridge's lanes) is deleted with the bridge; the only evidence is the v3 one
  (`meta_exchange::evidence_of` on the dialer, the inbound `local` view on the
  acceptor; §3.3 new rule). `limits::LEGACY_GATE_FRESHNESS` stays (frozen
  model) with a note that it is unused.
- **Acceptance greps** in `src/orchestrator/`: no `published-summary` fan-out
  (only the controller's own call on Ready, §3.3), no `RpcLane`, no
  `X-Tkfs-Wire`; the one `ws::call` left is `compat::worker_call`, a call to
  the folder's own loopback worker (the `Folder` passthrough), not a peer.

## Fix round 1 (independent review, verdict "approve" with three minors)

1. **A dialer's large event waited one idle interval** (`meta_exchange.rs`,
   accepted). With CCR-WP2.5-2 a dialer's event over `LARGE_EVENT_BYTES`
   is only flagged in its request page; the acceptor asks for it in its
   reply's `need`, and the dialer serves it in its next request. The dialer's
   `ExchangeOutcome.more` was `request.page.more || reply.page.more`, so the
   scheduler (`moved && more`) booked no follow-up and the event (with any
   staged child waiting on it at the acceptor, and any missing parent the
   acceptor asks of the dialer) waited for the next trigger, at worst the
   whole interval. Fix: `more` also counts a non-empty `reply.need`. No loop:
   an id the dialer does not hold comes back `unknown` and is not asked again
   for `NEED_RETRY_MS`; the scheduler books a follow-up only for an
   exchange that moved something; and a served event the acceptor stages,
   already holds or rejects leaves its need list (`receive_items` deletes the
   `feed_needs` row), so it is not asked for again.
   `meta_exchange.rs` is WP2.7's file; the line is the dialer's half of
   CCR-WP2.5-2, applied under WP2.INT's deferral of that CCR (deviation 1),
   not filed as a new CCR. New daemon test
   `a_dialers_large_event_reaches_the_acceptor_without_waiting_for_the_interval`:
   two daemons with `sync_interval_ms=20000`, one-way pairing (B dials A),
   B makes an event of about 330 KB (the request that served it was
   331,274 bytes; the test asserts it is over `LARGE_EVENT_BYTES`): the
   shared fork of 260 directories with 724-byte names (`publish` with
   `current_state_only`), made while its sync is paused, so
   resuming calls for exactly one exchange; A must commit it within 10 s.
   **Without the fix it fails (20.5 s: the flagging exchange, then the
   serving one exactly one interval later); with it, 0.59 s and 0.69 s.** The
   pause matters: a plain local commit often yields two triggers (the
   heartbeat reports the `sync` generation bump and the new tip in separate
   beats), and the second one hid the bug in a first version of the test
   (2.5 s without the fix): the bug shows whenever the flagging exchange is
   the last one anything calls for (one heartbeat carrying both, a relayed
   large event, a missing parent asked at the tail of the feed).
2. **The replay check could pass vacuously** (`tests/v3_wire_tap/mod.rs`,
   accepted). `WireTap::unidentified()` lists the `meta.exchange` and
   `objects.exchange` requests seen without an exchange identity;
   `sync_survives_latency_bandwidth_stalls_and_resets_without_replays`
   asserts it is empty and `faulty_link_no_stuck_sync_no_replay` checks it
   (and reports the count with the replay metric). The parser is also
   stricter: a message shorter than the frame prefix, or a header that is not
   one JSON object (every v3 frame's header is, pre-auth ones included), now
   marks the stream malformed (asserted 0) instead of being skipped, so a
   framing or encoding change cannot make requests silently disappear from
   the check either.
3. **Frozen-type members at the Wave 3 merge** (no change needed here,
   accepted as a merge note). CCR-WP3.1-5 now names the one literal found in
   the other Wave 3 branches' changes (WP3.3's `tests/objects_v3_lanes.rs:971`)
   and records that no other Wave 3 branch changes a file WP3.1 changes.

## Fix round 2 (independent review, verdict "approve" with two minors)

Both findings were accepted and fixed; no finding was rejected.

1. **A panicking shutdown sequence left the network running**
   (`src/orchestrator/run.rs`, accepted with one correction to its impact).
   `serve_with` used to stop the inbound accept loop itself; after the
   cutover it relied on step 2 of `shutdown::run` (`network.shutdown`) and
   only dropped its `Arc<DaemonNetwork>`. A sequence that panics at
   `shutdown::faults::SEQUENCE` (before step 2) never reaches it, and the
   drop stops nothing: the PeerManager and the InboundServer hold the `Ctx`,
   which holds the network. Fix: `serve_with` calls
   `net.shutdown(limits::SHUTDOWN_NETWORK)` after `shutdown::run` in every
   case (`DaemonNetwork::shutdown` takes both stacks out of their slots, so a
   second call is a no-op and the normal path is unchanged), then drops it;
   the comment that claimed the network was always stopped by then is
   rewritten. Correction to the finding's impact: peer sessions were not
   served on as it says. Both stacks' tokens are children of `ctx.shutdown`
   (`inbound::start_with`, `PeerManager::start`), which is cancelled before
   the main thread wakes, so the accept loop ends (dropping the listener),

## Known limitations

- **Windows dial interruption.** The cancel hook shuts the socket down; on
  Windows that sends our FIN but does not end a blocking read in progress by
  itself. A read ends as soon as the peer closes in turn (any tkfs server,
  relay or proxy does: the `peer_supervisor` tests through a slow proxy join
  every lane at once); a peer that ignores it is bounded by the step's
  socket timeout (3 s upgrade, 5 s handshake step), and a lane still in its
  dial at the join deadline is detached as before (`detached_lanes`). A TCP
  connect in progress (≤ 3 s per address) is not interrupted on any OS. The
  existing handshake watchdog has the same property on Windows (its socket
  timeouts are what bound the read).
- Refused pairings are shown until their endpoint pairs, is unpaired or
  fails otherwise; they are not persisted (a daemon restart forgets them).
- Inbound `objects.*` exchanges record no `ExchangeStarted` (WP3.3's file);
  probe sessions are not reported as lanes (CCR-WP2.8-4).
- The two legacy-value adapters stay until the hub does it (CCR-WP3.1-1/-2).
- A request page may now be a reset or probe with `remaining` counted from
  the start (O(min(feed, 100 000)) once, as `to_send` already was).
- The wire tap records a request once its whole body crossed it; a request
  cut off mid-body by a reset is not recorded (the peer never received it
  either, so sending it again would not be a replay of a delivered request).
