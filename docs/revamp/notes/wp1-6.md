Branch `revamp/wp1-6-inbox-fastpaths`, cut from `revamp/wave-1-base`
(`abc8234`). Owned files only (§13 rule 1): `src/core/inbox.rs`,
`src/core/commit.rs`, `src/paired_sync.rs`, `tests/activation_inbox.rs`,
`tests/qual_wp1_6_activation.rs`. No registry line, no frozen file and no

## Summary

1. **Inbox state machine** (`src/core/inbox.rs`, §4.4).
   - `inbox::ensure_schema` (`schema:inbox=1`, own savepoint, idempotent):
     `incoming_events` gains `state, received_ms, attempts, retry_at_ms, code,
     error_class, blocked_on` through `ADD COLUMN` guarded by
     `pragma_table_info` (its writers all use named columns, §9);
     `incoming_waits(child, parent, PK)` with an index on `parent`;
     `incoming_sources(event, peer, seq, PK(event, peer))`; an index on
     `incoming_events(state, received_ms)` and (fix round 1) a partial
     index on `incoming_events(blocked_on)`; an `AFTER DELETE` trigger that
     drops a row's waits and sources.
   - States `ready`, `waiting`, `retry`, `quarantined`, `blocked`, and NULL
     (legacy, classified lazily). The legacy `error` column is non-NULL
     exactly for `quarantined` and `blocked` (`QUARANTINED_CAUSAL_ANCESTOR:
     <root>`), so `status().incoming_quarantined` and a 6298d0b binary's drain
     see what they always saw.
   - `stage_incoming(&self, Vec<StagedEvent>, allowed) -> StageOutcome`: one
     write transaction on any connection; never activates. Per event:
     `REPOSITORY_MISMATCH`, `PRIVATE_EVENT_REJECTED`, `UNAUTHORIZED_EVENT`, a
     malformed id and `EVENT_ID_REUSED` (against committed and staged
     payloads) are `rejected`; identical committed/staged events are
     reported; new rows become `ready`, `waiting` (one `incoming_waits` row
     per missing or staged parent), `blocked` (a quarantined ancestor) or
     `quarantined` (invalid direct link, causal cycle); sources are recorded.
   - `activate_slice(SliceBudget) -> SliceOutcome`: one write transaction;
     classifies up to 512 NULL rows first; loads a window of the 512 oldest
     `ready` and due `retry` keys in `(received_ms, rowid)` order (payloads
     are point lookups when popped); point-queries every parent; validates
     direct links against the committed parents; takes the content, creation
     or namespace successor, or the slow path inline (≤ 1 per slice) or
     returns a `SlowTicket` (`inline_slow=false`, the row stays `ready`);
     commits each event in its own savepoint inside the slice; releases the
     children of every committed event (`waiting` → `ready`) into the same
     slice's queue; measures the budget after the window load.
   - Failure classification: `SQLITE_BUSY`, `LOCKED`, `IOERR`, `FULL`,
     `NOMEM`, `CANTOPEN` and any `std::io` error → `retry` with
     `retry_at = now + min(300 s, 2^attempts s)` (1 s → 5 min), never
     quarantined; everything else (validation, malformed payload) →
     `quarantined` (`code`, `error_class` = Fatal unless §8 says
     NeedsUserAction/Incompatible) and every staged descendant → `blocked`
     (`blocked_on` = the root quarantined event); `CausalPrerequisitesPending`
     → `waiting` on the parents outside the branch's journal.
   - `blocked_on` always names the root (fix round 1). A legacy
     `QUARANTINED_CAUSAL_ANCESTOR: <id>` names the *direct* parent (that is
     what the old `validate_direct_links` wrote), so classification follows
     that chain to the root (`rejected_root`); a row that becomes blocked
     re-points the rows blocked on it to its root. Whenever a row leaves the
     rejected states (it becomes `ready`, `waiting` or `retry`, or it
     commits), every row blocked on it becomes `waiting` on it (`unblock`),
     so it activates with it; activation re-checks every link, so a row with
     another quarantined ancestor is blocked again. A legacy transient
     quarantine (deviation 7) is a usable parent, not a rejected one. On
     open, a blocked row whose `blocked_on` is no longer a quarantined root
     is re-classified. `revalidate(Some)` follows `blocked_on` transitively.
     A partial index on `blocked_on` keeps the per-commit check a point
     lookup.
   - `inbox_counts`, `missing_parents`, `quarantined`, `revalidate`,
     `requeue`, `prepare_slow` (W1: `Prepared::Inline`), `commit_prepared`
     (W1: the slow path under the caller's lock; `Stale` when the row no
     longer applies).
   - Compatibility: `receive_with_budget` = the v6 page checks (unchanged),
     staging, then slices until `budget` attempts (`Some(32)`: ≤ 32 attempts
     and 50 ms of activation work, at least one attempt) or until no row is
     ready (`None`); returns already committed plus activated ids as before.
     `receive` and `drain_incoming` loop until nothing is ready.
     `startup_drain(defer)`: retry rows become due, waits on committed
     parents are dropped, rows whose `error` disagrees with their state are
     re-classified, NULL rows are classified (progress per chunk); with
     `defer=false` it activates (progress per slice) and seals the startup
     snapshot once if any fast-path activation happened.
2. **CCR-WP0.INT-5 item 2 applied.** Every inbox write transaction (stage,
   slice, revalidate, `commit_prepared`, the startup repairs) starts with
   `BEGIN IMMEDIATE` from autocommit (`RELEASE`/`COMMIT`, `ROLLBACK` on any
   failure, including a failed `COMMIT`); inside a caller's transaction it is
   only a savepoint. A busy writer slot makes activation wait
   (`busy_timeout`), never fail on a read-to-write upgrade.
3. **Remote fast paths** (`src/core/commit.rs`, §5.1).
   - `commit_ready` is split into `check_commit` (all projection-free
     validation, unchanged), `fast_successor` and `commit_checked` (the write;
     unchanged statements, including the forced seal after a slow commit), so
     activation decides fast/slow (and issues a `SlowTicket`) before writing.
   - `creation_successor` and `namespace_successor` accept any device unless
     `TKFS_REMOTE_FASTPATH=0` (`core::commit::remote_fast_paths_enabled`,
     `OnceLock`). Their conflict gate is `branch_has_unresolved_conflicts(
     event.branch)` (`EXISTS … resolved_by IS NULL`) instead of
     `!self.conflicts()?.is_empty()` (any row of the *active* branch). The
     restriction argument is in the module docs.
   - `namespace_successor` now derives `modified_ms` exactly as `project`
     does (latest winner of the non-`basic` registers). The old
     `max(old, created_ms)` diverged from full replay whenever the changed
     register's previous winner was the newest one and the event's clock is
     older (a remote device, or a local event after a remote one); the oracle
     fuzz found nothing else.
   - The "deleted directory has live children" check uses the slot index
     (`O(log n)`) instead of scanning every entry.
   - `Store::commit_path_counters()` (fast/slow commits per handle) and the
     fault point `core.commit.busy` (a genuine `SQLITE_BUSY` before any write).
     The counters count durable commits only (fix round 1): a commit made
     inside an enclosing transaction (a slice, a control request) is kept
     pending by event id and counted once the connection is back in
     autocommit with the event in the journal; a rolled-back one is dropped.
     Pending entries settle at the next outermost commit, at the end of
     every inbox write transaction and on every counters read.
   - The successors still do not count `NAMESPACE_HISTORY_LIMIT` cuts; see
     CCR-WP1.6-5 and Known limitations (documented in the `commit.rs`
     module docs).
4. **`paired_sync`**: `pending_events`, the local pending count and every
   `caught_up` use `inbox_counts().pending_active()` (ready + waiting + retry
   + unclassified: quarantined and blocked rows are excluded, missing-parent
   rows still count, so `received_mount_waits…` keeps its meaning).
   `content_status()` is gone from `receive_for_lane` and `published-apply`
   in `paired_sync.rs`; their `content` is `{incoming: InboxCounts,
   outgoing_unacknowledged}`. **Correction (fix round 1):** on the bulk lane
   (a `published-apply` page with object parts) `runtime/published.rs`
   (not this package's file) still overwrites that `content` with
   `transfer.content_status()` after installing the parts, because the
   status object has no `known_objects` key (`published.rs:68-74`). The
   O(repository) scan and the old `content` shape remain on that path;
   CCR-WP1.6-4 asks for the override to go. No adapter is possible from
   the owned files: the override runs after `worker_control` returns.
   `metadata_progress` gained `local_blocked` and `local_quarantined`
   (additive; the compat goldens allow extra keys).
5. **Activation cost.** Inbox-only writes (object bookkeeping, staging,
   classification, transaction boundaries) keep a fresh projection view
   fresh (`keep_view`/`rekey_view`), so a page no longer reloads the whole
   projection; with the commit's own view patch a fast-path activation is
   O(1) apart from the 128-event snapshot seal (CCR-WP1.6-1).

## Deviations from the spec, and why

1. **Stage also quarantines.** §14 lists `ready`/`waiting`/`blocked` as the
   stage-time states. An event whose direct link is invalid against a parent
   already known (committed or staged), or that closes a causal cycle, is
   quarantined at stage. The old drain refused both on its next pass
   (`validate_incoming_links` against every known event); a cycle could
   never become ready and would otherwise count as pending forever. A cycle
   is searched only when the new event already has waiting children, so
   in-order and reverse-order delivery stay O(1) per event.
2. **The legacy receive keeps whole-page refusals.** `receive_with_budget`
   stages in strict mode: an `EVENT_ID_REUSED` fails the page and stages
   nothing (as before), and a foreign repository or bad id inside a page is
   staged and quarantined at activation (as before). Only the new
   `stage_incoming` reports per-event `rejected`.
3. **`TKFS_REMOTE_FASTPATH=0` restores the whole previous gate**: successors
   only for this device's events, disabled by any conflict row of the
   branch (resolved or not). This is also §5.1's oracle fallback. The 100
   seeded scripts found no mismatch, so the default gate is
   `branch_has_unresolved_conflicts`.
4. **Startup seal after a fast-path drain.** Fast-path commits seal the
   startup snapshot every 128 events, so a startup drain of remote creates
   (previously all slow path, each sealed) left a suffix. The next open
   replays it correctly, but re-serializes the snapshot, which
   `harness_selftest::fixtures_are_deterministic_per_seed` (WP0.5) compares
   as a string. `startup_drain` seals each touched branch once after the
   drain (CCR-WP1.6-2).
5. **`namespace_successor`'s `modified_ms` is fixed for local events too**
   (Summary 3); the old value was only reachable with skewed clocks.
6. **Retries.** A restart makes every `retry` row due (a new process is the
   natural retry point; the qualification scenario `transient_retry` relies
   on it). `revalidate` also re-queues `retry` rows. A
   `CausalPrerequisitesPending` with no identifiable missing parent goes to
   `retry`, not `waiting` (nothing would ever release it).
7. **Legacy transient quarantines are retried.** A NULL-state row whose
   legacy `error` records a transient SQLite failure (`database is locked`,
   `disk I/O error`, …; RC11: the old drain quarantined everything) is
   re-classified instead of kept quarantined. A still-invalid event is
   quarantined again at activation.
8. **Additive API** beyond §14's list: `SliceBudget::{ACTIVATOR, UNBOUNDED}`,
   `PreparedCommit::ticket()`, `CommitPathCounters` and
   `Store::commit_path_counters()`; the free function lives at
   `tkfs::core::commit::remote_fast_paths_enabled` (`core.rs` is not this
   package's file, so no root re-export). Fault points `core.commit.busy`
   and `core.inbox.window` (hang during the window load).
9. **The qualification file stays `#[ignore = "WP1.6"]`.** `qualify.ps1`
   runs ignored scenarios only (`--ignored`), and
   `harness_selftest::qual_files_exist_and_ignores_name_their_owner` requires
   every ignore in it to name its owner; WP1.5 did the same. "Un-ignored"
   here means the scenarios pass. Changes to the file: counters and a
   fast-path check in `remote_linear_create`, an inbox-count check and
   `util::fault::reload_from_env()` in `transient_retry` (the fault
   configuration is read once per process, and the earlier scenarios of the
   binary hit `core.commit.busy` before the variables are set), a fast-path
   check and `slow_path_commits` metric in
   `local_create_after_resolved_conflict`. No assertion was weakened.
10. **A per-event rollback failure fails the slice.** If SQLite has already
    rolled the whole transaction back (I/O or full-disk error), the slice
    returns the error instead of writing state outside a transaction.
11. **Blocked rows are released when the row they are blocked on can
    commit again** (fix round 1). §4.4 only says descendants of a
    quarantined event become `blocked` and `revalidate` re-queues. A
    blocked row now becomes `waiting` on its root whenever that root
    becomes `ready`/`waiting`/`retry` or commits. Without this, the legacy
    transient roots of deviation 7 committed while their descendants stayed
    `blocked` for good (review blocker). In the current state machine a
    quarantined root only leaves quarantine through `revalidate`, which
    already re-queued its blocked rows, so nothing changes for rows written
    by this binary.
12. **Extra index** `incoming_events_blocked_on` (partial, `blocked_on IS NOT
    NULL`) beyond §9's `incoming_waits(parent)` and `incoming_events(state)`,
    so the release check on every commit is a point lookup. It is created
    with `IF NOT EXISTS` under the same `schema:inbox=1` stamp, which no
    released build has written yet.

No existing test file other than the two owned ones was edited, and no
assertion changed.

## CCRs filed

- **CCR-WP1.6-1 (snapshot seal cadence; `src/core/snapshot.rs`, no Wave 1
  owner).** A fast-path commit calls `snapshot::maybe_persist(.., false)`,
  which seals every 128 journal sequences; each seal re-reads and hashes
  the branch's whole journal and serializes the whole projection
  (≈ 200 ms at 5–10K events on the dev box). At 10K remote creates that is
  ≈ 1.6 ms of the ≈ 3–4 ms per event, and it grows linearly (≈ 8 ms/event
  at 50K). Requested: scale the interval with the branch size (for example
  `max(128, events/16)`, with the suffix-replay bound in
  `try_resume_snapshot` following it), or seal incrementally. Adapter: none;
  the 10K floor (≤ 5 ms) holds today.
- **CCR-WP1.6-2 (`tests/harness_selftest.rs`, WP0.5).**
  `fixtures_are_deterministic_per_seed` compares the clone's snapshot
  payload string with a re-serialized `serde_json::Value`, which only holds
  when no suffix was replayed on open. Requested: compare parsed JSON (or the
  cursor). Adapter: `startup_drain` seals once after fast-path activations
  (deviation 4), which is also good hygiene for the next start.
- **CCR-WP1.6-3 (`src/core/status.rs`, WP1.8; `src/runtime/control.rs`, no
  owner).** `status().incoming_pending` is still `count(*)` over the inbox,
  and `Engine::control("status")` requires it to be 0 for `caught_up`, so
  one quarantined event keeps the worker's own `caught_up` false forever
  (the lanes' `caught_up` is fixed here). Requested: `incoming_pending` =
  `inbox_counts().pending_active()` (keep `incoming_quarantined` as the
  legacy `error IS NOT NULL` count, add `incoming_blocked`), and the
  `content_status()` scan out of the status hot path (WP1.8 already plans
  `content_counters`). Adapter: none needed by WP1.6.
- **CCR-WP1.6-4 (`src/runtime/published.rs`, WP2.3; WP1.8 owns only its
  bulk-receive error path).** `published_rpc` replaces the
  `published-apply` result's `content` with `transfer.content_status()`
  whenever the page carried object parts (`published.rs:68-74`: the
  `else` branch of `result.get("known_objects")`, which is always taken for
  `published-apply`). That keeps the O(repository) scan WP1.6 task 6
  removed from `paired_sync`, and the old `content` shape, on the bulk
  lane. Requested: drop the `else` branch (the `content` that
  `worker_control` built, `{incoming, outgoing_unacknowledged}`, is
  already current after the parts are registered: neither counter depends
  on object installation), or set it from `inbox_counts()` and
  `outgoing_unacknowledged()`. Adapter: none possible; the override runs
  after `worker_control` returns. Found by the fix-round-1 review.
- **CCR-WP1.6-5 (`src/core/derive.rs`, WP1.7).** The creation and namespace
  successors never run `persist_projection`, so they never count
  `NAMESPACE_HISTORY_LIMIT` cuts (invariant 11: the refusal happens before
  ACK). A rename or move to a parent or `(parent, name)` slot the entity
  never used joins dependency cones (`NamespaceCones` unions historical
  parents and slot sharers), and a delete makes the entity's
  `alive = true` save assertions eligible as TRUE-presence extrema; either
  can raise the competing-cut count among *old* events past
  `MAX_NAMESPACE_CUTS`. Full replay would refuse that event; through a
  successor it commits, and the next slow commit or rebuild of the cone is
  refused instead (a rebuild on open then fails, as in
  `namespace_history_budget_refuses_commit_without_erasing_records`). The
  gap exists for local events since before WP1.6. WP1.6 widened it to
  remote ones, as §5.1 requires. Requested: expose the append-mode
  counting of §5.2 (d) (`relevant_after(C)` antichains of the touched
  cones, counting only) as a check the successors can call, or an index of
  historical slots and parents per entity so a successor can prove that no
  cone is joined. The counting must stay much cheaper than the slow path,
  or the remote fast paths lose their point. Adapter: none. The reviewer's
  first suggestion was to fall back to the slow path when a location
  change introduces a parent or slot new to the entity. I rejected it:
  every temp-file replacement (the temp entity has never used the target
  slot), every move into another directory and every rename to a fresh
  name hits that condition, so the remote namespace successor of §5.1
  would almost never apply, and it would still miss the delete case. The
  gap is documented in the `commit.rs` module docs. Found by the
  fix-round-1 review; not reproduced (it needs more than 4,096 competing
  cuts in a joined cone).

## Invariants at risk (4, 9, 10, 11)

- **4 (atomic commit, `synchronous=FULL`).** Each event commits in a
  savepoint inside the slice transaction, together with its inbox row
  bookkeeping (row delete, released children), so a crash keeps both or
  neither; the journal, projection, outbox, frontier, conflicts and seal
  statements are unchanged. Pragmas are unchanged.
- **9 (causal activation).** An event is tried only when the point queries
  find every dependency and change parent committed; children are released
  only by the commit of their last missing parent; stage-time waits are
  written under the writer lock, so a commit on another connection cannot
  slip between the check and the wait.
- **10 (committed-only acks).** `receive` returns the same ids as before
  (already committed plus activated); `paired_sync` still binds acks to the
  sent and committed set. Staged, waiting, retry and quarantined rows are
  never in an inventory.
- **11 (deterministic conflicts).** The successors are a restriction of full
  replay for conflict records (argument in `commit.rs`); the seeded oracle
  scripts and the kill-switch replay are the executable check, including
  restarts. They do not count `NAMESPACE_HISTORY_LIMIT` cuts, so the
  "refusal before ACK" half of invariant 11 is not guaranteed for successor
  commits (local since before WP1.6, remote now): CCR-WP1.6-5.

## Known limitations

- The background activator (WP2.3) and off-lock `prepare_slow` (WP2.4) are
  not here: `Prepared::Computed` carries only its ticket and commits inline.
  A slice with `inline_slow=false` stops at the first slow event and returns
  its ticket every time until the caller commits or re-queues it.
- Two-way activation (a receiver with unseen local events) is still the slow
  path (`two_way_backlog_2k` unchanged); WP1.7's append mode addresses it.
- Fast-path activation still pays the O(history) startup-snapshot seal every
  128 events (CCR-WP1.6-1).
- The worker's own `status.caught_up` still counts quarantined rows
  (CCR-WP1.6-3).
- The bulk-lane `published-apply` result still carries the
  `content_status()` scan and shape (CCR-WP1.6-4).
- Successor commits (creation and namespace, local and remote) do not
  count `NAMESPACE_HISTORY_LIMIT` cuts; a commit that joins dependency
  cones past the limit is accepted, and the next slow commit or rebuild of
  that cone is refused (CCR-WP1.6-5).
- Commit path counters settle lazily: a commit made inside a caller's
  transaction shows up only after the connection is back in autocommit
  (the next outermost commit, inbox write transaction or counters read).
- The seeded fuzz takes about 50–100 s in a debug build (oracle after every
  activation, 100 seeds, plus the kill-switch replay).
