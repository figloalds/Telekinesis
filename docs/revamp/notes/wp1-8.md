### 1. Schema (`objects::ensure_schema`, `config('schema:objects')=1`)

All `CREATE … IF NOT EXISTS` in one `SAVEPOINT objects_schema`:

| Table / trigger | Meaning |
|---|---|
| `object_availability(hash PK, size, state, mtime_ns, verified_ms)` + index `(state, verified_ms)` | state `0` missing, `2` available, `3` corrupt (`objects::{MISSING, AVAILABLE, CORRUPT}`) |
| `event_objects(hash, event, shared, PK(hash, event))` + index on `event` | triggers `AFTER INSERT`, `AFTER DELETE`, `AFTER UPDATE OF id,payload ON events`; `json_each(payload,'$.changes')` where `field='content'` and the value is text; `shared` from `$.branch.shared` (the same source as `Event::branch.shared`). A non-JSON payload yields no rows instead of failing the insert. |
| `staged_objects(hash, event, PK)` + index on `event` | same triggers on `incoming_events` (`UPDATE OF id,payload` only, so state/error updates by WP1.6 do not fire it) |
| `object_error_state(hash PK, code, class, attempts, retry_at_ms, last_ms)` | per-object backoff; the positional `object_errors` table and its writers are unchanged |

Because they are triggers, both reference indexes stay correct for writes by
older binaries (like `journal_sequence`).

**Backfill `event_objects_v1`** (in `ensure_schema`): events then
incoming events, 10,000 rowids per transaction, a cursor in
`config('event_objects_v1:events' | ':incoming')` so an interrupted backfill
resumes, `startup_progress("indexing object references")` per chunk from the
opening thread (invariant 28), cursors removed and the marker set at the end.

### 2. Startup (`objects::startup_object_check`, phase 4 of `Store::open`)

* `VerifyMode::Changed` is now the `Default`, so `Store::open_existing` (and
  `Store::open`) run `Changed`; `Full` and `Lazy` stay selectable through
  `open_existing_with`.
* **One directory enumeration** of `objects/` (`read_dir` returns size and
  mtime per entry on Windows) instead of one `stat` per object. Measured on
  this box: 1,000 `fs::metadata` calls ≈ 200 ms (an open per call, with the
  AV filter), 5,000 directory entries ≈ 10 ms.
* Candidates: `event_objects ∪ staged_objects ∪ object_availability`.
  * **Trusted** (no hash): row available, same size and mtime, verified, and
    not *racy* (`verified_ms` at least 3 s after the file mtime, so a
    same-size rewrite inside one timestamp tick cannot hide).
  * **Every install stamps the mtime** `objects::STAMP_SECS`
    (2001-01-01T00:00:00Z) on the temp file/spool before the rename, so new
    objects are trusted at once and any later write changes the mtime
    (verified on NTFS: the stamp survives close and `MoveFileExW`; directory
    listing and `fs::metadata` report the same value). If stamping fails the
    real mtime is recorded and the racy rule applies.
  * Untrusted present objects are hashed once (`Changed`), always (`Full`), or
    never (`Lazy`: size-consistent files become available with
    `verified_ms=0`, size mismatches are quarantined without hashing).
  * Corrupt: renamed to `<hash>.corrupt-<id>` (as before), legacy
    `object_errors` row, `object_error_state` backoff, state `CORRUPT`, and
    the download is queued.
  * **Deleted** (row available, no file): state `MISSING` and the request is
    queued (`object_requests`). Rowless absent objects get a `MISSING` row, so
    after an open every referenced object has a row.
  * 10,000 candidates per savepoint; progress per candidate (throttled).
* **One-time pass after upgrade** (`availability_v2` absent): the legacy
  per-open bookkeeping (`object_references` from `event_objects`; every
  event's `object_sizes` through `remember_object_size`, so
  `OBJECT_SIZE_CHANGED` still fails the open) runs once, chunked; every
  object without a row is hashed once. Rows written by an interrupted pass are
  trusted on resume, so the pass is resumable. The legacy `availability_v1`
  publication of verified shared objects is kept.
* `scrub_step(budget_bytes) -> ScrubOutcome{verified, corrupt, bytes}`:
  verifies available rows (unverified first, then racy, then least recently
  verified), quarantines corrupt ones, heals missing ones; at least one object
  per call when the budget is positive.

### 3. Availability, inventories and demand

* `object_available(h)`: point lookup in the index (rowless objects keep the
  legacy `stat` check). `object_available_checked(h)`: one `stat`, heals the
  row (missing, corrupt for a size mismatch, or available-unverified).
* Rows are written by `put_object` / `put_stream` (new install and verified
  dedupe), `register_received`, quarantine, verification failures
  (`open_object` marks `CORRUPT` on a hash mismatch and `MISSING` on
  `NotFound`: the read-path heal), and the startup check. Writes outside the
  startup check are best effort: the index is derived.
* **Physical presence for inventories and status** comes from one cached
  listing of `objects/` (`Store::presence`), shared by every handle of a store
  in the process (bulk lanes open a short-lived handle per RPC). It is reused
  while the directory mtime is unchanged and the listing is not racy (taken at
  least 100 ms after the directory's last change; 3 s on whole-second
  filesystems); every create, delete or rename of an entry changes the
  directory mtime (verified on NTFS). Cost when unchanged: one directory
  `stat` (~37 µs).
* `shared_object_inventory`: one SQL join over `published ∪ received`, the
  index (excludes `CORRUPT`) and `object_sizes`, confirmed against the
  listing — the legacy semantics without a `stat` per object, and bytes
  deleted behind the store's back are never advertised.
* `request_object`: `EXISTS` on `event_objects` (plus a heal of the row).
  `remember_requests`: one savepoint, `EXISTS … shared=1` per wanted object,
  presence from the listing, no journal parse. `wanted_objects`: newest
  demand first, requests younger than 24 h (`requested_ms`), at most 1,024,
  excluding available objects.
* `objects_referenced_committed(h)` (a committed **shared** event, the §6.4
  authorization meaning) and `objects_referenced_staged(h)` (an inbox row
  with `error IS NULL`, i.e. neither quarantined nor blocked).
* `record_object_error(h, e, retry_at_ms)`, `record_object_failure(h, e)`
  (§8 object backoff 30 s → 1 h by attempt, Contention never recorded),
  `object_backoff(h) -> Option<retry_at_ms>` while in backoff.
  `register_received` and new availability clear the backoff.

### 4. `content_counters` / `content_status`

One SQL pass over `event_objects` (grouped by hash) joined with sizes,
availability and the grants, plus one walk of the cached active projection;
presence from the listing. The compatibility shape (`items` ≤ 20 with path and
`object_state`, and the same keys as before) is built from the same scan, so
`content_counters` always matches `content_status`. The scan result is cached
per handle until `total_changes`, `PRAGMA data_version`, the transaction
state, the active branch or the listing changes (60 s at most); spool bytes,
demand and item details are read on every call. `object_state` keeps its
legacy `stat` (it runs for at most 20 items).

### 5. Per-object outcomes (`core/transfer.rs`)

* `receive_parts_outcomes(parts, events, allowed, locks) -> Vec<PartOutcome>`
  with `PartOutcome::{Completed{object,size}, Appended{object,offset},
  Skipped{object}, Failed{object, error: ErrorWire}}`. Page-level
  `UNAUTHORIZED_EVENT` still fails the call; every per-object problem fails
  only that object.
* `receive_parts_until(…, deadline)`: after the deadline the remaining parts
  are `Skipped` untouched (at least one part is received). Skipped objects
  stay out of the reply's inventory, so the peer offers them again.
* Authorization per object (`EXISTS` on `event_objects … shared=1`, or a page
  event) instead of parsing the journal per page.
* After taking the object lock: skip only if **shareable and available**
  (index, confirmed with one `stat` when the index says available) — no
  re-hash of a duplicate part. A physically present private object is
  received, verified, and registered by the caller (I4). An orphaned spool of
  an already-available object is removed.
* No spool is created for `offset > 0` without one (`Skipped`).
* The redundant second `sync_all` is gone; a spool completed by an earlier
  call or process is flushed once before hashing.
* If the destination exists: kept when it verifies, otherwise set aside as
  `corrupt-<id>` and replaced by the verified spool.
* `fault("object_installed")` after the install (crash between install and
  registration).
* Wrappers: `receive_parts_data[_locked]` (completed objects or the first
  error), `receive_parts` (registers the completed objects even when a part
  failed, records each failure's backoff, then returns the first error).
* `register_received` is one savepoint and also records availability and
  clears `object_error_state`.

### 6. `bulk_sync` (wire protocol 1 unchanged)

* Sender (`offer`): permitted objects come from one join
  (`peer_known ⋈ event_objects`); objects in backoff are skipped;
  unreadable objects are skipped and healed/backed off after the read
  snapshot ends (never failing the page); at most `MAX_PAGE_PARTS = 4,096`
  parts, each charged its exact JSON size (`"<hash>":{"offset":…,"total":…,"hex":"…"},`)
  instead of a flat 256 bytes.
* Receiver (`receive`): per-object outcomes within `RECEIVE_BUDGET = 5 s`;
  completed objects registered and failures' `object_error_state` written in
  one `BEGIN IMMEDIATE`; the page still answers the first failure.

### 7. `runtime/published.rs` (bulk-receive error path)

Per-object outcomes within the same 5 s budget. Completed objects are
registered first; then each failed object gets the unchanged positional
`object_errors` insert and its `object_error_state`; the first failure is
returned. A page-level failure keeps the old behaviour (an `object_errors`
row for every object of the page).

## Deviations from the spec, and why

1. **`VerifyMode::default()` is `Changed`** (WP0.3 described the default as
   `Full`). `Store::open_existing` lives in `core.rs` (not owned), and its
   `OpenOptions::default()` uses `VerifyMode::default()`, which is defined in
   `objects.rs` (owned). Changing the enum default is the in-ownership way to
   make `open_existing` default to `Changed`; it also applies to
   `Store::open`/`initialize`, which is harmless (a new store has nothing to
   hash; an old one gets the one-time pass). The doc comment on `OpenOptions`
   in `core.rs` still says "Wave 0: every VerifyMode verifies like Full"
   (CCR-WP1.8-1).
2. **Presence for inventories and status comes from a cached directory
   listing, not from the index alone.** The spec says `shared_object_inventory`
   becomes one SQL join and `content_counters` uses no `stat`. With the index
   alone, bytes deleted behind the store's back stayed advertised until a read
   healed them, and `tests/paired_sync.rs::legacy_missing_size_does_not_block_status_or_metadata_and_content_can_recover`
   (delete a CAS file, then expect `status.content.current_missing == 1` and a
   full offer that does not fail) broke. The listing keeps the legacy semantics
   at the cost of one directory `stat` per call when nothing changed, and one
   enumeration (≈ 2 µs per entry) after a change. The SQL join is still one
   statement; nothing `stat`s per object.
3. **In-place rewrites by other programs**: the listing caches lengths, and an
   in-place rewrite does not change the directory mtime. The store never
   rewrites a CAS file in place (installs are renames), so only an external
   program can do this; it is seen by the next directory change, any read
   (`open_object` hashes), `scrub_step` or the next startup. The property test
   models an out-of-band size change as a replace (delete + create).
4. **`receive_parts_until` and the 5 s receive budget** are additions. With
   the 4,096-part cap, one page of tiny objects took longer than the legacy
   15 s RPC deadline to install on this box (~10 ms of fsync per object, which
   the plan keeps on purpose: per-append fsync, whole-object verification), so
   `qual_wp1_8_objects::tiny_pending_objects_12k` failed with a socket timeout
   (`os error 10060`). Bounding the work per call keeps every RPC inside its
   deadline; the scenario now completes (below).
5. **`record_object_error` returns `Result<()>`** (the spec lists no return
   type), and `record_object_failure(h, e) -> Result<u64>` computes the §8
   object backoff. `objects_referenced_committed` means a committed **shared**
   event (the §6.4 authorization use); `request_object` keeps its legacy
   "any committed event" rule.
6. **Qualification scenarios stay `#[ignore = "WP1.8"]`.** They are
   implemented and pass, but run only in release through
   `scripts/qualify.ps1 … --ignored` (same convention as WP1.4 and WP1.12);
   their behaviours run in the default suite as `tests/availability_index.rs`.
7. **`wanted_objects` 24 h expiry** follows the spec; older requests stay in
   `object_requests` but are no longer advertised. Readers re-request on
   access (`fetch_verified` → `request_object` refreshes `requested_ms`).
8. **`object_state`** keeps a `stat` (legacy semantics, at most 20 calls per
   status) and reports `retrying` for an `object_error_state` row too.

## CCRs filed

* **CCR-WP1.8-1** — `src/core.rs` (WP0.3, frozen): update the `OpenOptions`
  doc comment ("Wave 0: every `VerifyMode` verifies like `Full`") to say that
  `VerifyMode::default()` is `Changed` and that `Lazy` skips hashing.
  *Reason*: the comment is now wrong. *Adapter*: none needed (behaviour comes
  from `objects.rs`).
* **CCR-WP1.8-2** — `src/core.rs`: add `pub use transfer::PartOutcome;` and
  `pub use objects::ScrubOutcome;` next to the existing re-exports.
  *Reason*: callers (WP2.3 maintenance, WP3.2) would use `tkfs::core::*`.
  *Adapter*: both are reachable as `tkfs::core::transfer::PartOutcome` and
  `tkfs::core::objects::ScrubOutcome`.
* **CCR-WP1.8-3** — `src/runtime/content.rs` (`fetch_verified`, not owned):
  quarantine corrupt bytes through the store (state `CORRUPT`,
  `object_error_state`) instead of a bare `rename`. *Reason*: the index learns
  of that rename only through a heal. *Adapter*: `fetch_verified` calls
  `request_object` right after, which reconciles the row (`MISSING`).
* **Integration note (not a CCR)**: WP1.4 turns `.lock().unwrap()` on the
  engine in `runtime/*` into `lock_engine`; `runtime/published.rs` now has two
  such locks in the bulk-receive error path (replacing one). WP1.6 removes
  `content_status()` from `published-apply`; `published.rs` still sets
  `result["content"] = transfer.content_status()?` after receiving parts (now
  cached and listing-based, but a fresh handle loads the projection).

## Known limitations

* Presence comes from a directory listing: after any change in `objects/`, the
  next inventory or status call enumerates it again (≈ 2 µs per entry here,
  ≈ 100 ms at 50K objects). During a large download this happens on most
  bulk rounds. It replaces 4–6 sweeps of one `stat` per object per round, but
  it is still O(objects) after a change; objects v3 (`objects.want` from the
  indexes, WP3.2) removes it from the data path.
* In-place rewrites of CAS files by other programs are seen late (deviation 3).
* The startup check still enumerates every candidate (O(objects) memory and
  SQL rows, no hashing). The rest of the restart cost at 20K is outside this
  package (journal validation, frontier rebuild and snapshot resume parse the
  journal).
* The receive path still fsyncs each spool append and installs with a
  write-through rename (the plan's conservative data plane): ~10 ms per object
  on this box, so tiny objects move at ~170 objects/s per lane.
* `scrub_step` is an API only; WP2.3's maintenance thread schedules it.
* The receiver still answers a page with its first per-object failure (wire
  behaviour unchanged); the opposite direction of that exchange is lost for
  that round (RC7's coupling is a v3 topic).
* Startup progress is emitted from the opening thread per backfill chunk and
  per checked object (throttled to one line per second); the cross-package
  guard test `worker_lifecycle::backfill_reports_progress` belongs to WP1.4.
