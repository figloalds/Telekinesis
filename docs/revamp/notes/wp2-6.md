# WP2.6 — PeerSupervisor, lanes, catalog client, v3 NetworkApi

Branch `revamp/wp2-6-peer-supervisor`, cut from `revamp/wave-2-base`
(`ca7d8a9`).

## Summary

WP2.6 lands the outbound half of the v3 peer stack (REVAMP_PLAN §3.7), built
standalone as §14 asks: nothing wires it yet (WP3.1 makes it `ctx.network`).
Only the two owned files changed; no registry line was needed (WP0.INT
already declared `pub mod peer;`).

| File | Content |
|---|---|
| `src/orchestrator/peer.rs` | `PeerManager` (implements `NetworkApi`), `PeerOptions`, `PeerView`/`LaneView`, the private per-peer `Supervisor`, the lane state machine, the catalog client, and the helpers `list_catalog`/`parse_catalog_reply` |
| `tests/peer_supervisor.rs` | 18 tests against fake v3 servers (`session::accept` plus a test handler), an emulated legacy server and a dropping listener, with a real `Catalog` and a real `StatusHub` |

### Provided API

- `PeerManager::start(ctx: Arc<Ctx>) -> Arc<PeerManager>` (the frozen
  signature) and `PeerManager::start_with(ctx, PeerOptions)` (explicit timing;
  `PeerOptions::default()` is the §3.7 policy).
- `impl NetworkApi for PeerManager`: `pair`, `remote_list`, `unpair`,
  `reconfigure`, `shutdown`.
- Read-only views for WP2.INT/WP3.1 and tests: `context(installation) ->
  Option<Arc<PeerContext>>` (the remote catalog), `peers()`, `peer(installation)
  -> Option<PeerView>`, `reconciled_generation()`, `options()`.
- `peer::list_catalog(conn, since)` and `peer::parse_catalog_reply(reply)`.

### Behaviour

**Manager.** One supervisor per catalog peer, keyed by installation. The
`peer-manager` thread follows the catalog generation (500 ms waits, like the
folder registry); `pair`, `unpair` and `reconfigure` reconcile synchronously.
Reconcilers are serialized and always diff the *newest* catalog snapshot
(taken under the serializing lock), so a reconciler holding an older snapshot
can never undo a newer change. A peer whose record changed (endpoint, code,
connections or revision) is stopped and respawned; its last good remote
catalog is carried into the new supervisor. A peer that left the catalog is
stopped and reported `PeerRemoved`. When several records name one
installation (legacy data), the first by endpoint is supervised.

**Lanes.** Pool `max(connections, 2)`: lane 0 control, lanes 1..N-1 bulk with
`LaneSpec{index: lane - 1, count: N - 1}` (the legacy numbering, so
`Lane::owns` sharding is unchanged). Each lane has its own thread and state
machine: `Idle → Dialing → Handshaking → Ready`, `Backoff` (1 s → 60 s, ±20 %,
attempt count reset after 30 s Ready, `util::Backoff` semantics),
`Incompatible` (recheck 10 min), `Unauthorized` (recheck 60 s), `Closed`.
Dials use `session::dial_expecting` with the catalog installation
(`PEER_INSTALLATION_CHANGED`), `CodeAuth`, role and lane spec, and the pool in
the hello.

`Incompatible` and `Unauthorized` are a **peer-level block**: every lane that is
not connected waits for it (showing the block's state, error and recheck time
once per block); when it expires exactly one lane re-dials (the probe) while
the others wait for its outcome. Success lifts the block for all lanes; the
same refusal re-arms it; a transient failure of the probe drops the block and
each lane falls back to its own backoff. `peer_meta.incompatible` is recorded
when a block starts or changes code, and cleared (with `last_seen_ms`) on
every control-lane session establishment. These `RecordPeerSeen` writes are
queued (bounded, 64) for a `peer-meta` thread and never run on a lane
thread: a slow or wedged catalog actor never holds a lane (§2.3, "Catalog …
must never stop … lanes"); a write that does not fit is dropped and logged.

Classification of dial failures: `NeedsUpgrade`, `Unsupported` and any
Incompatible-class code → `Incompatible`; `Unauthorized(_)` and any
NeedsUserAction/Fatal-class refusal (`PEER_INSTALLATION_CHANGED`,
`CANNOT_PAIR_WITH_SELF`, `PAIRING_CODE_NOT_SET`, `PEER_REVOKED`, …) →
`Unauthorized`; everything else (connect failures, timeouts,
`TOO_MANY_SESSIONS`, protocol violations) → lane `Backoff`. A Ready session
that closes always goes through `Backoff`, with the close reason (for example
the server's `GOAWAY{PAIRING_CODE_CHANGED}`) as its error; the redial decides
whether the peer is now `Unauthorized`.

**Runners.** On `Ready` the lane starts `scheduler::run_control` (lane 0,
thread `ctl-<installation>`) or `objects::run_bulk_lane` (thread
`bulk-<installation>-<lane>`) with a per-session child `Cancel`, and watches the
session with `Conn::wait_closed`. When the session ends the runner's token is
cancelled and the runner joined (≤ 1 s, then detached and logged). A runner
that returns while its session is open, or panics, gets the session closed,
so the lane restarts it on a fresh session after a backoff.

**Catalog client** (lane 0). `catalog.list{since: None}` as soon as the
session is Ready, then `since = last generation` every 2 s. An `unchanged`
reply changes nothing. `PeerContext.catalog` is stored when the generation or
the entries change; `PeerCatalog` is emitted on the first listing of each
supervisor and whenever the entries change. The copy survives reconnects and
respawns. Failures are logged (rate-limited) and retried at the next poll; a
Remote error never closes the session (invariant 17).

**Status.** `PeerConfigured` (supervisor start), `LaneState` on every
transition (Dialing, Handshaking, Ready with the RTT of `ConnHealth`,
Backoff with error and `backoff_until_ms`, Incompatible/Unauthorized with
error and the recheck time, Closed), Ready re-emitted when the RTT moves by
≥ 25 % and ≥ 5 ms, `PeerCatalog`, `PeerRemoved`.

**NetworkApi.**
- `pair(endpoint, code, connections)`: count defaults to
  `config.network.connections`, must be 1..=16 (`INVALID_CONNECTION_COUNT`);
  a `probe` session learns the remote installation (self → the handshake's
  `CANNOT_PAIR_WITH_SELF`, re-checked against `ctx.installation`); then
  `UpsertPeer` with a fresh revision; other endpoints of the same
  installation are removed; reconcile. Returns
  `{endpoint, installation, connections: max(count, 2),
  configured_connections: count, reserved_connections: 1}` (the legacy
  shape).
- `remote_list(endpoint)`: `PEER_NOT_PAIRED` unless paired; a probe session
  expecting the paired installation (`PEER_INSTALLATION_CHANGED`) and one
  `catalog.list`.
- `unpair(endpoint)`: `RemovePeer`, then reconcile: GOAWAY, cancel, join
  ≤ 5 s, `PeerRemoved`. Unpairing an unknown endpoint succeeds (the legacy
  `Unpair` did).
- `reconfigure()`: reconcile, then recheck every blocked peer now (one probe).
- `shutdown(deadline)`: refuse new work (`ORCHESTRATOR_STOPPING`), GOAWAY to
  every session, cancel, join everything by the deadline. Peers stay
  configured (no `PeerRemoved`).

**Stopping.** Cancelling a supervisor runs its per-session hooks, which send
`GOAWAY` at once: `PEER_NOT_PAIRED` (unpair), `WS_CLOSED` (respawn),
`ORCHESTRATOR_STOPPING` (shutdown). Following the WP1.INT re-review rule, a v3
server closes once idle after receiving a GOAWAY, and the sender (we) closes
when the peer closes or after the 5 s grace. To keep the join within 5 s, the
supervisor closes any session still open `force_close_margin` (1 s) before the
deadline. Measured: an idle peer closes at once (unpair < 1 s); a peer holding
a `catalog.list` forever is force-closed and unpair returns in about 4 s.

## Deviations from the spec, and why

1. **Thread layout.** §2.5 lists `peer-<installation>` (dialing and catalog
   client) plus `ctl-`/`bulk-` runners. Here lane 0's thread is
   `peer-<installation>` (it dials lane 0 and runs the catalog client) and
   every bulk lane has its own `lane-<installation>-<i>` thread for dialing
   and watching its session. A dial blocks for up to 3 s per resolved address
   plus the handshake steps, so one dialing thread per peer would make every
   lane and the catalog poll wait for the slowest dial, and would couple the
   lanes' failure domains (§2.3, "Connection").
2. **Peer-level block with a single probe.** §3.7 lists `Incompatible` and
   `Unauthorized` as lane states. They are a property of the peer, so one
   block covers every unconnected lane and only one lane re-dials per
   recheck; otherwise every recheck would cost one dial per lane.
3. **`Handshaking` is observed through `ClientAuth::key`.** `session::dial`
   runs connect and handshake as one call; the auth adapter emits
   `Handshaking` when the server's `HELLO_ACK` has arrived and the dialer
   derives its key. A refusal at `HELLO` (self, code not set) goes straight
   from `Dialing` to the block.
4. **"Recheck on catalog change"** (§3.7 `Incompatible`, §8) is read as a
   change of the peer's own record (which respawns the supervisor) or an
   explicit `NetworkApi::reconfigure`. Rechecking on *every* catalog
   generation change would loop: the supervisor's own `RecordPeerSeen`
   writes bump the generation.
5. **`pair` replaces other endpoints of the same installation.** One
   supervisor per installation (§3.7) cannot serve two endpoints; the legacy
   orchestrator kept both and ran two lane sets (RC13). Pairing an
   installation at a new endpoint removes its old endpoint records.
6. **Catalog `PeerCatalog` events** are emitted on the first listing of each
   supervisor and on entry changes only, not on every 2 s poll.
7. **A closed Ready session always backs off first**, whatever its close
   code; the redial decides `Unauthorized`/`Incompatible`. This keeps the
   block evidence-based (a handshake refusal), at the cost of one dial per
   lane after a rotation GOAWAY.
8. **Extra public surface** in the owned file: `start_with`, `PeerOptions`,
   `PeerView`/`LaneView`, `context`, `peers`, `peer`,
   `reconciled_generation`, `options`, `list_catalog`, `parse_catalog_reply`.

## CCRs filed

- **CCR-WP2.6-1 (spec clarification, §6.2 op table; for WP2.8 and WP2.INT).**
  The op table does not say where the `catalog.list` payloads travel.
  Requested: the request `CatalogListRequest{since}` is the REQUEST header,
  and the reply `CatalogListReply` is the JSON RESPONSE **body** (a catalog
  with branch lists can exceed the 64 KiB header bound; the body bound for
  `catalog.list` is 1 MiB through `max_body`).
  **Adapter:** the client sends the request in the header and reads the reply
  from the body when there is one, otherwise from the header
  (`peer::parse_catalog_reply`, tested both ways), so it works with either
  choice WP2.8 makes.
- **CCR-WP2.6-2 (session, `src/session/handshake.rs`).** An interruptible
  dial: `dial_expecting` (or a sibling) takes an abort signal, for example a
  `&Cancel` whose hook shuts the socket down (the step watchdog can already do
  that) and that is checked between steps.
  **Reason:** unpair, respawn and shutdown join a peer's lanes within 5 s, but
  a lane inside a dial cannot be interrupted (3 s per resolved address plus
  up to 5 s per handshake step).
  **Adapter:** such a lane is detached at the join deadline (logged); it sees
  its token cancelled as soon as the dial returns and closes the new session
  at once, so nothing it dialed stays open and nothing is served on it.
- **CCR-WP1.11-1 / CCR-WP1.11-2 (deferred to WP2.INT; WP2.6 is a producer).**
  No new request; the producer side is ready. When WP2.INT adds
  `PeerConfigured.display_name` and `LaneState.protocol`, fill them in
  `peer.rs` from values this package already computes:
  `display_name` in `PeerManager::spawn` from `peer_meta.display_name` (the
  same lookup as `PeerView::label`), and `protocol` in `Supervisor::set_lane`
  from `LaneView::protocol` (`"tkfs-peer/3"`, from the `ServerHello`, while
  Ready).

WP2.6 produces no `ExchangeFinished` events, so the re-review rules for them
(real `duration_ms`, completed objects only) apply to WP2.7/WP2.8/WP3.3, not
here. The GOAWAY rule (the sender closes when the peer closes or after 5 s)
is what the force-close margin accounts for.

## Tests added (`tests/peer_supervisor.rs`, 18 tests)

Lanes and status:
- `all_lanes_reach_ready_with_their_roles_and_lanes`: pool 4 → 1 control and
  3 bulk sessions with `LaneSpec{0..3, 3}` and `pool: 4` in every hello;
  `Dialing → Handshaking → Ready` per lane; `PeerConfigured` once; protocol

  the remote catalog listed into `PeerContext`.
- `catalog_client_polls_and_survives_a_control_reconnect`: `since` = `None`
  first, then the generation; no `PeerCatalog` for unchanged polls; the
  control session drops → the catalog stays, bulk lanes stay Ready (never
  reconnect), lane 0 backs off and reconnects with a full listing; a change
  (reply in the header this time) arrives at the next poll.
- `catalog_replies_parse_from_the_body_or_the_header` (CCR-WP2.6-1 adapter).
- `reconnect_backoff_stays_within_jitter_bounds`: against a listener that
  drops every connection, ≥ 6 backoffs per lane: each declared delay within
  `min(cap, base·2^(n-1)) ± 20 %`, and the next dial waits for it (not more
  than 500 ms longer); the error is `WS_CONNECT_FAILED` (Transient).
- `backoff_resets_after_a_healthy_session`: sessions closed right after
  establishment escalate the delay (200, 400 ms ±20 %); after > 400 ms Ready
  (`lane_reset_after` shortened) the next delay restarts at the base.
- `legacy_peer_is_incompatible_without_redial_before_the_recheck`: an
  emulated v2 server → every lane `Incompatible{PEER_NEEDS_UPGRADE}` with the
  recheck time; at most one dial per lane; `peer_meta.incompatible`; the hub
  badge is Incompatible; no dial before the recheck (2 s here); exactly one
  probe at the recheck; one more on `reconfigure`; the server never receives
  a message and the code appears in no event or snapshot.
- `wrong_code_is_unauthorized_without_a_tight_retry_loop`: every lane
  `Unauthorized{INVALID_PAIRING_CODE}`, hub badge Unauthorized; over 3.5 s at
  most one dial per 1 s recheck (counted on the client, `LaneView.dials`, and
  matched by the server's failed handshakes); re-pairing with the right code brings
  the lanes up at once (< 3 s); neither code appears in events, the hub
  snapshot or the manager's `Debug`.
- `rotation_goaway_closes_sessions_and_the_peer_becomes_unauthorized`: the
  server rotates and sends `GOAWAY{PAIRING_CODE_CHANGED}` → lanes back off
  with that reason → redial → `Unauthorized{INVALID_PAIRING_CODE}`.
- `a_wedged_catalog_write_never_holds_a_lane`: the catalog's
  `RecordPeerSeen` blocks; the lanes still reach Ready, the catalog client
  keeps polling, a control reconnect is not held, and `shutdown` returns in

  wrote `peer_meta` on the lane thread; this test would hang its lane 0
  before the catalog client started.)

NetworkApi and lifecycle:
- `pair_probes_stores_a_new_revision_and_supervises`: one `probe` hello; the
  stored record (installation, connections, revision); lanes Ready; a re-pair
  stores a new revision, respawns (no `PeerRemoved`) and keeps the remote
  catalog; pairing the same installation at a second endpoint replaces the
  first (sessions move to the new endpoint).
- `pair_refusals_store_nothing`: self → `CANNOT_PAIR_WITH_SELF`; wrong code →
  `INVALID_PAIRING_CODE`; counts 0 and 17 → `INVALID_CONNECTION_COUNT`; a
  dropping listener → `WS_CONNECT_FAILED`; a legacy server →
  `PEER_NEEDS_UPGRADE` and never receives the code; the catalog stays empty.
- `remote_list_lists_the_catalog_and_checks_the_installation`:
  `PEER_NOT_PAIRED`; entries from the body and from the header; a changed

  `Unauthorized{PEER_INSTALLATION_CHANGED}`.
- `unpair_cancels_and_joins_every_lane_within_5s`: pool 4; unpair returns in

  `PEER_NOT_PAIRED`, `PeerRemoved` once, the hub forgets the peer, no redial;
  a second unpair is harmless.
- `unpair_joins_within_5s_while_the_peer_holds_a_request`: the peer hangs
  `catalog.list`, so it never goes idle after the GOAWAY; the forced close
  bounds unpair (< 5.5 s asserted, about 4 s measured).
- `catalog_changes_respawn_or_stop_supervisors`: a peer added to the catalog
  is supervised without any call; more connections respawn with a bigger
  pool; removal stops and reports it; the other peer is untouched;
  `reconfigure` with nothing changed is a no-op.
- `shutdown_sends_goaway_and_joins_every_peer`: two peers; shutdown < 5 s;
  every session closed with `ORCHESTRATOR_STOPPING`; no `PeerRemoved`; no
  redial; `pair`/`remote_list` answer `ORCHESTRATOR_STOPPING`.
- `shutdown_of_the_daemon_token_stops_every_lane`: cancelling `ctx.shutdown`
  ends every lane (invariant 29).
- `the_default_policy_matches_section_3_7`.

## Known limitations

- **Not wired.** As planned for Wave 2, the daemon still uses the legacy
  bridge; WP3.1 makes `PeerManager::start` `ctx.network`.
- **Runner contract.** `scheduler::run_control` and `objects::run_bulk_lane`
  are still the WP0.INT stubs here, so no test observes a runner. The lanes
  rely on runners returning only when cancelled or when their session is
  gone; a runner that returns early makes the lane reconnect (with backoff),
  which WP2.INT should check once WP2.7's real runners merge.
- **Dials are not interruptible** (CCR-WP2.6-2): a lane in the middle of a
  dial when its peer is stopped can outlive the 5 s join; it is detached and
  closes its new session when the dial returns.
- **A Ready lane survives a block set by another lane** (for example the
  remote rotated its code while lane 0's session is still open). The hub's
  badge precedence shows the peer `Unauthorized` meanwhile.
- **`RecordPeerSeen` on every control session** is one catalog write per
  (re)connection; with the 60 s backoff cap a flapping peer costs at most
  about one write a minute. The resulting generation bump makes the
  `peer-manager` thread re-diff the catalog (a no-op).
- **`PeerCatalog` volume**: any field change of a remote entry (its
  `updated_at_ms` and content counters move with every remote heartbeat
  refresh) emits a `PeerCatalog`, at most one per 2 s poll per peer.
- **Duplicate installations in a legacy catalog**: only the first record by
  endpoint is supervised until a `pair` cleans them up.
