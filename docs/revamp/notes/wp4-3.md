## Deviations from the spec, and why

1. **`tests/docs_cli.rs` checks more than "`tkfs <cmd> --help` succeeds".**
   `--help` succeeds for many wrong lines (`tkfs manage stop X --bogus --help`
   prints help), so the test also checks the subcommand path word by word,
   the options each line uses, the positional arguments and required options
   (fix round 1), and that no command of the binary is undocumented. This is
   what "all `manage` commands" in the CLI row of the task needs to stay true.
2. **The previous release's validation records were removed from
   `docs/VALIDATION.md`** (they remain in git history, and their findings are
   in `docs/revamp/ROOT_CAUSES.md`). They described the replaced design's
   pages, lanes and timeouts in the present tense, which the review checklist
   forbids, and their measurements are of the previous release.
3. **The review checklist ("no 15 s timeouts as current behaviour")** is read
   as the previous release's 15 s peer socket timeout. Two current 15 s waits
   are documented because they are real: a read of a file whose bytes have
   not arrived waits up to 15 s before `CONTENT_UNAVAILABLE` (`mount.rs`,
   `runtime::prepare_content`), and `manage force-stop` waits up to 15 s
   (`limits::API_STOP_WAIT`; `manage stop` about 13 s,
   `manage::STOP_REPLY_WAIT`). The previous release's timeouts are mentioned
   only as past behaviour (the stuck-replica runbook, and the old client's
   15 s timeout in the upgrade steps). "List polling" is read as the previous
   desktop's 5 s refresh; the control lane's `catalog.list{since}` every 2 s
   (answered `unchanged` in O(1)) is current and documented as such.
4. **WP4.1 and WP4.2 passages describe the plan, not this base** (fix round
   1; the first submission described the base and listed the passages for
   WP4.INT instead). Where the plan leaves a user-visible detail open, the
   docs take it from the WP4.1 or WP4.2 branch; those details are marked in
   *For WP4.INT* as items to verify against the merged code. WP4.4 and WP4.5
   passages still describe this base (the plan's addendum fixes their goals
   and floors, not their user-visible behaviour).
5. **The upgrade runbook for the Docker example uses Docker commands that
   were not executed here** (`docker compose exec`, `docker update
   --restart`, `docker compose up -d`, `docker compose stop -t`): no Docker
   engine runs on this machine. The behaviour they rely on was checked in the
   code (the old daemon's shutdown action, the compose file's
   `restart: unless-stopped` and `exec ./tkfs start`, the new daemon's SIGTERM
   handling).
