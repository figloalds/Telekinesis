### Behaviour

- **Upgrade.**
  - The dialer sends `X-Tkfs-Sync: 3`. With no echo it returns `DialError::NeedsUpgrade` before sending anything, so the code never reaches a legacy server. An echo with another value gives `Unsupported`.
  - The server echoes `3` for v3 and refuses `3-loopback` with HTTP 400.
  - When the header is missing (a legacy client), the server reads one legacy message (≤ 16 KiB = 16,384 bytes of JSON exactly, 5 s) and calls `AcceptPolicy::legacy_attempt(addr, hello)` with `hello.code` replaced by `"<redacted>"`. It then sends the frozen `LEGACY_NEEDS_UPGRADE_REPLY` as a text message, closes gracefully and returns `PEER_NEEDS_UPGRADE`.
  - The server does not echo `X-Tkfs-Wire`, so a 6298d0b `ws::call` reads the reply as text JSON and surfaces `RemoteError("PEER_NEEDS_UPGRADE: remote runs tkfs peer protocol 3; upgrade this orchestrator")`.
- **Handshake** (§6.2 steps 1–6):
  - HELLO → HELLO_ACK | GOAWAY → AUTH → AUTH_OK | GOAWAY.
  - Server order of checks: protocol and version (`PEER_PROTOCOL_UNSUPPORTED`), hello validity (close frame `PROTOCOL_VIOLATION`), this server's own installation id (`INSTALLATION_REQUIRED`, its own failure: close code 1011, never `PROTOCOL_VIOLATION`; round 2), self-pair (`CANNOT_PAIR_WITH_SELF`), verifier (`PAIRING_CODE_NOT_SET`), `admit` (its code, e.g. `PEER_REVOKED`, `TOO_MANY_SESSIONS`), then HELLO_ACK with a fresh server nonce.
  - A bad proof gives `GOAWAY{INVALID_PAIRING_CODE}`, with a fixed message that carries no verifier data.
  - If the verifier generation or hash changed between HELLO_ACK and AUTH, the server sends `GOAWAY{PAIRING_CODE_CHANGED}`.
  - The client checks the server's echoed role and lane, a distinct and valid nonce, and self-pair. It verifies `server_proof` (mutual authentication; failure is `Unauthorized(INVALID_PAIRING_CODE)`). Optionally it checks the expected installation **after** authentication, so an unauthenticated server cannot trigger `PEER_INSTALLATION_CHANGED`.
  - **A peer's close frame is a closed connection** (round 2). During the handshake, a close frame from the peer is `WS_CLOSED` on the server, whatever its reason. The reason is kept only as diagnostic detail, truncated to 123 bytes and escaped (`{:?}`), so a peer-chosen string never becomes a `PROTOCOL_VIOLATION` detail. Only the client reads a server's close with code 1002 (what this server sends on a violation) as `DialError::Protocol`, with control characters escaped. Any other close code is `DialError::Connect` (Transient).
  - **The client always generates its own nonce.** `client_handshake` replaces `hello.client_nonce`. A caller that reused a hello could otherwise be fooled by a replayed HELLO_ACK and AUTH_OK pair.
- **Wire secrecy.** Only the salt, the nonces and the two HMACs cross the wire. `K` (the verifier digest) is key-equivalent to the code, and neither ever leaves the process (`pairing_code_never_crosses_the_wire` checks the raw and unmasked bytes in both directions).
- **Pre-auth bounds.**
  - The WebSocket message and frame bound is 8 + 16 KiB for v3 frames (prefix plus header). The legacy hello has no prefix, so `refuse_legacy` lowers the bound to exactly 16 KiB before reading it.
  - Handshake frames are validated with every §6.2 rule: known pre-auth kind, no flags, zero reserved field, header ≤ 16 KiB, no body or trailing bytes, header a JSON object.
  - Socket read and write timeouts are 5 s per step.
  - A per-handshake **watchdog** thread shuts the socket down when a step (upgrade, HELLO, AUTH) overruns its 5 s budget. Socket timeouts alone bound each `read` call, so a peer trickling one byte at a time could otherwise hold a slot. The dialer's TLS and WebSocket upgrade in `ws::connect_with` is bounded the same way, within the 3 s per-address budget.
  - **No watchdog, no handshake (fail closed).** `Watchdog::start` returns an error when no verified duplicate handle can be made (round 2: see below) or the thread cannot be spawned. `accept_v3` and `accept_loopback` then refuse the connection (`WS_CLOSED`, "handshake watchdog could not start"); `client_handshake` returns `DialError::Connect`, `server_handshake` `WS_CLOSED`, and a `connect_with` attempt fails with `WS_CONNECT_FAILED`. Nothing runs bounded only by per-call socket timeouts.
  - **A fired watchdog fails the step.** The watchdog's `fired` flag is final once `disarm` returns. Every step (`read_message`, `send`, the upgrade in `accept_v3`/`accept_loopback`/`connect_with`) and `Guarded::finish` check it afterwards. A step that completed just as its budget ran out is a `REQUEST_TIMEOUT` (`DialError::Timeout` on the client), never a shut-down socket handed to `Conn`.
  - **Control messages are not progress.** `read_message` also checks the step deadline on each Ping or Pong, and `close_gracefully`'s drain loop checks its own 1 s deadline. A peer that keeps pinging cannot extend a step or the drain, even if the watchdog's `shutdown` failed.
  - The watchdog lives in `ws::watchdog` (round 2; it was `session::handshake::Watchdog`), so `ws` no longer depends on `session`. `handshake.rs` imports it from there.
  - The watchdog shuts the socket down through a duplicate handle (`try_clone`). On Windows, a duplicate taken right after `TcpStream::connect_timeout` (a non-blocking connect) intermittently carries a stale "not connected" state, and `shutdown` on it then fails with `WSAENOTCONN`. A standalone check measured 66 failures in 3,000 connects. The trickling-server test caught this: the dial ran to tungstenite's 64-packet attack check, about 19 s. `watchdog_handle` therefore calls `getpeername` on the original before cloning (0 failures in 3,000) and verifies the duplicate. Round 2: a duplicate that fails verification three times is never used: `Watchdog::start` fails, and the connection is refused (fail closed). Rounds 0–1 fell back to an unverified clone. A round-2 measurement shows why that fallback was unsafe: 23 of 3,000 duplicates were stale, none recovered on a second `getpeername` or `shutdown`, and every re-duplicate from the refreshed original worked.
  - **When the watchdog fires** (round 2) it first shrinks the socket's read and write timeouts to 1 ms through its handle, then shuts the socket down. If `shutdown` fails, it logs `WATCHDOG_SHUTDOWN_FAILED` (`util::log`, warn). On Unix the timeouts belong to the socket, so the owner's next blocking call returns at once even when `shutdown` failed. On Windows they belong to the handle, so there the bound rests on `shutdown` through the verified duplicate. See Review round 2 for the measurement.
  - After authentication the bounds are raised (`set_config`) to `8 + max_header + max_chunk`, the socket timeouts are cleared, and `dial`/`accept` switch the socket to non-blocking and call `Conn::from_established`.
- **Refusals reach the peer.** After a `GOAWAY`, the legacy reply or a protocol close frame, the refusing side sends a close frame and drains for up to 1 s before dropping the socket. Closing a socket with unread input resets it, and on Windows the peer can then lose the `GOAWAY`.
- **Dialing** tries every resolved address, 3 s each. One deadline covers an address's whole attempt: the TLS and WebSocket upgrade gets what the TCP connect left, as its socket timeouts and its watchdog budget, so an address never takes 3 s + 3 s. A TLS connector is cloned per address; a connector that cannot be cloned is used once and never replaced by the default trust store.
- **Loopback.**
  - `dial_loopback` sends `X-Tkfs-Sync: 3-loopback`, plus `X-Tkfs-Token` when a token is given. With no echo it returns `NeedsUpgrade`; HTTP 401 or 403 gives `Unauthorized(ACCESS_DENIED)`.
  - `accept_loopback` refuses other kinds with HTTP 400. With a token set, a missing or different token is refused with HTTP 403 (constant-time compare).
  - Loopback `PeerInfo` has an empty installation, role `control` and a fresh session uuid.
- **The probe role** is a normal role in the hello and in `T` (no lane). Control, bulk and probe are all tested end to end. Bulk requires a valid `LaneSpec`; any lane present must satisfy `LaneSpec::is_valid`.

## Deviations from the spec

1. **`tests/contracts.rs` edited (WP0.4's file).**
   - `session_stubs_fail_closed_with_not_implemented` asserted that `accept`, `accept_loopback`, `dial`, `dial_loopback` and `CodeAuth::key` return `NOT_IMPLEMENTED`, which this package must replace. No implementation can pass it.
   - Only those five assertions changed. The test now pins the real fail-closed behaviour:
     - a dialer that hangs up before the upgrade → `WS_CLOSED` (for both `accept` and `accept_loopback`; the client end is dropped first, so the test stays fast);
     - nothing listening on port 1 → `WS_CONNECT_FAILED` (`dial`, `dial_loopback`);
     - `CodeAuth::key("salt") == Verifier::derive_key("salt", "c")`.
   - The WP1.9 frame-codec assertions in the same test are untouched.
   - This is not a weakening: each assertion still checks a specific fail-closed code. Filed as CCR-WP1.10-1 so the integrator can reconcile it with WP1.9's edit of the same test.
2. **Pre-auth frames are encoded and decoded in `handshake.rs`.** `session::frame::{encode, decode}` (WP1.9) are stubs on this branch. The layout is identical (8-byte prefix, JSON header, no body). `tests/session_handshake.rs` uses its own independent encoder and decoder, so any divergence would show up. See Follow-ups.
3. **Additive public API beyond the list in §14:**
   - `handshake::{client_hello, dial_expecting, connect_v3, accept_v3}`;
   - `auth::{Transcript, verify_proof, new_nonce, decode_nonce, valid_id, CLIENT_LABEL, SERVER_LABEL, MAX_ID_LEN}`;
   - `ws::RawSocket`;
   - `pub(crate) ws::watchdog::Watchdog` (`start(&TcpStream) -> io::Result<Watchdog>`, `arm`, `disarm`, `fired`), used by `ws::connect_with` and every handshake step. It was `handshake::Watchdog` until round 2.

   `connect_v3` and `accept_v3` exist because `Conn::from_established` is still a stub, so §14's "tests cover handshake functions up to the authenticated socket" needs a public entry point that stops there. They also serve WP1.INT, WP2.6 and WP2.8. No frozen signature changed.
4. **`ws::accept_with` can refuse.** The `on_request` callback receives `&mut Response`; setting a non-101 status refuses the upgrade with that status. The spec'd signature has no other way to refuse, and both loopback refusals (400, 403) need it.
5. **`PAIRING_CODE_CHANGED` as a handshake `GOAWAY`.** It is used for a rotation between HELLO_ACK and AUTH. The frozen `GOAWAY_HANDSHAKE_CODES` does not list it, so the client maps it to `Unauthorized` explicitly (CCR-WP1.10-2).
6. **`client_handshake` overrides `hello.client_nonce`** (see Behaviour). The spec passes the hello through, but a caller-chosen client nonce makes server-proof replay possible.
7. **`Verifier::verify` is now constant time.** Its behaviour is unchanged.

## Known limitations

- `Conn::from_established` is WP1.9's stub on this branch. `dial`, `accept`, `dial_loopback` and `accept_loopback` complete the handshake, then fail when they start the session: `WS_CONNECT_FAILED` or `CONNECTION_LOST`, wrapping a `NOT_IMPLEMENTED` cause. The authenticated socket is available through `connect_v3` and `accept_v3`.
- Each in-flight handshake (and each dial attempt) runs one short-lived watchdog thread. WP2.8 caps pre-auth handshakes at 32. When no thread can be spawned (thread or handle exhaustion), connections are refused until resources free up. This is fail closed by design: a handshake is never run bounded only by per-call socket timeouts.
- The fail-closed path is exercised through a `#[cfg(test)]` thread-local hook in `Watchdog::start` (`REFUSE_WATCHDOG`). It does not exist in non-test builds.
- If the watchdog fires but its `shutdown` fails, the Ping/Pong and drain loops still end at their deadlines, and the failure is logged (`WATCHDOG_SHUTDOWN_FAILED`). Unix also ends a byte-trickling peer's frame at its next pause, through the shrunk socket timeouts. Windows cannot do that: socket timeouts are per handle there, and only the owner's handle (held inside tungstenite during the read) could change them. So on Windows the bound rests on `shutdown` through a verified duplicate. Since round 2 that duplicate is always verified: a stale one is refused, never used. The one remaining known cause of a failed `shutdown` is a connection that is already gone, and that ends the owner's read by itself.
- A server whose `AcceptPolicy::installation()` is not a valid id refuses every handshake (`INSTALLATION_REQUIRED`). The dialer sees a 1011 close and reports `WS_CONNECT_FAILED` (Transient): it cannot fix the remote's configuration, so it retries with backoff.
- HMAC challenge-response does not stop a live relay (an active man in the middle forwarding both directions). As in §12, the model is HMAC plus an operator TLS proxy. Per-peer credentials and revocation arrive in WP4.1, which also owns `handshake.rs` and `auth.rs`.
- A legacy client that sends nothing is closed at 5 s with `REQUEST_TIMEOUT`. `legacy_attempt` is not called, because there is no hello to report. An oversize legacy message (> 16 KiB) is a `PROTOCOL_VIOLATION`, not a legacy attempt.
- A malformed stored verifier hash fails every handshake with `INVALID_PAIRING_CODE` rather than `PAIRING_CODE_NOT_SET`.
- Any handshake `GOAWAY` code outside `GOAWAY_HANDSHAKE_CODES` and `PAIRING_CODE_CHANGED` is reported as `DialError::Protocol`.
