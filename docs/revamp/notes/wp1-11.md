### Provided API (§14 WP1.11 *Provides*)

- `StatusHub::new(cfg: HubConfig{stall_after, interval, activity}, clock: Arc<dyn Clock>) -> Arc<StatusHub>`. It implements `StatusSink::record` and `StatusSource::{snapshot, wait_newer}`.
- `StatusHub::tick(&self)`. The caller runs it every `interval` (1 s). `StatusHub::spawn_ticker(&Arc<Self>, Cancel)` is a convenience that spawns the `hub-tick` thread of §2.5.
- `legacy_folder_sync(&self, &FolderRecord, &[PeerRecord]) -> Value` and `legacy_peers(&self, &[PeerRecord]) -> Value`: the §7.3 post-cutover projection.
- `hub_rules::{folder_state, peer_state, stall, Ewma, dedupe}`, plus the other pure helpers listed above.

Additive helpers, for the wiring packages:

- `HubConfig::for_sync_interval(d)` and `Default`. They give `stall_after = max(60 s, 20 × d)` (or `TKFS_STALL_AFTER_MS`), `interval = 1 s` and `activity = 500`.
- `stall_after_for(d, override)`.
- `set_daemon(DaemonStatus)`: the daemon identity (the hub owns `errors`).
- `set_stopping(bool)`.
- `set_peer_label(installation, Option<String>)`: see CCR-WP1.11-1.
- `snapshot_now()`: rebuilds regardless of the throttle. It is for one-shot readers that must see their own writes, and for tests.
- `legacy_links()`: the `LegacyLink` passthrough store.
- `rebuilds()` and `config()`: diagnostics.
- Constants: `STALL_AFTER_ENV`, `MAX_ITEM_ERRORS` (64), `MAX_INFLIGHT` (64), `MAX_LEGACY_LINKS` (4096), `SNAPSHOT_BURST` (2), `SNAPSHOT_MAX_PER_WINDOW` (4) and `SNAPSHOT_WINDOW` (1 s), `INBOUND_INCOMPATIBLE_TTL` (10 min), `MAX_INBOUND_NOTICES` (16), `MAX_NOTICE_HOST` (128), `MAX_NOTICE_MESSAGE` (512), `ORPHAN_GRACE` (10 s), `MAX_TOMBSTONES` (64).

### How the hub works

- **State maps** (spec task 1):
  - folders, by state: the last `FolderView`, heartbeat, mount status and error book;
  - (repo, peer installation) pairs: the last `ExchangeSummary`, EWMAs, progress and stall timers, and transfer episodes;
  - peers, by installation;
  - lanes, by (inbound?, lane): an outbound lane 0 and an inbound session on lane 0 never collide;
  - inbound sessions: a session count per inbound lane.
- **`record()`** applies the event under one `Mutex`. It does map work only: no I/O, no waiting and no durable write. It wakes waiters only on a clean→dirty transition.
- **Two clocks** (fix round 1). Every reported `*_ms` field is wall-clock time (`Clock::now_ms`). Every duration the hub measures runs on a monotonic timeline: the wall-clock time at hub start plus the `Clock::instant` time elapsed since. That covers the stall detector (eligibility, last progress, stall start), the Contention 30 s rule, the inbound-notice expiry and the orphan grace. A system clock jump (NTP, resume from sleep) therefore neither fires nor suppresses them. A timer kept on the monotonic timeline is reported by its age (`wall now − (mono now − t)`), and a producer's wall-clock `first_at_ms` enters the timeline the same way.
- **Folder registration** (fix round 1). Only `FolderLifecycle` registers a folder. Folder-scoped events (heartbeat, `ObjectError`, folder-scoped `Error`) for a folder removed by `FolderRemoved` are dropped: the last 64 removed states are remembered. An event for a state never seen still creates an entry, because it can race the first `FolderLifecycle`, but an entry that has no view after `ORPHAN_GRACE` (10 s) is pruned at a tick. So are pair rows and legacy lane repos of a repo without a registered folder, 10 s after their last exchange.
- **Rates.** Every `ExchangeFinished` adds its bytes to the EWMAs of its lane, its peer and its (repo, peer) pair. `tick()` folds them with the measured elapsed time. The EWMA is bias-corrected (see deviation 8). ETA is bytes remaining over the 10 s rate.
- **Remaining work of a (folder, peer) pair:**
  - metadata: `to_send + to_receive + local_pending + remote_pending`, taken from the last exchange summary. The worker's per-peer `PeerFeedCounters` in the heartbeat take over when they are at least as recent; they are matched by the peer's published replica.
  - download: our `shared_objects - shared_available` and `shared_missing_bytes - partial_bytes`, from heartbeat content counters.
  - upload: the same counters from the peer's published entry.
- **Progress** is any of:
  - events or objects moved (`sent`, `received`, `staged`, `acked`, `metadata_advanced`, `objects_*`);
  - an objects op that moved ≥ 64 KiB (a large object streams over many exchanges);
  - a decrease of remaining work, at an exchange or at a tick;
  - worker-side progress from heartbeats (missing bytes fall or partial bytes grow, or `activation.activated` grows).
- **Stall** (§7.1):
  - The pair can progress: shared, sync on, both folders serving, peer Online.
  - Work remains.
  - Nothing has progressed for `stall_after`, counted from the later of the last progress and the moment the pair became eligible. A reconnect after a long outage therefore does not stall at once.
  - The culprit is the pair's newest open error, or else the folder's newest Object/Event error. The display policy does not apply to the culprit.
  - Progress clears a stall immediately, at record time.
  - Start and clear are logged in the activity ring.
- **Snapshots** are rebuilt lazily, only when the state version moved.
- **Activity ring:**
  - It holds hub-generated entries: lifecycle, gate, peer badge, error shown, error resolved, stall, exchange and inbound-incompatible.
  - It also holds the producers' `Activity` events.
  - Consecutive `exchange` entries for the same (folder, peer) are coalesced, so a long transfer is one entry.

### Per-(folder, peer) precedence (`hub_rules::peer_state`), first match wins

| # | State | Condition |
|---|---|---|
| 1 | `NotShared` | the peer does not share the repo (see below) |
| 2 | `Paused` | folder sync disabled |
| 3 | `Incompatible` | peer badge Incompatible, or an Incompatible error on the pair |
| 4 | `Unauthorized` | peer Unauthorized or Revoked |
| 5 | `Offline` | peer Offline |
| 6 | `Connecting` | peer Connecting |
| 7 | `Backoff` | peer connection in reconnect backoff |
| 8 | `WaitingForWorker` | local folder not Running |
| 9 | `WaitingForRemote` | remote entry `starting`/`unavailable`/`paused`, or `REMOTE_WORKER_STARTING`/`FOLDER_SYNC_PAUSED` open on the pair |
| 10 | `Stalled` | stall detector fired |
| 11 | `Backoff` | a *visible* Contention/Transient error on the pair: the key is retrying |
| 12 | `Blocked` | a visible NeedsUserAction/Fatal error on the pair: the key does not retry |
| 13 | transfer | `Metadata`, `Downloading`, `Uploading`, or `Syncing` when mixed. No metadata evidence yet counts as metadata work |
| 14 | `Blocked` | only blocked, quarantined or rejected work remains |
| 15 | `UpToDate` | otherwise |

A peer **shares** a repo in any of these cases:

- its catalog lists the repo;
- it exchanged the repo with us inbound (inbound-only peers have no catalog);
- no catalog has been received and it exchanged the repo outbound;
- it is the gate source of the received folder.

### Peer badge (`hub_rules::peer_conn_state`)

First match wins:

1. Revoked (an open `PEER_REVOKED` in the peer's scopes);
2. Incompatible (any outbound lane);
3. Unauthorized (any outbound lane);
4. Online (any outbound lane Ready, or any open inbound session);
5. Connecting (dialing or handshaking);
6. Backoff;
7. Offline.

## Deviations from the spec, and why

1. **Folder rule 3b.** After `Paused`, a folder whose worker is not Running gives `Stopped`, and the summary says why: "worker starting (verifying objects)", "worker restarting (attempt 3)", "worker stopping". This covers Starting, Backoff, Stopping, StopBlocked, and Stopped while desired. The §7.1 table has no row for a desired folder whose worker is not running. Taken literally it falls through to `UpToDate`, which would be a false claim. Rules 1 (stopped and not desired) and 2 (`NeedsAttention`, which covers lifecycle `Failed`) still win.
2. **Folder rule 10 (`Offline`).** The "every sharing peer unreachable" set is wider than in §7.1: it is Offline, Incompatible, Unauthorized, Connecting, WaitingForRemote, WaitingForWorker or Backoff. With only §7.1's three states, a mix of one offline and one backing-off peer, or a remote folder that is starting, would read `UpToDate`. Rule 9 (*every* sharing peer in Backoff) still comes first.
3. **The per-(folder, peer) precedence table is defined here.** §7.1 lists the `FolderPeerState` values but gives no order. The table above is pinned by `peer_state_precedence_order`.
4. **Snapshot throttle.** At most 4 rebuilds in *any* 1 s window, which is §3.4's "at most 4 times per second" taken literally. Within that, a token bucket (one token per 250 ms, burst 2) allows at most 2 rebuilds back to back. This replaces a strict 250 ms spacing.
   - **Why:** WP2.2's acceptance needs `subscribe` to return within 50 ms of a recorded event. Strict spacing makes an event that arrives within 250 ms of any read wait up to 250 ms.
   - **Bounds** (tightened in fix round 1; the round-0 bucket alone allowed 6 rebuilds in a 1 s window):
     - no 1 s window holds more than 4 rebuilds, checked deterministically (`snapshot_rebuilds_never_exceed_four_in_any_second`) and under real threads (`snapshot_rebuilds_are_throttled_to_four_per_second`, bound `4 × ⌈elapsed⌉`);
     - an isolated event is published at once (`wait_newer_returns_on_record_and_on_timeout`: latency < 50 ms).
   - **Contract wording:** this still differs from the doc comment of `policy::SNAPSHOT_MIN_INTERVAL` ("rebuilt lazily at most this often", read as a minimum spacing). See CCR-WP1.11-4.
   - **Edge case:** `wait_newer` with a generation *ahead* of the hub (a client of a previous daemon run) returns at once.
5. **Error slots and "the same scope".**
   - One open error per (scope, slot). Generic `Error` events use the empty slot. Exchange failures use their op, so "the next success in the same scope" means the same (peer, repo, op) key, matching the §3.7 backoff key. Otherwise a metadata success every 500 ms would clear an objects error before its 3rd attempt, and it would never show (`errors_clear_per_op_and_hidden_errors_never_reach_history`).
   - Records owned by someone else are mirrored into fixed slots and resolve when they disappear: the FolderView `last_error`, the `Failed` error and `published_error`; mount `AttachFailed`/`Lost`; store health.
   - Store health and a `Lost` mount are *states* the worker re-reports in every heartbeat, not counted records (fix round 1). The same open code is one deduplicated record whose `count` rises once per report: once per applied heartbeat, or per `FolderLifecycle` that carries no newer heartbeat. The display policy counts reports like attempts, so a Transient condition (for example `RECOVERY_REQUIRED`) shows from its 3rd report on. `AttachFailed` keeps the mount supervisor's `attempt` as its count.
   - Implicit successes:
     - `Running` resolves generic folder errors;
     - `Attached`, or a mount intent other than Attach, resolves mount errors;
     - a Ready lane resolves its lane slot and the generic peer slot;
     - a heartbeat with no missing shared content resolves Object errors;
     - an inbox with no blocked or quarantined rows resolves Event errors.
6. **Display policy details.**
   - "Transient shown after 3 attempts" counts consecutive failures in the slot (a streak). A code change inside the slot continues the streak, and only a success ends it. Without this, alternating `REQUEST_TIMEOUT`/`CONNECTION_LOST` would never show.
   - Shown errors stay shown until resolved.
   - Only errors that were shown reach the history: a hidden `WORKER_BUSY` blip never does.
   - History keeps 50 entries per owner: the daemon, and each folder.
   - `daemon.errors` holds Daemon, Peer and Lane scopes; peer and lane rows also carry their own current error.
   - `FolderStatus.errors` holds Folder, Mount, Object, Event and FolderPeer scopes.
   - Each list is visible open errors first (newest first), then the history (newest first).
   - Open Object/Event errors are capped at 64 per folder, keeping the newest.
   - Inbound-incompatible notices (fix round 1) are keyed by remote **host**: the port is dropped, IPv4-mapped IPv6 is canonicalised, and the host is cut to 128 bytes. A legacy peer that reconnects from new ephemeral ports is therefore one notice whose count rises, with one `inbound_incompatible` activity entry per new notice. At most 16 hosts are kept; the least recently seen is dropped, not moved into the history, because these come from unauthenticated pre-auth traffic (invariant 22). Messages are cut to 512 bytes. A notice expires 10 min after its host's last attempt (the §8 Incompatible recheck period).
7. **Transfer attribution.**
   - A peer gets download work only when it can probably supply something: its counters are unknown, it is complete, or it misses strictly fewer bytes than we do. Two replicas missing the same objects (lost everywhere) therefore never show a transfer or a false stall.
   - Upload work is symmetric.
   - Non-sharing rows carry no transfer numbers.
   - `objects_down.bytes_remaining` and its `eta_s` are folder-level, because any sharing peer can serve them: the ETA uses the sum of the sharing peers' 10 s down rates. `rate_bps` is the peer's own share.
   - `total_bytes` = bytes moved in the current episode + remaining. The episode resets when remaining reaches 0.
   - In-flight counts come from the lanes' in-flight lists, so a dropped lane leaves no stale count.
8. **EWMA.**
   - Bias-corrected (Adam-style): a stream reads its true rate from its first tick instead of ramping up from 0 over ~30 s.
   - A single burst decays like 1/n at first.
   - Once both windows fall below 1 B/s, the stream is over and the next one is corrected afresh.
   - Schema 2 has no field for the 60 s rate. It is computed (`Ewma::long_bps`) but snapshots carry the 10 s rate everywhere, as §7.1's ETA rule implies.
9. **`metadata.caught_up`.** The value comes only from exchange evidence (summary or feed counters), never from content or acks (invariant 30). A counting (non-Contention) failure of a metadata exchange withdraws it until the next success, as the legacy lanes did. Contention never resets it (§8).
10. **Legacy projection.**
    - `transport` is always `"tkfs-peer/3"` and `parallel_bulk` always `true` (§7.3).
    - `remote_available` (fix round 1): `true` only when the peer's catalog lists the repo as `running`. Legacy published lists held only Running workers, so a remote folder that is starting, paused or unavailable reads `false`, and the legacy GUI's "worker may be stopped, starting" hint keeps working. It is `null` when lane 0 is down or no catalog has been received.
    - `offer_ms`, `remote_exchange_ms` and `apply_ms` are `null`: v3 has no such phases. `total_ms` is the exchange duration.
    - `metadata_progress` maps the summary (`local_events` = local tip, `remote_events` = remote tip, `local_only_events` = `to_send`, `remote_only_events` = `to_receive`, plus the pending counts).
    - `object_inventory` is derived from the two sides' content counters.
    - A bulk lane is `caught_up` after a successful objects exchange that moved no object.
    - `retry_at_ms` comes from `retry_after_ms`.
    - `LegacyLink` values are stored verbatim, keyed as given, and returned by `legacy_links()`. The projection does not consult them: in Waves 1–2 the legacy bridge (WP2.1) serves the legacy JSON itself, and WP2.1 also emits the typed `ExchangeFinished`/`LaneState` the hub derives from (§14 WP2.1 task 4).
11. **`DaemonStatus.version` is empty until `set_daemon`.** `env!("CARGO_PKG_VERSION")` trips the code-literal registry test in `tests/contracts.rs` (not owned here; see CCR-WP1.11-3). The daemon supplies its identity anyway.
12. **`PeerStatus.protocol` stays `None`.** No event carries the negotiated protocol (CCR-WP1.11-2).
13. **Size.** About 4,100 lines of source (rustfmt layout) against an estimate of ~1,600. The pure rules are about 900 lines, the hub about 3,200 (event application, error books, derivation, build, legacy projection, and the fix-round-1 clock split, notice cap and orphan pruning). The test file is about 3,400 lines.

## CCRs filed

- **CCR-WP1.11-1:** `StatusEvent::PeerConfigured` gains `#[serde(default)] display_name: Option<String>`.
  - **Reason:** §7.1 `PeerStatus.label` and `FolderPeerSync.label`, and the §7.4 sidebar, show peer names. These live in the catalog (`peer_meta.display_name`) and no status event carries them.
  - **Adapter:** `StatusHub::set_peer_label(installation, Option<String>)`. WP2.1 can call it from catalog snapshots. A label alone never makes a peer appear.
- **CCR-WP1.11-2:** `StatusEvent::LaneState` gains `#[serde(default)] protocol: Option<String>`, the negotiated `tkfs-peer/N`.
  - **Reason:** `PeerStatus.protocol` has no source.
  - **Adapter:** none. `protocol` stays `None`. After WP3.1 every Ready lane is v3, because v2 fails closed.
- **CCR-WP1.11-3:** add `"CARGO_PKG_VERSION"` to `NOT_CODES` in `tests/contracts.rs`.
  - **Reason:** the code-literal grep flags `env!("CARGO_PKG_VERSION")` as an unclassified error code, so no `src/` file can name the crate version.
  - **Adapter:** the hub's default version is empty; the daemon sets it through `set_daemon`.
- **CCR-WP1.11-4** (fix round 1): reword the doc comment of `policy::SNAPSHOT_MIN_INTERVAL` in `src/model/status.rs`. Current: "The snapshot is rebuilt lazily at most this often." Proposed: "The snapshot is rebuilt lazily at most 4 times in any 1 s window (this interval on average); 2 rebuilds may be back to back." No code change.
  - **Reason:** read as a minimum spacing, the comment conflicts with WP2.2's acceptance ("`subscribe` returns within 50 ms of a recorded event"). §3.4 and §14 say "at most 4 times per second", which the hub now meets literally. See deviation 4.
  - **Adapter:** none needed. The hub uses the constant as the token period and adds `SNAPSHOT_MAX_PER_WINDOW`/`SNAPSHOT_WINDOW`.

## Notes for the wiring packages (WP2.1, WP2.2, WP2.7, WP3.1)

- Build with `StatusHub::new(HubConfig::for_sync_interval(config.network.sync_interval_ms), clock)`, then `spawn_ticker(ctx.shutdown.clone())`, then `set_daemon(..)`, and `set_stopping(true)` on shutdown.
- **Producers:**
  - Emit `FolderLifecycle` on every controller transition. It also carries the heartbeat, but the view's own mount state wins.
  - Emit `WorkerHeartbeat`, whose mount state wins when it arrives later.
  - Emit `PeerConfigured`/`PeerRemoved`, `LaneState` (with `error` and `backoff_until_ms`), and `PeerCatalog` on every remote catalog change.
  - Emit `ExchangeStarted`/`ExchangeFinished` for every exchange. Inbound exchanges use `direction: inbound`; a repo's sharing peers include inbound-only ones only through these events.
  - Emit `InboundSession` open and close.
- **Op names:** object traffic must use op names starting with `objects` (or containing `bulk`, for the legacy bridge). Pulls end in `pull` and pushes in `push`. Everything else is treated as metadata.
- **Errors:** a failed exchange's `ErrorWire.retry_after_ms` becomes the pair's `backoff_until_ms`.
- **Reads:** `Action::Status` uses `snapshot()` (at most 4 rebuilds in any 1 s window, at most 2 back to back). `Subscribe` uses `wait_newer(since, min(wait_ms, 25 000))`.
- **Folder removal:** emit `FolderRemoved` only after the folder's last `FolderLifecycle`. A `FolderLifecycle` for a removed state registers it again.
- **Pairing codes:** never put a pairing code in an `ErrorWire` message, activity message or any other event field. The typed snapshot is built from events only and has no scrubber (see *Fix round 1*, finding 4).

## Known limitations

- **Hub only.** Nothing produces events yet: the hub is built standalone (Wave 1). WP2.1 wires the producers, WP2.2 the `Status`/`Subscribe` actions, and WP3.1 the legacy projection.
- **Folder-level download.** Download remaining is folder-level, because any sharing peer can serve it. With several sharing peers, each row shows the same remaining bytes and the folder-level ETA. Only `rate_bps` is per peer.
- **Lumpy rates.** Rates come from `ExchangeFinished` bytes, so a long single exchange reports its bytes at the end. Progress *within* a long objects stream (the `InflightOp.bytes` of §7.1) needs producer events that do not exist yet. `InflightOp.bytes` stays 0.
- **Unknown repos.** Errors of an exchange whose repo has no known folder are dropped: the pair data is kept, but the error needs the folder's state for its scope. The FolderController registers every folder before any exchange can name it.
- **Coarse stall timing.** Stall detection needs `tick()`. Eligibility starts at the first tick after the conditions hold, and the tick that follows an exchange's progress sees the same decrease of remaining work again. Either adds ≤ 1 s to the threshold.
- **Typed-snapshot redaction depends on producers.** The legacy projection scrubs pairing codes. The typed snapshot cannot: the hub never holds a code (§14 WP1.11 task 6), so a producer that put a code in an error message would leak it there (see *Fix round 1*, finding 4).
- **Late exchanges of a removed repo.** A late `ExchangeFinished` for a removed folder's repo re-creates its pair row, which is pruned 10 s later. A folder registered again for that repo within those 10 s inherits that one exchange's evidence (sharing, summary). This is harmless, because the next exchange replaces it.
- **Heuristic sharing.** Sharing evidence for a peer whose catalog was never received (offline since the daemon started) is limited to its outbound or inbound exchanges and the gate source. Until it is seen, such a peer is `NotShared`, so the folder can read `NotShared` rather than `Offline` right after a daemon restart.

## Fix round 1

The reviewer's verdict was `changes_required`: 1 major and 7 minor findings, no ownership violations. All eight are addressed and none is rejected. Each fix has a test that fails without it: every fix was reverted one at a time and its test re-run, and all ten mutations were caught.

1. **Major: inbound-incompatible notices unbounded and not deduplicated** (`hub.rs` `on_inbound_incompatible`).
   - **Fix:** the slot is keyed by remote host (`remote_host`: port dropped, IPv4-mapped IPv6 canonicalised, ≤ 128 bytes). One legacy peer reconnecting from new ports is one notice whose count rises. At most `MAX_INBOUND_NOTICES` = 16 hosts are open; the least recently seen is evicted, not moved into the history. The eviction scans only the `inbound:` key range of the daemon book. Messages are cut to 512 bytes. A host adds an `inbound_incompatible` activity entry only when its notice opens, not on every attempt.
   - **Expiry:** now 10 min after the host's *last* attempt, measured on the monotonic clock.
   - **Test:** `inbound_incompatible_notices_are_one_per_host_and_bounded`.
2. **Minor: Transient store-health and `Lost` mount mirrors never visible.**
   - **Fix:** `ErrorBook::condition` carries the open record forward and calls `ErrorRecord::observe` on each report, so `count` (and the streak) rises per report. The record shows from the 3rd report.
   - **Counting once per event:** a `FolderLifecycle` that carries a newer heartbeat now mirrors the mount only through that heartbeat. `on_heartbeat` returns whether it applied.
   - **Test:** `persistent_store_and_mount_conditions_show_from_their_third_report`.
3. **Minor: legacy `remote_available` true for non-running catalog entries.**
   - **Fix:** it now requires `entry.state == EntryState::Running`.
   - **Test:** `legacy_remote_available_means_a_running_remote_worker`.
4. **Minor: the `status_redacts_pairing_code` assertions on `good` were tautological.**
   - **Taken:** the first option, "state plainly that redaction of the typed snapshot depends on producers". The second option (give the hub the codes and scrub at record time) contradicts §14 WP1.11 task 6, "no pairing code ever reaches the hub". A scrub by pattern is not possible either: codes are 64 hex characters, the same shape as object hashes.
   - **Docs:** the hub module docs, the wiring notes and the limitations say this plainly.
   - **Rewritten test:** it checks things that can fail:
     - `PeerRecord` serialization and `Debug` (including `{:#?}`) never show the code;
     - on a non-leaking fixture, the legacy outputs contain neither the code nor `<redacted>`, so the projection never emits the code by itself;
     - the typed snapshot and the hub's `Debug`, taken *after* the projection received code-bearing records, have no trace of the code, so the projection never keeps them;
     - on the leaking fixture, both legacy outputs are scrubbed.
5. **Minor: zombie `FolderEntry` and orphan pairs after `FolderRemoved`.**
   - **Fix:** tombstones for the last 64 removed states. Late folder-scoped events for them are dropped, and a `FolderLifecycle` registers the state again.
   - **Pruning:** at each tick, `prune_orphans` drops viewless folder entries older than `ORPHAN_GRACE`, pair rows of repos without a registered folder untouched for `ORPHAN_GRACE`, and the matching legacy lane repos.
   - **Tests:** `late_events_of_a_removed_folder_are_dropped` and `unregistered_folder_state_is_pruned_after_the_grace`.
6. **Minor: durations on the wall clock.**
   - **Fix:** the `Now { ms, mono }` split described under *How the hub works*. Stall timers, error streaks (Contention), the inbound TTL and the orphan grace use `mono`. Reported fields use `ms`, and monotonic timers are reported by their age.
   - **Unchanged:** the pure rules (`rules::stall`, `error_visible`) are clock-agnostic and did not change.
   - **Test:** `wall_clock_jumps_neither_fire_nor_suppress_timers`.
7. **Minor: tick progress did not mark the snapshot dirty.**
   - **Fix:** `tick` sets `changed` when it records progress, and when it resets a non-zero transfer episode (`total_bytes` changes).
   - **Test:** `progress_seen_by_the_tick_is_published`.
8. **Minor: throttle beyond "≤ 4/s".**
   - **Fix:** a sliding window, so there are at most 4 rebuilds in any 1 s window, layered on the burst-2 bucket. A literal burst 1 would break WP2.2's 50 ms subscribe latency (deviation 4). The remaining wording gap with the `SNAPSHOT_MIN_INTERVAL` doc comment is CCR-WP1.11-4.
   - **Tests:** `snapshot_rebuilds_never_exceed_four_in_any_second`, plus the tightened threaded bound.
