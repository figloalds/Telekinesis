# WP2.2 — Management API v2, ControlClient, CLI

Branch `revamp/wp2-2-management-api`, cut from `revamp/wave-2-base`
(`ca7d8a9`).

## Summary

WP2.2 lands the typed control actions of §3.5 and §7.2, the persistent
`ControlClient`, and the first user-visible P4 improvement: `tkfs manage
status` and `tkfs manage watch`. Only the four owned files changed.

| File | Content |
|---|---|

### Management API v2 (`manage_v2::handle`)

| Action | What it does | Reply |
|---|---|---|
| `status` | `ctx.status_source.snapshot()` | `StatusSnapshot` |
| `subscribe{since, wait_ms?}` | `wait_newer(since, min(wait_ms ?? 25000, 25000))` | `StatusSnapshot` (the current one on timeout; at once for a `since` ahead of the hub, e.g. from a previous daemon run) |
| `attach{state}` | `FolderCmd::Attach`, waits ≤ 60 s (`ATTACH_DEADLINE`) | `{state, status}` |
| `detach{state, force}` | `FolderCmd::Detach{force}`, waits ≤ 60 s | `{state, status}` |
| `pause-sync`, `resume-sync` | `CatalogCmd::SetIntents{sync_enabled}` (skipped when the catalog already has the value), then `FolderCmd::SetSync`, ≤ 5 s | `{state, status}` |
| `override-gate{state}` | `CatalogCmd::OverrideGate` when a gate row exists and is not overridden yet, then `FolderCmd::OverrideGate` (which also re-arms a held attach: "mount now"), ≤ 5 s | `{state, status}` |
| `force-stop{state}` | `CatalogCmd::SetDesired(false)` (when still desired), then `FolderCmd::ForceStop`, waits ≤ 15 s (`API_STOP_WAIT`) | `{state, status}` |
| `retry{state}` | `FolderCmd::Retry`, ≤ 5 s | `{state, status}` |
| `revalidate{state, ids?}` | worker `revalidate{ids}` (30 s) through `FolderDirectory::client`; then, only while the gate is Blocked, `FolderCmd::Revalidate{ids: []}` so the controller reopens it without re-queuing twice | `{state, requeued, status}` |
| `diagnostics` | `diagnostics::collect(ctx)` (WP4.2's stub until then) | its value |

Common rules:

- **Order.** The durable intent goes first (`CatalogCmd`), then the folder
  command (invariant 26: `desired=0` is in the catalog before a force stop;
  the tests' fake registry checks this on every command).
- **Refusals before any write.** An unknown folder gives `FOLDER_NOT_FOUND`;
  a stopping daemon (`ctx.stopping`) gives `ORCHESTRATOR_STOPPING` for every
  write. Reads keep working (WP2.1's transport decides whether it lets them
  through during shutdown). A legacy action passed to `handle` gives
  `UNSUPPORTED_OPERATION`.
- **Read-your-writes.** The controller publishes its view (and records it to
  the hub) before it answers. The reply's `status` comes from the first hub
  snapshot whose lifecycle phase, intents and gate kind (plus the mount state
  for attach and detach) match the view the controller answered with,
  waiting at most 1 s (`STATUS_SETTLE`) through `wait_newer`, so the snapshot
  throttle never shows a stale status. `status` is `null` only if the hub
  does not know the folder.
- **Activity.** Every folder action records an `action` activity entry
  (`"attach requested"`), so `watch` shows who did what.

### ControlClient (`api.rs`, reachable as `orchestrator::manage_v2::ControlClient`)

- `ControlClient::connect(&Config)` reads `DATA/orchestrator.json` (again on
  every reconnect, so it follows a restarted daemon to its new port);
  `connect_endpoint(url)` uses a fixed endpoint. `call(&Action, deadline)`;
  also `endpoint()`, `connections()`, `disconnect()`.
- One socket for every call. Before sending, a socket the daemon closed
  (idle timeout, restart, a 6298d0b daemon that serves one request per
  connection) is detected with a non-blocking `peek` and replaced: nothing
  was sent on it, so this is never a replay.
- The call's deadline is applied to the socket's read and write timeouts, so
  a 25 s `subscribe` is not cut by `ws::connect`'s 15 s default.
- After the request was sent, a transport failure is `CONNECTION_LOST` and an
  expired deadline `REQUEST_TIMEOUT` (both uncertain, invariant 16); the
  connection is dropped. A read-only action (`List`, `Inspect`, `Peers`,
  `Status`, `Subscribe`, `RemoteList`) is then sent once more on a fresh
  connection if its deadline allows. A mutating action is never sent again;
  its error says so ("…it may or may not have run, and it is not sent
  again: check the status").
- An error reply keeps the connection (invariant 17) and is returned as
  `ws::RemoteError`, exactly as `client()` returned it before.
- `default_deadline(action)` covers each action's own wait plus 15 s:
  subscribe `wait + 15 s`, stop and force-stop 45 s, attach and detach 75 s,
  shutdown 52 s, create/receive/pair/remote-list/diagnostics 120 s,
  folder passthrough and revalidate 60 s, everything else 30 s.
- `orchestrator::client(config, action)` (used by the GUI and `tkfs
  create`) now opens a `ControlClient` and calls it with
  `default_deadline` (it used `ws::connect`'s fixed 15 s socket timeouts).

### CLI (`src/main.rs`)

```
tkfs manage status [--json]
tkfs manage watch [--json]
tkfs manage attach STATE | detach STATE [--force] | pause STATE | resume STATE
tkfs manage mount-now STATE | force-stop STATE | retry STATE
tkfs manage revalidate STATE [--id ID]...
tkfs manage diagnostics
tkfs manage stop STATE [--no-wait]           (new flag: `wait:false`)
```

- **Folder arguments** (every command that takes one, legacy ones
  included) accept the full state, a unique folder label, or a unique state
  prefix of at least 4 characters (the `[3c0f8a21]` that `status` shows).
  They are resolved with one `status` call on the same connection; an
  ambiguous label or prefix is refused (`INVALID_REQUEST`, listing the
  candidates); an argument that matches nothing, or any argument when the
  daemon has no `status` (a 6298d0b or pre-WP2.1 daemon), is passed on
  unchanged.
- **Output.** `status` prints `format_status`. The v2 folder actions print
  one sentence about the outcome ("Sync of Photos is paused.", "Photos is
  mounted at D:\Photos.", "Photos is not mounted: it waits for the initial
  sync (tkfs manage mount-now mounts it anyway).", "3 events of Photos
  re-queued for activation.") followed by the folder's block. `--json`
  (global on `manage`) prints the daemon's reply as it is; the legacy
  commands print JSON as before.
- **`watch`.** Long-polls `subscribe`. On a terminal it redraws in place
  (ANSI; on Windows the console's virtual-terminal mode is switched on via
  `SetConsoleMode`) every change and at least every 2 s, so ages and
  countdowns move. On a pipe it prints the status on every change; with
  `--json`, one snapshot per line. A daemon that goes away or is shutting
  down is waited for (retry every 2 s) and followed to its new port; any
  other error reply (an older daemon without `subscribe`) ends the command;
  a closed pipe ends it quietly.
- The CLI renders relative times against the local clock (`as_of_now`): the
  hub rebuilds a snapshot only when something changed, and the daemon runs
  on the same machine.

### The status text (`format_status`)

Per folder: the hub's sync summary (`! ` marks NeedsAttention, Stalled and
Blocked), lifecycle (phase, for how long, startup step, pid, adopted,
degraded, restarts, restart countdown, last exit with its fatal line or the
last log line), mount (state, path, age, attach failure with class, attempt
and retry countdown, or why it is not mounted), gate (source, age,
`waiting_on`), paused sync, store health with open files, pending saves and
unflushed files, inbox (pending by state, quarantined, blocked), activator
counters, content (available/missing with bytes, downloading, requested,
history), journal (events, not yet acknowledged by a peer, unresolved
conflicts), each sharing peer (direction, state with stall duration or

## Deviations from the spec, and why

1. **Where the client side lives.** `ControlClient` and `format_status` are
   in `api.rs` as §14 says, but `api` is a private module and
   `src/orchestrator/mod.rs` (its `pub use api::{…}` line) belongs to WP2.1.
   They are re-exported from the public `manage_v2` module
   (`orchestrator::manage_v2::{ControlClient, format_status, format_folder,
   default_deadline, is_read_only}`), which `main.rs` and the tests use.
   CCR-WP2.2-1 asks for the `orchestrator::` re-export.
2. **Revalidate** is one worker RPC (for `requeued`) plus, only while the gate
   is Blocked, `FolderCmd::Revalidate{ids: []}`. The controller runs the
   worker RPC itself and drops its result (`FolderView` has no field for it;
   WP1.2 notes, item 11), and only the command reopens a Blocked gate.
   Sending the command with the user's ids would re-queue and re-activate the
   rows twice; with an empty list the worker re-queues nothing. CCR-WP2.2-2
   (optional) would make it one call.
3. **Reply status is settled** (read-your-writes, ≤ 1 s, see above) rather
   than whatever snapshot the throttle last published; `status` may be
   `null` when the hub does not know the folder.
4. **Waits not given by §14:** detach 60 s (like attach: a force detach
   drains callbacks for up to 10 s), force-stop 15 s (`API_STOP_WAIT`, like
   Stop), pause/resume/override-gate/retry 5 s (they settle at once),
   revalidate 30 s, `subscribe` without `wait_ms` 25 s.
5. **ControlClient specifics:**
   - a deadline that expires after sending is reported as `REQUEST_TIMEOUT`,
     not `CONNECTION_LOST`; both are uncertain and never replayed;
   - a socket the daemon closed is replaced *before* sending, for every
     action (nothing was sent, so it is not a replay);
   - a read-only action is retried at most once, and only while its
     deadline allows.
6. **`client()` changed behaviour** (not its signature): per-action deadlines
   instead of a fixed 15 s socket timeout, one retry for read-only actions,
   and transport errors typed as `CallError` (`CONNECTION_LOST`,
   `REQUEST_TIMEOUT`). Error replies are unchanged (`ws::RemoteError`).
7. **Writes while stopping** are refused in `manage_v2` itself; reads are
   not (§3.6's "reject new actions" is done by WP2.1's transport for every
   action).
8. **Catalog writes are skipped when the catalog already holds the value**
   (pause, resume, force-stop) or there is no gate to override; the folder
   command is still sent, so a re-issued action still reaches the
   controller (it re-arms the attach, cancels nothing).
9. **CLI additions** beyond §14: folder-argument resolution (label, prefix),
   `stop --no-wait`, a global `--json` on `manage`, one-sentence outcomes for
   the folder actions, help text on every `manage` subcommand. `pause` and
   `resume` are the CLI names of `pause-sync` and `resume-sync`, `mount-now`
   of `override-gate`.
10. **Times in UTC.** No time-zone dependency exists in the tree, and UTC
    keeps the text a pure function of the snapshot (golden test). Ages
    ("12 s ago") carry the user-relevant part.

## CCRs

- **CCR-WP2.2-1** (`src/orchestrator/mod.rs`, WP2.1 / WP2.INT): add
  `pub use api::{ControlClient, default_deadline, format_folder,
  format_status, is_read_only};` (or make `api` public) so the client side is
  reachable where §14 names it (`api::format_status`,
  `orchestrator::ControlClient`). **Reason:** `mod api;` is private and the
  file is WP2.1's. **Adapter:** `manage_v2` re-exports them; nothing else
  needs to change after the CCR (the re-export can stay).
- **CCR-WP2.2-2** (optional; `src/orchestrator/folder.rs`, WP1.2's, or
  `model::orchestrator`): let `FolderCmd::Revalidate` report the worker's
  `requeued` (for example the last revalidate result in `FolderView`), so the
  API makes one call. **Reason:** the controller drops the RPC's result.
  **Adapter:** deviation 2.
- **CCR-WP2.2-3** (information for WP2.1; no contract change). What the
  `ControlClient` and the CLI rely on:
  1. `manage::manage` forwards the 11 v2 variants to `manage_v2::handle`
     (and `run.rs` serves them on the persistent control loop).
  2. Persistent connections: the loop must survive `ws::accept`'s 15 s
     socket read timeout only by closing that connection (the client
     replaces a closed idle socket before its next request); a
     `subscribe` long poll waits in `wait_newer` (≤ 25 s), not on the
     socket, and its reply is written within the 15 s write timeout.
  3. `StatusHub::set_daemon(DaemonStatus{installation, version, pid,
     started_at_ms, control, network, log_path})` once the endpoints are
     known, so the status header is complete; `set_stopping(true)` on
     shutdown (the header shows it).
  4. Keep the order "intent first, then command" in the legacy actions too
     (§3.5): the API's replies assume the controller publishes its view
     before it answers (it does, `after_step`).
- **CCR-WP2.2-4** (information for WP2.INT, `tests/w2_integration.rs`): the
  CLI check can assert on stable text: the folder heading `LABEL [xxxxxxxx]`
  and the rows `  lifecycle  running…` and `  mount      …`; `manage status
  --json` is the `StatusSnapshot`; `manage watch --json` prints one snapshot
  per line, the first at once.

No CCR assigned to WP2.2 was found in `notes/wp1-int.md` (nor in the other
notes); the WP1.11 notes' wiring guidance (`Status` = `snapshot()`,
`Subscribe` = `wait_newer(since, min(wait_ms, 25 000))`, no pairing code in
any event) is followed. CCR-WP1.11-4's reading of the snapshot throttle is
what makes the 50 ms `subscribe` latency hold.

## Known limitations

- **No daemon-level test here.** The daemon in this tree still runs the
  legacy `Supervisor` (WP2.1 wires the actors and forwards the v2 actions).
  Smoke-tested against it: `manage list/create/inspect/stop/start/shutdown`
  work through the `ControlClient` (folder-argument resolution falls back to
  pass-through), while `manage status` and `watch` end with the legacy
  `NOT_IMPLEMENTED: … is not served by the legacy orchestrator`. The CLI is
  tested end to end against an in-process endpoint serving
  `manage_v2::handle` (`cli_*` tests); WP2.INT's `w2_integration` covers the
  real daemon.
- **A close racing the send.** The stale-socket check cannot see a daemon
  that closes the connection in the instant the request is written; a
  mutating action then fails `CONNECTION_LOST` without having run, and the
  caller re-reads the status (never a replay). With WP2.1's persistent loop
  this needs an idle timeout to coincide with a request.
- **Connect time is not bounded by the call's deadline.** `ws::connect` has
  its own 3 s TCP connect timeout per address and 15 s handshake socket
  timeouts; the control endpoint is loopback.
- **`watch` on a terminal shorter than the text** scrolls on each redraw (no
  paging or truncation).
- **UTC only** in error times; ages are relative.
- **Hints name CLI commands** with the short state; the GUI (WP3.4) has its
  own buttons and does not need them.
