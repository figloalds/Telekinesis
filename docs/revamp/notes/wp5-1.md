# WP5.1 — Concurrent-edit activation

Branch `revamp/wp5-1-concurrent-activation`, cut from `revamp/wave-5-base`
(`c6948c9`). Owned files only (§13 rule 1): `src/core/commit.rs`,
`src/core/derive.rs`, `src/core/inbox.rs`, `src/core/snapshot.rs`, the new
`tests/qual_wp5_1_concurrent.rs`, and these notes. `src/core/verify.rs`,
`src/worker/activator.rs` and the other owned tests are unchanged. No frozen
file, no `Cargo.toml`/`Cargo.lock` change and no other package's file was
edited.

The design note `wp5-1-design.md` was written first, with the baseline
profile and the approaches; its section 3 was revised to describe what was
built.

## Summary

A slow commit no longer re-derives the branch.

- It projects incrementally from the handle's view (`project_append`, with
  incremental namespace passes).
- It derives through a per-branch derivation index kept beside the event
  cache (`BranchIndex`): everything append mode used to recompute from every
  event on every commit.
- It writes only what changed: stored rows are skipped, the seal trusts the
  handle's own anchor, and the view slots are patched.

Full mode (fallbacks, rebuilds, the oracle) runs on an interned engine:
integers instead of `String` sets, one causal sweep per cone, antichains
enumerated over concurrent sets, and cuts projected from the cone's own
registers.

fixtures; details below):

## Tasks

1. **CCR-WP4.INT-3.**
   - *Derive only the touched cones when the precondition fails only for
     untouched ones.* Append mode never examined untouched cones:
     `append_plan` derives the cones of the entities that reach an entity
     the event touches. The fallbacks that remain fail on a touched cone (in
     the baseline profile, all of them were witness displacements). What
     made them unaffordable was full mode's cost: a fallback that took 53 s
     at 4.5K events now takes about 0.3 s. A scoped full derivation was not
     built (deviation 2).
   - *Remote namespace changes that touch no conflicted entity keep the
     fast path.* Done by WP4.INT (fix 6); unchanged.
   - *One replay for several queued slow events*, and *keep a prepared
     replay when the branch moved only by unrelated commits*: not built
     (deviation 3). A preparation now costs the event's cones, so a stale
     one is re-prepared in milliseconds. The scenarios show a third of the
     baseline's stale outcomes and no backlog.
2. **CCR-WP4.INT-4.** Competing-cut counts are memoized per cone,
   process-wide, keyed by a digest of the branch, the cone's relevant events
   and the ancestry among them (`derive::cut_counts`). A successor recounts
   only the cones whose relevant events changed. Its cones come from the
   branch index (`check_successor_cuts` with the index), so the bound that
   scanned every event is no longer needed there.
3. **Interning.** `NsContext`, `ConeGraph` and `project_refs` use integers
   for entities and events. Entity numbers follow the ids' order, so every
   iteration order is the historical one. No `String` sets remain.
4. **Full rebuild.** Full mode projects cuts from the cones' registers under
   the same condition as append mode (`projection_cannot_fail`). It uses the
   sweep and the enumeration of task 3, and groups location pairs by slot.
   Results in (d) below.
5. **`check_commit`.** `commit::verified` is an in-memory set keyed by store
   root and hash. It holds the file's size and mtime and the instant this
   process verified the object. A local commit skips the re-hash of a new
   object verified within five minutes whose file still has that size and
   mtime. Invariant 1 holds: the bytes this process hashed are unchanged by
   `stat`, the rule the startup marker already applies. The installers that
   hash the bytes are in `src/core/objects.rs`, which this package does not
   own: CCR-WP5.1-1, with an adapter.
6. **`backfill_journal_branch`.** The cursor is upserted
   (`INSERT … ON CONFLICT DO UPDATE`), so a backfill that crashed before its
   first progress row resumes.

The measurements required more than the tasks (design §3):

- the appended projection with incremental namespace passes;
- the branch index;
- a write that skips rows stored with the same payload;
- a seal that trusts the handle's own last anchor and reuses its header;
- view slots patched for the changed entities;
- the inbox attempt keeps its view across its savepoint (it was reloaded on
  every slow commit).

WP4.INT's two-hour storm reached 9,399 open conflicts and did not converge;
this one converges with 24K. Its backlog grows during editing once the
open conflicts pass about 10K. A probe on a copy of the running stores at
16.8K events and 13K open conflicts shows why. It is (c')'s measurement
with temporary phase timers, run from a separate tree:

- a slow commit's derivation takes 20 ms and its appended projection
  1.4 ms;
- its write takes 168 ms: the stored projection's header 87 ms (per
  conflict-changing commit) and the seal 104 ms.

Both rows hold the projection's whole conflict list, 5.7 MB each at that
size (CCR-WP5.1-2). Commit `5d11e5a`
then serializes those lists from per-record texts and stops reading back the
anchor the handle wrote. That took the header write from 87 to 51 ms and
the seal from 104 to 90 ms on the same probe; the rest is SQLite writing two
5.7 MB rows. The two-hour runs predate it.

**Fallbacks and full mode.** In the baseline profile, 1.4 % of append
commits fell back to full mode, each costing 13–53 s at 3–4.5K events. On
the interned engine the same fallback takes about 0.3 s at 4K events. The
fallback reasons are unchanged (design §3.5).

**Release oracles.** Both ran on the final code (`5d11e5a`), sharded:

- `derive_oracle::fuzz_300_seeds_release` with `TKFS_DERIVE_SEED_START=1000`
  and `TKFS_DERIVE_SEEDS=1000`: **1,000 seeds (1000–1999) pass**. That is
  68,193 append commits, 35,279 verify-mode commits, 40 fallbacks and
  103,541 checked commits. Every commit was compared with a derivation from
  no rows. Under the checks, every extension of a kept index is compared
  with a fresh build, and every indexed derivation and successor count with
  the scan's.
- `fuzz_stress_release`: **40 seeds (5000–5039) pass**, with 6,970 append,
  3,475 verify, 7 fallbacks, 11,129 checked and 318 refused deliveries

The same seeds also passed at `a2d95ae`, before the header cache. That

## Deviations

1. **(c) is measured on WP1.7's shape with the open conflicts added.** It
   was not measured on the daemon workloads: those report the worker's whole
   CPU, which is mostly not activation (see above). The storm-shaped variant
   (c') is reported next to it.
2. **No scoped full derivation** (CCR-WP4.INT-3, item 1; design §2.B and
   §3.7). A touched cone that fails the precondition still derives the
   branch in full, but full mode now costs a fraction of a second where it
   cost tens of seconds. The memoized model of full mode (design §2.C) was
   the plan for that. It was not needed and was not built.
3. **No batched preparation and no rebase of a prepared replay**
   (CCR-WP4.INT-3, items 3 and 4). Both would save only a re-preparation,
   and a preparation now costs the event's cones. The pooled read store
   keeps its event cache and branch index across tickets (they are extended
   from the journal). Its view is reloaded when the engine's commits changed
   the stored projection.
4. **The stored projection's header and the anchor's header still hold the
   whole conflict list** (snapshot format 2). A slow commit that changes the
   conflict list serializes, hashes and writes it twice: `current_meta`, and
   the rows anchor's header. That is O(open conflicts) bytes. Changing the
   anchor's layout needs a format bump, which `tests/startup_snapshots.rs`
   (not owned) pins at 2: CCR-WP5.1-2.
5. **Test adaptations, no weakening.**
   - `derive::tests::cut_memo_is_bounded_by_retained_bytes` measures the cut
     memo with whole-cut projections (`Memo::unrestricted`), because full
     mode now projects restricted records when no cut can fail (task 4). Its
     assertions are unchanged, and it now also asserts that the restricted
     derivation equals the reference and uses no cut memo.
   - The other unit tests changed call sites only: an `NsContext` takes its
     base, `append_plan` takes the cone graph, and `check_successor_cuts`
     takes the index or `None`. Where an index is available, they compare
     the indexed path too.
6. **`DeriveInput`** gained `fresh` (the projection's records that are not
   stored yet) and the crate-private `index`. `derive::thread_indexed_appends`
   is a telemetry counter. The development phase timers were removed.
7. **Which code each measurement ran on.**
   - The final tree is `5d11e5a`.
   - The two-hour, 20-minute and 30-minute daemon runs ran before it, at
     `a2d95ae` / `f1c4017` (the same library apart from `5d11e5a`'s
     header-write change).
   - `5d11e5a` only changes how the header and anchor texts are built and
     when a seal reads back its own anchor. Debug builds assert the texts
     equal to the serialized output on every write. After it, the full
     suite, the release oracles (1,000 + 40 seeds), WSL and (c)/(c') were
     run again on the final tree.
8. **(c') is 8–10×, not 10×.** It is this package's extra scenario, next to
   the acceptance's (c). Its remaining cost is the storm cone's own
   antichains (about 100 new cuts per event).

## CCRs filed

- **CCR-WP5.1-1** (`src/core/objects.rs`, WP5.3). *Requested:* after hashing
  the bytes they install, `put_object` and `put_stream` call
  `commit::verified::note(root, hash, len, mtime_ns)`, so `check_commit` finds
  the object in the in-memory verified set (task 5). *Reason:* the installers
  are not owned by WP5.1. *Adapter:* `check_commit` (`verify_new_object`)
  trusts the object's availability row when its trusted size and mtime match
  the file and it was verified within `FRESH_MS` (five minutes); the row is
  what the installer writes after hashing. It then records the object in the
  set and skips the re-hash. Otherwise it re-hashes and records the object.
- **CCR-WP5.1-2** (snapshot format; `tests/startup_snapshots.rs`, which
  pins format 2). *Requested:* allow a format 3 in which the rows layout's
  anchor header and `current_meta` list the projection's conflicts by id,
  with their payloads in rows, as `snapshot_conflicts` already holds the
  conflict rows. A conflict-changing slow commit would then write O(change).
  *Reason:* each such commit serializes, hashes and writes the whole list
  twice. The list is the current projection's records: 2 MB at 9K open
  conflicts in (d)'s store, and 5.7 MB at 13K in the two-hour storm. There,
  the header write took 87 ms and the seal 104 ms of a 190 ms slow commit.
  After `5d11e5a` (per-record texts, no read-back of the handle's own
  anchor) they take 51 and 90 ms; what remains is SQLite writing the two
  rows. *Adapter:* none; format 2 is kept and the cost is recorded here.
- **CCR-WP5.1-3** (`docs/ARCHITECTURE.md`, docs owner). *Requested:*
  describe the slow path as built: the appended projection, the branch index
  beside the event cache, the skipped stored rows, and the seal's anchor
  cache. The module docs of `derive.rs` (*The branch index*) and
  `commit.rs` describe them.

## Known limitations

- The header writes of deviation 4 (CCR-WP5.1-2) grow with the current
  projection's conflicts.
- Fallbacks are still full derivations: up to about 3 s each at 9K events
  (the reconstruction of (d) is one). In the 24-name storm that built (d)'s
  store, 99 of about 9.5K commits fell back, all of them witness
  displacements, and the storm's denser cones met the competing-cut limit
  (refused events, as full mode refuses them).
- A few O(history) integer passes remain per slow commit: the event cache's
  merge and the index's position move (about 1 ms at 5K events), the
  guard's scan for the new event's id, and `review_receipts`' scan.
- The pooled read store reloads its view after engine commits that changed
  the stored projection (deviation 3).
- In the daemon workloads, the worker's CPU per minute grows with the
  history at a constant edit rate, in both builds and with few open
  conflicts. In (b), it went from 17.5 to 70 s/min before, and from 14 to
  56 s/min after, as the history grew from 2.6K to 9.5K events (about
  10 open conflicts). Activation's own slow commits stay near 10 ms (c);
  this package did not profile the rest (the sync and status paths, the
  editors' imports). A profile of a worker past 10K events is the next
  step.
