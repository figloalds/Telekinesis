## Summary

A slow-path event no longer projects, derives or serializes anything while
the engine lock or the SQLite writer is held (M5, I7). The background
activator (WP2.3) gets:

```text
activate_slice(SliceBudget{64, 25, inline_slow:false})   // under the lock: fast paths; stops at a slow event
  -> SlowTicket { id, branch, base_seq }
Store::prepare_slow(&read, &ticket) -> Prepared::Computed(PreparedCommit)   // off-lock, read handle
commit_prepared(prepared) -> Committed | Stale | Failed                     // under the lock: checks + rows + seal
Stale -> requeue(id, backoff)                                                // never committed inline
```

Measured (release, Windows dev box shared with other agents' builds): the
engine lock is held **10.8–23.3 ms** (probe's worst wait; floor < 50 ms) for
the two-way slow event at 2K (`commit_prepared` 12–24 ms); the same event
committed inline takes 105–176 ms under the lock. Details in *Qualification*.

### `src/core/derive.rs` (task 1)

- **`derive_conflicts(&DeriveInput) -> Result<DeriveOutput>`** (pure; reads
  no table) and **`write_projection(tx, branch, &DeriveOutput)`** (cheap).
  `persist_projection` keeps its signature and is now: rewrite
  `current_state`, read the stored rows the new event reviews
  (`read_reviewed`), `derive_conflicts`, `write_projection`.
  - `DeriveInput { branch, projection, events, new_event, reviewed }`: the
    only stored rows a derivation used to read (those the event reviews) are
    pre-read into `reviewed`.
  - Review validation (`INVALID_CONFLICT_REVIEW`) moved from the write into
    the derivation (`review_receipts`): it reads only the derived list and
    the events. The write applies the receipts (`resolved_by`) in the same
    order. Every refusal surfaces with the same text as before.
  - Append / full / fallback / rebuild produce one record set (`Rows`: rows
    deduplicated by id, receipts, whether full mode's namespace DELETE
    runs). Verify mode derives both off-lock and `write_projection` writes
    each in its savepoint and compares (as before; the comparison needs the
    stored rows). Under `set_thread_commit_checks` the derivation from no
    rows is computed off-lock too and compared at write time; the refusal
    parity check (mode refused ⇒ full refuses with the same text) is
    decided in `derive_conflicts`.
  - Counters: rebuild/full/append/fallback/restricted/checked and
    `commit_micros` are counted where the derivation runs (the preparing
    thread for an off-lock commit); `verified` at the write.
- **CCR-WP1.6-5** (successor counting): `successor_may_add_cuts(events, new)`
  and `check_successor_cuts(branch, events, new)` (+ `NsContext::count_cuts`,
  the enumeration of `cone_conflicts` without projections). See
  `commit.rs` below.
- The historical-signature helpers `derive_full` / `derive_append` remain for
  the unit tests only (`#[cfg(test)]`); the code paths use
  `derive_full_with` / `derive_append_with` over a `DeriveInput`.

### `src/core/commit.rs` (tasks 2, 3; CCR-WP1.INT-4, CCR-WP1.6-1, CCR-WP1.6-5)

- **Split of the slow commit.** `compute_slow(event, committed_view,
  precompute)` (reads only: the event cache, `project`, the reviewed rows,
  `derive_conflicts`, the stored-projection delta of CCR-WP1.INT-4; with
  `precompute` also the projection's JSON, the seal's journal hash and the
  view slots) and `write_commit(event, local, checked, plan, view_base)`
  (one savepoint: journal, object rows, the stored projection as the
  `current_parts` delta or the full rewrite from the precomputed JSON,
  `write_projection`, frontier, forced seal). The inline path
  (`commit_checked`, unchanged signature) is `compute_slow` + `write_commit`
  under the caller's lock, exactly as before; the prepared path computes
  off-lock and writes under the lock.
- **CCR-WP1.INT-4 kept**: the delta decision (`projection_delta`, unchanged)
  is made against the stored projection of the state the computation read
  (the read handle's view); the write happens only if the branch is still at
  that state, so it equals the inline decision. The forced seal serializes
  the projection the commit holds.
- **Forced seal of a prepared commit** (`seal_prepared`): the payload
  `snapshot::persist` writes (same bytes; `seal_payload`, pinned by the unit
  test `seal_payload_is_snapshot_persist_byte_for_byte` and by the
  differential fuzz, which compares `startup_snapshots` byte for byte with
  the inline commit's `snapshot.rs` seal), built from the projection's JSON
  and the journal hash state over the branch's earlier rows, both computed
  off-lock; under the lock only the event's row is hashed and the small parts
  (conflicts, frontier, descriptor) read. Falls back to
  `snapshot::maybe_persist` if the branch's journal is not exactly that
  prefix plus the event. CCR-WP2.4-2 asks `snapshot.rs` to expose this.
- **Event cache** (`Cache::events`, task 2): one branch's events, parsed, in
  `id` order (exactly `Store::events()` filtered by branch: the slow path's
  historical input order), plus the seal's journal hash state. Keyed by the
  global journal: `upto` (max `seq`) and `total` (row count), read with one
  aggregate per use; a use loads only rows with a larger `seq` (range scan,
  merged by id) and checks that the count grew by exactly those rows, else
  reloads in full (deletions). Rows read inside a write transaction may roll
  back and their sequence numbers be reused, so they are kept as tentative
  `(seq, id)` pairs and checked before every later use; `with_write`
  promotes them after its transaction (`settle_event_cache`). A full load
  inside a write transaction is not kept (and is redone after it). Used by
  `prepare_slow` (read handle), the inline slow path and the successor
  count. `Store::cached_branch_events` exposes it to tests.
- **CCR-WP1.6-5**: `fast_successor` (and `fast_successor_in`) run
  `check_namespace_successor` after a namespace successor applies: the
  branch's cached events plus the event go through
  `derive::successor_may_add_cuts`, a scan that finds the only two ways a
  successor event (after the whole history, parenting every head) can change
  a cone's competing-cut count: placing an existing entity under a parent it
  never had or into a slot it never used that another entity used (a cone
  join), or the first tombstone of an entity with `alive = true` versions
  outside its placements (presence witnesses join the relevant set). Then
  `derive::check_successor_cuts` counts every cone with the event that
  contains a touched entity, exactly as full replay does, and refuses with
  full replay's `NAMESPACE_HISTORY_LIMIT` text (a remote event is
  quarantined, a local operation fails; nothing is committed). The creation
  successor needs no count (a fresh entity joins one existing cone) nor does
  the content successor (no relevant event; a TRUE version that descends from
  all). Snapshot suffix replay (accepted events) does not count. Telemetry:
  `Store::successor_cut_checks()`.
- **CCR-WP1.6-1 (adapter, owned side)**: a fast commit whose periodic seal is
  due patches the connection's view first and seals that projection
  (`maybe_persist(.., Some(&view.projection))`) instead of reading the
  projection back and parsing it (about 31 ms at 2K, 117 ms at 10K saved per
  seal). `SEAL_INTERVAL` mirrors `snapshot::INTERVAL` only to know that the
  seal is due; `snapshot.rs` still decides. Telemetry:
  `Store::known_projection_seals()`.
- `slow_commit_view` takes precomputed slots; `view_slots`, `patch_view`
  factored out (the post-commit view patch never fails the commit: a name
  that cannot be keyed drops the view).

### `src/core/inbox.rs` (tasks 3, 4)

- **`PreparedCommit`** (opaque: only `prepare_slow` makes one): the ticket,
  the staged event as read, `base_seq` (the branch's journal sequence the
  computation read) and the outcome (`Slow(plan)`: projection,
  `DeriveOutput`, delta, JSON, journal hash, slots; `Fast(delta)` when a
  successor applies at that state; `Pending`; `Refused(error)`; `NotReady`).
  Accessors `ticket()`, `event()`, `base_seq()`, `projection()`,
  `derived()`, `is_computed()`.
- **`Store::prepare_slow(read, ticket)`**: one read transaction of its own on
  the read handle (`BEGIN` … `ROLLBACK`), so every read sees one committed
  state; re-reads the row, its links and the commit validations, records
  `base_seq`, then computes. A refusal is recorded, not returned. Afterwards a
  PASSIVE WAL checkpoint, off-lock (see *Qualification*: SQLite's automatic
  checkpoint inside the next commit was the largest part of the hold). `Err`
  only if the read transaction cannot be used.
- **`commit_prepared(Prepared::Computed)`**, in its own write transaction:
  the row must still be staged `ready`/`retry` (else `Committed{slow:false}`
  if it was committed meanwhile, or `Stale`), its links all committed (else
  re-classified and `Stale`), the event unchanged, and the branch's journal
  sequence still `base_seq` (else `Stale`, nothing written); then the commit
  validations are **re-run** (`check_commit`: `EVENT_ID_REUSED`,
  `OBJECT_SIZE_CHANGED`, `BRANCH_DESCRIPTOR_CHANGED`,
  `UNREFERENCED_OBJECT_SIZE`, size limits; invariants 6 and 7, I7). A failure
  quarantines (or retries, if transient) exactly as the inline path; a
  recorded refusal is applied the same way. Then the precomputed write:
  row bookkeeping (children released), `write_commit`, the projection
  becomes the connection's view. No projection, derivation or serialization
  of the projection under the lock. `Prepared::Inline` keeps the Wave 1
  compatibility path (the slow path under the caller's lock).
- `branch_seq` (the ticket's and the staleness check's sequence) uses a
  `CROSS JOIN` so the journal is the outer loop (newest first): a few point
  lookups instead of a join over every event of the branch (0.7 ms at 2K,
  11.8 ms at 10K before).
- Task 4 (`activate_slice{inline_slow:false}` returns a `SlowTicket`,
  `inline_slow:true` the compatibility path) was already in WP1.6's code and
  is unchanged.

## Deviations from the spec, and why

1. **`PreparedCommit` shape.** The spec lists `PreparedCommit { event,
   base_seq, projection, derived: DeriveOutput, reviewed: Vec<Conflict> }`.
   It has those (behind accessors; `reviewed` is folded into the
   derivation's input and output) plus the outcome kinds a preparation can
   find besides a slow plan (`NotReady`, `Fast`, `Pending`, `Refused`), so
   that `commit_prepared` applies them under the lock as the inline path
   would instead of committing anything inline. The fields are private: a
   commit must never write a computation `prepare_slow` did not derive.
2. **`write_projection` writes the derived records only.** The stored
   projection (the CCR-WP1.INT-4 delta or the full rewrite) is written by
   `commit.rs`, which owns that decision; `persist_projection` (rebuilds,
   evacuation) still rewrites `current_state` itself.
3. **Event cache key.** The spec keys it by `(branch, max seq, count)`. It is
   keyed by the global journal's `max(seq)` and row count (one aggregate over
   the small `journal_sequence` table, 0.1 ms at 2K, 0.4 ms at 10K; the
   per-branch aggregate is a join over every event, 1–11 ms), with tentative
   rows for reads inside write transactions (a rolled-back row's sequence
   number is reused, which a `(max seq, count)` key cannot see).
4. **The prepared seal mirrors `snapshot.rs`'s payload** in `commit.rs`
   (`seal_payload`, `SEAL_FORMAT`): `snapshot.rs` is not owned. Byte
   equality is pinned by a unit test and by the differential fuzz.
   CCR-WP2.4-2.
5. **PASSIVE checkpoint in `prepare_slow`** (not in the spec): without it the
   commit under the lock ran SQLite's automatic checkpoint after the forced
   seal's ~3 MB of WAL (commit 21–25 ms typical, one 505 ms outlier); with
   it the commit's own `COMMIT` took 5–14 ms.
6. **Qualification scenarios.** WP2.3's activator is not in this tree, so a
   worker process still activates inline on the legacy lane. The floored
   `lock_hold_slow_event_2k` and `stale_convergence` drive the store API as
   the activator does (§4.4) around a `Mutex<Store>`, with a probe counted
   as a filesystem waiter (the activator yields to waiters, §4.2). The
   original worker-process versions are kept as `lock_hold_slow_event_2k_worker`
   and `stale_convergence_worker`; they skip until the worker activates in the
   background (its `status` carries `activation`). WP2.INT can move the floor
   to the worker variant once WP2.3 is merged.
7. **`stale_convergence` writer.** WP0.5's scenario raced a writer that
   commits every 50 ms for the whole run. Preparing is O(history) (about
   60 ms at 2K: the read handle loads the stored projection, ~30 ms, then
   projects, ~20 ms, derives, ~8 ms, serializes, ~6 ms), so such a writer
   makes every ticket `Stale`: with `Stale` never committed inline (§4.4,
   M5) the 200 chained slow events starve, which WP2.3 reports as
   `activation.starved_since_ms`. The scenario now writes in bursts (every
   100 ms for 0.5 s, then 1 s idle): 73 stale tickets, all 200 events
   converged in 35 s, oracle empty.
8. **CCR-WP1.6-1 partly applied.** Scaling the seal interval needs the
   suffix-replay bound in `snapshot.rs`'s `try_resume_snapshot` to follow it
   (otherwise every restart past 128 unsealed events rebuilds the branch);
   filed as CCR-WP2.4-3. The owned-side adapter removes the projection
   reload and parse from periodic seals.
9. **`tests/activation_inbox.rs`** (not owned): one assertion pinned the
   Wave 1 stub (`Prepared::Inline` from `prepare_slow`); it now asserts
   `Prepared::Computed` with a computation. CCR-WP2.4-1.

## CCRs filed

- **CCR-WP2.4-1 (`tests/activation_inbox.rs`, WP1.6; applied in this
  branch, for ratification).** `slow_events_yield_tickets_and_commit_prepared_commits_them`
  asserted `matches!(prepared, Prepared::Inline(_))`: the Wave 1 stub's
  output ("W1: Ok(Prepared::Inline(t.clone()))", §14 WP1.6), which WP2.4's
  "Provides" (`Prepared::Computed(Box<PreparedCommit>)`) replaces. Changed to
  `matches!(&prepared, Prepared::Computed(p) if p.is_computed())` (stronger:
  a computation was made off-lock); every other line of the test, including
  the commit outcomes it checks, is unchanged and passes. Without the change
  VERIFY cannot pass; no adapter is possible (the behaviour is the
  deliverable).
- **CCR-WP2.4-2 (`src/core/snapshot.rs`, WP0.3 / WP1.INT).** Expose a
  prepared seal, for example `pub(super) fn persist_parts(db, branch, cursor,
  journal_hash: &str, projection_json: &str)` (the body of `seal_payload`
  plus the insert and its fault points) and make `journal_hash` incremental
  (`fn journal_row(digest, seq, id, payload)`), so `commit.rs` stops mirroring
  the payload format. Adapter: `commit.rs::{seal_payload, seal_prepared,
  journal_row, SEAL_FORMAT}`, pinned by
  `commit::tests::seal_payload_is_snapshot_persist_byte_for_byte`.
- **CCR-WP2.4-3 (`src/core/snapshot.rs`; the rest of CCR-WP1.6-1).** A
  periodic seal of a fast commit still hashes the branch's whole journal and
  serializes the projection under the lock every 128 events (3 + 6.5 ms at
  2K, 19 + 18 ms at 5K, 40 + 33 ms at 10K, plus the ~3–14 MB write).
  Requested: (a) scale the interval with the branch (for example
  `max(128, events / 16)`) in `maybe_persist` **and** use the same bound for
  the suffix in `try_resume_snapshot` (today `tail.len() > INTERVAL` forces a
  full rebuild, so scaling only the seals would rebuild on every restart);
  (b) accept the journal hash state from the caller (the event cache keeps
  it), as for CCR-WP2.4-2. Crash tests to keep green:
  `startup_snapshots::{crashes_during_suffix_and_snapshot_replacement_keep_the_committed_view,
  periodic_seals_bound_replay_and_oversized_legacy_suffix_reconstructs}`,
  `offlock_commit::{periodic_seals_of_fast_commits_use_the_projection_they_hold,
  crashes_during_a_prepared_commit_keep_the_committed_state}`; add one that
  restarts after `interval - 1` unsealed fast commits and asserts the open
  resumes (no rebuild). Adapter: the known-projection seal above.
- **CCR-WP2.4-4 (WP2.3, information for the activator).** Keep the read
  handle across `prepare_slow` calls (its event cache then loads only new
  journal rows; a fresh `SyncStore` per call reloads the branch, 6 ms at 2K,
  49 ms at 10K). Treat `Stale` as "computed from an old state", not as a
  failure: re-queue with a short backoff (the qualification emulation uses
  10 ms doubling to 80 ms; WP0.5's 1 s → 5 min transient backoff starves a
  causal chain of slow events behind local writes). `prepare_slow` returns
  `Err` only when its read transaction fails (retry later; nothing changed).
  `commit_prepared` opens its own `BEGIN IMMEDIATE`; call it under the engine
  lock. `PreparedCommit::is_computed()` tells a computation from a ticket the
  read handle could not prepare (`commit_prepared` then returns `Stale` or
  applies the refusal).
- **CCR-WP2.4-5 (WP2.3 maintenance; optional).** SQLite's automatic WAL
  checkpoint runs inside whichever commit crosses 1,000 WAL pages, under the
  engine lock; the forced seals and periodic seals cross it often. A 505 ms
  checkpoint stall was observed inside one commit. `prepare_slow` now runs a
  PASSIVE checkpoint off-lock before the commit; maintenance (1 Hz) could do
  the same for the fast path.
