# WP3.4 — Desktop GUI and view model

Branch `revamp/wp3-4-desktop-gui`, cut from `revamp/wave-3-base`
(`686718f`).

## Summary

WP3.4 replaces the desktop's list-and-poll window with the UI of §7.4,
driven by one status subscription, with commands that never wait behind it.
This is the owner's pain point P4: every sync state is now legible at a
glance, per folder and per peer. Only the owned files changed.

| File | Content |
|---|---|
| `src/ui_model.rs` | the view model (`tkfs::ui_model`): pure, cross-platform row, detail, header and activity models built from a `StatusSnapshot`; the two background loops (`Feed`, `CommandPool`) behind transport traits; the CCR-WP2.1-7 display adapter (`MountSmoother`); `RateMeter`, `Busy`, `route_action` |
| `src/gui.rs` | Slint glue only: transports over `ControlClient`, the daemon spawner, model → Slint mapping, callbacks, the render-to-file mode |
| `ui/app.slint` | the UI of §7.4 in the visual language of `misc/prototype.html` (dark palette) |
| `tests/gui_model.rs` | 33 tests (below), including the four tests that lived in `src/gui.rs` |

### What the window shows (§7.4)

- **Header:** the daemon (version, uptime, installation, listening address)
  in the host card, a **Log** button, and the **global errors banner** (open
  daemon-level errors, and those of peers the snapshot does not list). A
  connection banner says when the daemon does not answer (attempt, error,
  next retry, how old the shown status is), when it is being started (and
  where its output goes), or that it was shut down (with **Start the
  daemon**).
- **Overview cards:** folders in sync (and how many syncing or needing
  attention), mounted (and unresolved conflicts), peers online (and
  inbound-only), transfer rates.
- **Folder row:** label and mount path; the **sync status** with its numbers;
  a progress bar while transferring; a detail line (peers in sync, files not
  downloaded, changes not yet backed up, conflicts); the **mount status**; the
  **worker status**; the row's main action and Details; and the newest open
  error with its class, time, count, next retry and suggested action. Each
  status that has a remedy carries its button (`Mount failed [Retry]`,
  `Waiting for initial sync [Mount now]`, `Crash loop [Retry]`,
  `Stopping — 3 files open [Force stop]`, `Blocked — … [Revalidate]`,
  `Paused [Resume]`). A remedy another button of the row already offers is
  shown once.
- **Sync status texts** (from the structured per-peer progress, not the
  hub's summary line, so each state shows its own numbers):

  | `FolderSyncState` | Text |
  |---|---|
  | `UpToDate` | `Up to date` (`Up to date · 1 of 2 peers unreachable`) |
  | `Metadata` | `Syncing metadata · 1,588 of 2,000 · 412 left` |
  | `Downloading` | `Downloading 1.2 GiB of 3.0 GiB · 3.4 MiB/s · ETA 10 min` (done of total), or `Downloading 120 files` |
  | `Uploading` | `Uploading 120 files`, or bytes, rate and ETA |
  | `Syncing` | `Syncing · ↓ … · ↑ … · 3 events` |
  | `InitialSync` | `Initial sync from office-nas · 1,588 of 2,000 events` |
  | `Stalled` | `Stalled 4 min — CORRUPT_OBJECT 1a2b3c4d5e6f` (since the last progress, and the culprit) |
  | `Blocked` | `Blocked — 3 events quarantined` (or the blocking error's code) |
  | `Backoff` | `Retrying in 12 s — CONNECTION_LOST` |
  | `Offline` | `Waiting for laptop (offline 5 min)`; several peers: `Waiting for 2 peers (needs upgrade, offline)` |
  | `Paused` | `Paused` |
  | `NotShared` | `Not shared with any peer` |
  | `NeedsAttention` | `Needs attention: crash loop` / `mount failed — MOUNT_PATH_MUST_NOT_EXIST` / `initial sync blocked — …` / the severe error's code |
  | `Stopped` | `Stopped`, or `Not syncing — worker restarting in 32 s` |

- **Folder dialog** (tabs): **Overview** (lifecycle with pid, restarts and
  last exit; mount with its error and attempt; the gate with its
  `waiting_on` list; store health; open files, pending saves, unflushed
  files; the three separate claims of invariant 30: metadata caught up,
  content complete, backed up by a peer; journal; intents; identity),
  **Sync** (per sharing peer: direction, state, n of m, to send/receive,
  local/remote pending, blocked/quarantined/rejected, ↓/↑ bytes, rate, ETA,
  last progress and exchange, error with class, time, next retry and
  suggestion), **Activation** (backlog by kind, quarantined, blocked,
  activator counters, rate, last slice, starvation, **Revalidate
  quarantined**), **Content** (counters, and the missing files from the
  worker's `status`), **Conflicts** (the existing review/resolve/recover UI),
  **Errors** (open first, then history: first/last time, count, class,
  resolved), **Activity** (the folder's entries). The action bar lists every
  action that applies: Start, Stop, Force stop, Mount now, Attach, Detach,
  Pause/Resume sync, Retry, Revalidate, Change path.
- **Peer sidebar and dialog:** state badge (`Online`, `Connecting…`,
  `Offline 5 min`, `Backoff (retry in 12 s)`, `Peer needs upgrade`,
  `Unauthorized — re-pair`, `Revoked`), inbound-only peers marked; the dialog
  adds direction, protocol, RTT, ↑/↓ rates, lanes (role, state, in-flight op
  with repo, age and bytes, since, bytes, rates, reconnects, error), shared
  folders, the peer's error, and Browse folders / Pair again / Disconnect.
- **Activity view:** the activity ring, newest first.

### Never frozen by a slow daemon

The UI thread does no I/O. `ui_model::Feed` runs one subscription thread
(`subscribe(since, 10 s)`, 15 s deadline) that hands newer snapshots to the
UI through `upgrade_in_event_loop`; after a failure it reconnects with
backoff (250 ms → 5 s) and asks for `since = 0` (a restarted daemon has
fresh generations; a timed-out long poll that echoes the same generation is
not re-delivered). When no daemon answers it starts one (`tkfs -f CONFIG
orchestrator`, output appended to `DATA/logs/orchestrator.log`, at most once
per 15 s). It never restarts a daemon that was shut down on purpose: after a
Shutdown from the window, or when the daemon's last word was that it is
stopping (a `stopping` snapshot or `ORCHESTRATOR_STOPPING`, e.g. `tkfs manage
shutdown`); the banner then offers **Start the daemon**.
`ui_model::CommandPool` runs commands on four threads, each with its own
`ControlClient`, so a command never waits behind the subscription, and a
15 s Stop never delays another row. `Busy` allows one command per row (per
folder; dialog commands share a `global` key; detail loads use
`detail:<state>`) and the row shows its spinner and caption. A 1 s timer
re-renders relative times between snapshots. Models are updated in place
(rows that did not change are not touched), so scroll positions survive a
refresh. Errors come only from the snapshot rendered: one absent from a
snapshot is gone from the window.

### Smaller things

- Paths drop the `\\?\` verbatim prefix the daemon reports
  (`ui_model::display_path`).
- Clock times are local (`GetTimeZoneInformation`), relative times use the
  local clock, never earlier than the snapshot.
- **Force stop asks for confirmation** (`route_action`: the confirmation
  sends `confirmed-force-stop`).
- A desktop started without a terminal (Explorer, a shortcut) releases the
  console window the console-subsystem `tkfs.exe` gets (`FreeConsole` when
  it is the only process attached); one started from a terminal keeps it.
- Invariant 21: the snapshot never carries a pairing code; the window shows
  one only from the `ResetPairingCode` reply, in Settings, and clears it when
  the dialog closes.
- **Render-to-file** (`TKFS_GUI_RENDER=<out.bmp>`, optional
  `TKFS_GUI_RENDER_SNAPSHOT=<status.json>`, `TKFS_GUI_RENDER_VIEW=folders |
  activity | folder:<state>[:<tab>] | peer:<installation>`,
  `TKFS_GUI_RENDER_SIZE=WxH`): renders one frame with the software renderer
  and no window, from a saved snapshot or the running daemon's `Status`, at
  the snapshot's own time. It produced the screenshots below and is meant
  for WP4.3's manual checklist.

## CCR-WP2.1-7 (hub mount from a stale heartbeat), applied as a display adapter

WP2.INT deferred it here. The real fix needs the mount generation the
FolderView was built from (`model::orchestrator::FolderView`, frozen) and a
change in `src/orchestrator/hub.rs` (not owned by WP3.4), so it is filed
again as **CCR-WP3.4-1** and adapted on the display side, in two parts:

1. `mount_chip`: a mount the controller still wants (`intent: attach`) that
   shows `preflight`/`attaching`/`detached` while its last failure is still
   open in the Mount scope is shown as `Mount failed · retrying [Retry]`
   (it is: the controller is retrying a failed mount).
2. `MountSmoother` (the glue applies it to every snapshot before rendering):
   keeps a settled mount state (`Attached`, `AttachFailed`, `Lost`) on screen
   while a regression to a transitional or detached state is younger than
   1.5 s (one heartbeat and a half), within the same worker instance, while
   the folder is Running with the mount still wanted (mount enabled, the same
   path, no user Detach). A regression that lasts is real and shown; a local
   command on the folder releases the hold at once. This removes the
   `Mounted → Mounting… → Mounted` flicker after every successful attach, and
   the `Mount failed → Not mounted → Mount failed` one after a failure.

## CCRs filed

- **CCR-WP3.4-1 (`model::orchestrator::FolderView`, `src/orchestrator/hub.rs`;
  WP3.INT).** Requested: the hub prefers the controller's mount over a
  heartbeat older than the attach/detach result, e.g. `FolderView` carries
  the worker's mount generation (`WorkerHeartbeat.generations.mount`) its
  mount state was built from, and `on_heartbeat(take_mount: true)` takes the
  heartbeat's mount only when `hb.generations.mount` is newer. Reason:
  CCR-WP2.1-7 (the snapshot's `mount` can be one heartbeat stale; display
  only). Adapter: the two-part display adapter above; it can stay after the
  fix (it then never triggers).
- **CCR-WP3.4-2 (information for WP4.2, `ctx.rs`).** `DaemonStatus.log_path`
  is always `None` today (`ctx.rs` sets `DaemonEndpoints.log_path: None`).
  The desktop starts a missing daemon with its stdout and stderr appended to
  `DATA/logs/orchestrator.log`; WP4.2's logging should either write there or
  report its file in `log_path`. Adapter: the Log button opens `log_path`
  when set, else `DATA/logs/orchestrator.log` (and says so when that file
  does not exist).
- **CCR-WP3.4-3 (information, `src/main.rs`).** `tkfs.exe` is a console
  program, so the desktop started from Explorer opens a console window.
  Adapter: `gui::run` releases a console only this process is attached to.
  No change requested (a `windows_subsystem = "windows"` binary would lose
  the CLI's console output).
- **CCR-WP3.4-4 (information for WP3.1/WP3.INT).** On the Wave 2 legacy
  lanes the hub reports `metadata.cursor_seq = remote_tip = 0`, so the "n of
  m" part of `Syncing metadata · 1,588 of 2,000 · 412 left` appears only once
  the v3 feed counters fill them (WP3.1); until then the text is
  `Syncing metadata · 412 left`. No change requested.

## Deviations from the spec, and why

1. **The four `src/gui.rs` unit tests** tested JSON helpers of the old
   window (`sync_label`, `folder_summary`, `folder_rows`, `peer_rows` over the
   legacy List/Peers JSON) that no longer exist. Each is rewritten against
   the new model under its old name, keeping its intent:

   | Old test | New test (same name) |
   |---|---|
   | `connected_peer_does_not_hide_an_unavailable_folder_or_stale_sync` | a connected peer whose folder is not serving shows `Waiting for office (its folder is not serving)`, never in sync; a stall is shown as a stall; caught-up metadata with objects left is a download |
   | `summary_distinguishes_current_content_from_history_and_pending_metadata` | the Content tab distinguishes current files (`100 of 108 files available`) from shared history (`108 of 291 objects available`); the Activation backlog shows the 673 pending events; the Overview's backup claim the 4 unacknowledged changes |
   | `folder_snapshot_preserves_headless_and_failure_states` | rows keep headless (`Headless`, no path) and failed (`Mount failed`, its error line) folders; mounted count 1; the search filter by label and path, case-insensitive |
   | `peer_is_online_when_any_lane_is_connected` | the hub decides the badge from the lanes (`hub_rules::peer_conn_state`, tested in `status_hub`); the window shows it, counts online peers from it and summarizes lanes (`1 of 2 lanes ready`) |

   The binary's unit test count goes from 4 to 0; `tests/gui_model.rs` adds
   33.
2. **The background loops live in `ui_model`**, not in `gui.rs`: the
   acceptance test (command latency < 200 ms while a slow subscribe is in
   flight, with a fake client) and the reconnect/respawn rules then run on
   every platform. `gui.rs` only provides the `ControlClient` transports and
   the spawner.
3. **Units:** `format_bytes` is `hub_rules::format_bytes` (binary units,
   §0), so §7.4's `3.4 MB/s` reads `3.4 MiB/s`; `Downloading 1.2 GiB of
   3.0 GiB` is read as done of total (the progress bar's fraction).
4. **Daemon respawn** (task 1) is not done for a daemon that was shut down on
   purpose (see above): an open window would otherwise undo `tkfs manage
   shutdown` (for example before an upgrade).
5. **Additions not in §7.4:** the Conflicts tab (the existing conflict review
   UI, kept), the Activity view, the overview cards, Force stop's
   confirmation, the console release, the render-to-file mode.
6. **Peer sidebar** is a list with badges plus a peer dialog for the lanes
   (the lanes table needs more room than a sidebar).
7. **Slint:** a function named `close` on the `Window` crashes the Slint
   1.17 compiler (it resolves to a builtin; internal error in
   `access_item_rc`); the dialog closer is `dismiss()`.

## Verification on Windows (beyond the tests)

Two throwaway daemons with their own configs and data under the session's
scratch directory (`listen 127.0.0.1:0`; never the user's data directory):
A created `Photos` (headless) and `Design assets` (mounted under scratch)
with six files; B paired with A and received both. Then:

- `TKFS_GUI_RENDER` against B's live `Status`: folders view, folder dialog
  (Overview, Sync), peer dialog, activity view: all rendered with the live
  data (`Up to date`, `Mounted`/`Headless`, the peer online with 3 of 3
  lanes, the activity ring).
- The same against a crafted snapshot derived from B's real JSON (nine
  folders in every row state, four peers including a needs-upgrade and an
  inbound-only one, a daemon error): every state rendered as in the tables
  above.
- The real window (`tkfs -f B gui`): opened, showed B's folders and peer,
  kept updating (uptime), no console window when started without a
  terminal; captured with `PrintWindow` (that window only).
- Respawn: `tkfs -f C gui` with no daemon for C started one (its output in
  `C/data/logs/orchestrator.log`); after `tkfs -f C manage shutdown` the
  window showed `The daemon is shut down … [Start the daemon]` and did not
  restart it (checked 22 s later).
- All test daemons and windows were shut down or closed afterwards (only
  processes started by this package, by recorded pid).

## Manual checklist (for WP4.3)

1. Start `tkfs gui` with no daemon running: the banner says it is starting
   the daemon and names `DATA/logs/orchestrator.log`; the folders appear.
2. Create a folder (New folder): the row shows `Starting…` (busy), then
   `Running`, `Mounted`, `Not shared with any peer`.
3. Pair with a second host (Pair with a host, its code from its Settings),
   browse and receive a folder: the received row shows `Initial sync from
   <host>` and `Waiting for initial sync [Mount now]`, then `Up to date` and
   `Mounted`.
4. Copy a large file into one side: the other side's row shows
   `Downloading x of y · rate · ETA` with a progress bar, then `Up to date`.
5. Stop the other host's daemon: the row shows `Waiting for <host> (offline
   N min)`; the sidebar badge `Offline N min`.
6. Create a folder whose mount path already exists: `Mount failed [Retry]`
   with `[needs action] MOUNT_PATH_MUST_NOT_EXIST` and its suggestion.
7. Open a file in a mounted folder and Stop it: `Stopping — 1 file open
   [Force stop]`; Force stop asks for confirmation.
8. Pause sync: `Paused [Resume]`.
9. Generate a new pairing code in Settings: it is shown once and cleared
   when Settings closes; the other host's badge becomes `Unauthorized —
   re-pair`.
10. Pair with a 6298d0b host: its badge reads `Peer needs upgrade`.
11. Shut the daemon down from Settings: the banner offers `Start the
    daemon`; nothing restarts it until clicked. `tkfs manage shutdown` from
    a terminal has the same effect on an open window.
12. While a Stop is in flight (a folder with open files), Start another
    folder: it starts at once.
13. Screenshots for the documentation: `TKFS_GUI_RENDER=out.bmp
    TKFS_GUI_RENDER_VIEW=folder:<state>:sync tkfs gui`.

## Known limitations

- Clicking through the window was not automated (no UI automation in this
  environment): the actions are covered by `route_action`, the command
  pool tests and the server-side tests of the actions (`management_api`);
  the live checks above covered start-up, rendering, updating, respawn and
  the shutdown banner.
- The `Log` button opens the GUI-started daemon's output file until WP4.2
  reports `log_path` (CCR-WP3.4-2).
- The missing-files list is the worker `status` reply's (its first
  `CONTENT_ITEMS` entries), read when the Content tab opens or on Refresh.
- The local time zone offset is read once at start (a DST change during a
  session shifts clock times by an hour until the window is reopened).
- A long poll in flight when the window closes ends with the process.
- No Linux desktop (scope cut, §12); `tests/gui_model.rs` runs in WSL.
