## Summary of changes

### `src/worker/mount_ctl.rs`: the MountController (§4.3)

- **Same constructor and trait** as the WP0.INT stub:
  `MountController::new(engine: Shared, previous: Option<WorkerRecord>) -> Arc<Self>`,
  `impl MountControl` (`attach`, `detach`, `status`). Additive methods:
  `previous()`, `set_instance(&str)`, `instance()`, `generation()` (the status
  snapshot generation, bumped on every state change), `inflight()`,
  `mount_errors()`.
- **State machine:** `Detached` → `Preflight` → `Attaching` → `Attached{since_ms}`
  or `AttachFailed{error, attempt, next_retry_at_ms}`; `Attached` → `Detaching` →
  `Detached`; `Attached`/`Attaching` → `Lost{error}` when the adapter reports
  that the mount went away (FUSE dispatch death, failed checkout remount). A
  refused graceful detach restores the previous state (still `Attached`).
  `intent` is `Attach` after an attach request and `Detach` after a detach.
- **Mailbox (§2.5 `mount-ctl` thread):** attach and detach are enqueued to one
  thread per controller and run one at a time; the caller blocks on its own
  reply channel. This replaces the stub's mutex held across mount I/O (WP0.INT
  review finding 5). Each transition runs under `catch_unwind`; a panic
  publishes `Lost` (adapter still attached) or `Detached`. The thread exits
  when the controller is dropped.
- **`status()`** loads a `Snapshot<MountStatus>`: no engine lock, never waits
  for a transition (pinned by `status_never_waits_for_a_transition`).
- **Preflight:** `bind(engine)` first (before any path check), then the path
  is resolved without creating anything (absolute, nearest existing ancestor
  canonicalized), `MOUNT_OVERLAPS_STATE` is checked against the canonical store
  root (mount inside the state or state inside the mount), the parent
  directory is created (as `worker::run` does today), Linux recovers a stale
  mount proven ours (below), and the path must be vacant. Classification:
  `MOUNT_PATH_MUST_NOT_EXIST`, `MOUNT_OVERLAPS_*`, `WINFSP_RUNTIME_UNAVAILABLE`
  are NeedsUserAction (`next_retry_at_ms: None`); every other attach failure
  is Transient with `next_retry_at_ms = now + Backoff::mount_retry().nominal(attempt)`
  (advice for the FolderController, which owns retries per §3.3; the worker
  never retries by itself). `attempt` counts consecutive failures and resets
  on success.
- **FUSE recovery (invariant 27):** only when `previous` is ours (same repo
  and device as this store, a valid instance different from this process's),
  `fuse_linux::recover_managed(path, previous.instance)` runs. It touches
  nothing when no mount is at the path, refuses (NeedsUserAction, untouched)
  an unrelated or still-responding mount, and otherwise unmounts the stale
  `fuse.tkfs` mount whose source is `tkfs-<previous.instance>` and removes its
  then-empty mount point.
- **Instance naming (FUSE source `tkfs-<instance>`):** `set_instance` if
  called; otherwise the `instance` of this process's `STATE/worker.json`
  (written before the mount by §4.1 step 7; matched on `pid`); otherwise a
  generated uuid (such a mount is never provably ours later, so a crash
  leaves a NeedsUserAction path instead of a wrong unmount).
- **Reconciliation:** a controller never adopts or detaches a mount that
  serves another engine (`mount::serves`). On attach it adopts a mount of its
  own engine started around it (legacy `mount::start`), and it does not trust
  its own `Attached` once the adapter was stopped around it (legacy
  `mount::stop`). Detaching with nothing native attached is a no-op that never
  fences the engine.

### Adapter support (`worker::mount_ctl::adapter`, used by both adapters)

- `callback()` guard: the in-flight callback counter (`mount::inflight()`).
- `drain(timeout)`: condvar wait until no callback runs.
- `fence(engine, force)`: sets `Engine.switching`. A graceful detach first waits
  up to `QUIET_WAIT` (1 s) for quiet: no dirty session and no handle the
  application still holds; otherwise `BUSY_VIEW`, unfenced.
- `persist_dirty`: `retain_all_dirty()` (force, step 3).
- `release`: after the native stop, retains dirty sessions again (a write may
  have raced the drain), drops every handle, **keeps dirty sessions** with no
  references (the 250 ms pending-save retry commits them; a re-attach opening
  the file sees their bytes at once), drops clean sessions, clears queued
  notifications, then `mounted = false` and the fence is lifted.
- `fs_error(op, error, counted)`: the mount-scoped error counter
  (`mount_errors()`) plus a JSON event through `util::log` (rate limited per
  code). Counted: close-path failures and unexpected I/O errors, except
  contention (`BUSY_VIEW` while fenced). Expected answers (not found,
  collision, …) are `debug` events (dropped at the default level).
- `report_lost(error)`: an `error` event plus the `Lost` signal to the
  controller that attached last (a hook holding a `Weak`).

### `src/mount.rs` (WinFsp)

- `bind(engine)`: idempotent for the same `Arc` (`Arc::ptr_eq`), independent of
  any path check (fixes `mount.rs:72`: the `ENGINE` `OnceLock` was set before
  the path check, so one failed attach poisoned the process). The binding is an
  `RwLock<Option<Shared>>`; see deviation 1.
- `attach(path)`: WinFsp runtime check, vacancy check, then `tk_mount_start`
  (a fresh native instance per attach); `mounted = true`.
- `detach(force)`: fence → drain (≤ `DETACH_DRAIN` = 10 s; a graceful detach
  that does not drain is `BUSY_VIEW`) → [force: `retain_all_dirty`] →
  `tk_mount_stop` (no engine lock held) → release → unfence. **The permanent
  fence is gone** (`mount.rs:98-108` left `switching = true` until process exit).
- `tk_call` counts itself in flight, takes the engine through `lock_engine`
  (so WP1.4's poison policy applies), and the close-path `e.health` write
  (`mount.rs:339-347`) became `fs_error` (counter + bounded log). The
  per-failure `eprintln!` became the same bounded event. NTSTATUS mapping
  unchanged (moved into `nt_status`).
- `checkout(engine, request, payload)`: signature unchanged; drains before
  stopping; a remount failure no longer writes `e.health = "REMOUNT_FAILED…"`:
  the adapter forgets the instance, releases the engine (`mounted = false`,
  unfenced) and reports `Lost{REMOUNT_FAILED}`.
- `notify` uses `try_lock`: during a transition it answers `BUSY_VIEW` and
  `deliver_notifications` keeps the notification for its next delivery,
  instead of blocking behind a detach's quiet wait and drain.
- Also: `attached()`, `serves(engine)`, `vacant(path)`, `inflight()`,
  `mount_errors()`; legacy wrappers `start(engine, path)` = bind + attach and
  `stop(engine)` = `quiet()` + graceful detach (the `stop` op path).

### `src/fuse_linux.rs` (FUSE)

- Same names: `bind`, `attach(path)` (source `tkfs`), `attach_managed(path,
  instance)` and `start_managed(engine, path, instance)` (source
  `tkfs-<instance>`), `detach`, `inflight`, `attached`, `serves`, `vacant`
  (also refuses a live or stale mount at the path, which `stat` cannot see),
  `checkout`, `recover_managed`, `start`, `stop`.
- The dispatch thread (`fuse-dispatch`) polls `/dev/fuse` (non-blocking) and a
  wake socket, so a detach can stop it. Dispatch death (`serve` returning an
  error) sets `mounted = false` and reports `Lost{FUSE_DISPATCH_FAILED}`
  instead of `e.health`.
- Graceful detach: fence → drain → `fusermount3 -u` (a refusal is `BUSY_VIEW`,
  unfenced, still attached) → stop and join the dispatch thread → remove our
  mount point (`remove_dir`, never content) → release.
- Force detach: as above with `retain_all_dirty`; when the kernel still has
  files open, `fusermount3 -u -z`, then stopping the dispatch thread closes the
  device and aborts the connection (open files fail instead of hanging). A
  mount whose dispatch thread died is always detached this way.
- Callbacks (inline and the content threads) are counted in flight and use
  `lock_engine`; failures go to `fs_error`.
- `checkout`: drains, unmounts gracefully (refusal → `BUSY_VIEW`, unfenced),
  stops the dispatch thread, runs the control op, relaunches; a relaunch
  failure reports `Lost{REMOUNT_FAILED}` (no `e.health`).

### Fault points (qualification hooks, `util::fault`)

`fs.close` (after a close callback closed its handle; WinFsp op 10, FUSE
RELEASE/RELEASEDIR), `fs.remount` (checkout remount, both adapters),
`fs.dispatch` (FUSE dispatch loop).

## Deviations from the spec

1. **`bind` replaces the engine while nothing is attached.** §4.3 says `bind`
   "runs once (idempotent for the same `Arc`)". It is idempotent for the same
   `Arc`, and a different engine is refused (`ONE_MOUNT_PER_RUNTIME`) while a
   mount is attached, but with nothing attached it rebinds. A worker has one
   engine, so production behaves exactly as "once"; the relaxation lets one
   test process mount several engines in turn (in-process tests).
2. **Graceful quiet ignores cleaned-up handles and waits up to 1 s.** §4.3:
   "Graceful detach requires quiet (no handles, no dirty sessions)". The
   kernel reports a close asynchronously: WinFsp's `Close` arrives after
   `CloseHandle` returned (its `Cleanup` already flushed and set
   `Handle.cleaned`), and FUSE's `RELEASE` after `close(2)`. An immediate check
   refused a detach right after the application closed its last file (seen in
   the first test run). A cleaned handle accepts no writes and holds no unsaved
   bytes, so it does not count as open; the 1 s wait covers FUSE `RELEASE` and
   scanners. Dirty sessions always refuse.
3. **Force detach keeps dirty sessions in memory.** §4.3 step 5 says "drop
   orphaned handles and sessions (dirty ones are already in `pending_saves`)".
   Dropping them would leave the bytes in `pending_saves` but invisible until a
   restart (`load_pending` runs only in `Engine::new`). As the task requires
   ("sessions must be kept or reloaded"), handles are dropped, clean sessions
   are dropped, and dirty sessions are kept with no references, which is
   exactly the state `load_pending` recovers to; the pending-save retry
   commits them. They are also retained a second time after the native stop.
4. **FUSE force detach unmounts lazily.** The plan specifies the order but
   not how a force detach gets past the kernel's `EBUSY` for open files:
   `fusermount3 -u -z`, then the dispatch thread is stopped (new poll/wake
   loop) so the connection aborts.
5. **`recover_managed` semantics.** It was never called before (RC: "the FUSE
   managed start/recover functions are never called"). It no longer removes an
   empty directory unless it just unmounted a stale mount of ours there, and
   its refusals are `MOUNT_PATH_MUST_NOT_EXIST` (NeedsUserAction) instead of
   `WORKER_START` (Transient).
6. **Instance source for FUSE names** (see above): `MountController::new` has
   no instance argument, so the controller reads it from this process's
   `worker.json` (or `set_instance`).
7. **`mount_errors` counts more than the close path**: also unexpected I/O
   errors (EIO / `STATUS_IO_DEVICE_ERROR`), never contention. The spec names
   only the close path; the counter is mount-scoped either way.
8. **Notifications** queued in `Engine.notifications` are cleared on attach and
   detach (a fresh native instance has no cached names), and `mount::notify`
   no longer blocks during a transition.

## Known limitations

- **WinFsp file contexts of handles still open at a force detach leak** (one
  small `TK_HANDLE` allocation each): WinFsp sends no `Close` after the file
  system is deleted. The Rust side drops the handles.
- **FUSE force detach with open files** leaves a lazily detached mount that the
  kernel tears down when the last file closes; I/O on those files fails
  (`ENOTCONN`).
- **After a force detach with dirty sessions, `Engine.health` reads
  `PENDING_SAVE: DIRTY_SESSION_RETAINED`** until the pending-save retry commits
  them (WP0.2 `retain_pending` behavior in `engine.rs`, owned by WP1.4).
  `quiet()` and the legacy `stop` refuse meanwhile; in a worker the retry runs
  every 250 ms. This is a store state, not a mount error.
- **`status()` can be stale** while the adapter is driven around the
  controller (the legacy wrappers); the next attach or detach reconciles it.
  After WP1.INT only `checkout` bypasses the controller, and it reports `Lost`.
- `MountState::Disabled` is never produced (every built platform has an
  adapter).
- `Engine.notifications` still grows without bound while a worker is detached
  or headless (`receive_peer` queues them; `deliver_notifications` skips
  delivery when not mounted). The controller clears the queue on attach and
  detach; the bounded notifier is WP2.3 task 7 (`runtime/notify.rs`).
- **Observed, not mine:** `orchestrator::unavailable_worker_does_not_fail_remote_discovery_and_reports_its_error`
  failed once in a parallel run and passed in five reruns (alone and in its
  binary). It uses headless folders only. `peering::published` replaces
  `publication_errors` wholesale, so a concurrent `published()` that read the
  discovery before the test rewrote `runtime.json` can clear the recorded
  error before `Inspect` reads it. Legacy orchestrator code (deleted in WP3.1).
