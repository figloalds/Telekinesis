**Finding 1 (blocker), in detail.**

- `serve` now says why it stopped: `Exit::Woken` (the wake end, i.e. a
  detach or checkout) or `Exit::DeviceGone` (`ENODEV` or end of file: the
  connection ended because the mount was unmounted).
- Every launch has a `stopping` flag. A detach or checkout sets it before it
  unmounts, and `stop_dispatch` sets it before it wakes the thread. A refused
  unmount clears it again.
- When the dispatch thread exits with `stopping` unset:
  - an error exit gives `Lost{FUSE_DISPATCH_FAILED}`, as before;
  - `DeviceGone` gives `Lost{MOUNT_NOT_RUNNING: the FUSE mount at … was unmounted outside the worker}`.
  - Both run `adapter::lost` first: dirty sessions go to `pending_saves`, then
    `mounted = false`.
- `fuse_linux::detach` checks `Mount::present()`: is a `fuse.tkfs` mount with
  our source still at the canonical path in `/proc/self/mountinfo`? An
  unreadable table counts as present.
  - A mount that is no longer present is handled like a force detach. Nothing
    is unmounted (`fusermount3` exits 1 on a path that is not mounted). The
    thread is joined, our empty mount point is removed (`remove_dir` never
    removes content or a mount point), and the engine is released.
  - A refused graceful unmount is returned as `BUSY_VIEW` only while the
    dispatch thread still serves.
  - A failed lazy unmount is accepted only if the mount has disappeared in the
    meantime.
- `checkout` on a mount that is no longer present runs the checkout on the
  engine, does not remount (the path is no longer proven ours), forgets the
  instance and reports `Lost{MOUNT_NOT_RUNNING}`.
- The lazy case. After `fusermount3 -u -z` or `umount -l` with files still
  open, the kernel keeps the connection, so the dispatch thread notices
  nothing until the last file closes.
  - New adapter probe `mount::vanished()`. On FUSE it tries the transition
    lock and asks whether our mount has left the mount table. It never waits,
    and it answers `false` while a transition runs. WinFsp always answers
    `false`.
  - The controller's `attach` checks it first. A vanished mount becomes
    `Lost{MOUNT_NOT_RUNNING}`, is cleaned up with `detach(true)` (which aborts
    the lingering connection) and is attached afresh. It is never answered
    with the old `Attached`.
  - Test: `lazy_external_unmount_with_an_open_file_is_not_reported_attached`.
- With these changes the reviewer's probe sequence ends as follows. External
  unmount → `Lost` and `mounted = false` within milliseconds. `detach` →
  `Detached`. `attach` to the same path → a real mount (the
  "Lost with a native instance → detach(true)" path). Attach elsewhere works
  after that.
- Mutation checks:
  - with the `DeviceGone` report disabled, `external_unmount_is_lost_and_recovers`
    fails at its `Lost` wait;
  - with `vanished()` ignored, the lazy test fails.

**Finding 3, in detail.**

- When `Inner::lost` sees `Detaching`, it records the error in
  `lost_while_detaching`. It does this inside the status snapshot's `update`,
  so under its write lock.
- The refused-detach branch chooses its state inside `status.update` too: the
  recorded `Lost` if there is one, the previous state otherwise.
- So either the signal is seen by the detach, or it arrives after the detach
  restored `Attached` and then changes that to `Lost`.
- Mutation check: with recording disabled, the new test fails.

**Finding 5, in detail.**

- `attach` waits at most `ATTACH_WAIT` = 50 s and `detach` at most
  `DETACH_WAIT` = 14 s. Both include queue time and stay below the
  orchestrator's `deadlines::MOUNT_ATTACH` (60 s) and `MOUNT_DETACH` (15 s).
  The detach bound covers the quiet wait (1 s), the drain (10 s) and the
  native stop.
- On timeout the caller gets `WORKER_BUSY` (Contention, `retry_after_ms` 1000)
  with the current state in the message. The transition goes on, and
  `status()` shows its progress.
- `set_reply_wait(Option<Duration>)` is an additive method that overrides the
  bound (used by the test).

## Summary of changes

### `src/worker/mount_ctl.rs`: the MountController (§4.3)

- **Same constructor and trait** as the WP0.INT stub:
  `MountController::new(engine: Shared, previous: Option<WorkerRecord>) -> Arc<Self>`,
  `impl MountControl` (`attach`, `detach`, `status`).
  - Additive methods: `previous()`, `set_instance(&str)`, `instance()`,
    `inflight()`, `mount_errors()`, `set_reply_wait(..)` (fix round 1), and
    `generation()`.
  - `generation()` is the status snapshot generation, bumped on every state
    change.
  - Additive constants: `ATTACH_WAIT`, `DETACH_WAIT`.
- **State machine:**
  - Attach: `Detached` → `Preflight` → `Attaching` → `Attached{since_ms}` or
    `AttachFailed{error, attempt, next_retry_at_ms}`.
  - Detach: `Attached` → `Detaching` → `Detached`.
  - `Attached`/`Attaching` → `Lost{error}` when the adapter reports that the
    mount went away: FUSE dispatch death (error, or external unmount), or a
    failed checkout remount.
  - A refused graceful detach restores the previous state (still `Attached`),
    unless the mount was lost in the meantime (`Lost`).
  - `intent` is `Attach` after an attach request and `Detach` after a detach.
- **Mailbox (§2.5 `mount-ctl` thread):**
  - Attach and detach go to one thread per controller and run one at a time.
    The caller waits on its own reply channel, bounded by
    `ATTACH_WAIT`/`DETACH_WAIT`, then gets `WORKER_BUSY`.
  - This replaces the stub's mutex held across mount I/O (WP0.INT review
    finding 5).
  - Each transition runs under `catch_unwind`. A panic publishes `Lost` if the
    adapter is still attached, `Detached` otherwise.
  - The thread exits when the controller is dropped.
- **`status()`** loads a `Snapshot<MountStatus>`. It takes no engine lock and
  never waits for a transition (pinned by `status_never_waits_for_a_transition`).
- **Preflight**, in this order:
  1. `bind(engine)`, before any path check.
  2. The path is resolved without creating anything: made absolute, nearest
     existing ancestor canonicalized.
  3. `MOUNT_OVERLAPS_STATE` is checked against the canonical store root, both
     ways (mount inside the state, or state inside the mount).
  4. The parent directory is created (as `worker::run` does today).
  5. Linux recovers a stale mount proven ours (below).
  6. The path must be vacant.
- **Classification:**
  - NeedsUserAction, with `next_retry_at_ms: None`: `MOUNT_PATH_MUST_NOT_EXIST`,
    `MOUNT_OVERLAPS_*`, `WINFSP_RUNTIME_UNAVAILABLE`.
  - Every other attach failure is Transient, with
    `next_retry_at_ms = now + Backoff::mount_retry().nominal(attempt)`. This is
    advice for the FolderController, which owns retries (§3.3); the worker
    never retries by itself.
  - `attempt` counts consecutive failures and resets on success.
- **FUSE recovery (invariant 27):**
  - Runs only when `previous` is ours: same repo and device as this store, and
    a valid instance that is not this process's. Then
    `fuse_linux::recover_managed(path, previous.instance)` runs.
  - It touches nothing when no mount is at the path.
  - It refuses an unrelated or still-responding mount (NeedsUserAction) and
    leaves it untouched.
  - Otherwise it unmounts the stale `fuse.tkfs` mount whose source is
    `tkfs-<previous.instance>`, then removes its now-empty mount point.
- **Instance naming (FUSE source `tkfs-<instance>`)**, first match wins:
  1. the instance given to `set_instance`;
  2. the `instance` in this process's `STATE/worker.json` (written before the
     mount by §4.1 step 7; matched on `pid`);
  3. a generated uuid. Such a mount is never provably ours later, so after a
     crash the path needs user action rather than risking a wrong unmount.
- **Reconciliation:**
  - A controller never adopts or detaches a mount that serves another engine
    (`mount::serves`).
  - On attach it adopts a mount of its own engine that was started outside it
    (legacy `mount::start`).
  - It does not trust its own `Attached` once the adapter was stopped outside
    it (legacy `mount::stop`).
  - Detaching with nothing native attached is a no-op that never fences the
    engine.

### Adapter support (`worker::mount_ctl::adapter`, used by both adapters)

- `callback()` guard: the in-flight callback counter (`mount::inflight()`).
- `drain(timeout)`: condvar wait until no callback runs.
- `fence(engine, force)`: sets `Engine.switching`. A graceful detach first waits
  up to `QUIET_WAIT` (1 s) for quiet: no dirty session and no handle the
  application still holds. Otherwise `BUSY_VIEW`, unfenced.
- `persist_dirty`: `retain_all_dirty()` (force, step 3).
- `release`, after the native stop:
  - retains dirty sessions again (a write may have raced the drain);
  - drops every handle;
  - **keeps dirty sessions** with no references. The 250 ms pending-save retry
    commits them, and a re-attach that opens the file sees their bytes at once;
  - drops clean sessions and clears queued notifications;
  - then `mounted = false` and the fence is lifted.
- `lost(engine)` (fix round 1): `retain_all_dirty`, then `mounted = false`, for a
  native instance that died underneath us.
- `attached_path()` / `set_attached_path(..)` (fix round 1): the attached
  instance's path, set by the adapter under its transition lock. The slot is
  only ever locked for a copy, so readers never wait for a transition.
- `fs_error(op, error, counted)`: the mount-scoped error counter
  (`mount_errors()`) plus a JSON event through `util::log` (rate limited per
  code).
  - Counted: close-path failures and unexpected I/O errors, except contention
    (`BUSY_VIEW` while fenced).
  - Expected answers (not found, collision, …) are `debug` events, dropped at
    the default level.
- `report_lost(error)`: an `error` event, plus the `Lost` signal to the
  controller that attached last (a hook holding a `Weak`).

### `src/mount.rs` (WinFsp)

- `bind(engine)`:
  - Idempotent for the same `Arc` (`Arc::ptr_eq`), independent of any path
    check.
  - This fixes `mount.rs:72`: the `ENGINE` `OnceLock` was set before the path
    check, so one failed attach poisoned the process.
  - The binding is an `RwLock<Option<Shared>>`; see deviation 1.
- `attach(path)`: WinFsp runtime check, vacancy check, then `tk_mount_start`
  (a fresh native instance per attach); `mounted = true`.
- `detach(force)`:
  - Order: fence → drain (≤ `DETACH_DRAIN` = 10 s; a graceful detach that does
    not drain is `BUSY_VIEW`) → [force: `retain_all_dirty`] → `tk_mount_stop`
    (no engine lock held) → release → unfence.
  - **The permanent fence is gone.** `mount.rs:98-108` left `switching = true`
    until process exit.
- `tk_call`:
  - It counts itself in flight.
  - It takes the engine through `lock_engine`, so WP1.4's poison policy
    applies.
  - The close-path `e.health` write (`mount.rs:339-347`) became `fs_error`
    (counter plus bounded log). The per-failure `eprintln!` became the same
    bounded event.
  - NTSTATUS mapping unchanged (moved into `nt_status`).
- `checkout(engine, request, payload)`:
  - The signature is unchanged. It drains before stopping.
  - A remount failure no longer writes `e.health = "REMOUNT_FAILED…"`. Instead
    the adapter forgets the instance, releases the engine (`mounted = false`,
    unfenced) and reports `Lost{REMOUNT_FAILED}`.
- `notify` uses `try_lock`. During a transition it answers `BUSY_VIEW`, and
  `deliver_notifications` keeps the notification for its next delivery,
  instead of blocking behind a detach's quiet wait and drain.
- `MOUNT` is the transition lock, held by `bind`, `attach`, `detach` and
  `checkout`. `attached()` (fix round 1: the adapter's path slot), `serves()`,
  `inflight()` and callbacks never take it.
- Also: `attached()`, `serves(engine)`, `vacant(path)`, `inflight()`,
  `mount_errors()`.
- Legacy wrappers: `start(engine, path)` = bind + attach, and `stop(engine)` =
  `quiet()` + graceful detach (the `stop` op path).

### `src/fuse_linux.rs` (FUSE)

- Same names: `bind`, `attach(path)` (source `tkfs`), `attach_managed(path,
  instance)` and `start_managed(engine, path, instance)` (source
  `tkfs-<instance>`), `detach`, `inflight`, `attached`, `serves`, `checkout`,
  `recover_managed`, `start`, `stop`.
- `vacant` also refuses a live or stale mount at the path, which `stat` cannot
  see.
- `vanished()` (fix round 1; WinFsp has the same name and always answers
  `false`): whether our mount has left the mount table.
- The dispatch thread (`fuse-dispatch`) polls `/dev/fuse` (non-blocking) and a
  wake socket, so a detach can stop it.
  - An exit nobody asked for gives `Lost`: `FUSE_DISPATCH_FAILED` for an error,
    `MOUNT_NOT_RUNNING` when the mount was unmounted outside the worker.
  - Dirty sessions are retained first, and `mounted = false` (fix round 1).
  - `e.health` is never written.
  - The engine is marked attached before the thread starts (fix round 1).
- Graceful detach: fence → drain → `fusermount3 -u` (a refusal is `BUSY_VIEW`,
  unfenced, still attached) → stop and join the dispatch thread → remove our
  mount point (`remove_dir`, never content) → release.
- Force detach:
  - Same steps, plus `retain_all_dirty`.
  - When the kernel still has files open, `fusermount3 -u -z`. Stopping the
    dispatch thread then closes the device and aborts the connection, so open
    files fail instead of hanging.
  - A lost mount (dead dispatch thread, or no longer in the mount table) is
    always detached this way. One that is no longer in the mount table is not
    unmounted again (fix round 1).
- Callbacks, inline and on the content threads, are counted in flight and use
  `lock_engine`; failures go to `fs_error`.
- `checkout`:
  - drains, then unmounts gracefully (a refusal is `BUSY_VIEW`, unfenced);
  - stops the dispatch thread, runs the control op, relaunches;
  - a relaunch failure reports `Lost{REMOUNT_FAILED}` (no `e.health`);
  - a mount that is no longer in the mount table is not remounted:
    `Lost{MOUNT_NOT_RUNNING}` (fix round 1).

### Fault points (qualification hooks, `util::fault`)

- `fs.close`: after a close callback closed its handle (WinFsp op 10, FUSE
  RELEASE/RELEASEDIR).
- `fs.remount`: checkout remount, both adapters.
- `fs.dispatch`: FUSE dispatch loop.

## Deviations from the spec

1. **`bind` replaces the engine while nothing is attached.**
   - §4.3 says `bind` "runs once (idempotent for the same `Arc`)".
   - It is idempotent for the same `Arc`. A different engine is refused
     (`ONE_MOUNT_PER_RUNTIME`) while a mount is attached, but with nothing
     attached it rebinds.
   - A worker has one engine, so production behaves exactly as "once". The
     relaxation lets one test process mount several engines in turn
     (in-process tests).
2. **Graceful quiet ignores cleaned-up handles and waits up to 1 s.**
   - §4.3: "Graceful detach requires quiet (no handles, no dirty sessions)".
   - The kernel reports a close asynchronously. WinFsp's `Close` arrives after
     `CloseHandle` returned (its `Cleanup` already flushed and set
     `Handle.cleaned`), and FUSE's `RELEASE` after `close(2)`.
   - An immediate check refused a detach right after the application closed
     its last file (seen in the first test run).
   - A cleaned handle accepts no writes and holds no unsaved bytes, so it does
     not count as open. The 1 s wait covers FUSE `RELEASE` and scanners.
   - Dirty sessions always refuse.
   - Cost: the WinFsp leak described under Known limitations.
3. **Force detach keeps dirty sessions in memory.**
   - §4.3 step 5 says "drop orphaned handles and sessions (dirty ones are
     already in `pending_saves`)".
   - Dropping them would leave the bytes in `pending_saves` but invisible until
     a restart, because `load_pending` runs only in `Engine::new`.
   - As the task requires ("sessions must be kept or reloaded"): handles are
     dropped, clean sessions are dropped, and dirty sessions are kept with no
     references. That is exactly the state `load_pending` recovers to, and the
     pending-save retry commits them.
   - They are also retained a second time after the native stop.
4. **FUSE force detach unmounts lazily.** The plan specifies the order but not
   how a force detach gets past the kernel's `EBUSY` for open files. Here:
   `fusermount3 -u -z`, then the dispatch thread is stopped (new poll/wake
   loop) so the connection aborts.
5. **`recover_managed` semantics.**
   - It was never called before (RC: "the FUSE managed start/recover functions
     are never called").
   - It no longer removes an empty directory unless it just unmounted a stale
     mount of ours there.
   - Its refusals are `MOUNT_PATH_MUST_NOT_EXIST` (NeedsUserAction) instead of
     `WORKER_START` (Transient).
6. **Instance source for FUSE names** (see above): `MountController::new` has
   no instance argument, so the controller reads it from this process's
   `worker.json` (or `set_instance`).
7. **`mount_errors` counts more than the close path**: it also counts
   unexpected I/O errors (EIO / `STATUS_IO_DEVICE_ERROR`), never contention.
   The spec names only the close path; the counter is mount-scoped either way.
8. **Notifications** queued in `Engine.notifications` are cleared on attach and
   detach (a fresh native instance has no cached names), and `mount::notify`
   no longer blocks during a transition.
9. **Bounded reply wait (fix round 1).**
   - §4.3 does not specify what the caller of a slow transition sees.
   - Here it gets `WORKER_BUSY` (an existing Contention code) after
     `ATTACH_WAIT`/`DETACH_WAIT`, below the orchestrator's RPC deadlines.
   - The transition itself is not interrupted. A native stop has no
     cancellation point.
10. **Lost code for an external unmount (fix round 1).** The spec names no
    code. `MOUNT_NOT_RUNNING` is used because it is already registered. A new
    code would need `model::errors` (frozen), and `tests/contracts.rs` rejects
    unregistered codes.
11. **A checkout on a vanished FUSE mount is not remounted (fix round 1).** The
    checkout runs, and the mount is reported `Lost{MOUNT_NOT_RUNNING}` rather
    than mounted again at a path no longer proven ours (invariant 27). The
    controller's next attach mounts it again.

## Known limitations

- **WinFsp file contexts leak at a detach.**
  - Each leak is one `TK_HANDLE`, about 540 bytes, `calloc`ed in
    `native/mount.c` and freed only by `close_file`.
  - WinFsp sends no `Close` after `tk_mount_stop` deletes the file system. The
    contexts are lost for:
    - handles still open at a force detach;
    - handles that are cleaned up but not yet closed at a graceful detach
      (deviation 2 lets that detach proceed);
    - (a checkout requires `quiet()`, i.e. no handle at all, so it leaks
      nothing).
  - The Rust side drops the handles either way.
  - The amount is bounded by the number of handles open at detach time.
  - A fix needs either a C-side registry of live contexts freed after
    `FspFileSystemDelete`, or a wait for `Close` with a deadline.
- **FUSE force detach with open files** leaves a lazily detached mount that the
  kernel tears down when the last file closes. I/O on those files fails
  (`ENOTCONN`).
- **A FUSE external unmount is reported when the dispatch thread sees the
  connection end.** That takes milliseconds for `fusermount3 -u`, or for
  `umount -l` with no open files.
  - With a lazy unmount and open files, the kernel keeps the connection until
    the last file closes. Until then `status()` (and so the heartbeat) still
    reads `Attached`.
  - The next `attach` (`vanished()`) or `detach` (`present()`) sees that the
    mount is gone and cleans it up.
  - A periodic probe was not added: ending the connection on our own would
    fail the files the user kept open.
- **After a force detach or a lost FUSE mount with dirty sessions,
  `Engine.health` reads `PENDING_SAVE: DIRTY_SESSION_RETAINED`** until the
  pending-save retry commits them.
  - This is WP0.2's `retain_pending` behavior in `engine.rs`, owned by WP1.4.
  - `quiet()` and the legacy `stop` refuse meanwhile. In a worker the retry
    runs every 250 ms.
  - It is a store state, not a mount error.
- **`checkout` and `bind` are transitions.** They wait on the adapter's `MOUNT`
  lock while another transition runs. The wait is bounded by the quiet wait
  (1 s), the drain (10 s) and the native stop. A hung `tk_mount_stop` or
  `fusermount3` would hold them. The controller's own callers are bounded by
  `ATTACH_WAIT`/`DETACH_WAIT`.
- **`status()` can be stale** while the adapter is driven outside the
  controller (the legacy wrappers). The next attach or detach reconciles it.
  After WP1.INT only `checkout` bypasses the controller, and it reports `Lost`.
- `MountState::Disabled` is never produced: every built platform has an
  adapter.
- `Engine.notifications` still grows without bound while a worker is detached
  or headless. `receive_peer` queues them, and `deliver_notifications` skips
  delivery when not mounted. The controller clears the queue on attach and
  detach. The bounded notifier is WP2.3 task 7 (`runtime/notify.rs`).
- **Observed, not mine:**
  `orchestrator::unavailable_worker_does_not_fail_remote_discovery_and_reports_its_error`
  failed once in a parallel run during round 1 and passed in five reruns (alone
  and in its binary). It uses headless folders only.
  `peering::published` replaces `publication_errors` wholesale. So a concurrent
  `published()` that read the discovery before the test rewrote `runtime.json`
  can clear the recorded error before `Inspect` reads it. This is legacy
  orchestrator code, deleted in WP3.1.
